# ADR 0022: 応答の握りつぶしは、いかなる者にも許されない

- **状態**: 採用（2026-09-09）

## 決定

**サーバの応答（status と理由）を受けた側は、それを呼び手の次の手へ写す責務を負う。** 理由を捨てて汎用の失敗に落とすこと、catch して黙ること、ログにだけ出して振る舞いを変えないこと——いずれも**違反**である。主体を問わない。画面・MCP ツール・巡回・plugin・スクリプト・テストのどれであっても同じ。

1. **応答の理由は、呼び手の次の手を決める材料である。** 契約が次の手を定めている応答（`docs/specs/api/contract.md`「約束」）は、その手が取れる形でユーザーまたは次の呼び手に届けなければならない。届かなければ、サーバが正しく断ったことにならない
2. **区別できるものを区別しない実装は違反である。** 同じ status でも理由（`data.reason`）が違えば次の手が違う。特に「待てば通る」と「直すまで通らない」を同じ文言に落としてはならない
3. **黙ってよいのは、契約がその応答を「知らせない」と明示している場合だけ。** その明示は docs に置く。コードのコメントに書いた理由付けは明示にならない
4. **握りつぶしを見つけた者は、直すか change を立てる。** 「範囲外」として記録して済ませない

## 理由

昇格の endpoint は、対象で AI が走っている間は 409 `busy` を返して何も変えない。契約はこの応答の次の手を「待てば通る。応答が終わってから同じ操作をやり直す」と定めている。ところが承認画面はこの 409 を汎用の「プロジェクトを作れませんでした」に落としていた。ユーザーには、走っている AI を待てばよいのか、名前を変えるべきなのか、何が起きたのかが伝わらない。

サーバの判定が正しくても、それが届かなければ判定しなかったのと同じである。「実 UI に避ける仕掛けが無い」という欠陥を直したはずが、断る側だけを直して伝える側を直さなかったために、ユーザーから見た症状は変わっていなかった（2026-09-08 に発見）。

この種の欠陥は、応答を受ける側それぞれの判断で生じる。個別に直しても、次に応答を受ける側を書く者が同じことをする。だから受ける側の責務として置く。
