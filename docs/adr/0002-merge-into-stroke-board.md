# `stroke-board` へ単一の Nuxt アプリとして統合する

`stroke-board-frontier` は `stroke-board` へ統合する。**2つを1つの Nuxt アプリにする**。1つの `nuxt.config.ts`、1つのプロセス、1つのポートで動かし、画面も endpoint も同じルーティングの木の上に載せる。

統合の手法は `git merge --allow-unrelated-histories` とする。

2つは意味的に別のものである。片方はユーザーと AI が往復して合意を作りプロジェクトを起こすもの、片方は起きたプロジェクトを本家 spec-workflow-mcp 越しに見張るもの。**別々のものを1つのアプリに入れる**のがこの決定であり、片方をもう片方に合わせることではない。

## Considered Options

### 1リポジトリ2アプリ（yarn workspaces）

`apps/portal` と `apps/stroke` に分け、workspaces で束ねる案。パスの衝突が全て消えるためマージ自体は加算で済む。

退けた理由は、**2つが1つの流れだから**である。概要 → ストローク → proposal → 承認 → プロジェクト生成 → そのプロジェクトを見張る、という一本の流れになっている。`/opt/projects` が両者の実接点で、片方の生成先がもう片方の走査対象そのものである。これを2つのアプリに割ると、ユーザーは1本の流れの途中でプロセスとポートをまたぐことになる。

### ポータルを土台に frontier を作り直す

`openspec/specs/` の12 capability を仕様の参照物として残し、実装は書き直す案。規約の食い違いを最初から持ち込まずに済む。

退けた理由は、**捨てる量に見合う対価が無い**こと。動いている実装が `app/` と `server/` の両方にあり、archive 済みの change 20本が積み上げた判断もそこに入っている。整える作業（10本）のほうが、書き直しより小さい。

## 手法: `git merge --allow-unrelated-histories`

両リポジトリはローカルのみで remote を持たず、**共通コミット0件・root commit も別**であることを実測で確認した（`31131e4` と `3756461`）。git は共通祖先を持たない履歴の merge を既定で拒否するため、このオプションが要る。

```sh
cd <stroke-board>
git remote add frontier <stroke-board-frontier>
git fetch frontier
git merge --allow-unrelated-histories frontier/master
```

共通祖先を空のツリーとみなして3者比較するので、**両方に在る同名ファイルは add/add 衝突になる**。中身がバイト単位で一致するものだけが衝突しない。

代替として `git subtree` も検討したが、全サブコマンドが `--prefix=<subdir>` を要求する——サブディレクトリに入れるためのコマンドであり、単一アプリにする本決定と噛み合わない。ファイルをコピーして1コミットにする案は、片方の commit 履歴を失う。

## Consequences

- **意味で切ることが衝突対策の本体になる。** 衝突は個々のファイル名の問題ではなく、2つが同じ形をしていることの帰結である。ぶつかっているファイルを個別に退かすのは、その時点のファイル一覧に対する最適化にしかならない。意味の区分を設計し、そこから名前と置き場を導けば、意味が被っていない以上、名前も被らない
- **マージ先の構成に合わせにいかない。** 追いかけると、あちらが動くたびにこちらの設計が前提を失う。統合時に確かめるのは「両者の意味区分が被っていないか」「それぞれが自分の命名・配置の戦略に従っているか」の2点とする
- **衝突の数を目標値にしない。** 現状のまま merge して数える手順は再現できるが、それは設計の確認手段であって出発点ではない
- **統合して初めて生まれる期待は、統合前に change にしない。** 1つになったことで新しく要るもの（画面外への通知など）は、統合後の実物を見てから決める
- **片方の前提が、もう片方を止めてはならない。** frontier は書き込み先が用意されていないと `process.exit(1)` で落ちる設計だが、ポータルは本家が動いていなくても「未接続」と表示して動き続ける設計である。1プロセスになる以上、前者の作法を後者に及ぼさない
- 道筋・区分・終了条件は `docs/mainline-merge.md`、意味の区分と命名・配置の戦略は `design-semantic-structure` が持つ
