# 設定は `docs/specs/core/settings-reference.md` を正とする

- **状態**: archive（2026-08-29。全貌は [`docs/specs/core/settings-reference.md`](../specs/core/settings-reference.md) 冒頭の規定に確定 — 正の宣言・「ここに無いものは設定ではない」・改定は change 起こし＋ユーザー承認）

> [0003](0003-settings-precedence.md)（設定値はコードの既定値に優先する）に取って代わる。`NUXT_*` の環境変数は、置き場の2件（`NUXT_SESSIONS_ROOT` / `NUXT_PROJECTS_ROOT`）を除いて全廃した。

`docs/specs/core/settings-reference.md` が設定の**正**である。コードに書かれた値ではなく、この資料に載っている内容が、この製品の設定として定まったものを表す。

このため、次の3つを守る。

1. **設定の中身を変えるとき、`docs/specs/core/settings-reference.md` の編集を必ず伴う。** コードだけを直す変更は成立しない。資料に無い設定は存在しないものとして扱い、資料と食い違うコードは誤りとして直す
2. **`docs/specs/core/settings-reference.md` の編集は、必ず OpenSpec の change を起こして行う。** 資料の直接編集はしない
3. **その change には、ユーザーの承認を得る。** 承認のない編集は差し戻す

設定を1つ足す・消す・既定値を変える、のいずれも、change の提案 → ユーザー承認 → 資料の編集 → コードの追随、の順で進む。

## Considered Options

### コードを正とし、資料を追随させる

既定値も検証規則もコードが持ち、資料はそれを読める形に写しただけとする案。資料が古くなっても、コードを見れば正しい値が分かる。

退けたのは、**設定が「気付いたら増えている」状態を止められない**ためである。コードを正とする限り、設定の追加はコードを1行足すだけで済み、資料の更新は後追いの善意に依存する。実際、資料と `.env.example` とコードの3者が食い違う状態が生じた。資料を正に置くことは、設定を増やす行為そのものに承認を挟むことを意味する。

### 資料をコードから自動生成する

`DEFAULT_*` を走査して一覧を作る案。食い違いは原理的に起きない。

退けたのは、**生成物には承認を挟めない**ためである。生成の仕組みは資料をコードに従わせるので、正がコード側に戻る。加えて、生成の仕組み自体が保守対象になる。

### 資料を設けず `.env.example` だけを置く

テンプレート1本に寄せる案。

退けたのは、**変えられないものを書けない**ためである。ビルド時に決まる設定と、設定にしてはならないと判断したものは `.env` に並ばない。「書かれていないこと」が「変えられない」なのか「書き漏れ」なのかを判別できない状態が残る。

## Consequences

- **設定を増やす提案は、必ずユーザーの目を通る。** change を起こす時点で、その設定が本当に必要かを問える
- **資料に無い値をコードが読んだら、それは実装の誤りである。** 資料を直すのではなく、コードを資料に合わせる
- **資料と食い違うコードを見つけたら、資料が勝つ。** 食い違い自体を change として起こし、どちらを直すかを承認の上で決める
- **資料の編集を伴わない設定変更は、レビューで差し戻す対象になる。** 「コードだけ直した」は完了ではない
- この ADR は資料の**扱い**を定めるものであり、資料に何を載せるかの構成は資料自身が持つ
