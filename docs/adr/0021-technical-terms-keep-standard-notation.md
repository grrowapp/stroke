# ADR 0021: 開発・システム系の用語は一般に通用する表記で書き、無理な日本語化と誤用を禁じる

- **状態**: 採用（2026-09-09）

## 決定

**開発・システム系の用語は、その分野で一般に通用している表記で書く。無理に日本語へ置き換えない。絶対厳守。**

1. **英語のまま、またはカタカナで通用している語はその表記を使う。** stub・mock・hook・handler・entrypoint・adapter・listen・lookup・hydration・opacity・no-op・worktree・rebase・merge・sparse checkout など。訳語が定着している語（例外・継承・依存関係・環境変数・待ち受けポート）はその訳語でよい
2. **一般的な用法として日本語表記では意味が通らない語を禁じる。** 原語を知る技術者が読んで、即座に原語へ戻せない表記は使わない。例: stub を「詰め物」、entrypoint を「起動口」、lookup を「引き当て」、dim（opacity を下げる）を「沈める」、launch を「起こす」と書くこと
3. **原語の意味からずれた誤用の当て字を禁じる。** 見た目が日本語として自然でも、指している概念が原語と一致しない語は使わない
4. **既存の文書に該当する表記があれば、触った箇所から直す。** 新しく書くものには一切持ち込まない
5. **適用範囲は書くものすべて。** docs・ADR・`openspec/` の artifact と ticket・steering・コードのコメント・コミットメッセージ・PR の本文・ユーザーへの応答

`CONTEXT.md` で定義されたドメイン用語（ストローク・概要・フロンティアなど）はこの決定の対象外である。あれは product の語彙であり、開発・システム系の用語ではない。

## 理由

日本語の文章に揃えようとして技術用語を独自の日本語へ置き換えると、読み手は原語へ翻訳し直す作業を強いられる。置き換えが一意に戻せない語（「詰め物」「起動口」「引き当て」）は、書いた本人以外には意味が定まらず、同じ概念に複数の表記が生まれる。表記が揺れれば grep で追えず、docs・specs・コードの対応が取れなくなる。

一般に通用する表記は、その分野の読み手が共有している辞書である。辞書に無い語を作る利益は無く、損失だけがある。

## 判定の仕方

迷ったら次の順で判定する。

1. その語を、日本語のまま技術記事や公式ドキュメントの訳で見たことがあるか。あればその表記
2. 無ければ英語のまま、またはカタカナで書く
3. 自分で訳語を作らない
