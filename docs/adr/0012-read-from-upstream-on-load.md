# ADR-0012: 画面を開いたら本家を見に行く

- **状態**: 採用
- **日付**: 2026-08-25

## 決定

**本家に在るものが画面に出ないことを許さない。**

- 画面を開いた・リロードした時点で、表示するものは**本家から取り直す**
- 「起動後に起きた変化しか出せない」を理由に、本家に在るものを出さないことを正当化しない

サーバー側でデータを保持すること自体は禁じない。保持していてもよいが、
**保持しているものを理由に本家を見に行かないことは許さない**。

**本家に無い機能を実現するために基本的な機能が損なわれるなら、その機能を勝手に入れるな。**

- 本家に在るものを出す・見に行けるようにする、が基本的な機能である
- 本家に無い機能（変化の検出、出来事の記録、集計など）を足した結果、
  基本的な機能が損なわれるなら、その足した機能のほうを採らない
- 足すかどうかはユーザーが決める（[ADR-0005](./0005-do-not-derive-from-upstream-data.md)）。
  基本的な機能を犠牲にしてよいかは、なおさらユーザーが決める

## 背景

通知の一覧が、本家に承認依頼が1件あるにもかかわらず空になっていた（2026-08-25 実測）。

原因は、通知を**本家のスナップショットどうしの差分から作り、それだけを表示していた**ことに
ある（`openspec/specs/notification-feed`）。この作りでは次のことが起きる。

- サーバーを再起動すると一覧が空になる。本家に承認依頼が在っても出ない
- 逆に、本家で処理済みになった承認依頼が、通知としては一覧に残り続ける
- 「未処理の通知」という列が、実際の未処理件数と合わない

本家に在るものが出ず、本家に無いものが出る。表示が本家と食い違う。

「変化を検出して出来事として出す」は本家に無い機能である。その機能を成立させるために
差分方式を採り、その結果「本家に在るものを出す」という基本的な機能が壊れた。
順序が逆になっている。

## 根拠

- 本家の承認一覧・仕様書一覧・タスク一覧は、本家に問い合わせれば**今の状態がそのまま取れる**。
  下層の `/approvals` は既にそうしており、正しく追随している
- 差分から積んだ記録だけを表示に使うと、本家に在るものが出ない状態が生まれる。
  記録を持つこと自体が問題なのではなく、**それで本家を見に行かなくなること**が問題である

## 影響

- `openspec/specs/notification-feed` は問い直しの対象になる。とくに
  「サーバーを再起動する → 通知の一覧は空になり、次の変化が起きるまで通知は発生しない」は、
  本家に承認依頼が在っても出さないことを許す記述で、この決定と衝突する
- 通知として何を出すか（本家に在るものを並べるのか、変化を出すのか、両方か）の
  再設計が要る。変化を出す機能を残すかどうかはユーザーが決める
- 対応は別 change として起こす。ライブラリ置換の change
  （`replace-handrolled-with-libraries`）には含めない
