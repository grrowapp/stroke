# ADR 0014: change の命名は動詞始まりにする

## 状態

採用（2026-08-28）

## 決定

change-id は `<動詞>-<対象>` の kebab-case とし、**何をするか**を先頭の動詞で示す。動詞は次の5つから選ぶ。

| 動詞 | 使うとき |
| --- | --- |
| `create` | 完全な新規。その定義の塊がこのシステムに存在しなかった |
| `add` | 既存への機能追加。product が利用者に対してできることが1つ増える |
| `update` | バグではない既存の修正。機能そのものではなく、機能への呼び口が変わる |
| `fix` | バグの修正。壊れているものを直す |
| `remove` | 削除 |

change は「何をするか」の単位である。名詞句だけの名前は、その領域に関する何かとしか読めず、`openspec list` を眺めても作業の中身が分からない。

## `create` の判定は定義で見る

`create` かどうかは、**何が新しく定義されたか**で判定する。**コードがどこから来たかでは判定しない。**

コードの出どころで見ると、既存コードを使い回す作業がすべて「移設」に見え、5つのどれにも当てはまらなくなる。実際に迷いが出た（下記の例）。

product は、それ自体で1つの定義を成すものである（`CONTEXT.md`）。実装手段（新規に書いたのか、既存を使い回したのか）は名前に出ない。実装手段は design が持つ。

## 例: markdown を module にした回

コードの出どころで見ると、`app/components/` と `nuxt.config.ts` にあったものを `modules/markdown/` へ移しただけである。この見方をすると `extract`（切り出す）や `move`（移す）と呼びたくなり、5つの動詞のどれにも当てはまらない。

定義で見ると違う景色になる。

1. stroke-board という product が、機能として markdown-editor を内に持っていた
2. 別の product として **markdown-module** を新しく定義した
3. どう作るかは問わない。stroke-board に部品があるから使い回した、というのは実装手段でしかない
4. module は product に機能をアタッチする性質のもので、markdown-module は markdown-editor の機能をアタッチする
5. そこで部品提供として終わってもよかったが、疎結合によるメンテナンス性を取り、stroke-board が持っていた markdown-editor を削除して markdown-module を採用した

**markdown を扱う module はこのシステムに存在しなかった。** だから `create` である。既にある module に手を入れるなら `add` になる。

定義の塊を作り、付け替えた、というのがこの回の実体である。

## `add` と `update` の境

`add` は product が利用者に対してできることが1つ増えるとき。編集画面の追加、削除機能の追加がその粒度である。

`update` は、機能そのものではなく**機能への呼び口**が変わるとき。押せる場所が増える、ラベルが変わる、入力の取り方が変わる、開き方が変わる。呼ばれる側は変わらない。

判定に迷ったら、**利用者にとってできることが増えたか**を見る。増えていなければ `update` である。

- レビュー画面に却下ボタンを置く → `update`。却下という機能は既にあり、押せる場所が増えるだけ
- 却下の理由入力をモーダルにする → `update`。入力の取り方が変わるだけ
- 編集画面を追加する → `add`。編集できることが増える

## `update` と `fix` の境

壊れているかどうかで分ける。

意図どおり動いているが分かりにくい・置き場が悪い・名前が悪い、は `update`。意図どおり動いていないものは `fix`。

例として、却下の理由を入力して送信すると入力欄が閉じるだけに見える件がある。送信自体は成功しており、成功したことを示していないだけなので `update` である。送信できていなければ `fix` だった。

## 対象の並び

対象は「何を」→「何の」の順に置く。

- `create-module-markdown` — module を作る。markdown の
- `update-ui-approval-review` — ui を直す。承認レビューの

## 修正の回

archive から戻された feature を直す回は `update-<feature名>` を使う（`docs/feature/overview.md` の「archive からの戻しへの対応」）。これも動詞始まりで、この規約と矛盾しない。

## 既存の例外

この規約より前に作られた change のうち、`full-width-markdown-editor`（形容詞句）と `spec-document-management`（名詞句）は当てはまらない。改名しない。
