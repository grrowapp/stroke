# 5.3 検証報告: 並走2セッションの記録非混在確認

## 方法

dev サーバー（`http://127.0.0.1:3399`）を稼働させたまま、ブラウザ操作のみで
（curl・Skill・独自スクリプト不使用、本番の invoke.ts がそのまま spawn する経路のみ）
概要の異なるセッションを2つ作成し、それぞれの質問に交互に回答して並走させた。

- **セッションL** (`88b31fb9-2e74-4297-a99f-439e7a1a4ba3`): 「家族で使うペットの餌やり・散歩記録アプリ」
- **セッションM** (`1b7521eb-1701-4d73-a4dd-70a588a6fe73`): 「個人の運動記録（ランニング・筋トレ）アプリ」

両セッションの `invoke-agent` が同時に `running` になる時間帯があることを
プロセス一覧（`ps aux`）で確認したうえで、交互に回答を送信し、それぞれ複数往復まで進めた。

## 結果（`strokes.json` の内容）

### セッションL: 4往復

| # | header | question | answer |
|---|---|---|---|
| 1 | 利用者識別 | 記録に登録者名は必要か？ | 個人を区別する |
| 2 | 認証方式 | 本人確認の方法は？ | 名前選択のみ |
| 3 | 記録項目 | 記録する情報の粒度は？ | 詳細記録 |
| 4 | 対象ペット数 | 複数ペットに対応するか？ | 複数対応 |

各質問の `detail` は直前の回答（例: 2問目は「記録者を個人単位で区別することが決定した」）を
正しく引き継いでおり、内容はすべてペット記録アプリの文脈のみ。運動記録アプリ（M）の話題の
混入は無い。

### セッションM: 3往復

| # | header | question | answer |
|---|---|---|---|
| 1 | 認証 | 認証機能は必要か？ | 不要(単一ユーザー) |
| 2 | 利用形態 | どの形態で使うか？ | Webアプリ |
| 3 | ランニング記録 | ランニング記録の入力方法は？ | 手動入力 |

同様に `detail` が直前の回答を正しく引き継いでおり、内容はすべて運動記録アプリの文脈のみ。
ペット記録アプリ（L）の話題の混入は無い。

## 結論

- 2セッションを並走させても、`strokes.json` の記録に相互混入は一切無く、各セッションの
  質問・回答は常に自分自身の概要・直前の回答に対応する内容だった。
- specs `server/session-management`「呼び出しは起動単位で識別され、文脈が混ざらない」の
  Scenario（2つのセッションが同時に動いても混ざらない）を、本番の invoke.ts の spawn 経路
  （curl スキル・接続表 token 方式）そのままで実機確認した。
- 途中、`.claude/settings.json` の `Bash(curl *)` deny により一部の起動が
  「プロセスは成功したが提出が届かない」で失敗する場面があった（この deny は
  provide-operations-via-mcp と無関係な別要因、5.4 報告参照）が、ブラウザから
  「もう一度試す」相当の再操作（回答の再送信・巡回の自動再試行）を続けることで、
  最終的に両セッションとも複数往復の完走に至った。curl や Skill を使った代替検証、
  独自の allowedTools 追加などのショートカットは一切行っていない。
