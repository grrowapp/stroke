# 次の拡張案: エージェント実行の3区分（未着手）

**これは着手していない案である。** change にも起こしていない。`docs/stroke-modules.md` の
2つのモジュールを、問い専用から汎用のエージェント実行へ広げるとどうなるかを記録しておく。

## 何を汎用化するのか

エージェントを使う往復は、突き詰めると3つしかない。

| 区分 | 内容 |
|---|---|
| **実行主体** | 何を起動するか |
| **入力** | 実行主体へ渡すもの（prompt を含む） |
| **応答** | 返ってくるものの構造 |

今はこの3つがコードに固定で埋まっている。実行主体は `server/utils/claude.ts`、入力は
`server/utils/prompt.ts`、応答の構造は `server/utils/question.ts` の zod。

これを1つの JSON に載せて画面からサーバへ渡す。サーバはフローごとの契約を持たず、
この3区分だけを知る。

```json
{
  "runner":   { "...": "実行主体" },
  "input":    { "prompt": "...", "...": "渡すもの" },
  "response": { "...": "返ってくる構造" }
}
```

## なぜ器がそのまま使えるのか

`docs/stroke-modules.md` の切り分けが、この3区分にそのまま重なる。

- 往復（composable）が **実行主体と入力** を持つ
- 面（コンポーネント）が **応答** を出す
- 面は `$fetch` を持たず、props と emit だけで往復と繋がる

つまり汎用化しても、切れ目を引き直す必要がない。問い専用の実装は、この汎用形の
**1インスタンス**（応答の構造が `Question` である run）として畳める。破壊的な作り直しにはならない。

## 骨子

### 1. 応答の構造は JSON Schema で持つ

zod をそのまま JSON には載せられない。応答の構造は JSON Schema として payload に載せる。

そのうえで、**同じ1つの定義を2つの用途に使う**。

- サーバがエージェントの提出を検証するときの規則
- エージェントに「この構造で返せ」と伝えるために prompt へ載せる文言

定義が1つなので、検証と指示がずれない。今は zod（検証）と template（指示）が別々にあり、
食い違ってもすぐには分からない。ここが構造として一番効く。

### 2. 実行主体はサーバのレジストリで解決する

payload が指すのは実行主体の**名前**で、それをどう起動するかはサーバが持つ表で引く。
知らない名前は実行しない。

これは制限ではなく、既に決まっている方向と同じ場所に着地する——起動フラグは設定値として
外に出す（`openspec/specs/ai-invocation`・ADR 0001）、ワークフローは定義ファイルで持ち
コード変更なしで反映する（`openspec/specs/workflow-definition`）。

### 3. 提出と配信の口を run 単位にする

今の A5（`POST /api/:id/question`）と W1（`/api/:id/ws/question`）は問い専用。
これを run 単位に開く。

- 開始: `POST /api/:id/agent-run` — 3区分の JSON を渡す。受理のみで結果は待たない
- 提出: エージェントが run を指して結果を出す。サーバは run の応答定義で検証する
- 配信: run のチャネルで画面へ中継する。接続時にも現在分を1件流す（再接続で組み直せる性質を保つ）

WS で受ける形は変えない。待つ順番の管理はサーバ側にあり、画面は再接続して受け直すだけでよい、
という今の性質がそのまま要る。

### 4. 面は差し替える。中を slot で改造しない

応答の構造が違えば、それを出す面も違う。`AgentQuestionModal` は「選択型の問い」という
構造に対応する面であり、別の構造には別の面を置く。

構造が同じなら面も同じ、構造が違うなら面ごと差し替える——この対応が1対1なので、
面の中を slot で部分改造する必要が出てこない。改造の余地を作らないことが、
`openspec/specs/agent-question` の「問いの見え方は画面によって変わらない」を保つ。

### 5. 画面側の形

```ts
const { result, waiting, failed, send } = useAgentRun(sessionId, definition)
```

`useAgentQuestion` は、この `useAgentRun` に問いの定義を与えた薄い包みになる。
置く側から見た形（状態は返り値、`options` は振る舞いの設定だけ）は変わらない。

## 見積もり

今の `modularize-agent-question` より明確に大きい。change 2〜3本分。

| 何を | 大きさ |
|---|---|
| JSON Schema による検証の導入（zod からの移行 or 併存） | 中 |
| 実行主体のレジストリと、起動の組み立ての汎用化 | 中 |
| 提出・配信の口を run 単位に開く | 大 |
| 画面側の composable の汎用化 | 小 |
| 既存の問いを1インスタンスへ畳む | 中 |

## 前提

- 実行主体を payload で指す以上、サーバは「知っている実行主体か」だけは判定する（骨子2）
- ブラウザは実行内容を決めない。決めるのは「どれを、何を渡して」まで
- 単一ユーザー・認証なしという前提（`.scratch/stroke-board-frontier/decisions.md`）は変わらない
