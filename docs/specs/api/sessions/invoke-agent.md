# AI の起動 — `GET /api/sessions/:id/invoke-agent`

**AI を起こす唯一の入口。** 受理系の endpoint は起動を持たない。共通の約束は [contract.md](../contract.md)。

- input: クエリ `cwd`（省略可。実行する場所）と `reset`（省略可。ユーザーの再実行）
- output: `{}`（200）。読み取り（GET）のため 204 を使わない

**endpoint は cwd を自分で導出しない**——キックする側（画面・巡回・承認処理）が path を渡す。省略時はセッションディレクトリ。`reset` があればリトライ回数を 0 に戻してから起こす。

## 振る舞い

- **受理で即完結する。** `running` 化・起動・完了検知・タイムアウト・上限判定は非同期の invokeAi が担い、応答はそれを待たない
- **完了は invokeAi が子プロセスの output stream で検知する。** 提出（A5・A7）は完了の合図ではない
- 初回か継続か・渡す定型は、セッション一覧（U12）に符合するかで導く。初回は実行環境（openspec ルート・スキーマ設定）を整えてから起動する
- 昇格後（`approved` / `activated`）でも受け付ける。昇格したプロジェクトでは steering を起こすためで、渡す定型と cwd だけが変わる（起動処理は呼び出し元を区別しない）。定型の選び分けと、完了時に完成の記録（U15）を試みるかどうかは、endpoint ではなく `invoke.ts` が phase から導く——生成中（`approved`）の steering だけが U15 を叩き、完成済み（`activated`）の起こし直しは叩かない。**叩くのはさらに、その起動で作業が行われたとき（`didWork` が true）だけである**——完成の判定は `didWork` が持ち、U15 は持たない（[activate.md](./activate.md)・ADR-0014）
- 画面は U1・U7・U9 の成功応答の直後にこれを呼ぶ

## 起こせなかったときは受理しない

**起動の材料を組み立てられなかった呼び出しは受理せず、503 を返す。** 200 を返して黙って終わると、呼び手は起きたと思い、実行の記録は `idle` のまま誰も起こし直さない。

受理したときの応答が即完結する性質は変わらない。503 になるのは**起動に至る前**に決着した場合だけである。

**409 と 503 の違い**は [contract.md](../contract.md) の「約束」にある。409 は待てば通る、503 は環境か設定を直すまで通らない。

## エラー

| status | 状況 |
|---|---|
| 404 | セッションが無い |
| 409 | busy（同じ対象で実行中） |
| 503 | 前提が欠けている、または起動の材料を組み立てられない |
