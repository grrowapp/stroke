# AI の起動 — `GET /api/sessions/:id/invoke-agent`

**AI を起動する唯一の入口。** 受理系の endpoint は起動を持たない。共通の約束は [contract.md](../contract.md)。この endpoint が受理した後の仕組み（起動の材料・接続 token・完了検知・作業の判定・完成の記録・実行の記録）は [architecture/invoke-agent.md](../../architecture/invoke-agent.md) が定める。ここは endpoint の契約だけを持つ。

- input: クエリ `cwd`（省略可。実行する場所）と `reset`（省略可。ユーザーの再実行）
- output: `{}`（200）。読み取り（GET）のため 204 を使わない

**endpoint は cwd を自分で導出しない**——キックする側（画面・巡回・承認処理）が path を渡す。省略時はセッションディレクトリ。`reset` があればリトライ回数を 0 に戻してから起動する。

## 振る舞い

- **受理で即完結する。** 応答が待つのは起動の材料を組み立てられたかまでで、実行の完了は待たない
- **起動の要求は冪等である。** 対象が既に実行中なら、その要求は満たされているものとして受理し（200）、新しい呼び出しを開始しない。呼び手は要求を出し直さない。同じ対象とみなす単位は作業場所ディレクトリの実体で、昇格の改名の前後で変わらない
- **完了の検知と決着を受け持つ。** 提出（A5・A7）は完了の合図ではない。完了を検知した invoke-agent は、その実行で提出されたものに応じて局面を切り替え、画面へ届ける（[contract.md](../contract.md) の A9）
- 昇格後（`approved` / `activated`）でも受け付ける。昇格したプロジェクトでは steering を起動するためで、どの定型を渡すか・完了時に完成の記録（U15）を試みるかは endpoint ではなく invoke-agent が phase から導く。endpoint は phase を渡すだけで判定を持たない
- 画面は U1・U7・U9 の成功応答の直後にこれを呼ぶ

## 起動できなかったときは受理しない

**起動の材料を組み立てられなかった呼び出しは受理せず、503 を返す。** 200 を返して黙って終わると、呼び手は起動したと思い、実行の記録は `idle` のまま誰も起動し直さない。

受理したときの応答が即完結する性質は変わらない。503 になるのは**起動に至る前**に決着した場合だけである。

**この endpoint は 409 を返さない。** 実行中を理由に断ることが無くなった（起動は冪等）ので、受理しないのは前提が欠けているか材料を組み立てられないとき、つまり 503 だけである。**503 は待っても通らない**——環境か設定を直すまで通らない（[contract.md](../contract.md) の「約束」）。

## エラー

| status | 状況 |
|---|---|
| 404 | セッションが無い |
| 503 | 前提が欠けている、または起動の材料を組み立てられない |
