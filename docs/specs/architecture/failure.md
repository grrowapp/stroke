# 異常系の後始末

失敗が起きたとき、**どこまでをシステムが畳み、どこからユーザーへ引き渡し、引き渡した先で何を
選べるようにするか**を定める。工程と画面を問わず、ここが正である。

リトライの回数・タイムアウト・巡回が拾う対象は、この資料ではなく
`docs/specs/architecture/session-workflow.md`「実行の記録（`invocation`）」と
`docs/specs/core/settings-reference.md` が持つ。ここが持つのは**判定より後**である。

## 失敗の段階

失敗は2段階に分かれる。

| 段階 | 誰が畳むか | ユーザーに見えるか |
|---|---|---|
| **一時的な失敗** | システム。リトライで畳む | 見せない。回復した失敗は表示しない |
| **完全な失敗** | ユーザー。システムは自動では何もしない | **必ず見せる** |

**リトライの上限に達した失敗を完全な失敗とする。** 判定はその時点で確定し、以後システムは自動での
再起動も状態の書き換えも行わない。セッションと昇格したプロジェクトでは、これが `invocation` の
`error` にあたる。

完全な失敗に達した対象は、ユーザーの操作を待つ状態として保つ。**ユーザーが選ぶまで、対象と
それまでのやり取りを消さない。**

## 通知

完全な失敗は画面に示す。**待機表示のまま置き続けない。** 進行中と見分けの付かない表示のまま
留めると、ユーザーは終わらない待機を待ち続けることになる。

示すのは、何が失敗したかと、**いまシステムが自動では何もしないこと**である。

## 対処の選択肢

完全な失敗を示す画面には、**性質の異なる選択肢を2つ以上**出す。そのうち**少なくとも1つは対象を
壊さないもの**とする。

| 性質 | 何が起きるか | 壊すか |
|---|---|---|
| **そのまま再実行する** | 同じ対象を、それまでのやり取りを保ったまま再起動する。リトライの回数はリセットされる | 壊さない |
| **時間を置いて再開する** | いまは決めずに画面を離れ、後で同じ対象へ戻る。対象は完全な失敗のまま残る | 壊さない |
| **最初からやり直す** | それまでのやり取りを捨てて始めの場所へ戻る | **壊す** |
| **人へ引き渡す** | 自力で畳めないと判断できるようにし、問い合わせ先を示す | 壊さない |

**どの性質を出すかは画面が選ぶ。4つすべてを出すことは求めない。** ただし出すものが1つだけの
画面を作らない。

**「時間を置いて再開する」を出すなら、戻り道を用意する。** 離れた先から対象へ戻れないなら、その
選択肢は成り立たない——出してはならない。ストロークのセッションでは、上層のプロジェクト一覧に
**「中断したストローク」**として昇格前のセッションを並べ、そこから開き直せるようにしてある。
これはプロジェクトの一覧とは別の母集合であり、走査の母集合（`.spec-workflow` を持つディレクトリ）は
変えない。

## 破壊を伴う選択肢の承諾

それまでのやり取りや対象そのものを消す選択肢は、**何が消えるかを示して承諾を得てから**実行する。
**承諾の前に消さない。**

- 警告色で示し、壊さない選択肢と同じ見た目で並べない
- 押し間違いで到達できる位置に、承諾の一手を挟まずに置かない
- 承諾せずに閉じたときは、何も消えていない状態で元の画面に留まる

例 — セッションの画面では、ヘッダーに警告色の「最初に戻る」を出す。押すと「それまでのやり取りが
削除される」ことを示す確認が出て、承諾したときだけセッションを削除して概要の入力へ戻る。再実行の
ボタンはその間も同じ画面に在り、承諾しなければどちらもまだ選べる。

## 行き止まりを作らない

**ユーザーが選べるものが1つも無い画面を出さない。**

- 閉じる操作の無いモーダルの中であっても、出した選択肢へ到達できる
- 出した選択肢が同時にすべて塞がる状態を作らない。1つが通らないなら、通る別の道が同じ画面に在る
- 失敗の表示から、ユーザーが自分の操作だけで**元の場所へ戻れる**か、**人へ引き渡せる**かの
  どちらかは常に成り立つ

再実行を選んで再び失敗したときも同じで、画面は選択肢を示し直す。**失敗の回数は行き止まりの
理由にならない。**
