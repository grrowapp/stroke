# Design — implement-spec-document-editing

## Context

動機は proposal.md — Why を参照。設計に効く現状だけを挙げる。

- 下層の文書は `/specs/:specName/:document` と `/steering/:name` で、**文書1本が1つの URL**を持つ。本家はモーダルで開くため URL を持たない。
- 本文の表示は `DocumentView.vue`（40行）が担い、仕様書・ステアリング・承認対象の3用途で共有されている。描画は md4x の AST を `MarkdownNodes.ts` が Vue ノードに落とす形で、**md4x は読み取り専用**（`init` と `parseAST` のみで、シリアライズを持たない）。
- 下層の読み取りは `useProjectApi` → `server/api/**` → `control/upstream-proxy.ts` → `upstream/rest.ts` の一本道。ブラウザから本家へは触らない。
- `upstream/rest.ts` は書き込み関数を承認への応答1本に絞ってあり、`read-only.test.ts` がその範囲を検査している。
- 本家の保存 API は検証が3つだけ（文書名が許可リストに含まれる / `content` が文字列 / プロジェクトが存在する）。**バージョン照合も更新時刻の比較も無く、単純な上書き**である。

## Goals / Non-Goals

**Goals:**

- 文書を開いている URL の上で直して保存できる
- 直しかけを取りこぼさない（離脱時に引き止める）
- 追加の依存を増やさずに実現する

**Non-Goals:**

- 競合の検出・解決。本家に照合の手段が無いため、できないものをできるように見せない
- 自動保存。本家も持たない
- 仕様書そのものの作成・削除・アーカイブ
- 注釈と差分表示。別 change（`implement-approval-annotations` / `implement-approval-diff-snapshots`）

## Decisions

### 編集は markdown のテキストをそのまま扱う

**選択肢**

1. **markdown のテキストを直接編集し、プレビューは既にある md4x で描く**
2. `@nuxt/ui` の `Editor`（TipTap）で WYSIWYG にする
3. CodeMirror 6 を入れてソース編集にする

**選んだのは 1。**

決め手は **変換を挟まないこと**。編集した文字列がそのまま保存され、保存された文字列がそのまま編集に戻る。読み込みと取り出しで内容が変わる余地が構造的に存在しない。

2 を実際に検証したところ、12の記法のうち11は往復して元に戻ったが、**表が1行に潰れた**。

```
元:   | 列1 | 列2 |
      | --- | --- |
      | a | b |
往復: | 列1 | 列2 | | --- | --- | | a | b |
```

`StarterKit` は表を持たず、Nuxt UI の `Editor` も table 拡張を読み込んでいない（読み込むのは code / horizontal-rule / image / mention / placeholder / starter-kit のみ）。チェックボックスも同様に欠けていたが、こちらは `@tiptap/extension-list` の `TaskList` / `TaskItem` を渡して解決した。

仕様書もステアリングも表を使う。**開いて保存しただけで表が壊れる**編集機能は入れられない。拡張を足せば直る見込みはあるが、記法ごとに検証と拡張の追加を積み上げることになり、取りこぼしが残り続ける。

3 は依存が増える。1 で足りる。

なお md4x は `parseAST` のほかに `renderToHtml` / `renderToMarkdown` / `renderToText` / `heal` を持つ。今回の構成では変換を通さないため使わないが、整形が要るようになった場合の余地はある。

**本家との違い** — 本家は MDXEditor による WYSIWYG である。1 は生の markdown を書く形なので、編集中の見え方は本家と揃わない。保存される中身と、閲覧時の見え方は揃う。書いたものが壊れないことを優先する。

### `DocumentView` は据え置き、編集用を別に作る

`DocumentView` は3用途で共有されているが、**承認画面は読み取りのまま**（`document-editing` の要件）。ここにモードを足すと、承認画面が「編集できるが編集させない」状態を持つことになり、間違って有効になる余地が残る。

読み取り専用の `DocumentView` と、編集用の新しいコンポーネントに分ける。**編集できないものは編集の口を持たない**という形をコンポーネントの境界で表す。

配置は `app/components/workspace/`。下層の仕様書・ステアリングからしか使わないため（`app-structure` の規約）。

### 保存も既存の経路を通す

読み取りと同じく `useProjectApi` → `server/api/**` → `upstream-proxy` → `rest.ts` を通す。ブラウザから本家へ直接送らない。

`rest.ts` に保存の関数を2つ足す。承認への応答だけに絞っていた範囲が広がるため、`read-only.test.ts` の期待値を更新する。**書き込み関数を無制限に開くのではなく、6文書の保存2本を明示的に足す**形にして、検査は続ける。

### 文書名の検証はサーバー側でも行う

画面が6本以外を送らない作りにしても、サーバー側で検証する。本家も同じ検証を持つが、そこに頼ると**退けられた理由が本家の応答経由になり、画面での見せ方が本家の文言に左右される**。

`upstream/schema.ts` に許可リストを置き、`server/api/**` の入口で弾く。

### 引き止めは2系統いる

画面内の遷移と、ブラウザごと閉じる操作は別の仕組みで捕まえる。

- 画面内の遷移 — `onBeforeRouteLeave`。留まるか離れるかを選ばせる
- 再読み込み・タブを閉じる — `beforeunload`。ブラウザ標準の確認になり、文言は選べない

「変更がある」の判定は、**保存されている内容と現在の内容の比較**で行う。編集操作の有無ではない。直して元に戻した場合に引き止めないため（`document-editing` の要件）。

比較は文字列の同値で行う。変換を挟まないため、開いた直後の内容は取得した内容と完全に一致する。揺れを吸収する仕組みは要らない。

### 保存中の状態を持つ

本家は `saving` / `saved` / `error` を props でエディタに渡し、保存後3秒で `saved` を消す。同じ3状態を持つ。

二重送信は `saving` のあいだ保存を受け付けないことで防ぐ。

## Risks / Trade-offs

- **編集中の見え方が本家と揃わない** → 本家は WYSIWYG、こちらは生の markdown。保存される中身と閲覧時の見え方は揃う。壊れないことを優先した結果として受け入れる
- **後から保存したもので上書きされる** → 本家に照合の手段が無く、仕様として受け入れる（`document-editing` に明記）。画面を開き直せば最新が出ることで運用上の逃げ道を残す
- **`beforeunload` の文言を選べない** → ブラウザ標準の確認になる。画面内の遷移では自前の確認を出すため、そちらの体験を揃える
- **書き込みの範囲が広がる** → `read-only.test.ts` の検査を消さず、許可する2本を明示して検査を続ける。範囲が意図せず広がったらテストが落ちる
- **承認画面の対象文書が編集できると誤解される** → コンポーネントを分け、承認画面は編集用を import しない

## Migration Plan

段階的な移行は不要。保存の口が増えるだけで、既存の読み取りの経路と画面は変わらない。

検証は E2E で行う。編集して保存し、開き直して内容が変わっていることを確かめる。E2E のスタブ（`e2e/fixtures/upstream-stub.mjs`）に `PUT` の2本を足す必要がある。
