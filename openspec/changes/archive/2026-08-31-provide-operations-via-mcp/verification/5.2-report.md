## `get-send-back` の成功経路（`1e1dc150-2626-49a1-bda9-86c7ec20d179`）

5.1 と 5.3 では差し戻しが無く、`get-send-back` は 404 `no_send_back`（正常動作だが成功結果ではない）しか返していなかった。`yarn check:stroke --send-back` で proposal を一度差し戻し、成功経路を通した。

差し戻し前の3回は `404` / `no_send_back` / `差し戻しはまだ無い。`。差し戻し後の1回が成功:

```json
{"status":200,
 "response":"差し戻し（コメント 1 件）\n\n全体へのコメント:\n1. v1 で対応する settings.json キーの範囲が「検討事項」のまま proposal が成立していない。…",
 "comments":[{"id":"comment_1788117479955_vwmbnggwt","comment":"…","timestamp":"2026-08-30T19:17:59.955Z","type":"general"}]}
```

エージェントは指摘を受けて `Q3（差し戻し後） v1対象キー: v1の対象キーは?` を出しており、**取得した差し戻しが実際に次の往復へ効いている**。

この実行はその後、ブラウザが閉じて（`page.waitForTimeout: Target page, context or browser has been closed`）道具側で落ちた。成果物ではなく `scripts/stroke-check.ts` 側の問題で、`get-send-back` の判定には影響しない。

## steering 工程の初回実行（2026-08-30・`setai-2`）

`steeringPrompt` から実体の無い `/write-steering-v2` を外したうえで `yarn check:stroke --approve` を流した。**steering 工程が実際に動いた**——proposal 提出 → 承認（名前衝突で `setai-2` へ改名）→ プロジェクト昇格 → steering の claude 起動まで到達し、`get-steering` が3回呼ばれた（起動を外す前は 0 回。assistant のターンをひとつも持たずに終わっていた）。

**ただし3回とも失敗した。**

```json
{"status":404,"errorCode":"project_not_registered","error":"対象のプロジェクトが本家の一覧に無い。"}
```

原因はデバッグログの `system` / `init` に出ていた。

```
{ "name": "specworkflow", "status": "failed" }
{ "name": "stroke-board",  "status": "connected" }
```

**本家 MCP（`npx @pimzino/spec-workflow-mcp@latest <cwd>`）の起動に失敗している。** 本家の一覧は起動中のプロジェクトしか返さない（ADR-0006・`resolve-project-id.ts` のコメント）ので、本家 MCP が上がらなければプロジェクトは登録されず、`get-steering` は projectId を引けない。実際 `activeProjects.json` に `setai-2` は載っていない。

同じコマンドを手で叩くと成功する（`Project registered: fK7DzwrmRf3VCAGK` → 終了時に unregister）。したがって npx やパッケージの問題ではなく、**claude が起動する条件の側**にある。

この実行では `--strict-mcp-config` がまだ入っておらず、開発者個人の MCP が8本ぶら下がっていた（`claude.ai Slack` / `Google Drive` / `Canva` 等）。それを外したうえで再実行する。

### 分かったこと

- `errorCode` を `project_not_registered` として本家由来の `upstream_error` から分離した判断（6.2 の1周目）が効いた。**404 の内訳を見ずに原因へ辿り着けた**
- steering 工程の代行は「本家 dashboard の起動中プロジェクト一覧に対象が載っていること」に依存する。**昇格しただけでは載らない**。この依存は design に書かれておらず、実機で初めて表に出た

なお `yarn check:stroke` は proposal 提出の後、画面の更新を捉えられずに待ち時間切れで落ちた（サーバー側は着地している）。道具側の問題で、成果物の判定には影響しない。

## steering 2本が通せない理由（2026-08-30 に確定）

`--approve` を今日4回流し、4回とも**承認画面の手前**で止まった。原因は道具の不安定さではなく、サーバー側の状態遷移である。

`server/utils/stroke/invoke.ts` の `didWork: submittedSince(sessionId)` は「1回の実行は必ず提出で終わる」を前提にしている。`phase: proposed` に達した後は提出するものが無いので、巡回が起こし直すたびに `failed` → リトライ上限 → `error`（終端）に落ちる。画面は `AI からの応答が得られませんでした。` を出し、承認へ進めない。

最後の実行（`31b55ff6-…`）の実測:

| 見たもの | 結果 |
|---|---|
| claude の実行 | 8回すべて `success` / `is_error: false` |
| MCP ツール | `get-overview` 2 / `get-strokes` 8 / `get-send-back` 8 / `send-question` 6 / `submit-document` 1 |
| 結果の内訳 | 200×10 / 204×7 / 404×8。**500 も `is_error` も0件** |
| 成果物 | `phase: proposed`、`docs/proposal.md` 80行、`projectName: setai` |
| それでも | `"invocation": "error", "retries": 3` |

**成果物（MCP ツール）は完全に動いている。** 止まっているのはセッションのワークフローの側で、本 change の範囲外（tasks.md「proposal 着地後の再キックが `error` に落ち、承認へ進めない」に記録）。

したがって 5.2 の残り2本は、`adr0016-sub-add-stroke-check-approval-option` の完了だけでなく、**この再キックの問題の解消も前提になる**。

## 残る2本について

`get-steering` と `submit-document`（steering 種別）は**承認後の工程**で、`yarn check:stroke` は proposal で止まる。`--approve` オプションは実装されているが、`adr0016-sub-add-stroke-check-approval-option` が未完（tasks 22/30）で、**削除の直後にディレクトリが作り直される**というクリーンアップの不具合が未解決のまま残っている。

承認は共有の `/opt/projects` と本家の registry に触れるため、その change の完了を待つ。tasks 5.2 の記述どおり。

なお `get-steering` は、工程ごとの公開ツールの絞り（`x-mcp-tools`）が入って以降、**flontier の接続には見えなくなった**。絞りが入る前は flontier の claude が呼んで 51回中48回が `[500] この接続は steering 工程向けではない。` になっていた（6.2 の1周目で判明）。やり直した実行では 500 は0件。
