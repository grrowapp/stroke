# Proposal — document-app-structure

## Why

`restructure-app-directories` でアプリ層の配置は階層に揃った。だがそれは `app/` の話であり、システム全体—接点層（本家との通信）・制御層（差分検出と配信）・API 層・画面層—がどう積まれ、どこからどこへ依存しているのかは、どこにも書かれていない。

現状これを知る手段はソースを読むことしかない。`server/utils/upstream/` と `server/utils/control/` が層として分かれていることも、通知がどの経路を通って画面に出るのかも、ファイルを開いて追わないと分からない。新しく入る人間やエージェントが最初に必要とするのは、その全体像である。

配置の規約（どこに置くか）は spec が持つようになったが、規約は「これから置く場所」を定めるもので、「今どうなっているか」は示さない。両方が要る。

## What Changes

- **`docs/structure-design.md` を新設する** — システムの層構成、ディレクトリの配置、依存の向き、データの流れを1つの資料にまとめる
- 資料に含めるもの:
  - 層の一覧と各層の責務（接点層 / 制御層 / API 層 / 画面層 / 共有型）
  - ディレクトリツリーと、各ディレクトリが何を持つか
  - 画面の2階層（上層ポータル / 下層ワークスペース）と12ページの対応
  - 依存の向きを示す図
  - 通知が本家から画面に届くまでのデータの流れ
  - モジュールの配置規約への参照（`app-structure` spec）
- **既存ドキュメントとの棲み分けを守る** — `CONTEXT.md`（用語集）と `docs/adr/`（決定の記録）には手を入れない。この資料は「今どう組まれているか」だけを扱う

**BREAKING** なし。コードは1行も変更しない。

### CONTEXT.md を使わない理由

`docs/agents/domain.md` は、このリポジトリの `CONTEXT.md` をドメイン用語集と定義しており、かつ「存在しなければ黙って進め、先回りして作成を提案するな」と明記している（`/domain-modeling` が用語や決定が実際に固まったときに遅延生成する）。構造資料の置き場としては用途が違うため、独立した `docs/structure-design.md` を作る。

## Capabilities

### New Capabilities

- `architecture-docs`: システムの層構成と配置を1つの資料として持ち、コードを読まずに全体像を掴め、かつ資料が実装と食い違わない状態を保つ

### Modified Capabilities

なし。

## Impact

- **新規** `docs/structure-design.md` 1ファイル
- **コード変更なし** — 資料のみ。テストの結果は変わらない
- **前提** `restructure-app-directories` の配置を記述対象とする。あの change が先に成立している必要がある
