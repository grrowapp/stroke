# Design — document-app-structure

## Context

動機は proposal.md — Why を参照。

- リポジトリには既に3種のドキュメントがある。`CONTEXT.md`（ドメイン用語集、現在は未作成）、`docs/adr/`（決定の記録、4本）、`openspec/changes/`（計画）。いずれも「今どう組まれているか」を持っていない。
- `docs/agents/domain.md` は `CONTEXT.md` を用語集と定義し、「存在しなければ黙って進め、先回りして作成を提案するな」と明記している。構造資料の置き場には使えない。
- ソース側の状況は良い。`server/utils/**` と `app/**` のほぼ全モジュールがファイル冒頭に責務コメントを持ち、多くが根拠となる ADR や spec を参照している。資料はこれを集約する形で書ける。
- `restructure-app-directories` で `app/` の配置は階層に揃った。資料はその結果を記述対象とする。

## Goals / Non-Goals

**Goals:**

- コードを読まずに全体像を掴める1枚の資料を置く
- 資料の記述をすべて実装で裏の取れる事実に限る
- 資料が実装から取り残されない条件を要件として決める

**Non-Goals:**

- `CONTEXT.md` を作ること。用語集は `/domain-modeling` が用語の確定時に作る領分
- 決定の理由を書くこと。`docs/adr/` の役割を侵さない
- モジュール一覧の網羅。ファイル単位の説明はソースの冒頭コメントが既に持っており、資料に写すと二重管理になる
- コードの変更。この change は資料のみ

## Decisions

### 置き場所を `docs/structure-design.md` にした

**選択肢**

1. `CONTEXT.md` に書く
2. `docs/structure-design.md` を新設する
3. ルートの `README.md` に書く
4. `docs/structure-design/` の下に複数ファイルで分ける

**選んだのは 2。**

1 は `docs/agents/domain.md` が `CONTEXT.md` を用語集と定義しており、用途が違う。加えて同ファイルが先回りの作成を明示的に禁じている。

3 は `README.md` が使う人向けの入口であり、構造の説明で埋めると本来の役割が薄まる。

4 は現時点で分ける量が無い。層は5つ、ディレクトリは十数個で、1ファイルに収まる。分割は読む側に「どれから読むか」の判断を強いるため、量が要求するまで避ける。

### 資料の粒度をモジュール単位ではなく層とディレクトリ単位にした

ファイル単位の責務説明は既にソースの冒頭コメントにあり、そちらが実装と同じファイルにある分だけ腐りにくい。資料が同じことを書くと、変更のたびに2箇所を直すことになり、いずれ片方が古くなる。

資料が持つのは、ソースの冒頭コメントからは見えないもの—層の積み方、依存の向き、層をまたぐデータの流れ—に絞る。個々のモジュールについては「どのディレクトリに何系統が入るか」までを書き、詳細はソースを見れば分かる状態を前提にする。

### 更新義務の範囲を「配置と層をまたぐ依存」に限定した

「実装を変えたら資料も更新する」を無条件で課すと、関数を1つ足すたびに資料を見に行くことになり、守られなくなる。守られない要件は資料の信頼性をかえって下げる。

資料が扱う粒度が層とディレクトリなので、更新が要るのはその粒度が動いたとき—配置の変更と、層をまたぐ依存の増減—だけである。層の内部で完結する変更は資料の記述を変えないため、免除を要件に明記した。

### 依存図を実測から起こした

図を記憶や推測で描くと、実装との食い違いが最初から入り込む。全 `import` 文を機械的に抽出し、そこから層の関係を組み立てた。

この抽出で確認できた事実を資料に書く。とくに `server/utils/upstream/` が `server/utils/control/` を一度も import していないこと—依存が接点層から制御層へ逆流していないこと—は、境界が実際に保たれている証拠として資料に載せる価値がある。

### 実在しないものを実在しないものとして書く

`app/components/portal/` が無いこと、プロジェクトの登録・作成が入口だけで中身が無いことは、資料を読む側が最初につまずく点になる。触れずに済ませると「書き漏れ」に見え、現状として書くと誤解を生む。

そのため「無い」ことと「なぜ今は無いか（どの change の判断か）」への参照を明記する形にした。理由そのものは書かず、参照先に置く。

## Risks / Trade-offs

- **資料が実装から取り残される** → 更新義務を要件化し、その範囲を守れる大きさに絞った。加えて粒度を層とディレクトリに保つことで、更新が要る頻度自体を下げている。
- **ソースの冒頭コメントと二重管理になる** → 資料はモジュール単位の責務を書かない。役割分担を Decisions に明記した。
- **`CONTEXT.md` が後から作られたときに内容が重なる** → 資料は用語の定義を持たない。用語を使うときは `CONTEXT.md` の語彙に従うだけで、定義は書かない。
- **図が古くなる** → 図は層の関係だけを示し、モジュール名を細かく並べない。層の構成が変わる頻度は低い。
