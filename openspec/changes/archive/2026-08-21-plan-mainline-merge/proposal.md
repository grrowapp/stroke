# plan-mainline-merge

## Why

`stroke-board` への統合に向けた change が9本立っている。どれも単体では正当化されているが、**全体像がどこにも無い**。

- **前提が9箇所に散っている。** 9本はそれぞれ Why の中で「マージ先の規約はこうだ」を個別に述べている。同じことを9回書いていて、食い違っても誰も気付かない
- **統合形態の決定に記録が無い。** 単一の Nuxt アプリにする、という選択は後から変えにくいのに、決めた場所が残っていない。退けた案（1リポジトリ2アプリ、ポータルを土台に作り直し）とその理由も残っていない
- **終了条件が無い。** 9本を消化した後、何をもって「マージに着手してよい」と判断するのかが決まっていない
- **相手も動いている。** マージ先の `implement-portal-mvp` は 68/69 で、残る1件は本家の承認フローを通す必要があるユーザー操作。こちら側の進み具合だけでタイミングが決まらない

そして、統合後の姿を突き合わせた時点で**イメージのずれが1つ見つかっている**。

マージ先はプロジェクト一覧の母集合を「親パス直下で `.spec-workflow/` を持つディレクトリ」で作る（`server/utils/upstream/scan.ts`）。こちらが承認時に作るのは `/opt/projects/<name>/` とその中の `docs/proposal.md` だけで、`.spec-workflow/` は作らないと `project-generation` が明示的に規定している。**つまり統合しても、承認して生成したプロジェクトはポータルの一覧に現れない。** spec-workflow が誰かの手でそのディレクトリを受け取り `.spec-workflow/` を作るまで、そのプロジェクトはどの画面からも見えない。

「プロジェクトを起こす側」と「起きたプロジェクトを見張る側」を1つにするのが統合の狙いなのに、その2つの間に誰も居ない区間がある。同じ種類のずれが他にもあるはずで、9本を消化してから見つけるより先に洗い出したい。

## What Changes

- **統合後の姿を1つの資料にする。** 何が1つになり、何が並び、どこで接するか。両側の現状（マージ先は 68/69、こちらは9本）を含む
- **統合形態の決定を ADR に残す。** 単一 Nuxt アプリを選んだ理由と、退けた2案
- **9本の位置づけと順序を、その資料の上に置く。** どの change がどのずれを埋めるためのものか
- **終了条件を決める。** 何が満たされたらマージに着手してよいか。こちら側の条件だけでなく、マージ先の条件も含む
- **統合イメージのすり合わせを行い、出たずれと補足を掻き出す。** 上記の `.spec-workflow/` の断絶を含め、突き合わせで見えたものを全て拾う。掻き出した結果、9本の内容が変わるなら直し、新しい change が要るなら立てる
- **掻き出したものを、統合との関係で3つに分けて置く。** 何を今やり、何を統合後に回すかの判断がぶれないようにする

  | | 何が起きているか | 扱い |
  |---|---|---|
  | A 統合できない | 物理的にマージが成立しない。パスが衝突する、設定が共存できない、片方の前提がもう片方を殺す | マージ前に消化する |
  | B 統合しても目的が立たない | 1つになっても、狙った流れが繋がらない | マージ前に片を付ける。統合の意味に直結するため |
  | C 統合して初めて要る | 1つになったことで、それまで無かった期待が生まれる | **統合後に扱う。** 資料に区画を設けて書き残し、change にはしない |

  C を今 change にすると、まだ動いていないものに対して仕様を書くことになる。統合後の実物を見てから決めるほうが、当てが外れない
- **資料は進捗を持たない。** 「今どこまで来たか」は OpenSpec の change 状態が既に持っている。二重に持つと必ず片方が腐るため、資料が持つのは決定・全体像・終了条件だけとする

## Capabilities

この change が作るのは資料と決定の記録であり、アプリの振る舞いを変えない。spec の差分を持たない（`.openspec.yaml` に `skip_specs: true`）。

すり合わせの結果として振る舞いを変える必要が見つかった場合、それはこの change では実装せず、別の change として立てる。この change の役目は、何を作るべきかを見えるようにするところまでである。

## Impact

- `docs/` — 統合の全体像を置く資料（新規）
- `docs/adr/` — 統合形態の決定（新規。既存は `0001-claude-p-invocation.md` のみ）
- `openspec/changes/` の既存9本 — すり合わせでずれが出た分だけ proposal を直す
- `docs/known-issues.md` — 掻き出した事項のうち、まだ change に起こさないもの
- `CLAUDE.md` — Docs の一覧に追加
- 新しい change — すり合わせで必要と分かったもの

**前提**: なし。**9本すべての前に置く。** この change の結果で9本の内容が動きうるため、先に地図を描く。

**立てないことにした1本**: `modularize-server-utils`（`server/utils/` 平置き15本の切り直し）。隣の `modularize-stroke` ワークツリーとは担当が被らないことを確認したが、どう切るかは意味の区分そのものなので、`design-semantic-structure` の適用結果として扱う（design.md 決定10）。
