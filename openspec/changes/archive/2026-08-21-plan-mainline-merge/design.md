## Context

統合に向けた change を洗い出す過程で、判断がぶれた箇所が3つあった。いずれも同じ原因で、**全体を見る場所が無かった**ことによる。

- 衝突を「今ぶつかっているファイルを個別に退かす」形で潰そうとした。数えた件数は今の配置に対する偶然の数字でしかなく、目標値にならない
- 統合で新しく生まれる期待（画面外への通知など）を、統合前の change として立てかけた。統合後に扱うべきものと、今やるべきものの区別が無かった
- **同じ理由で立つものを別々の change に割った。** 「1つのアプリになるから揃うしかないもの」（テスト・依存・auto-import・設定）を5本に分けていた。理由が同じで、同じファイルを触り、順番に実施するしかないものは1本でよい

統廃合の結果、マージ前に消化するものが4本（地図を含む）、統合後に回すものが2本、統合とは別軸の不具合が1件（`docs/known-issues.md`）になった。

マージ先の状態も確かめてある。`implement-portal-mvp` は 68/69 で、残る1件は本家の承認フローを通す必要があるユーザー操作。実質できあがっていて、こちらを待っている。

統合手法は `git merge --allow-unrelated-histories` を採る。両リポジトリは共通コミット0件・root commit も別で、共通祖先を持たないことを実測で確認した。

## Goals / Non-Goals

**Goals:**

- 統合後の姿と、そこへ至る道筋を1箇所で見えるようにする
- 掻き出したものを「今やる / 統合後に回す」で迷わず振り分けられる基準を持つ
- 何が満たされたらマージに着手してよいかを決める
- まだ決められないことを、決められないまま保持できる形にする

**Non-Goals:**

- **統合後の structure そのものを決めない。** `design-semantic-structure` の仕事であり、地図はその結論を指すだけ
- **個々の change の中身を決めない。** 各 proposal が持つ
- **進捗を持たない。** 後述の決定2
- **マージ先のリポジトリを直さない。** あちらの `CLAUDE.md` が実在しない `.scratch/` を指している件などは、あちらで扱う

## Decisions

### 決定1: 地図が持つのは一覧・依存図・ポインタまで。それ以上は複製しない

地図に各 change の内容を書き写すと、proposal が更新された瞬間に地図が古くなる。古い要約は「かつて正しかったもの」であって、判断の根拠にしてはならない。

一方、**何本あって、それぞれ何をやるもので、どういう順で消化するのか**が一望できないと、地図の用を成さない。そこで境界をこう引く。

| 地図が持つもの | 地図が持たないもの |
|---|---|
| change の一覧表（id / タイトル / 一行の概要 / 区分 / ポインタ） | Why、What Changes、Impact、前提の詳細 |
| change の依存関係の図 | 各 change の中の作業手順 |
| structure の結論への**ポインタ** | structure そのもの |
| ドメイン用語への**ポインタ** | 用語の定義 |

一行の概要は複製にあたるが、これが無いと表がただの id の羅列になる。**一行を超えたら本体を見に行く**——この線を守る限り、地図と proposal が食い違っても一行の粗さの中に収まる。

本体の所在は次のとおり。change の内容は `openspec/changes/<id>/proposal.md`、structure は `design-semantic-structure` の成果物、ドメイン用語は `CONTEXT.md`、統合形態の決定は `docs/adr/0002-*.md`。

_代替案_: 地図に全部書いて一望できるようにする。読む手間は減るが、12本＋structure＋ADR の内容を二重に持つことになり、必ずどこかが食い違う。一望性は一覧表と依存図で足り、それ以上の一望性は食い違いと引き換えになる。

### 決定1-a: 依存関係は Mermaid の有向グラフで持つ

順序は文章で書くと読み解けない。12本のうち依存を持つものが8本あり、`align-settings-conventions` のように4本を前提に持つものがある。

図の形式は Mermaid とする。レンダリングされない環境でもテキストとして依存が読め、ASCII の枝分かれ図と違って本数が増えても書き手が線を引き直さずに済む。

図が持つのは**依存の有無だけ**とする。各 change が何をやるかは一覧表が、なぜその順なのかは各 proposal の「前提」が持つ。図に理由を書き込むと、そこが本体になってしまう。

### 決定2: 進捗を持たない

「今どこまで来たか」は `openspec list` が持っている。地図にも書くと二重管理になり、更新が漏れた瞬間に嘘になる。

地図が持つのは**変わらないもの**——統合後の姿、判断の基準、終了条件、未決の論点——に限る。

_代替案_: チェックリストを置く。見やすいが、change を1本 archive するたびに地図も直す運用が要る。守られない運用は書かない。

### 決定3: 掻き出したものを A / B / C で振り分ける

| | 何が起きているか | 扱い |
|---|---|---|
| A 統合できない | 物理的にマージが成立しない | マージ前に消化 |
| B 統合しても目的が立たない | 1つになっても狙った流れが繋がらない | マージ前に消化 |
| C 統合して初めて要る | 1つになったことで新しい期待が生まれる | **統合後に扱う** |

C を今 change にすると、まだ動いていないものに仕様を書くことになる。統合後の実物を見てから決めるほうが当てが外れない。

この区分は既に効いている。`connect-portal-and-strokes`（B）を change にし、問いの通知（C）を統合後に回した判断は、この基準で説明できる。

### 決定4: 未決の論点を、決めないまま持つ区画を設ける

判断材料は揃っているが、今決めても実施時には前提が変わっている——というものがある。git の繋ぎ方の詳細がこれにあたる。

こうしたものを「決定」の欄に無理に埋めると、後から覆ったときに地図が嘘をつく。**未決であること自体を記録し、判断材料と、いつ決めるかを添える。**

### 決定5: 衝突は「測り方」を持ち、「数」を持たない

現状のまま merge して衝突を数える手順は再現できる。

```sh
git clone <base2> /tmp/probe
cd /tmp/probe && git checkout <対象ブランチ>
git remote add frontier <mvp> && git fetch frontier
git merge --allow-unrelated-histories frontier/master
git diff --name-only --diff-filter=U
```

ただし**測った数は地図に書かない**。今の配置に対する数字であり、`design-semantic-structure` が構造を決めれば前提ごと変わる。数字を書くと、それが目標値として一人歩きする。

地図が持つのは手順と、「この数字を目標にしてはならない理由」である。

### 決定6: 統合形態の決定は ADR に分ける

「単一の Nuxt アプリとして統合する」は後から変えにくい決定で、`docs/adr/` の対象である。退けた案（1リポジトリ2アプリ、ポータルを土台に作り直し）とその理由も残す。

地図とは別ファイルにする。地図は状況が進むと書き換わるが、ADR は決定の時点を凍結して残すものだからである。地図は ADR を指す。

### 決定7: 終了条件は「衝突ゼロ」にしない

`package.json` と `nuxt.config.ts` は、今の形のままなら統合後も1つずつ必要で、両者が別々に育てている。ただしこれは**両者がルート直下に同じ構造を持っている前提**での話であり、`design-semantic-structure` の結論次第で変わる。

したがって終了条件は、衝突の数ではなく次の形で書く。

- A に属するものが全て片付いていること
- B に属するものが全て片付いていること
- structure が決まり、各 change がそれに沿っていること
- マージ先の `implement-portal-mvp` が archive されていること
- 残る衝突が、事前に把握され、解き方が決まっているものだけであること

### 決定8: 置き場

- 地図 — `docs/mainline-merge.md`
- 統合形態の決定 — `docs/adr/0002-*.md`（既存は `0001-claude-p-invocation.md` のみ）

`CLAUDE.md` の Docs 一覧に地図を足す。ADR は `docs/agents/domain.md` の規約どおり `docs/adr/` に入るので、個別の導線は要らない。

### 決定9: 並走するワークツリーを依存図に含めない

同じ commit から3つのワークツリーが切られている。実際に動いているのは2つで、状況はこうである。

| ワークツリー | 状態 |
|---|---|
| `plan-mainline-merge` | 統合準備の12本 |
| `modularize-stroke` | `modularize-agent-question`（問いの往復を composable へ切り出す）と、その資料。**app/ 側に閉じていて、サーバ側は変更しないと明記されている** |
| `refactor` | 走っていない |

`modularize-agent-question` は `app/composables/` `app/components/` `app/pages/s/[sessionId]/proposal.vue` を触るため、`design-semantic-structure` と `align-coding-conventions` が触る範囲と重なる。しかしこれを依存関係として図に持たない。

**structure を先に決めることで吸収できる**からである。`design-semantic-structure` が置き場と境界を決めていれば、`modularize-stroke` の成果を取り込む時点で、その制約に沿わせる調整を入れれば足りる。取り込みが統合の前になっても後になっても、やることは同じで順序上の損失が無い。

依存図に並走を書くと、図が「今どのワークツリーがどこまで進んだか」を映すものになり、進捗を持たない方針（決定2）と衝突する。地図が持つのは統合準備の12本の依存だけとする。

### 決定10: `server/utils` の層分けを個別の change として立てない

`server/utils` は平置き15ファイルで、名前は `ai.ts` `claude.ts` `project.ts` `question.ts` と機能名が並ぶだけで、どの意味に属するかを示していない。当初これを `modularize-server-utils` として立てる候補にしていたが、立てない。

意味の区分と、そこから名前・置き場を導く規則を決めるのは `design-semantic-structure` の仕事であり、`server/utils` の切り直しはその適用結果にあたるからである。規則より先に個別の層分け change を立てると、**意味を決めずにファイルを動かす**ことになる。それは衝突を個別に潰そうとして部分最適に陥ったのと同じ形である。

_代替案_: 先に層分けだけ済ませておく。ただし「どう切るのが正しいか」こそが決めるべきことなので、先に切って後から切り直すなら二度手間になる。

### 決定11: マージ先の構成に合わせにいかない。意味で切る

マージ先は今まさに構成を組み替えている（43ファイルが未コミットで、`components/ui/` と `components/notification/` を `components/shared/` へ、`composables/` を `shared/` と `workspace/` へ切り直している）。

これを見て「あちらの構成が確定するまで待つ」と考えたが、誤りである。**合わせにいくから待つことになる。**

2つは意味的に別のものである。片方はユーザーと AI が往復して合意を作りプロジェクトを起こすもの、片方は起きたプロジェクトを本家越しに見張るもの。意味が被っていないのだから、**それぞれが自分の意味で切れば、名前は自然に分かれる**。現に、あちらが今やっている組み替えも意味で切る作業である（`shared` と `workspace` は役割の名前であって、ファイルの種類の名前ではない）。

したがって地図は、マージ先の構成をどこにも書かない。持つのは「両者がそれぞれ意味で切れていること」という条件だけである。あちらが何回組み替えても、この条件は動かない。

`design-semantic-structure` も同じ立場を取る。出発点はマージ先の Module Boundaries ではなく、こちら側の意味である。

_代替案_: マージ先の構成を追いかけ、同じ区分を採る。見た目は揃うが、あちらが動くたびにこちらの設計が前提を失う。追いかけ続けるコストが、意味で切るコストを上回る。

### 決定12: 衝突チェックは「意味が被っているか」で行う

意味の構造が資料としてあれば、統合時に確かめるのは次の2点だけになる。

1. 両者の意味区分が被っていないか
2. それぞれが自分の命名・配置の戦略に従っているか

ファイルを1つずつ突き合わせる作業は要らない。**被らないと分かっていれば、数える必要が無い。**

これは決定5（数を持たず測り方だけ持つ）を一段進めたものである。測るのは設計の確認手段として残るが、確認の主役は意味の突き合わせになる。

## Risks / Trade-offs

**[地図が腐る]** → 決定1（複製しない）と決定2（進捗を持たない）で、腐りうる面を減らしてある。残るのは決定そのものが覆った場合で、そのときは地図を直すのが正しい。覆った決定を放置するほうが害が大きい。

**[structure が決まると地図の記述が変わる]** → 地図は structure の結論を**指す**だけにする（決定1）。`design-semantic-structure` が終わった時点で地図に書き足すのは、ポインタと、それが決まったという事実だけになる。

**[A / B / C の振り分けが人によってぶれる]** → 境界が微妙なものは出る。特に B と C は「目的が立たない」か「新しい期待」かで割れうる。基準そのものを地図に書いておき、振り分けた結果ではなく**なぜそう振り分けたか**を各項目に添える。

**[未決の論点が、決めないまま放置される]** → 決定4 で「いつ決めるか」を必ず添える。終了条件（決定7）が未決の論点の解消を含むので、放置したままマージには入れない。

**[マージ先の変化に追随できない]** → あちらは 68/69 で止まっているが、動く可能性はある。地図はあちらの状態を数字で持たず、「あちらが archive されていること」という条件の形で持つ（決定7）。
