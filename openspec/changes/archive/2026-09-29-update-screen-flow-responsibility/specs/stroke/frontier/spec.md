## MODIFIED Requirements

### Requirement: 作成の入口は常に押せ、ストロークをモーダルで開く

システムは、プロジェクト一覧画面の「作成」を常に押せる状態に置く SHALL。押せるかどうかをサーバーが返す可否から決めてはならない（MUST NOT）。

作成を押したとき、一覧のオーバーレイ上のモーダルとしてストロークの概要入力を開く SHALL。モーダルは画面全体を覆って一覧を隠し、閉じる操作を持ってはならない（MUST NOT）。モーダルを開いた状態で再読み込みしたとき、同じ途中の場面に復帰する SHALL。

作成の飛び先は、**`/` とは別の path** とする（SHALL）。`/` へ飛ばしてはならない（MUST NOT）——どちらの入口から入ったかが URL から読み取れなくなるためである。飛び先の path と `/` の対応は `screen-flow` が規定する。

#### Scenario: 作成を押す

- **WHEN** プロジェクト一覧で「作成」を押す
- **THEN** オーバーレイ上のモーダルが開き、その中にストロークの概要入力が出る。一覧は見えず、閉じる操作は無い

#### Scenario: 作成を押した後の URL

- **WHEN** プロジェクト一覧で「作成」を押す
- **THEN** URL は `/` ではなく、ストローク開始の path になっている

#### Scenario: 前提が欠けている状態で作成を押す

- **WHEN** AI 実行の前提が揃っていない状態で「作成」を押す
- **THEN** 「作成」は押せてモーダルが開き、前提の欠けはモーダルの中で概要を投稿したときのエラーとして現れる

#### Scenario: モーダルを開いた状態で再読み込みする

- **WHEN** モーダルでストロークを進めている途中で画面を再読み込みする
- **THEN** 同じ途中の場面が再びモーダルとして開いている

### Requirement: 概要からセッションを開始する

システムは概要の投稿からセッションを1つ開始し、AI の最初の問いを表示する SHALL。投稿の受理・セッションの作成・phase の初期化は `api/session/overview` が、AI の起動は `api/session/invoke-agent` が規定する。認証は行わず、単一ユーザーを前提とする。

概要の投稿は、**`/` とストローク開始の path のどちらから行っても同じ結果になる**（SHALL）。入った URL によってセッションの作られ方・phase の初期値・AI の起動の仕方を違えてはならない（MUST NOT）。

#### Scenario: 概要を投稿する

- **WHEN** ユーザーが画面1で概要を投稿する
- **THEN** セッションが1つ作られ、phase は `stroking` となり、AI の最初の問いが表示される

#### Scenario: ルートから概要を投稿する

- **WHEN** ユーザーが `/` で概要を投稿する
- **THEN** ストローク開始の path から投稿したときと同じく、セッションが1つ作られ、phase は `stroking` となり、AI の最初の問いが表示される

#### Scenario: 概要が空のまま投稿する

- **WHEN** 概要が空のまま投稿される
- **THEN** システムはセッションを作成せず、入力が必要である旨を示す
