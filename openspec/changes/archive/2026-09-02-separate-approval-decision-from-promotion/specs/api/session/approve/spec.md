## REMOVED Requirements

### Requirement: U10 POST /api/sessions/:id/approve — 承認を受理して昇格を実行する

**Reason**: 1つの受け口が、承認の判断・昇格の実行・次の実行の起こしの3つを抱えていた。3つを別々の段として扱えるようにするため、この要件を「判断を記録することだけ」の要件に置き換える。判断が下りた印が昇格の途中（`phase: 'approved'` の書き込み）にしか現れず、判断だけを取り下げる形も、失敗した段だけをやり直す形も作れなかった。

**Migration**: 昇格は `api/session/promote`（U14）が受け持つ。次の実行は `api/session/invoke-agent`（U13）を昇格の成功後に要求する。承認の1呼び出しで済ませていた側は、**承認 → 昇格 → 起動**の順に3つを呼ぶ。承認だけを呼んで止めた場合、セッションはセッションのまま残り、プロジェクトは作られない。

## ADDED Requirements

### Requirement: U10 POST /api/sessions/:id/approve — 承認の判断を受理して記録する

システムは `POST /api/sessions/:id/approve` を公開する SHALL。確定された名前を伴う承認の判断を受け取り、**その判断が下されたことを記録する** SHALL。

この受理は、セッションディレクトリを改名してはならない（MUST NOT）し、phase を変えてはならない（MUST NOT）し、次の実行を起こしてはならない（MUST NOT）。**判断が記録されているセッションは、まだセッションである**——プロジェクトとして一覧に現れず、生成中としても現れない。

承認の判断を受理するのは、proposal が出ている局面だけとする SHALL。判断の対象となる proposal が残っていなければ受理しない SHALL。既に判断が記録されているセッションへ重ねて判断を下すことは受理しない SHALL——取り下げてから下し直す。既に昇格した対象への判断は受理しない SHALL。存在しないセッション id への判断は受理しない SHALL。

確定された名前が保存先で既に使われているときは受理しない SHALL。衝突は昇格の直前にも確認されるが（`project/generation`）、判断の時点で分かるものはその場で伝える。

判断を記録できなかったときは失敗を返し、セッションを何も変えない SHALL。

#### Scenario: 承認の判断が受理される

- **WHEN** 確定された名前を伴う承認の判断が `POST /api/sessions/:id/approve` に届く
- **THEN** 判断が記録され、受理が返る。ディレクトリの名前も phase も変わらず、次の実行は起こされない

#### Scenario: 判断を記録した直後にセッションを見る

- **WHEN** 判断が記録された直後に、そのセッションを一覧とプロジェクト一覧の両方で探す
- **THEN** セッションとして在り、プロジェクトとしては——生成中としても——現れない

#### Scenario: proposal が残っていない

- **WHEN** 判断の対象となる proposal が残っていないセッションへ承認が届く
- **THEN** システムは受理せず、判断は記録されず、セッションは何も変わらない

#### Scenario: 既に判断が記録されている

- **WHEN** 判断が記録されているセッションへ、もう一度承認が届く
- **THEN** システムは受理せず、記録されている判断はそのまま残る

#### Scenario: 昇格した後に承認が届く

- **WHEN** 既に昇格した対象へ承認が届く
- **THEN** システムは受理せず、何も変えない

#### Scenario: 名前が既に使われている

- **WHEN** 保存先で既に使われている名前を確定して承認が届く
- **THEN** システムは受理せず、名前が衝突していることを伝える。判断は記録されない

#### Scenario: 存在しない id で承認が届く

- **WHEN** 存在しないセッション id に承認が届く
- **THEN** システムは受理せず、存在しないことを伝え、何も変えない

#### Scenario: 判断を記録できない

- **WHEN** 承認は届いたが、判断の記録そのものが失敗する
- **THEN** 失敗が返り、判断は記録されず、セッションは判断の前と同じ状態で残る

### Requirement: 記録した判断は、昇格の前なら取り消せる

システムは `DELETE /api/sessions/:id/approve` を公開する SHALL。記録された判断を取り下げ、セッションを判断が下される前の状態へ戻す SHALL。取り下げた後、同じセッションへ改めて承認の判断を下せる SHALL。

**昇格が済んだ対象への取り消しは受理してはならない（MUST NOT）。** 昇格の後に残っているのはプロジェクトであり、それを片付けるのはプロジェクトの削除である（`api/project/delete`）。取り消しは判断を戻すものであって、出来たものを消すものではない。

判断が記録されていないセッションへの取り消しは、何も変えない SHALL。存在しないセッション id への取り消しは受理しない SHALL。

取り消しは、そのセッションが持つ proposal・ストロークの往復の記録・ディレクトリの中身を、いずれも変えてはならない（MUST NOT）。

#### Scenario: 判断を取り消す

- **WHEN** 判断が記録されているセッションへ `DELETE /api/sessions/:id/approve` が届く
- **THEN** 判断は取り下げられ、セッションは判断の前の状態に戻る。proposal もストロークの往復の記録も残っている

#### Scenario: 取り消した後にもう一度判断する

- **WHEN** 判断を取り下げた後、同じセッションへ承認が届く
- **THEN** システムは受理し、新しい判断を記録する

#### Scenario: 昇格した後に取り消そうとする

- **WHEN** 既に昇格した対象へ取り消しが届く
- **THEN** システムは受理せず、プロジェクトは消えない

#### Scenario: 判断が無いのに取り消す

- **WHEN** 判断が記録されていないセッションへ取り消しが届く
- **THEN** システムは何も変えない

### Requirement: 判断は、それが下された proposal に結びつく

システムは、記録された判断を、その判断が下された時点の proposal に結びつける SHALL。**proposal が出し直されたとき、記録されていた判断は失効する SHALL**——古い proposal に対して下された判断で、新しい proposal を昇格させてはならない（MUST NOT）。

失効した後、ユーザーは新しい proposal を読んで改めて判断できる SHALL。失効は proposal の出し直しそのものを妨げてはならない（MUST NOT）。

#### Scenario: 判断の後に proposal が出し直される

- **WHEN** 判断が記録されている状態で proposal が出し直される
- **THEN** proposal は出し直され、記録されていた判断は失効する

#### Scenario: 失効した後に昇格を要求する

- **WHEN** 判断が失効したセッションへ昇格が要求される
- **THEN** システムは受理せず、判断が無いことを伝える。改名は起こらない

#### Scenario: 失効した後に改めて判断する

- **WHEN** 判断が失効したセッションへ、新しい proposal を読んだユーザーが承認を送る
- **THEN** システムは受理し、新しい判断を記録する
