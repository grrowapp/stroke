## Why

**異常系が起きた後、どこまでをシステムが畳み、どこからユーザーへ引き渡し、引き渡した先で何を選べるようにするかを定めた資料が無い。** いま在るのは断片である。

- `docs/specs/api/contract.md` — U2 の `invocation` の説明として「`error` はリトライ上限に達した終端。システムは自動では何もしない。画面は再実行か削除を出す」
- `docs/specs/architecture/session-workflow.md`「実行の記録（`invocation`）」 — `idle → running → failed → error` の遷移図
- `openspec/specs/stroke/frontier`「実行が error に達したら画面が示し、回復はユーザーが選ぶ」 — セッションの画面に限った規定

いずれも**セッションの実行（`invocation`）についてだけ**の記述であり、対象が広がらない。上層のプロジェクト一覧・spec 画面・文書の編集・本家への問い合わせで同じ「もう自動では通らない」が起きたときに、画面が何を示し、ユーザーに何を選ばせるかは決まっていない。行き止まり（待機表示のまま操作が現れない、閉じる操作の無いモーダルから出られない）を禁じる規定も `stroke/frontier` の中にしか無く、他の画面には及ばない。

選択肢の側にも欠けがある。いまユーザーへ出るのは**再実行と削除の2つ**（`app/composables/useWaitingRetry.ts` の `retryFromError` / `discard`）で、どちらも「いま決める」ことを求める。**時間を置いて戻ってくる**道と、**人へ引き渡す**道が無い。削除は破壊を伴うのに、何が消えるかを示して承諾を得る手順も規定されていない。

ユーザー指示（2026-09-09）は、**失敗した実行は原則リトライし、上限に達したら完全な失敗と判定して、画面通知と対処の選択肢の提示を行い、行き止まりにならないルートを必ず用意する**ことである。工程と画面を問わない共通の規範として置く。

## What Changes

### docs（規範）

- **新設 `docs/specs/architecture/failure.md`** — 異常系の後始末と回復の導線。書き出し先はユーザーへ諮って確定した（2026-09-09。`architecture/` への新設を採り、名前は指摘を受けて短くした）。内容は次のとおり。
  - **失敗の段階** — 一時的な失敗はシステムがリトライで畳み、ユーザーへ見せない。上限に達したものだけを**完全な失敗**と判定してユーザーへ引き渡す。判定は上限に達した時点で確定し、それ以降システムは自動では何もしない
  - **通知** — 完全な失敗は必ず画面に示す。待機表示のまま置き続けない
  - **対処の選択肢** — 性質の異なる選択肢を2つ以上出す。少なくとも1つは**対象を壊さない**ものとする。性質は4つ——(1) そのまま再実行する、(2) 時間を置いて再開する（いまは決めずに離れ、後で戻ってこられる）、(3) 最初からやり直す（それまでのやり取りを捨てる）、(4) 人へ引き渡す（問い合わせ先を示す）
  - **破壊を伴う選択肢の扱い** — 何が消えるかを示して承諾を得てから実行する。承諾の前に消さない。警告色で示し、通常の操作と並べない
  - **行き止まりを作らない** — 閉じる操作の無いモーダルの中であっても選択肢へ到達できる。すべての選択肢が塞がる状態を作らない。選べるものが1つも無い画面を出さない
- **参照へ寄せる** — `docs/specs/api/contract.md`（U2 の `error` の記述）と `docs/specs/architecture/session-workflow.md`（「実行の記録」）は、`invocation` に固有の事実だけを残し、後始末の判断は新設の資料を参照する形にする

ユーザーが例として挙げた形——再実行ボタンを出しつつ、ヘッダーに警告色の「最初に戻る」を出し、押下すると今までのやり取りが削除される警告を出し、承諾の後に最初へ戻る——は、(1) と (3) を同時に出し、(3) に承諾を挟んだ適用例にあたる。資料には規範を書き、この形は例として添える。

### 範囲外

- 実装の変更。この change は docs と specs の確定までを持つ。画面への反映（「時間を置いて再開」「人へ引き渡す」「最初へ戻る」の3つは現状 存在しない）は tasks で切るが、**問い合わせ先の値**——誰へ、どこへ問い合わせるか——は設定として持つ必要があり、`docs/specs/core/settings-reference.md` への追加を design.md でユーザーへ諮る
- リトライの機構そのもの（上限・タイムアウト・巡回の対象）。`agent/invocation` と `portal/batch` が既に持っており、変えない
- 本家 spec-workflow が落ちているときの表示（`upstream-connection` と `notification-toast`）。接続の欠落であって実行の失敗ではなく、段階の判定が別である

## Capabilities

### New Capabilities

- `failure`: 異常系の後始末と回復の導線。完全な失敗の判定・画面への通知・対処の選択肢の性質・破壊を伴う選択肢の承諾・行き止まりの禁止を、工程と画面を問わない共通の規範として持つ

### Modified Capabilities

- `stroke/frontier`: 「実行が error に達したら画面が示し、回復はユーザーが選ぶ」と「巡回に拾われない実行の失敗は画面が示し、ユーザーが再試行できる」を、`failure` の適用として書き直す。出す選択肢を再実行と削除の2つから、性質の異なる選択肢の組（再実行・一覧へ戻って後で再開・最初に戻る）へ広げ、破壊を伴うもの（削除＝最初に戻る）に承諾を課す。**削除した後の行き先を変える**——いまは「モーダルが閉じてプロジェクト一覧へ戻る」だが、ユーザー指示の「最初へ戻る」に合わせて**概要の入力へ戻る**（削除したセッションを見に行く先が一覧である理由が無く、やり直しの起点は概要の入力である）

## Impact

- docs: 新設1件（`architecture/failure.md`）、参照の付け替え2件（`api/contract.md`・`architecture/session-workflow.md`）
- 画面: `app/composables/useWaitingRetry.ts`（`retryFromError` / `discard` の2つに、離脱と最初へ戻るが加わる）、`app/components/AgentQuestion.vue`・`app/components/WaitingIndicator.vue`・`app/pages/strokes/[sessionId]/`（`error` の表示）
- 設定: 問い合わせ先（design.md で諮る）
- テスト: `test/` の画面側と E2E（`error` から各選択肢への遷移）
