# project/generation Delta

## ADDED Requirements

### Requirement: 昇格したプロジェクトを本家に存在させるのは生成の依頼だけであり、AI のプロセスではない

システムは、昇格したプロジェクトを本家 spec-workflow に存在させる（本家の一覧に載せ、`.spec-workflow/` を持たせる）手段として、**生成の endpoint（`api/project/generate`）による本家への登録の依頼だけ**を持たなければならない（SHALL）。生成はサーバー自身のアクションである。

**AI のプロセスにプロジェクトを生成させてはならない（MUST NOT）。** 承認の後の実行（steering）の起動に、本家 spec-workflow の MCP を配線してはならない（MUST NOT）——その配線は起動時の登録簿への自己登録、すなわち AI の起動に乗せた生成そのものである。AI の起動定義に、本家へプロジェクトを登録しうるものを含めてはならない（MUST NOT）。

生成を依頼するのはサーバーである SHALL。**ユーザーが叩く endpoint（画面が呼ぶ受理系・起動の受け口）に生成を持たせてはならない（MUST NOT）。** 承認の判断（U10）・昇格（U14）・起動（U13）・完成の記録（U15）はいずれも生成に触れない。依頼する時点は `agent/invocation` が定める（承認の後の実行の、起動の材料を組み立てるとき）。

生成は phase を動かさない SHALL。生成中か完了かの判定（この capability「生成中か完了かはファイルシステムの事実だけで判定する」）は変わらず、本家に登録されたことを完了の根拠にしてはならない（MUST NOT）。

#### Scenario: 承認するとプロジェクトが本家に現れる

- **GIVEN** 本家 dashboard が動いている
- **WHEN** ユーザーが proposal を承認し、昇格が成功し、承認の後の実行が起こされる
- **THEN** AI が起動する前に生成が依頼され、そのプロジェクトが本家の一覧に載る。AI の中で何が起きるかに依らない

#### Scenario: AI の起動はプロジェクトを生成しない

- **GIVEN** 生成の依頼が通らない状態で（本家 dashboard を止めて）昇格したプロジェクトが在る
- **WHEN** その対象の AI を起こそうとする
- **THEN** 本家の登録簿にそのプロジェクトは現れず、`.spec-workflow/` もできない。AI の起動定義に本家 spec-workflow の MCP は含まれていない

#### Scenario: 本家に載る生きたインスタンスは本家自身のものだけ

- **GIVEN** 本家 dashboard が動いている
- **WHEN** 昇格したプロジェクトの承認の後の実行が起こされ、終わる
- **THEN** 本家の登録簿でそのプロジェクトが持つ生きたインスタンスは本家 dashboard 自身のプロセスだけで、AI が起こした本家 MCP のプロセスは1つも無い

#### Scenario: 昇格の受け口は生成に触れない

- **WHEN** 昇格（U14）が成功する
- **THEN** その時点では本家へ何も依頼されていない。昇格の応答は本家の状態に依らず返る

#### Scenario: 生成は完了の根拠にならない

- **GIVEN** phase が `approved` のプロジェクトの生成が受理され、本家の一覧に載った
- **WHEN** 一覧を見る
- **THEN** そのプロジェクトは生成中のまま出ている。完了になるのは完成の記録が書かれたときである

#### Scenario: 本家が停止していても承認は成立する

- **GIVEN** 本家 dashboard が起動していない
- **WHEN** ユーザーが proposal を承認する
- **THEN** 昇格は成功し、画面は一覧へ戻り、生成中の行が出ている。生成は承認の後の実行が依頼して失敗し、その実行は起こし直しの対象として残る

## MODIFIED Requirements

### Requirement: 生成中か完了かはファイルシステムの事実だけで判定する

システムは、昇格したプロジェクトが生成中か完了かを、**`state.json` の `phase` だけで判定しなければならない（SHALL）**。`approved` は生成中、`activated` は完了である。完了の記録（`activated`）は、呼び手が完成と判定したときに `api/session/activate` が書く。判定は呼び手（`agent/invocation` の実行ごとの判定と、下の起動時の書き上げ）が持ち、`api/session/activate` は持たない。

システムは、本家がプロジェクトルートとして読む `.spec-workflow/` の有無を、生成中か完了かの判定に使ってはならない（MUST NOT）。そのディレクトリは生成（`api/project/generate`）の依頼を本家が受理したときに本家が作り、AI が起動する前、成果物が1つも無いうちから完了に見えるためである。`.spec-workflow/` の有無は、一覧に載せるプロジェクトの母集合を作るためにだけ使う SHALL。

システムは、AI の呼び出しの実行状態を、この判定の材料にしてはならない（MUST NOT）。実行状態は永続値として記録される一方、その見張りは実行中のプロセスの中にしか無く、プロセスが失われると実行中のまま誰も戻さない。それを判定に使うと、**完了することのない行**が生まれる。

この禁止が掛かるのは、**行が生成中か完了かを読み出すとき**である（SHALL）。下の「既に完成しているプロジェクトは起動時に完成を記録し直す」が実行状態で対象を選ぶことは、これに含まれない（SHALL）——あちらは phase を**書く**一度きりの移行で、書いた後の読み出しはこの Requirement のとおり phase だけを見る。禁止の理由（実行状態に依存すると完了することのない行が生まれる）も、一度きりで終わる移行には当たらない。

生成中の行を本家との接続の判定から外すこと、および生成中の行に入場できないことは、`project/directory` が定める。生成中であるかどうかの根拠は、そこでもこの phase とする（`.spec-workflow/` の有無を根拠にしない）。

この判定に厳密さを求めない（SHALL NOT）。数秒の遅れ、および取りこぼしを埋めるための作り込みを行ってはならない（MUST NOT）。表示は、次に一覧を取得し直した時点で必ず正しくなればよい。

#### Scenario: 生成が完了する

- **WHEN** 承認後に走った生成が steering 文書を出し終え、完成が記録される
- **THEN** そのプロジェクトは生成中ではなくなり、通常のプロジェクトとして一覧に並ぶ

#### Scenario: 完了の瞬間を取りこぼす

- **WHEN** 完了の瞬間の配信が届かないまま、後で一覧を取得し直す
- **THEN** そのプロジェクトは生成中ではない状態で出ている

#### Scenario: 実行状態の記録が実行中のまま残る

- **WHEN** 生成の実行を記録したプロセスが失われ、実行状態が実行中のまま残った状態で、完成は記録されている
- **THEN** そのプロジェクトは完了として出ている

#### Scenario: .spec-workflow/ ができただけでは完了にならない

- **WHEN** 生成の依頼が受理されて `.spec-workflow/` ができたが、完成がまだ記録されていない
- **THEN** そのプロジェクトは生成中のまま出ている。本家の登録に載っていてもアクティブにはならず、入場できない

#### Scenario: 成果物ゼロで実行が正常終了する

- **WHEN** steering の実行が文書を1本も出さずに正常終了する
- **THEN** そのプロジェクトは生成中のまま出ており、完了として扱われない

### Requirement: 既に完成しているプロジェクトは起動時に完成を記録し直す

システムは、完成の記録（`activated`）が導入される前に昇格し、**既に生成を終えていた**プロジェクトを、起動時に一度だけ完成として記録し直さなければならない（SHALL）。

対象は、phase が `approved` で、かつ**実行の記録（`invocation`）が `idle`** のものとする SHALL——最後の実行が正常終了して平常に戻っている、つまり生成が終わっているものである。判定の材料は一覧が返す state だけとし、ファイルシステムを読んで成果物を数えてはならない（MUST NOT）——`.spec-workflow/` は生成の依頼を本家が受理したときにでき、成果物が無いうちから在る。

実行の記録が `failed`・`error`・`running` のものは生成中のまま残す SHALL——`failed` と `error` は生成が終わっていないもの（巡回とユーザーの再実行が拾う）、`running` は起動時の後始末が `failed` へ倒す途中である。起動時の記録し直しに失敗しても起動を止めてはならない（MUST NOT）。

#### Scenario: 導入前に生成を終えていたプロジェクト

- **WHEN** phase が `approved` で実行の記録が `idle` のプロジェクトが在る状態でサーバーが起動する
- **THEN** 起動後の一覧で、そのプロジェクトは完了として出ている

#### Scenario: 導入前に生成が終わらなかったプロジェクト

- **WHEN** phase が `approved` で実行の記録が `failed` または `error` のプロジェクトが在る状態でサーバーが起動する
- **THEN** 起動後の一覧で、そのプロジェクトは生成中として出ている

#### Scenario: 宙に浮いた実行の記録を持つプロジェクト

- **WHEN** phase が `approved` で実行の記録が `running` のまま残ったプロジェクトが在る状態でサーバーが起動する
- **THEN** 書き上げの対象にならず、生成中のまま残る。起動時の後始末がその実行を畳んだ後は、巡回が起こし直す
