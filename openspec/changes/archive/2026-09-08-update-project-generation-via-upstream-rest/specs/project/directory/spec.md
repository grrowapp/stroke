# project/directory Delta

`.spec-workflow` ができる契機が「本家 MCP が接続した瞬間」から「生成（`api/project/generate`）の依頼を本家が受理したとき」に変わる。AI の起動に乗せた生成は無くなる。各 Requirement の規定そのものは変えず、その前提と Scenario の契機だけを改める。

## MODIFIED Requirements

### Requirement: プロジェクトの母集合を親パスの走査で作る

システムは、設定された親パスの配下を走査し、`.spec-workflow` ディレクトリを持つディレクトリをプロジェクトとして扱わなければならない（SHALL）。本家 API はプロジェクト一覧の母集合として使ってはならない（MUST NOT）。本家 API は停止中のプロジェクトを返さないためである。

システムは、これに加えて、**承認によって昇格したが `.spec-workflow` をまだ持たないディレクトリを、母集合に加えなければならない（SHALL）**。プロジェクトの実体は承認した瞬間に存在しており、走査が拾えるようになるのを待つと、承認した本人が自分の起こした変化を確かめられない時間が生まれるためである。

走査が果たすのは**母集合を作ること**だけとする SHALL。行が生成中か完了かは、`.spec-workflow` の有無からではなく、`state.json` の phase から導く（`project/generation`「生成中か完了かはファイルシステムの事実だけで判定する」）。`.spec-workflow` を持つことを完了の根拠にしてはならない（MUST NOT）——そのディレクトリは生成（`api/project/generate`）の依頼を本家が受理したときに本家が作り、AI が起動する前、成果物が1つも無いうちからできている。

システムは、走査対象を読み取りのみで扱わなければならない（MUST）。プロジェクトのディレクトリにも `.spec-workflow/` にも書き込んではならない（MUST NOT）。

#### Scenario: 親パスの配下にプロジェクトがある

- **WHEN** 設定された親パスの配下に `.spec-workflow` を持つディレクトリが複数ある
- **THEN** それらすべてがプロジェクトとして一覧に並ぶ

#### Scenario: `.spec-workflow` を持たないディレクトリは拾わない

- **WHEN** 親パスの配下に、昇格しておらず `.spec-workflow` も持たないディレクトリがある
- **THEN** そのディレクトリは一覧に現れない

#### Scenario: 承認した直後に一覧を開く

- **WHEN** proposal を承認した直後にプロジェクト一覧を開く
- **THEN** 昇格したプロジェクトが生成中として一覧に載っている

#### Scenario: .spec-workflow ができても生成中のまま

- **WHEN** 昇格したプロジェクトの生成が受理されて `.spec-workflow` ができたが、完成はまだ記録されていない
- **THEN** 走査で拾われるようになっても、その行は生成中のまま出ている

#### Scenario: 親パスが未設定

- **WHEN** 親パスが設定されていない状態でプロジェクト一覧を開く
- **THEN** 「親パスが未設定である」と分かる表示になり、「プロジェクトが0件である」状態とは区別できる

#### Scenario: 親パスの配下にプロジェクトが1件も無い

- **WHEN** 親パスは設定されているが、配下に `.spec-workflow` を持つディレクトリも生成中のプロジェクトも1つも無い
- **THEN** 「プロジェクトが0件である」と分かる表示になり、「親パスが未設定である」状態とは区別できる

#### Scenario: 親パスが読み取れない

- **WHEN** 設定された親パスが存在しない、または読み取り権限が無い
- **THEN** 走査の失敗が画面に出て、0件の状態と区別できる

### Requirement: アクティブと未接続を判定して示す

システムは、各プロジェクトが **アクティブ**（本家の MCP サーバーが繋がっている）か **未接続**（繋がっていない）かを判定し、一覧に示さなければならない（SHALL）。判定は本家のグローバル状態（`activeProjects.json`）または本家 API を母集合に重ねて行う。

システムは、**生成中のプロジェクト（phase が `approved`）を、この判定の対象にしてはならない（MUST NOT）**。生成中のプロジェクトは、生成（`api/project/generate`）が受理された時点で本家のグローバル状態に載る——本家は登録に自分自身のプロセスを生きたインスタンスとして書く。載っていることを理由にアクティブと示すと、成果物が無いまま入場できる行になる。生成中の行は「生成中」とだけ示し、アクティブとも未接続とも示さない。

システムは、アクティブ判定が本家ダッシュボードの起動時に1回しか更新されないという本家の制約を、そのまま受け入れなければならない（SHALL）。本家プロセスの生存を stroke-board が独自に確認してはならない（MUST NOT）。

#### Scenario: 本家に繋がっているプロジェクト

- **WHEN** 本家のグローバル状態に、そのプロジェクトの生きたインスタンスが登録されている
- **THEN** 一覧のその行は「アクティブ」として表示され、選択できる

#### Scenario: 本家に繋がっていないプロジェクト

- **WHEN** 走査では見つかるが、本家のグローバル状態に生きたインスタンスが無い
- **THEN** 一覧のその行は「未接続」として表示され、選択できない

#### Scenario: 生成中のプロジェクト

- **WHEN** 生成中のプロジェクトの行を見る
- **THEN** 状態は「生成中」であり、「未接続」とは区別できる

#### Scenario: 生成中のプロジェクトが本家に載っている

- **WHEN** 生成中のプロジェクトの生成が受理され、本家のグローバル状態に生きたインスタンスが登録されている
- **THEN** 一覧のその行は「アクティブ」にならず「生成中」のままで、選択も入場もできない

#### Scenario: アクティブなプロジェクトが1件も無い

- **WHEN** 走査で見つかったすべてのプロジェクトが未接続である
- **THEN** 一覧には行が並ぶが、どの行も選択できない状態になる

### Requirement: 一覧は4つの列を持つ

システムは、プロジェクト一覧の各行に次の4つを示さなければならない（SHALL）。

- **プロジェクト** — 走査で見つかったディレクトリ名。生成中のものは、承認で確定した名前
- **状態** — **アクティブ / 未接続 / 生成中** のいずれか。**プロセス ID は示さない（MUST NOT）**——一覧で下す判断は「その行に入るかどうか」だけで、プロセス ID はその判断に使われない。**「作成に失敗」の状態は持たない（MUST NOT）**——失敗は決着のモーダルで片付き、行として居座らない（`project/generation`）
- **未処理の通知** — そのプロジェクトで発生していて一覧に残っている通知の件数。0件のときは件数を出さず、無いことが分かる表示にする。生成中のものは、通知が起きていても示さず、同じく無いことが分かる表示にする
- **最終更新** — そのプロジェクトの `.spec-workflow` がいつ更新されたか。取れないときは、取れないことが分かる表示にする

「最終更新」は未接続のプロジェクトについても示さなければならない（SHALL）。未接続では本家 API から何も取れないため、ここが唯一の手がかりになる。

**生成中のプロジェクト（phase が `approved`）には、本家から取れる値を示してはならない（MUST NOT）。** 「最終更新」も「未処理の通知」も、取れないことが分かる表示にする SHALL。取れない事実を、承認した時刻など別の値で埋めてはならない（MUST NOT）。根拠は phase であって `.spec-workflow` の有無ではない（SHALL）——そのディレクトリは生成が受理されたときに本家が作り、生成中の対象は AI が起動する前から持つ。本家に載っていれば通知も最終更新も実際に取れてしまう。取れるかどうかではなく、**生成中のあいだは見せない**という決めである。

システムは、3つの状態を **同じ形・同じ幅** で示さなければならない（SHALL）。状態によって形や大きさを変えてはならない（MUST NOT）。幅を揃えるのは、状態の列が行をまたいで縦に揃い、一覧を上から下へ流し読みできるようにするためである。

システムは、**アクティブだけを際立たせ**なければならない（SHALL）。未接続と生成中は際立たせない。3つの違いは、形の違いではなく、際立っているかどうかと文言で示す。ここで「際立つ」とは、同じ形のまま色と明るさだけが変わることを指す。

#### Scenario: アクティブなプロジェクトの行

- **WHEN** アクティブなプロジェクトの行を見る
- **THEN** 状態に「アクティブ」が出ており、プロセス ID は出ていない

#### Scenario: 未接続のプロジェクトの行

- **WHEN** 未接続のプロジェクトの行を見る
- **THEN** 状態は「未接続」で、アクティブと区別できる

#### Scenario: 生成中のプロジェクトの行

- **WHEN** 生成中のプロジェクトの行を見る
- **THEN** 名前は承認で確定した名前が出ており、状態は「生成中」、未処理の通知と最終更新はいずれも無いことが分かる表示になっている

#### Scenario: 生成中のプロジェクトが .spec-workflow を持つ

- **WHEN** 生成中のプロジェクトの生成が受理されて `.spec-workflow` ができ、走査でその最終更新が取れる
- **THEN** 「最終更新」は取れないことが分かる表示のままで、走査で拾えた値を埋めない

#### Scenario: 3つの状態を並べて見る

- **WHEN** アクティブ・未接続・生成中の行が同じ一覧に並んでいる
- **THEN** 3つの状態は同じ形と同じ幅で示されており、状態の列は縦に揃っている

#### Scenario: 際立っているものを見分ける

- **WHEN** 一覧の状態の列を見る
- **THEN** 際立っているのはアクティブの行だけであり、未接続と生成中は際立っていない

#### Scenario: 通知が発生していないプロジェクト

- **WHEN** そのプロジェクトの通知が1件も無い
- **THEN** 未処理の通知の列は件数ではなく、無いことが分かる表示になる

#### Scenario: 通知が発生したプロジェクト

- **WHEN** そのプロジェクトで通知が2件発生している
- **THEN** 未処理の通知の列に 2 が出ている

#### Scenario: 未接続のプロジェクトの最終更新

- **WHEN** 未接続のプロジェクトの行を見る
- **THEN** 最終更新が出ている

### Requirement: 未接続のプロジェクトは選択できない

システムは、未接続のプロジェクトの行を選択不可としなければならない（SHALL）。押せないことが見て分かる表示にし、キーボード操作のフォーカス対象にしてはならない（MUST NOT）。

システムは、**生成中のプロジェクト（phase が `approved`）の行も、同じく選択不可としなければならない（SHALL）**。根拠は phase であって中身の有無ではない（SHALL）——生成中でも、生成が受理されれば `.spec-workflow` はでき、下層に見せられるものが在ることはある。それでも入場させないのは、**完成が記録されるまでは作りかけを見せない**という決めだからである。

システムは、押せないことを示すために行を弱めるとき、**状態の列を弱めてはならない（MUST NOT）**。弱めるのは名前・未処理の通知・最終更新であり、状態はアクティブの行と同じ読みやすさを保たなければならない（SHALL）。

行を弱めるのは「その行に入れない」ことを示すためである。状態はその理由そのものを名指しているため、理由まで一緒に弱めると、押せない行を前にして原因が読み取れなくなる。行全体に一律の弱め方を掛ける実装は、この要件を満たさない。

#### Scenario: 未接続の行をポインタで押す

- **WHEN** 未接続のプロジェクトの行を押す
- **THEN** 何も起きず、下層に入らない

#### Scenario: 生成中の行をポインタで押す

- **WHEN** 生成中のプロジェクトの行を押す
- **THEN** 何も起きず、下層に入らない

#### Scenario: 中身を持つ生成中の行を押す

- **WHEN** 生成が受理されて `.spec-workflow` ができた生成中のプロジェクトの行を押す
- **THEN** 何も起きず、下層に入らない。中身が在ることは入場の理由にならない

#### Scenario: キーボードで一覧を辿る

- **WHEN** キーボードでプロジェクト一覧のフォーカスを順に送る
- **THEN** フォーカスはアクティブな行だけを通り、未接続・生成中の行では止まらない

#### Scenario: 未接続の行の状態を読む

- **WHEN** 未接続のプロジェクトの行を見る
- **THEN** 名前・未処理の通知・最終更新は弱く示されるが、状態はアクティブの行と同じ読みやすさで読める

#### Scenario: 生成中の行の状態を読む

- **WHEN** 生成中のプロジェクトの行を見る
- **THEN** 名前・未処理の通知・最終更新は弱く示されるが、状態はアクティブの行と同じ読みやすさで読める

#### Scenario: 動きを抑える設定で生成中の行を読む

- **WHEN** 動きを抑える設定（`prefers-reduced-motion: reduce`）で生成中のプロジェクトの行を見る
- **THEN** 状態の読みやすさは、動きを抑えない設定のときと変わらない

#### Scenario: 未接続の行とアクティブの行を並べて見る

- **WHEN** 未接続の行とアクティブの行が同じ一覧に並んでいる
- **THEN** 状態の列だけは、どちらの行でも同じ読みやすさで示されている
