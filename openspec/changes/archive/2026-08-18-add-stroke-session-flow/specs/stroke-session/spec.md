## Purpose

概要を起点にユーザーと AI がストロークを重ね、把握完了に至るまでの進行と状態を扱う。設計ツリーを詰める場そのものであり、proposal を起こす合図もここが出す。

## ADDED Requirements

### Requirement: 概要からセッションを開始する

システムは概要の投稿を受け取り、セッションを1つ作成し、phase を `stroking` として AI の最初の問いを返す SHALL。認証は行わず、単一ユーザーを前提とする。

#### Scenario: 概要を投稿する

- **WHEN** ユーザーが画面1で概要を投稿する
- **THEN** システムはセッションを1つ作成し、phase を `stroking` とし、AI の最初の問いを表示する

#### Scenario: 概要が空のまま投稿する

- **WHEN** 概要が空のまま投稿される
- **THEN** システムはセッションを作成せず、入力が必要である旨を示す

### Requirement: ストロークの往復を進める

システムはユーザーの入力と AI の応答の1往復をストロークとして扱い、同一セッションの継続として進める SHALL。

#### Scenario: 問いに答える

- **WHEN** ユーザーが回答を送信する
- **THEN** システムは同一セッションの継続として AI に渡し、返ってきた次の問いを表示する

#### Scenario: 応答を待っている

- **WHEN** AI の応答をまだ受け取っていない
- **THEN** システムは待機中であることを示し、同じセッションへの追加送信を受け付けない

### Requirement: 把握完了の判定は grilling の終了条件に従う

システムは把握完了の判定を自作せず、`grilling` の終了条件（フロンティアが空）に従う SHALL。

#### Scenario: フロンティアが残っている

- **WHEN** まだ問える決定が残っている
- **THEN** phase は `stroking` のままで、次の問いが返る

#### Scenario: フロンティアが空になる

- **WHEN** フロンティアが空になる（把握完了）
- **THEN** AI が proposal を起こし、phase を `proposed` に変え、画面2を表示する

### Requirement: セッションの状態を保持する

システムはセッションごとに phase（`stroking` / `proposed` / `approved`）と、履歴に出す問いと回答のペアを保存する SHALL。会話の全文は保存しない。

#### Scenario: ブラウザをリロードする

- **WHEN** ユーザーがブラウザをリロードする
- **THEN** システムは保存された phase に対応する画面を表示し、履歴も同じ内容で開ける

### Requirement: proposal が起きた後の画面1 は画面2 へ送る

phase が `proposed` 以降のとき、画面1 には答えるべき問いが無い。通常の操作では、画面と画面を移る導線を置かないため、この状態の画面1 へ移ることはない。**エッジケース**として、URL を直接開く・ブックマークから開く・リロードする経路が残る。システムはこのとき画面1 を描かず、画面2 を表示する SHALL。

#### Scenario: 通常 — stroking で画面1 を見る

- **WHEN** phase が `stroking` のときユーザーが画面1 を見る
- **THEN** 画面1 が最新の問いと回答欄を表示する

#### Scenario: エッジ — proposal が起きた後に画面1 の URL へ入る

- **WHEN** phase が `proposed` または `approved` のとき、URL の直接入力・ブックマーク・リロードで画面1 に入る
- **THEN** システムは画面1 を描かず、画面2 を表示する
