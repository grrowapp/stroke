# Proposal — steering-dashboard-portal

## Why

spec-workflow-mcp のダッシュボードは**プロジェクト単位**でできている。`projectId` は `localStorage` に持たれていて URL に出ない（`ProjectProvider.tsx`）ため、「どのプロジェクトの何が起きたか」を指すリンクを作れず、複数プロジェクトを並行して回すと、どこで承認待ちが発生したかは各プロジェクトのダッシュボードを順に開くまで分からない。

stroke-board は、その上に**プロジェクト横断の通知ポータル**を置く。横断であることが本家に無い価値そのもので、上位互換の実体はここにある（interview Q34）。

## Who

**単一のペルソナに絞らない**（interview Q33）。開発者本人を含む複数の関係者が同じ画面を見る。役割ごとの機能差もユーザー概念も持たない（Q10・Q33）。

そのうえで具体的に言えるのは、インタビューの回答者＝**複数プロジェクトを並行して回している開発者**の状況だけである。

- **文脈**: spec-workflow-mcp を複数プロジェクトで使い、本家ダッシュボードは自分で起動している（Q20）
- **痛み**: 承認待ちやタスク進行が「見に行かないと分からない」。プロジェクトごとに開き直す必要がある
- **雇う仕事**: 起きたことに気づくこと、そこから対象ドキュメントに直行すること — その2つだけ（Q13）

🔶 **仮定**: これ以外の関係者（レビュアー、管理者など）が何を必要とするかは聞けていない。外部公開する以上いるはずだが、想像で書かない。

## Outcome

**測定指標を置かない**（interview Q22）。数値目標を設定しないことを、そのまま本プロジェクトの立場とする。発明した指標をここに置かない。

## What Gets Built

- **上層 — プロジェクト横断ポータル**（本家に無い）
  - 通知画面: プロジェクト / 種別 / 内容 / 最終更新 の4列の一覧
  - プロジェクト一覧画面: アクティブが上、未接続が下。未接続は選択できない
  - プロジェクトの**登録**と**作成**: 一覧画面の操作として持つ。stroke-board は入口だけで、実処理は接続先の別プロジェクトが担う（Q40）
  - 通知トースト: 本家の実装と完全に同じ形（右上固定・5秒で自動消滅・種別4色・クリック不可）
- **下層 — プロジェクト単位の画面群**: 仕様書 / ステアリング / タスク / 承認 / 設定（Q35）
- **日本語と英語の2言語**（Q14）
- ステアリング文書3本（product.md / tech.md / structure.md）を新規に書く（Q1）

既存資産への影響はない。stroke-board は本家とは別のアプリケーションで、本家に変更を加えない。**BREAKING** なし。

## Capabilities

- **横断で気づく**: 複数プロジェクトで起きた承認依頼とタスクの変化を、1つの画面で見られる
- **その場で知る**: 起きた瞬間に画面内へトーストが出る。OS 通知は使わない
- **対象へ直行する**: 通知の行から対象ドキュメントを開ける。本家には作れない横断リンクがここで成立する
- **プロジェクトを見渡す**: どのプロジェクトが今つながっていて、どれが止まっているかが分かる
- **プロジェクトを増やす**: 一覧画面から登録・作成の入口に入れる
- **プロジェクトの中に入る**: 一覧から下層に入り、仕様書・ステアリング・タスク・承認・設定を見られる

**出す通知は本家と同じ4種**（Q41）— タスク完了（完了数が増えた）／タスク着手（in-progress に変わった）／全件完了／承認依頼の発生。本家 `NotificationProvider` が出しているものをそのまま踏襲する。

Q17 では「本家が出すもの全部」と決めたが、実測の結果ここまでしか取れない。ステアリング文書の更新は payload が変化せず検出できず、承認と却下の区別も pending の消滅としてしか観測できない。`spec-update` / `steering-update` は再描画用の同期信号であり通知にしない。

## Out of Scope

- **Jobs / Logs / Statistics**（Q6）— 本家にはあるが作らない
- **他ソースの集約**（Q5）— CI やファイル監視など spec-workflow-mcp 以外のイベントは受けない。汎用通知ポータルにはしない
- **ワークフローの状態変更**（Q11・Q39）— 承認・却下・タスク更新は本家に委ねる。stroke-board は `.spec-workflow/` に書き込まない
- **通知の永続化**（Q16）— 履歴も既読未読も持たない。自前のデータストアを持たない
- **ユーザー概念と購読モデル**（Q10）— 認証は現時点で持たない。将来の導入は否定しないが、今のスコープには入れない
- **本家プロセスの起動・監視**（Q20）— 本家は利用者が別途起動する
- **OS 通知**（Q19）— Notification API / Service Worker / Push API / VAPID をいずれも使わない

## Principles & Constraints

**MUST**

- 本家が持つ範囲の状態は本家に委ねる。stroke-board は `.spec-workflow/` に書き込まない（Q11・Q39）
- 通知・既読状態を独自に永続化しない。表示は本家のデータ状態から導出する（Q16）
- ブラウザは stroke-board のサーバーとだけ話す。本家 WebSocket にブラウザから直接つながない（Q15）

**SHOULD**

- 取得手段は ①本家 REST API → ②MCP ツール → ③`.spec-workflow/` の直接読み取り の順で選ぶ（Q11）
- 本家に見た目を合わせる。design token は本家 v2.2.5 に準拠する（ui.md）

**MAY**

- 本家に無い範囲（プロジェクトの作成など）は stroke-board 側の機能として持ってよい（Q39）

認証・外部公開に関する制約はここに置かない（Q29 の明示的な決定）。

## Technology

**プロジェクト種別** — 単一利用者向けの Web アプリケーション。**規模の成長は考慮しない**（Q27）。想定台数も同時接続数も増えないため、成長シナリオと性能目標をステアリングに置かない。

**アプリケーション構成** — Nuxt4 の **SSR あり**（Q21）。Nitro サーバーが本家 WebSocket のクライアントとなり、そこにイベント発火の制御層を置く。ブラウザは stroke-board のサーバーとだけ話す（Q15）。

- 採らなかった案: ブラウザから本家 WebSocket へ直結。監視するプロジェクトの数だけブラウザが接続を張ることになり、差分計算がクライアントに散る
- 採らなかった案: W3C Push API + Service Worker + VAPID。Q19 で「ブラウザ画面内に出る通知」だと確定したため不要になった

**言語とランタイム** — TypeScript / Node.js（Nuxt4 + Nitro の前提）。

**主要な依存** — Nuxt4 / Nuxt UI / TailwindCSS。

- 🔶 Nuxt UI v4 が要求する Tailwind CSS のメジャーバージョンは公式に明記が無く、実装時に `package.json` の解決結果で確定する
- 🔶 Nuxt UI のテーマ機構で本家の design token を再現できるかは未検証。プロトタイプは本家の CSS バンドルを直接読んでおり、Nuxt UI を通していない

**互換性の基準** — 本家 **spec-workflow-mcp v2.2.5**。本プロジェクトが依存しているのは公開 API だけでなく、WebSocket ペイロードの形・registry の構造・PID による生存判定といった内部の振る舞いも含む。基準バージョンを明示し、実測で分かった事実は記録として残す。

**テスト** — ロジックは Vitest、通知から対象ドキュメントへの導線は Playwright で E2E を取る（Q24）。

**コード品質ツール** — **規定しない**（Q26）。lint / format の選定をステアリングで縛らない。

**セキュリティ姿勢** — アプリ自身は認証を持たない（Q7・Q10）。外部公開はするが、現時点で認証機構を組み込まない。将来の導入を否定しない。

**配布と設置** — Nitro サーバーとして起動するところまでを決め、外に出す手段（トンネル・リバースプロキシ・ポート開放）は運用側の問題としてステアリングから外す（Q28）。本家の URL は設定で受け取る（Q20）。

**バージョン管理** — git、作業単位で feature ブランチを切って main にマージする（Q25）。`base2` は現状 git リポジトリではないため `git init` から始まる。

**すでに効かないと分かっていること**（実測）:

- 本家 API から**未接続プロジェクトは取れない**。`cleanupStaleProjects()` が生きた instance の無いエントリを registry ごと削除するため。プロジェクト一覧の母集合は、設定した親パスを走査して `.spec-workflow` を持つディレクトリを拾う方式で作る（Q37）
- 本家のイベントはすべてスナップショット型で「何が起きたか」を含まない。本家サーバーは `tasks.md` を毎回パースして今の `taskList` を送るだけで前回値を持たないため、通知文にするには**受け取った側が前回値と比べる**必要がある。これは本家フロントが既にやっていることで、stroke-board もそれを踏襲する（Q41・ADR-0001 に照らして確認済み）
- ステアリング文書の更新は検出できない。承認と却下も区別できない
- `SPEC_WORKFLOW_HOME` にはファイルしか無く、それ自体はプロジェクト一覧の出どころにならない。ただし `SPEC_WORKFLOW_SHARED_ROOT`（この環境では `/opt/projects/stroke-board`）の**一つ上が集合親**にあたり、`.spec-workflow/` を外出しした `/opt/projects/<name>/` が並ぶ。走査先はここになる

## Structure

**モジュール境界** — 構成から素直に下りる3層で切る。

- **本家との接点** — REST API クライアント、WebSocket クライアント、`activeProjects.json` の読み取り、親パスの走査。本家の形が変わったときに直す範囲をここに閉じる
- **制御層（Nitro 側）** — 受信したスナップショットから前回値との差分を出し、通知として意味のあるものだけをブラウザ向けの WebSocket に流す。stroke-board 固有の判断はすべてここに集まる（この差分計算は Q41 で本家の踏襲として承認済み。ADR-0001 参照）
- **画面（Nuxt 側）** — 上層（横断ポータル）と下層（プロジェクト単位）。上層と下層はナビゲーションの形が違い（タブ / サイドバー）、同じ階層に並ばない

**越えてはいけない線** — 画面から本家へ直接触らない。本家に触るのは接点層だけで、画面は制御層が整えた形だけを見る。

**`packages/` による deep module 構成は採らない**（Q18）。`base2/CLAUDE.md` にあった当該記述は、この決定に合わせて削除済み。

**import の規約** — Nuxt の **auto-import を使わない**（Q32）。`imports: { autoImport: false }` で composable / util の自動 import を止め、`#imports` からの明示 import を使う。コンポーネントは `components.dirs` を空にして止めるが、**Nuxt UI がモジュールとして登録するコンポーネントは止まらない**（公式に "this will not affect components added by modules" と明記）。したがって「明示 import を規約とする。ただし Nuxt UI 由来のコンポーネントは例外」が実際に守れる線になる。

**命名規則・ファイルサイズ上限・ファイル内の構造** — **規定しない**。インタビューで決めたのは auto-import の可否だけで、それ以外を発明しない。

**書き残すもの** — ルートの `CONTEXT.md` に用語を、`docs/adr/` に設計判断を残す（Q31）。本家の内部挙動に関する実測（registry の生存判定、ペイロードの形、検出できないイベント）は、後から読む人が同じ調査を繰り返さずに済むよう ADR に残す。

## Risks

- **本家の内部実装に依存している** — 公開 API だけでなくペイロードの形や registry の構造に依存する。本家の更新で壊れる → 基準を v2.2.5 と明示し、依存している事実を ADR に残す。接点層に閉じ込めて直す範囲を狭くする
- **未接続プロジェクトの一覧が走査頼み** — 設定した親パスが誤っていると一覧が空になる → 「親パス未設定」「プロジェクト0件」を区別できる状態として画面に出す
- **MCP がクラッシュすると誤表示になる** — 生存確認は本家ダッシュボードの起動時1回だけなので、死んだ PID がアクティブとして残る → 本家の再起動でしか解消しないことを既知の限界として記録する
- **通知の網羅性に限界がある** — ステアリング更新は検出できず、承認と却下も区別できない → 取れないものを取れると見せない。Capabilities に書いた4種だけを通知とする
- **認証なしで外部公開する** — 現時点の割り切り（Q7・Q10） → 公開手段は運用側の責任とし（Q28）、将来の認証導入を閉じない構造にする
- **作成の実処理が外部にある** — 接続先の別プロジェクトが未定のため、この機能だけ完成させられない（Q40） → 入口と非活性状態まで作り、中身は接続先が決まってから

## Open Questions

- **stroke-board の「登録」が何を指すか** — 本家に `POST /api/projects/add` が実在する一方、一覧は親パスの走査で作る。その API を叩くのか、走査対象の親パスを足すのか、別物なのかが未確定
- **登録・作成の中身** — 何をどう作り、どう登録するか。接続先が決まるまで確定しない
- **接続先の別プロジェクトが何であるか** — 作成の実処理を担う相手が具体的に決まっていない
- **Nuxt UI v4 が要求する Tailwind CSS のメジャーバージョン** — 公式に明記が無く、実装時に確定する
- **Nuxt UI で本家 design token を再現できるか** — 未検証

## Dependencies

- **spec-workflow-mcp v2.2.5**（別途起動されている前提・Q20）— 依存しているのは REST API、WebSocket（`ws://<host>/ws?projectId=<id>`）、`SPEC_WORKFLOW_HOME` 配下の `activeProjects.json`、および `.spec-workflow/` の構造
- **各プロジェクトの `.spec-workflow/`** — プロジェクト一覧の母集合を走査で判定するための目印として読む（書き込まない）
- **Nuxt4 / Nitro / Nuxt UI / TailwindCSS** — 実装基盤
- **Vitest / Playwright** — テスト
- **作成の実処理を担う接続先プロジェクト** — 未定。これが決まるまで作成機能は入口までしか作れない
