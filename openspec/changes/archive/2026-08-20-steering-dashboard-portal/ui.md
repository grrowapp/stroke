## Surfaces

**上層（プロジェクト横断ポータル）** — stroke-board 固有で、本家には無い（interview Q34）

- **通知** — 受け取った通知を一覧で見る画面 ✅ 承認済み
  - **一覧型のリスト表示（表形式）** で並べる ✅ 承認済み
  - 列は **プロジェクト / 種別 / 内容 / 最終更新** の4列 ✅ 承認済み
- **プロジェクト一覧** — 見えているプロジェクトを並べる画面。**登録**と**作成**はこの画面の操作として持ち、独立したメニュー項目にはしない ✅ 承認済み

**下層（プロジェクト単位）** — ステアリング / 仕様書 / タスク / 承認 / 設定（interview Q35）。統計と実装ログは非対応（interview Q6）

**その他**

- **通知トースト** — イベント発生時にブラウザ画面内に出る通知。**本家と完全に同じ形**にする ✅ 承認済み。OS 通知は使わない（interview Q19）
  - 右上に固定、複数を縦に積む。5秒で自動的に消え、× でも閉じられる
  - 中身は1行テキストのみ。**クリックできない**（知らせるだけ）
  - 種別は info / success / warning / error の4つで色分け
  - 対象ドキュメントを開く導線は通知ポータル画面に一本化する
  - **出す通知も本家と同じ4種**（interview Q41）: `Task completed`（完了数が増えた・success）/ `Task started`（in-progress に変わった・info）/ `All tasks completed`（全件完了・success）/ `New approval request`（承認 ID が増えた・info）
- **ドキュメント表示先** — 通知から開く先。開くだけで、該当セクションへのスクロールやハイライトはしない（interview Q13）

### ナビゲーション — 階層ごとに形と位置を変える ✅ 承認済み

上層と下層は階層が違うので同じナビゲーションには並べない（interview Q34）。並べない代わりに、**ナビゲーションの形そのものを階層ごとに変える**。

| 階層 | ナビゲーションの形 | 位置 |
|---|---|---|
| 上層（横断ポータル） | タブ（通知 / プロジェクト一覧） | ヘッダー直下の横並び |
| 下層（プロジェクト単位） | サイドバー（仕様書 / ステアリング / タスク / 承認 / 設定） | 画面左の縦並び |

- 下層へ入るのは**プロジェクト一覧の行から**。上層へ戻るのは**ヘッダー左の「← ポータルへ戻る」**
- 別のプロジェクトへ移るときは上層を経由する。下層にプロジェクト切替の口を置かない
- 形が違うので、ナビゲーションを見た時点でどちらの階層にいるかが分かる

## Primary Flows

**1. 通知に気づいてドキュメントを開く**

1. 入口: 上層の通知画面を開いている。またはイベント発生時にトーストが出て、それに気づいて通知画面を開く
2. 一覧から対象の通知を選ぶ
3. 終了状態: 対象ドキュメントが開いている

トーストは知らせるだけで、そこから直接ドキュメントへは進まない（本家と同じ形にすると決めたため）。開く導線は通知画面の行だけ。

Q13 で「ただ開くだけ」と決めたので、このフローに承認・却下などの操作は含まない。状態を変える操作は本家に残る（interview Q11「自分では書き込まない」）。
一覧の各行から対象を選ぶ手がかりは、プロジェクト / 種別 / 内容 / 最終更新 の4列。

**2. プロジェクトに入る**

1. 入口: 上層のプロジェクト一覧
2. アクティブな行を選ぶ（未接続の行は選べない）
3. 終了状態: そのプロジェクトの下層に入り、左サイドバーの先頭画面が開いている

別のプロジェクトへ移るには「← ポータルへ戻る」で上層に戻ってから選び直す。

**3. プロジェクトを登録する / 作成する**

1. 入口: 上層のプロジェクト一覧の [ 登録 ] / [ 作成 ]
2. モーダルで必要事項を入れて実行する
3. 終了状態: 一覧に反映されている

登録と作成は同じ扱いで、どちらも一覧画面の操作として持つ。

**stroke-board が持つのは入口だけ**（interview Q40）。実際に作るのは接続先の別プロジェクトで、接続が無ければ作成は行えない。**中身（何をどう作り、どう登録するか）はこの時点では決めていない**。

## States

### 通知

一覧型リスト表示に対して、以下の状態が起こりうる。実測に基づく。

- **通知ゼロ件** — 接続直後は必ずこの状態になる。本家は接続時に `initial` で現在のスナップショットを送るだけで、それ以前に何が起きたかは送らない。差分の基準ができるまで通知は発生しない
- **本家に未接続 / 再接続中** — 本家ダッシュボードは別途起動されている前提（interview Q20）なので、起動していない状態が普通に起こる
- **対象ドキュメントが存在しない** — 通知が持つ `filePath` の指す先が、開く時点で削除・アーカイブされている場合がある
- **同一対象に対する通知が連続する** — 本家が 300ms / 500ms でデバウンスしてから送るため、まとめて 1 件になる場合と、連続して届く場合の両方がある

### プロジェクト一覧

- **アクティブが1件も無い** — 全プロジェクトが未接続で、行はあるが1つも選べない。実測時の `activeProjects.json` は実際に `{}` だった。珍しい状態ではない
- **プロジェクトが1件も無い** — 設定した親パスの配下に `.spec-workflow` を持つディレクトリが無い
- **親パスが未設定** — 初回起動時に必ず通る
- **作成の接続先が無い** — 実処理を担う別プロジェクトに繋がっていない状態（interview Q40）。[ 作成 ] は非活性になる

各状態で何を表示するかは **未決**（実装中に決めてよい）。

## Interaction & Feedback

- **通知からは「開く」だけ** — 状態を変えないため確認も取り消しも要らない
- **トーストは知らせるだけ** — 5秒で自動的に消える。× で閉じられる。押しても何も起きない。複数同時に発生したら縦に積む（本家と同じ）
- **登録・作成は状態を変える操作** — 通知まわりとは性質が違うので、実行前の確認が要る。取り消しの要否は中身が決まってから
- **未接続プロジェクトは選択できない** — 押せないことが見て分かる形にする（非活性表示）
- **楽観的更新は無し** — 表示内容は本家のデータ状態から導出する（interview Q16）ので、こちら側で先回りして書き換えるものがない
- **待ち時間** — 通知の発生は本家からの WebSocket 受信が起点で、こちらから要求しない。ドキュメントを開く際は本家 API への取得待ちが発生する
- **失敗の見せ方** — 本家との接続断、ドキュメント取得失敗、登録・作成の失敗が起こりうる。どう見せるかは **未決**

本家 spec-workflow-mcp v2.2.5 の design token に準拠する。稼働中の実物から実測して確認した値:

| token | 値 |
|---|---|
| `--surface-base` | `#0f172a` |
| `--surface-panel` | `#1e293b` |
| `--surface-sunken` | `#0f172a` |
| `--border-default` | `#334155` |
| `--interactive-primary` | `#6366f1` |
| `--text-primary` / `--text-secondary` / `--text-muted` | `#f1f5f9` / `#cbd5e1` / `#94a3b8` |

- 既定はダークテーマ（`ThemeProvider.tsx` の初期値が `'dark'`）
- 書体は Inter、等幅は JetBrains Mono
- 角丸は 4 / 6 / 8px、余白は 4px グリッド
- アクセントは indigo 1 色に集約されており、種別ごとに色を撒かない。本家の `Not Created` / `No tasks` 相当の表示は無彩色
- アクティブ / 未接続の区別は色ではなく、チップの文言と行の非活性（不透明度）で示す
- **例外はトースト** — 本家のトーストだけは種別で色を撒く（info=青 / success=緑 / warning=黄 / error=赤、いずれも `*-50/-200/-800` とダーク時 `*-900/20` の組み合わせ）。本家と同じ形にすると決めたので、ここは indigo 集約の外に置く

🔶 **未検証**: 実装は Nuxt4 + NuxtUI + TailwindCSS（interview で与えられた前提）だが、NuxtUI のテーマ機構でこれらの token を再現できるかを確認していない。プロトタイプは本家の CSS バンドルをそのまま読み込んでおり、NuxtUI を通していない。

## Accessibility

- キーボードのみで一覧を辿り、対象を開けること
- 未接続プロジェクトの行はフォーカス対象にしない。押せない行にフォーカスが止まらないこと
- フォーカスが視覚的に判別できること。本家のアクティブ表現は `rgba(99,102,241,0.10)` の背景 + `#6366f1` の文字で、フォーカスリングとは別
- モーダルが出たときにフォーカスがモーダルへ移り、閉じたら戻ること。これは登録・作成のモーダルに効く
- **トーストはフォーカスを奪わない** — 作業中に割り込むものなので、出てもフォーカスは動かさない。ただし × ボタンにはキーボードで到達できること

🔶 **未検証**: 上記のコントラスト比を測っていない。本家がどの水準を満たしているかも確認していない。未接続行の不透明度を落とした状態のコントラストも測っていない。

## Prototype Outcome

**プロトタイプの所在**: `openspec/changes/steering-dashboard-portal/prototype/`（使い捨て。`index.html` が常に最新のプロトタイプを指す。本家の CSS バンドルを `prototype/assets/spec-workflow.css` に取り込んでいる）

### 1回目 — 通知ポータルの情報構造（`notification-portal.prototype.html`）

**問い**: 通知集約ポータルの情報構造と、イベント発生時のブラウザ内通知の出し方はどれが正しいか。

- **A** — 2ペイン インボックス。左に通知リスト、右に詳細とドキュメント本文プレビュー。通知は右下トースト
- **B** — 種別レーン。承認 / タスクをレーンに分けて並べる。通知は中央モーダル
- **C** — 全幅テーブル。表形式の一覧＋種別タブ。行から直接ドキュメントへ。通知は上部バナー

**選ばれたもの**: **C の「一覧型のリスト表示」**。C に含まれていた種別タブ・列構成・上部バナー・左メニューは承認外。

### 2回目 — 行の列構成（`row-composition.prototype.html`）

レイアウトを表に固定したうえで、行に何を出すかを問うた。

- 案1 最小3列（プロジェクト / 内容 / 時刻）
- 案2 1行 = 1対象ドキュメント（同じ対象への通知を畳む）
- 案3 詳細7列（プロジェクト / 種別 / 内容 / 対象 / 状態 / 時刻 / 操作）

**選ばれたもの**: 混在指定で **プロジェクト / 種別（案3）/ 内容（案3）/ 最終更新（案2）** の4列。対象・状態・操作・未処理の各列は落とす。

### 3回目 — ナビゲーションの形と位置（`navigation.prototype.html`）

**問い**: 上層と下層をどう行き来させるか。Q34/Q35 で「同じナビゲーションには並べない」ことは決着済みで、残るのは形と位置。

この回の途中で上層の中身が増えた（プロジェクト一覧・登録・作成）ため、前提を組み直して5案を出した。

- **A** — 階層でナビの形を変える。上層は上部タブ、下層は左サイドバー
- **B** — ヘッダーのプロジェクトスイッチャー。シェルは1つで、タブ行の位置は同じまま中身が入れ替わる
- **C** — 左端のレール。上段が上層、区切り線の下がプロジェクト
- **D** — ホーム1画面。上層はナビを持たず、通知とプロジェクトカードを縦に並べる
- **E** — 上層をオーバーレイに。常に下層にいて、通知は右ドロワー、一覧は全面シート

**選ばれたもの**: **案A**。

**この回で実測して確定した事実**（意匠ではなく制約なので記録する。出典は本家 v2.2.5 のソースと実機）:

- **アクティブの実体** — registry entry の `instances` に生きた PID があること。`isProcessAlive(pid)` で判定する（`src/core/project-registry.ts`）
- **本家 API は未接続プロジェクトを返さない** — `cleanupStaleProjects()` は生きた instance が無いプロジェクトを registry ごと削除する。MCP サーバーは `stop()` で自分の instance を unregister し、instances が 0 になるとエントリ自体が消える（`src/server.ts` / `project-registry.ts`）
- **生存確認はダッシュボード起動時の1回だけ** — 定期実行は明示的に外されている（`project-manager.ts:42` とその下のコメント）。したがって MCP がクラッシュした場合、死んだ PID を持つエントリが次の起動まで「アクティブ」として残る
- **グローバル状態の置き場** — `SPEC_WORKFLOW_HOME`。中身は `activeProjects.json` / `settings.json` / `migration.log` などの**ファイルのみ**で、プロジェクトのディレクトリ一覧は入っていない
- 🔴 **訂正**: 当初この2点を既定値 `~/.spec-workflow-mcp` で実測し「`activeProjects.json` は `{}`」「`SPEC_WORKFLOW_SHARED_ROOT` は一覧の出どころにならない」と書いたが、**見る場所を間違えていた**。この repo の `.mcp.json` は `SPEC_WORKFLOW_HOME=/opt/projects/.spec-workflow-mcp` / `SPEC_WORKFLOW_SHARED_ROOT=/opt/projects/stroke-board` を指しており、`.spec-workflow/` は各リポジトリ直下ではなく `/opt/projects/<name>/` に外出しされている。したがって **`SPEC_WORKFLOW_SHARED_ROOT` の一つ上（`/opt/projects`）が集合親**で、そこを走査すればプロジェクト一覧が取れる。base2 は `projectId: YRzzH6mvc1uUzZN3` として登録済み・アクティブ（interview Q37 の訂正を参照）
- **プロジェクトの追加・削除 API** — `POST /api/projects/add`（body `{projectPath}`）と `DELETE /api/projects/:projectId` が実在する。ただし中身は registry への登録・解除であり、**プロジェクトを新規に作る機能は本家に無い**

**この回で決めたこと**:

- 上層のメニューは 通知 / プロジェクト一覧 の2つ。登録と作成は独立メニューにせず一覧画面の操作にする
- プロジェクト一覧の母集合は、stroke-board の設定で指定した親パスの走査（`.spec-workflow` を持つディレクトリ）。アクティブ判定は `activeProjects.json` / 本家 API を重ねる。**登録簿は持たない**
- アクティブが上、未接続が下。未接続は非活性で選択できない

### 通知の出し方 — プロトタイプではなく本家の実装をそのまま踏襲

**問い**: イベント発生時のブラウザ内通知に何を載せ、どう閉じ、複数同時発生時にどうするか。

**決めたこと**: **本家と完全に同じにする** ✅ 承認済み。変種を作って選ぶ必要が無くなったので、この問いにプロトタイプは作っていない。

**本家の実装（`src/dashboard_frontend/src/modules/notifications/NotificationProvider.tsx` を読んで確認）**:

- 形は**トースト**であってモーダルではない。`fixed top-4 right-4 z-50 space-y-2 max-w-sm` — 右上固定、縦積み、最大 `max-w-sm`
- 種別は `info` / `success` / `warning` / `error` の4つ。種別ごとに色とアイコンが変わる
- 中身は1行テキスト（`<p className="text-sm font-medium break-words">`）のみ。リンクも件名・本文の区別も無い
- **5秒で自動削除**（`setTimeout` 5000）。× ボタンで手動削除もできる
- 音を鳴らす。Howler.js を使い、`soundEnabled` と `volume` は localStorage に保持。ヘッダーに `VolumeControl` がある
- 初回ロードでは通知しない（`isInitialLoadRef`）
- 通知の生成元は本家フロント自身。**承認は ID 集合の差分**、**タスクは `getSpecTasksProgress` の再取得と前回値の比較**（完了数の増加 / in-progress への遷移 / 全件完了）で検出している

🔶 **未検証**: 本家の通知音は外部URL（`notificationsounds.com` の mp3）を直接読んでいる。stroke-board が「完全に同じ」を満たすときに、この外部依存まで真似るのかは決めていない。

### 1回目のプロトタイプで実測して確定した事実（通知まわり）

- 本家 WebSocket は `ws://<host>/ws?projectId=<id>`。接続直後に `projects-update` と `initial`（`{specs, approvals}`）が届く
- 本家のイベントはすべてスナップショット型で「何が起きたか」を含まない。通知文にするには受信側で前回値との差分計算が要る
- 通知にできるのは **承認依頼**（`approval-update` の pending 配列の ID 増加。`title` と `filePath` から件名とリンク先が取れる）と **タスクの状態変化**（`task-status-update` の `taskList` の `status` 差分）の 2 つ
- **ステアリング文書の更新は検出不能**。`tech.md` を更新しても payload が一切変化せず、ディレクトリの `lastModified` すら同一だった
- **承認と却下の区別は不能**。`approval-update` も `GET /api/projects/:projectId/approvals` も pending しか返さず、結果は消滅としてしか観測できない
- `spec-update` / `steering-update` は通知ではなく再描画用の同期信号。`.md` を保存するたびに発火するため、通知対象から外した
