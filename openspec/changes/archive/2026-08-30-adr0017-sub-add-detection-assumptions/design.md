制約が4つある。

**1. `plain.test.ts` だけパーサを通さない。** 生テキストの面は DOM と文字列の対応を見るだけで、解析を経由しない。**それでよい**（親 tasks 6.10.5）。パーサの変化を捉える役ではないので、ここに検知を足しても効かない。

**2. パーサの上げ先が無い。** `@nuxtjs/mdc@0.23.1` が最新。実際に上げて壊れることを確かめられないため、親 change は**パーサを直接変異させて**検知力を測った。この change も同じ手を採るしかない。

**3. 素通りした変異が3件ある。** `li` の段落ほどき・改行だけの text ノードの除去・見出しの id。**出力が実際に変わったのに143本すべてが通過した。** テストはフェンスの幾何と text ノードの位置をよく固めているが、AST の構造を何も固めていない。

**4. `MarkdownView` は `<MDC>` のスロットだけを差し替える形でなければならない。** 自前で `parseMarkdown` を呼ぶ形に戻すと、クライアントで解析が二重に走り、shiki の色が SSR とずれてアプリ全体のアイコンが消える（実測）。いまこの形を固定しているものが無い。

## Goals / Non-Goals

**Goals:**

- 崩れた前提を踏んだ人が、資料を読んでいなくても赤いテストで止まる
- 「書いたが検知できていない」状態を残さない

**Non-Goals:**

- 変換そのものの正しさを増やすこと。既存134本が固定済みで、この change が足すのは**壊れたときに落ちる仕掛け**である
- `@nuxt/icon` の 404 を直すこと（`proposal.md` の対象外）
- 変異検査の自動化（決定4）

## Decisions

### 決定1: 既存の役割分担を保ち、AST の構造だけ新しい置き場に切る

6.1〜6.6 は該当する既存ファイルへ足す。**6.10（AST の構造）だけ `position/ast-shape.test.ts` を新設する。**

理由は検査の対象が違うからである。既存6本はいずれも「**位置**が正しく引けるか」を見ている。6.10 が固定したいのは「**AST がどんな形で降りてくるか**」で、位置の話ではない。既存ファイルへ混ぜると、パーサの構造が変わったときにどこを見ればよいかが読めなくなる。

**代替: `silent-failure.test.ts` に足す。** 却下。あそこは「黙って壊れる3件」を名前で示す場所で、AST の構造は4件目ではない（素通りしたことは事実だが、症状は「位置がずれる」ではなく「形が変わる」）。

### 決定2: `MarkdownView` の形は、`<MDC>` が使われたことで固定する

6.1.1 は **`<MDC>` のスタブが実際に描かれたことを確かめる**形にする。自前で `parseMarkdown` を呼ぶ実装に戻せば、スタブは一度も描かれず落ちる。

`render/markdown-view-position.test.ts`（`adr0017-sub-create-position-port-preview` が置いた）が既に `<MDC>` をスタブしてマウントしているので、そこへ足す。

**代替1: ソースを読んで `parseMarkdown` の import が無いことを検査する。** 却下ではないが**従**にする。文字列検査は書き方に依存し、`import()` の動的形や再輸出で抜ける。ただし安いので補助として1本置く。

**実装（2026-08-30）: 従は書き足さなかった。** 同じ文字列検査が `silent-failure.test.ts` の「件1」に既に5本ある（`parseStageViolations`）ので、もう1本置くと同じことを2箇所で固定して片方が腐る。**在るものを従と名指しし**、主（`markdown-view-position.test.ts`）との相互の指し先を両方のファイルへ書いた。R6 の「偽陽性が続くなら代替1だけ落とす」もあの束の頭に残してある。

**代替2: E2E で SSR と客側の DOM を突き合わせる。** 既に `e2e/markdown-hydration.spec.ts` が在る。**残すが、これだけに頼らない。** 単体で落ちるほうが直したときの距離が近い。

### 決定3: 逃げ道は残す。経路の見分けはテストで固定し、実行時の仕組みは足さない

6.5.3 の「逃げ道が要らなくなったなら消す。残すなら、どちらの経路を通ったかが分かるようにする」について。

**逃げ道は残す。** 親 change の実測では、印が付かない `pre` は「文書がフェンスで始まる場合」の1種類だけ実在し、逃げ道は実際にそれを解ける。消すとその文書で位置が引けなくなる。

**どちらの経路を通ったかは、テストで別々に固定することで示す。** 印がある入力と無い入力を別のテストに分け、名前で経路が読めるようにする。実行時に経路を返す仕組み（デバッグ用の戻り値など）は**足さない**。検査のために内部の形を外へ広げると、そこが新しい公開面になる。

### 決定4: 変異検査は手順として資料に残し、自動化しない

6.10.4 と 6.9.1 の「実際に変異させて落ちることを確かめる」は、**人が手で行い、結果を記録する**。

自動化（`node_modules` のパーサへパッチを当てて回すスクリプト）は作らない。理由は2つ。パーサの内部構造に依存するため上げるたびに壊れる。そして共有ストア（`hardlinks-global`）の下で `node_modules` を書き換えると、**他の worktree の実行を巻き込む**（実測: この worktree の `node_modules` は他7本と同じグローバルストアへハードリンクされている）。

親 change は手で8種類の破壊を行っている。同じやり方を踏襲し、何をどう壊して何本落ちたかを tasks に書き残す。

**実装で分かったこと（2026-08-30）。**

- **6.10 の変異は `node_modules` ではなく解析の結果（AST）へ加えた。** 自動化を退けた理由（共有ストアへのハードリンク。実測でリンク数9）は、手で書き換える場合にも同じだけ当てはまる。パーサの手当てが止まったときの形を AST の上で作り、テストと同じ判定関数へ通せば検知力は測れる。毒見は `ast-shape.test.ts` に3本として常設した
- **毒見の作り方で測れる範囲が変わる。** `alignWrapper` を「差を中央で按分」に崩すと落ちるのは3本だけで、**インラインコードの検査は1本も落ちない**（記号が前後に同じ数だけ付くので中央の当て推量がたまたま当たる）。「範囲の頭に合わせる」崩し方だと8本落ちる。**按分への検知を実際に支えているのはエスケープと実体参照の2本**である（あそこだけは当て推量が当たらない）

### 決定5: 6.14.1（属性だけのずれ）は調べた結果を記録に留める

Vue は本番ビルドで要素の属性のずれを直さないため、SSR と客側で**色だけが違う**場合に `markdown-hydration.spec.ts` が素通りする（実測: 配る HTML の `style` を書き換えても、ハイドレーション後の DOM はサーバの値のまま残った）。

**別の手段を探すが、見つからなければ「拾えない」ことを記録して終わりにする。** 実測した症状（アイコン消失）は字と要素の並びのずれから来るので、主の検知はそちらで足りている。色だけのずれを拾う仕掛けを新設すると、この change が検知の作り込みへ広がる。

**探した結果（2026-08-30）。手段は1つだけ在るが、採らない。**

- **DOM の突き合わせでは原理的に出ない。** 属性のずれは「客側が描こうとした値」と DOM の食い違いであって、DOM もサーバの HTML もサーバの値のまま一致する
- **Vue は本番ビルドで属性の照合そのものを回していない。** `propHasMismatch` の呼び出しも `console.error('Hydration completed but contains mismatches.')` も `__VUE_PROD_HYDRATION_MISMATCH_DETAILS__` で囲われている（実測: `node_modules/@vue/runtime-core/dist/runtime-core.esm-bundler.js` の 2202行と 1900行）。**本番では警告すら出ない**
- したがって拾うには**そのフラグを立てたビルド**で E2E を回し、コンソールの `Hydration … mismatch` で落とすほかない。**配るものを変える話**になるので、検知のためだけには入れない

この結論と根拠は `e2e/markdown-hydration.spec.ts` の冒頭に書いた（資料だけに残さない）。

## Risks / Trade-offs

| # | リスク | 緩和 |
| --- | --- | --- |
| R1 | 変異検査を手で行うため、**やったつもり**で済ませられる | 何をどう壊して何本落ちたかを tasks に**数字で**書く。書けないものは終わっていない |
| R2 | 決定1で新設する `ast-shape.test.ts` が、既存6本とどう住み分けるか読めなくなる | ファイル冒頭に「ここはパーサが返す形を固定する。位置の検査は隣の6本」と書く |
| R3 | 6.10 の3件を固定すると、`@nuxtjs/mdc` の正当なマイナー更新でも落ちる | それが目的である。落ちたときに「意図した変更か」を人が判断できるよう、各テストに**何を固定しているか**を名前と冒頭コメントで書く |
| R4 | 26件は大きい。途中で力尽きると「テストはあるが検知できていない」状態が残る | 黙って壊れる3件と 6.10 を先に片付ける。tasks の並びをその順にする |
| R5 | `plain.test.ts` に検知を足しても効かないことを忘れて足す | 6.10.5 として「効かないことが正しい」を明記する項目を残す |
| R6 | 決定2の代替1（ソース検査）が、書き方の変更で偽陽性を出す | 従に留め、主はスタブが描かれたことで見る。偽陽性が続くなら代替1だけ落とす |

## Migration Plan

段階は無い。足すのはテストと `readOffset` のガード1件で、既存の呼び出し側は影響を受けない。

ロールバックは追加したテストを消すだけ。`readOffset` のガードは空文字を弾くだけで、いま返るべき値を変えない。
