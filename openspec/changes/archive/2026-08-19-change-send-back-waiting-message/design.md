## Context

- 待機表示は `app/components/WaitingIndicator.vue` 1つに共有されており、文言「AI が次を考えています…」を部品自身が持つ。使用箇所は画面1（`app/pages/index.vue` / `app/pages/s/[sessionId]/index.vue`）と問い返しの面（`app/components/review/FollowupModal.vue`）の3箇所。
- 画面2（`app/pages/s/[sessionId]/proposal.vue`）は差し戻し中を `busy` としてヘッダー帯の中に `WaitingIndicator` で示している。spec はこのヘッダー待機表示を禁止し、「AI が修正中です」の待ち受け画面への遷移に置き換える。
- 差し戻しの送信と応答の受け取りは `useProposalReview.ts` の `sendBack()` が担い、送信中は `busy`、応答が問い返しなら `followupOpen`、修正なら表示更新、という分岐が既にある。問い返し中の待機は `followupWaiting` が担う。

動機は proposal.md - Why、要求は specs/ を参照。

## Goals / Non-Goals

**Goals:**

- 差し戻し中だけを「AI が修正中です」の待ち受け画面として見せ、応答が返ったら元の画面遷移ロジックに合流させる
- 待機文言を部品の既定値から呼び出し側の明示指定へ移す

**Non-Goals:**

- 問い返しの1問1答の面の挙動変更（待機文言の明示指定のみで、見た目は従来どおり）
- 画面1のストローク待機の見た目変更
- 差し戻し送信・リトライなど通信まわりの変更

## 画面の切り替えイメージ

```text
┌─ proposal 画面（画面2）──────────────────────────────
│ パンくず｜ビュー切替｜差し戻す｜承認して作る
│ proposal 本文（プレビュー / 注釈）＋コメント一覧
└──────────────────────────────────────────────────────
     │ 差し戻す                    ▲ 修正が返る
     ▼                             │（待ち受けを抜けて戻る）
┌─ 待ち受け画面 ───────────────────────────────────────
│ パンくず｜ビュー切替｜差し戻す｜承認して作る（薄く表示・さわれない）
│
│        AI が修正中です…（点滅）
│
│   ヘッダーに待機表示は出さない（本文だけを差し替える）
└──────────────────────────────────────────────────────
     │ 問い返しが返る（待ち受けを抜ける）
     ▼
┌─ 問い返しの面 ───────────────────────────────────────
│ 1問1答（話題タグ・詳細説明・問い本文・選択肢・自由入力）
│ 回答後の待機は面の中で「AI が次を考えています…」（点滅）
│ 問いが尽きる → 出し直された proposal（proposal 画面へ）
└──────────────────────────────────────────────────────
```

## Decisions

- **文言は required prop にする。** `WaitingIndicator` に `message` prop を必須で持たせ、既定値を置かない。既定値を残して上書き可にする案は、新しい呼び出し箇所で既定文言が黙って出るため退けた（spec「共有する表示部品は既定の文言を持たない」）。必須 prop なら渡し忘れが型エラーで出る。
- **待ち受け画面はルート遷移ではなく画面2内の表示切替で実現する。** 差し戻しの応答待ちの間は、上部固定バー（パンくず・ボタン系）は残したまま、proposal 本文の代わりに待ち受け表示を全面に出し、応答が返ったら戻す。バーだけ残すのは、文言だけの画面では殺風景で文脈も失われるため。残したバーは薄くし、さわれない状態にする。別ルートへの `navigateTo` は、待機がページ内状態で完結していること、URL に待機状態を持たせると再読み込み・戻る操作の扱いが複雑になることから退けた。ユーザーから見える「遷移して戻る」は表示切替で満たす。
- **待ち受け画面の条件は `busy` ではなく差し戻し専用の状態で持つ。** `busy` は承認実行中にも立つため、そのまま使うと承認中に「AI が修正中です」が出てしまう。差し戻しの応答待ちだけを表す状態（`sendingBack`）を分け、待ち受け画面はこれに連動させる。承認実行中の待機は承認モーダル内のボタンの loading 表示が既に担っている。
- **応答の分岐は `sendBack()` の既存分岐をそのまま使う。** 修正が返れば表示更新（待ち受けを抜けて proposal 画面）、問い返しなら `followupOpen` を開く（待ち受けを抜けて問い返しの面）。分岐の新設はしない。
- **既存3箇所は従来文言を明示で渡す。** 画面1と問い返しの面は `message="AI が次を考えています…"` を渡すだけで、表示は変わらない。

## Risks / Trade-offs

- [待ち受け中も上部固定バーが見える] → バーは薄い表示でさわれないため、待機中の誤操作は起きない
- [ヘッダー帯の v-if/v-else 連鎖（問い返し知らせ・承認済み・出し直し通知）の並び替えが必要] → `busy` を連鎖から抜いて全面表示へ移すだけに留め、他の帯の優先順は変えない
- [文言の重複定義（「AI が次を考えています…」が3箇所に書かれる）] → 場面ごとに文言を規定するという spec の帰結として受け入れる。共通定数への括り出しは実装時の裁量とする
