## Context

動機は proposal.md（Why）を見ること。ここでは今の作りのうち、切り出しの形を決めるうえで効いてくる制約だけを挙げる。

- 今の1問は W1（`/api/:id/ws/question`）で届く。購読は接続時にも現在分が1件流れる。`useQuestionChannel` が既にこれを担っている
- 回答の受理（`api/answer`）と AI の起動（`api/invoke-agent`）は分かれている。受理の成功応答の直後にフロントが起動を要求する（design 決定6・`specs/api/answer`）
- 待機の決着は WS の配信で付く。次の1問が W1 で届けば待機は明ける。再接続時も W1 が現在の1問を流すため、ブラウザを開き直しても状態はそこから組み直せる
- `useProposalReview` は `pendingAction`（`'send-back' | 'followup'`）で「今どちらの決着を待っているか」を見分けている。差し戻しと問い返しは別の往復だが、待っている対象は同じ1本の `claude -p` である
- 画面2 の spec には「指摘の対象である proposal を見たまま答えられることを優先する」がある（`specs/proposal-review`）

## Goals / Non-Goals

**Goals:**

- 問いの往復（購読・回答送信・起動要求・待機・失敗）を、セッション id を渡すだけで使える1つの composable にまとめる
- 問いを出す面を、置かれる画面を知らないコンポーネントにする
- 画面2 の問い返しを、その composable と面に載せ替える。見た目と操作は今のまま

**Non-Goals:**

- 画面1（ストローク）の載せ替え。今の形のまま残す
- サーバ側（endpoint・スキーマ・W1）の変更
- 問いのスキーマ（`Question` / `Answer`）の変更
- 新しい画面の追加。置ける形にするところまでが今回

## Decisions

### 決定1: 切り出しは composable 1つとコンポーネント1つに分ける

往復の状態（`useAgentQuestion`）と、それを出す面（`AgentQuestionModal`）を別々に切り出す。面は問いと待機を props で受け、回答を emit するだけで、`$fetch` を持たない。

- **なぜ**: 面だけを差し替えたい場面（オーバーレイでなくインラインで出す、など）と、往復だけを使いたい場面が独立して起こりうる。片方に寄せると、置く側がもう片方を丸ごと書き写すことになる
- **却下した案**: 面の中に往復を書き込む1コンポーネント案。置くのは一番楽だが、面の形を変えたい画面が現れた時点で往復ごと複製される。今回の動機そのものを再発させる
- **却下した案**: composable だけを出し、面は画面ごとに書く案。今の重複（`QuestionCard` と `FollowupModal` が同じ並びを二度書いている）が残ったままになる

### 決定2: 問いの購読は composable が単独で持つ

`useQuestionChannel` の呼び出しは `useAgentQuestion` の中だけに置く。`useProposalReview` は自前の購読をやめ、composable が持つ問いを読む。

- **なぜ**: 同じセッションの W1 を2箇所から購読すると、同じ画面で WebSocket が2本開く。届く内容は同じでも、接続時配信が二重に走り、どちらが今の1問かを追う先が2つになる
- **却下した案**: 購読は置く側が持ち、composable は問いを props で受け取る案。置く側が W1 を知らないと使えなくなり、「セッション id を渡すだけ」が崩れる

### 決定3: 待機は W1 の配信で決着させ、状態は返り値として出す

`useAgentQuestion(sessionId)` は待機の状態を内側に持ち、`waiting` と `failed` を返す。状態を外から渡す口は設けない。

送れなかったときの理由も返り値として出す（`error`）。送信そのものの失敗と、起動要求が 409（まだ前の応答を待っている）を区別するのは往復の側の判断であり、置く側はその文言を出すだけにする。

待機が明けるのは W1 が次の1問を配信した瞬間とする。W1 は接続時にも現在の1問を1件流すため、ブラウザを開き直しても再接続で今の1問が届き、そこから状態を組み直せる（`server/routes/api/[id]/ws/question.ts`）。待つ順番の管理はサーバ側にあり、画面は再接続して受け直すだけでよい。

今の画面2 は W1 の到着を見ていない（`useProposalReview` に問いの到着を見る watch が無い）。画面1（`app/pages/s/[sessionId]/index.vue`）は `watch(question, ...)` で配信を見て待機を終えている。載せ替えで画面1 と同じ形に揃える。

- **なぜ状態を返すのか**: composable は内部で持った状態を返す側であって、状態を受け取る側ではない。`@vueuse/core` の `useWebSocket(url, options)` がその形で、`options` は振る舞いの設定（`autoReconnect` / `onMessage`）だけを取り、状態は全て返り値（`data` / `status` / `ws`）として出す（型定義で確認）
- **却下した案**: 待機の実体を `options` で渡させる案。置く側に中の作りを知ることを強いる
- **却下した案**: 待機をセッション単位のグローバル状態（`useState`）にする案。設置が1画面1インスタンスである限り必要が無く、セッションを跨いだ取り違えの経路を新たに作る

### 決定4: 面の開閉は置く側が持ち、閉じさせないことだけを機構が保証する

`open` は `v-model` で置く側が持つ。面は、回答が済んでいない間の閉じる要求（ESC・背景クリック・閉じるボタン）を受け付けない。

- **なぜ**: 開く引き金は画面ごとに違う。画面2 は点滅する知らせを選んで開く（既存の spec）。一方「答えずに閉じて問いを見失わない」は画面に依らず守りたい。開く条件を機構に持たせると、画面2 の知らせ帯の作りまで機構が知ることになる
- **却下した案**: 問いが届いたら機構が勝手に開く案。画面2 の「知らせを選ぶと面が開く」を壊す。画面1 を載せ替えないため、自動で開く必要のある画面が今は無い

### 決定5: 面は `app/components/` の直下に置く

`AgentQuestionModal.vue` は `app/components/review/` ではなく直下に置く。

- **なぜ**: `review/` 配下は画面2 に属する部品の置き場になっている。画面を知らない部品をそこへ置くと、次に使う画面から見て「画面2 のものを借りている」形になる
- **却下した案**: `stroke/` 配下。ストロークと問い返しの両方が使う機構であり、どちらか一方の名前を冠すると同じ誤解が起きる

### 決定6: `FollowupModal` は置き換え、`QuestionCard` は残す

`app/components/review/FollowupModal.vue` は `AgentQuestionModal.vue` へ置き換えて消す。`app/components/stroke/QuestionCard.vue` はそのまま残す。

- **なぜ**: `FollowupModal` は今回の面そのもの（同じ並び・同じモーダル）で、残すと同じものが2つになる。`QuestionCard` は画面1 の載せ替えを Non-Goal に置いた以上、消せない
- **トレードオフ**: 問いの並びを書いた場所が `AgentQuestionModal` と `QuestionCard` の2つ残る。画面1 を載せ替えるときに解消する

## Risks / Trade-offs

- **面が閉じられないため、問い返し中に proposal 本文を読み返せない** → 面は画面を覆い切らない幅に留め、背後の proposal が見えるようにする（今の問い返しモーダルと同じ）。覆い切る全画面の面にはしない
- **問いの並びを書いた場所が2つ残る（決定6）** → 片方（`QuestionCard`）は画面1 専用として据え置く。並びの規定そのものは spec 側（`agent-question` と `stroke-session`）にあり、食い違えば spec で検出できる
- **画面2 に待機の状態が2つ並ぶ（差し戻し用と問い返し用）** → 同時には立たない。差し戻しの待ち受け中は全面が待ち受け画面になり、問い返しの知らせ帯が出ないため、待機中に回答を送る経路が無い。`pendingAction` が単一スロットであることも同じことを示している。実装時にこれを確かめる
- **`useProposalReview` から問い返し関連の状態が抜け、差し戻しの決着判定（`pendingAction`）が composable を跨ぐ** → 決着の判定は今どおり `useProposalReview` に残し、`useAgentQuestion` は自分が送った回答の待機だけを知る形にする
