## Context

現状は起動時チェックが1つでも失敗すると `process.exit(1)` でプロセスごと終わる。動機は proposal.md - Why を参照。

実装のコメントは「Nitro のプラグインで throw しても、サーバはそのままリクエストを受け付けてしまう」を根拠にしている。この前提を `nitropack@2.13.4`（`@nuxt/nitro-server@4.5.2` が依存する実体）のソースで確認した。

```js
// node_modules/nitropack/dist/runtime/internal/app.mjs:156-165
function runNitroPlugins(nitroApp2) {
  for (const plugin of plugins) {
    try {
      plugin(nitroApp2);        // ← await していない
    } catch (error) {
      nitroApp2.captureError(error, { tags: ["plugin"] });
      throw error;
    }
  }
}
```

読み取れることは3つ。

1. **同期的な throw は伝播する。** `runNitroPlugins(nitroApp)` はモジュールのトップレベルで呼ばれるため、同期 throw はモジュール評価そのものを失敗させる。コメントの前提はこの場合には当たらない。
2. **async プラグインの throw は捕まらない。** 戻り値の Promise が await されないため、reject は上の try/catch を素通りして unhandled rejection になる。コメントの前提が当たるのはこちらで、現状のチェックは `async` なのでこの経路にいる。
3. **現状の実装は目的を完全には達成していない。** チェックは `await access(...)` を含むため、`process.exit(1)` に到達する前に await で制御が戻る。その間サーバはリクエストを受け付けうる。「実行中はじめて気付く形にしない」ために選ばれた手段が、非同期であるがゆえに隙間を持っている。

3 は本 change の判断を補強する。プロセスを殺しても「起動前に確実に止める」ことにはなっておらず、代償（全断・復帰に再起動が必要）だけが確実に発生している。

## Goals / Non-Goals

**Goals:**

- 前提の欠けを、プロセスの生死ではなく操作の可否として表す
- 前提が回復したときにサービスの再起動を要さない
- 前提を必要としない操作（既存セッションの閲覧・履歴）を、欠けている間も通す

**Non-Goals:**

- 欠けた前提をアプリが自力で埋めること（`/var/lib/stroke-board/` の作成と所有権付与はアプリ外の配置作業。decisions.md - セッションディレクトリ）
- 起動時チェックの対象を増やす・減らすこと。確かめるものは現状と同じ
- 監視・アラートの導入

## Decisions

### 決定1: プロセスを落とさず、前提を必要とする操作を断る

前提が欠けていることは「サービスが存在してはいけない状態」ではなく「AI を起動できない状態」である。止めたい対象は AI の起動であって、サーバの生存ではない。

**代替案と却下理由:**

- **プラグインで throw する** — 同期化すれば起動を止められる（上記1）。しかし止まった後の状態は `process.exit` と同じで、復帰に再起動が要る。代償が変わらない
- **middleware で全リクエストを 503 にする** — サーバは生きるが、既存セッションの閲覧まで止まる。前提を必要としない操作まで巻き添えにする点で `process.exit` と同じ過剰さを持つ
- **現状維持＋プロセス監視での自動再起動** — 前提が回復しない限り再起動ループになる。外部要因（ディレクトリ権限）で全断する性質も変わらない

### 決定2: 判定は起動時に固定せず、必要になった時点で行う

起動時の判定結果を保持して使い回すと、前提を直しても再起動するまで反映されない。現状の欠点をそのまま持ち越すことになる。

起動時にも一度判定するが、それは**運用者へ伝えるため**であって、以後の判断材料として保持するためではない。起動要求を受けた時点で改めて判定する。

判定は `access()` 2回と zod の `safeParse` 1回で、AI の起動要求という低頻度・高コストな操作の前段としては無視できる。

**代替案と却下理由:**

- **起動時に一度だけ判定して保持** — 実装は最小だが、復帰に再起動が必要という現状の欠点が残る。本 change の目的の半分を捨てることになる

### 決定3: 断り方は既存の「受理しない」に揃え、409 とは区別する

`api/invoke-agent` は既に2つの受理しない条件（多重起動・承認後）を持つ。前提の欠けを3つ目として同じ位置に置く。

ただし多重起動は 409 で返しており、クライアントはそれを「まだ前の応答を待っています」と解釈している（`app/composables/useProposalReview.ts`）。前提の欠けは意味が異なるため 409 に混ぜず、**503 Service Unavailable** で返す。一時的にサービスを提供できない状態であり、要求自体は正しいという意味に合う。

クライアント側の変更は本 change では要らない。画面2 は 409 以外を汎用メッセージ（「AI を起動できませんでした」＋本文）で出すため、返す本文に欠けている前提を載せれば運用者に届く。画面1 も同様に汎用メッセージを出す。

### 決定4: startup-readiness は判定の口だけを持ち、状態を持たない

決定2 により保持する状態が無いため、この capability は「今の前提の充足を答える」関数の集まりになる。起動時のプラグインと `invoke-agent` の両方が同じ口を呼ぶ。現在 `describeClaudeConfigError()` が担っている役割を、書き込み先の確認と合わせて1つにまとめた形になる。

## Risks / Trade-offs

- **配置作業の不備に気付きにくくなる** → 起動時のログ出力は現状のまま維持する。加えて 503 の本文に欠けている前提を載せるため、気付く経路は減らず増える
- **前提が欠けたままサービスが見えている状態が生まれる** → 意図した変更。既存セッションの閲覧は成立するべきであり、AI の起動だけが断られる
- **既存の運用が「落ちること」に依存している可能性** → 未確認。systemd の `Restart=` や監視の有無を確かめていない。ただし現状は再起動しても前提が回復していなければ再び落ちるため、依存が成立しているとは考えにくい。デプロイ前に運用側の確認を1度行う
- **毎回の判定が I/O を伴う** → `access()` 2回。AI の起動は分単位の操作なので影響しない

## Migration Plan

前提が揃った環境では振る舞いが変わらないため、段階移行は不要。デプロイして再起動するだけでよい。ロールバックは revert。

前提が欠けた環境では、これまで起動に失敗していたサービスが起動するようになる。デプロイ後にログへ「欠けている前提」が出ていないことを確認する。
