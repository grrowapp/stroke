# adr0016-sub-define-request-validation-messages

## Why

受け口の入力検証が、送り手に「何を直せばよいか」を伝えていない。

A5（問いの提出）で実際に起きた（実測 2026-08-28）。エージェントが送った問いのうち 13回中5回が 400 で弾かれ、原因はすべて選択肢の説明が 51 文字（上限 50）という 1 文字の超過だった。返っていたのは次の1文だけである。

```
問いの構造として読み取れない。
```

どの項目がどの制約に反したのか分からないため、エージェントは形を当てるまで送り続けた。`header` 3 文字・`question` 6 文字・`detail` 4 文字という、内容を捨てた極端に短い問いを投げて通し方を探る挙動になった（`分けるか？` `分けるか2？`）。

違反箇所を返すようにしたところ、400 は 5 件から 1 件へ減り、その 1 件も理由が届いて次の送信で通った。**送り手が直せる情報を返すかどうかで、成否がここまで変わる。**

同じ穴が他の受け口にも残っている。

- 検証を通していない受け口がある: `strokes/[id]/question.post.ts`（この change で入れた `questionViolations` は別経路）、`strokes/[id]/delete.post.ts`
- 検証は通すが、制約にメッセージを定義していない箇所が多い。`request-schemas.ts` では `overview` / `value` / `comment` などには日本語のメッセージがあるが、`id` / `timestamp` / `bg` / `border` / `startOffset` などには無い。`question.ts` の長さ・件数の上限はすべて無い
- メッセージが無いと、送り手には検証ライブラリの既定文（`Too big: expected string to have <=50 characters`）が届く。何の項目かも、いま幾つなのかも分からない

## What Changes

- **変更**: 送り手が値を組み立てて送るすべての受け口で、入力を検証の定義に通す。定義を経ずに受ける経路を無くす
- **変更**: 検証の各制約に、**その制約ごとの**メッセージを定義する。既定文に委ねない。何の項目が、どの決まりに反したかが、そのまま読める文にする
- **変更**: 違反が複数あるときは、すべてを返す。1つ直すたびに送り直させない
- **変更**: 長さ・件数の制約に反した場合は、いま幾つなのかを添える。あと幾つ削ればよいかが分かる形にする

## Capabilities

### New Capabilities

- `api/request-validation`: 受け口の入力検証と、その失敗の伝え方。検証を経ること、制約ごとにメッセージを定めること、違反をすべて返すこと、超過は現在値を添えること。

## Impact

- **影響コード**: `server/utils/stroke/request-schemas.ts`、`server/utils/stroke/question.ts`、`server/api/strokes/**`、`server/api/projects/**`
- **影響する相手**: エージェント（MCP ツール経由で送る）と画面。どちらも受け取るエラーの中身が変わる
- **影響しないもの**: 検証の中身（何を許すか）は変えない。伝え方だけを変える
- **ADR-0014 との関係**: 検証の正は受け口に置いたままにする。MCP ツール側に事前検証を足すことはしない。ツール側の契約は説明（`.describe()`）で上限を伝えるに留める
