specs/broker/operations — delta

Purpose

broker を「動くコード」から「常駐して運用できるサービス」にするまでを規定する。 設定、起動、停止、状態の外部への公開を担う。

ADDED Requirements

Requirement: 設定はリポジトリ直下の broker.config.json から読む

システムは起動時に、リポジトリ直下の broker.config.json を読んで設定とする SHALL。 環境変数から設定を読んではならない（MUST NOT）。

設定できるキーは次の 5 つに限る。

キー内容
portセッションが接続する待ち受けポート
hostbind するアドレス
heartbeatIntervalMs生存確認の間隔（broker-liveness）
maxPayloadBytes1 フレームで受け取る上限
apiPort状態公開の待ち受けポート

Scenario: 設定ファイルが待ち受けポートを指定している

  • WHEN broker.config.json に { "port": 9000 } が書かれた状態で起動する
  • THEN システムは 9000 番で待ち受ける

Scenario: 環境変数だけを与える

  • WHEN 環境変数 BROKER_PORT=9000 を与え、broker.config.json を置かずに起動する
  • THEN 環境変数は無視され、既定の 8787 番で待ち受ける

Requirement: 書かれていない項目は既定値になる

システムは broker.config.json が存在しない場合、5 つの項目すべてを既定値として起動する SHALL。 ファイルが存在する場合、書かれている項目だけをその値とし、書かれていない項目は既定値とする SHALL。

設定ファイルを必須にしてはならない（MUST NOT）。

既定値は次のとおり。

キー既定値
port8787
host"0.0.0.0"
heartbeatIntervalMs30000
maxPayloadBytes1048576
apiPort8788

Scenario: 設定ファイルが存在しない

  • WHEN broker.config.json が存在しない状態で起動する
  • THEN システムは 8787 番・0.0.0.0・生存確認 30000ms・上限 1048576 バイト・状態公開 8788 番で起動する

Scenario: 1 つの項目だけが書かれている

  • WHEN { "heartbeatIntervalMs": 5000 } だけが書かれた broker.config.json で起動する
  • THEN 生存確認は 5000ms になり、port は既定の 8787 のままになる

Requirement: 起動経路は設定を引数で受け取れる

システムの起動経路は、5 つの項目を引数で受け取れる SHALL。 引数で与えられた項目は broker.config.json の値より優先される SHALL。

port に 0 が与えられた場合、システムは OS に空きポートを割り当てさせ、 実際に割り当てられた番号を呼び出し側へ返す SHALL。

統合テストは待ち受けポートを固定できない（並行実行と、開発機で broker が 既に動いている場合に衝突するため）。この経路はそのために要る。

Scenario: 引数がファイルより優先される

  • WHEN broker.config.json に { "port": 9000 } がある状態で、起動経路に { port: 9100 } を渡す
  • THEN システムは 9100 番で待ち受ける

Scenario: 待ち受けポートに 0 を渡す

  • WHEN 起動経路に { port: 0 } を渡す
  • THEN OS が空きポートを割り当て、その番号が呼び出し側へ返る

Requirement: 設定が不正なら待ち受けを始めずに終了する

システムは設定の検証に失敗した場合、待ち受けを一切始めずに異常終了する SHALL。 一部だけ起動した状態を作ってはならない（MUST NOT）。

不正な値を既定値へ読み替えてはならない（MUST NOT）。 設定を書いたつもりが効いていない状態に気づけなくなるためである。

検証に失敗する条件は次のとおり。

条件例
port / apiPort が 0〜65535 の整数でない"9000"、-1、70000
heartbeatIntervalMs が 1 以上の整数でない0、-5
maxPayloadBytes が 1 以上の整数でない0
JSON として解釈できない途中で切れたファイル
設定できる 5 つのキーに無いキーがあるportt

Scenario: ポートに文字列が書かれている

  • WHEN { "port": "9000" } で起動する
  • THEN 待ち受けを始めず、port が整数でない旨を日本語で示して異常終了する

Scenario: 生存確認の間隔に 0 が書かれている

  • WHEN { "heartbeatIntervalMs": 0 } で起動する
  • THEN 待ち受けを始めず、1 以上が必要である旨を示して異常終了する

Scenario: JSON として壊れている

  • WHEN { "port": 9000, で終わる broker.config.json で起動する
  • THEN 既定値へ読み替えることなく、解釈できない旨を示して異常終了する

Scenario: 知らないキーが書かれている

  • WHEN { "portt": 9000 } で起動する
  • THEN 待ち受けを始めず、portt が設定できるキーに無い旨を示して異常終了する

Requirement: 不正な項目が複数あれば一度にすべて報告する

システムは検証に失敗した項目が複数ある場合、すべての理由を 1 度の出力にまとめて示す SHALL。 1 つ報告して終了してはならない（MUST NOT）。 1 つずつ直して再起動を繰り返す運用にしないためである。

Scenario: 2 つの項目が同時に不正である

  • WHEN { "port": "x", "apiPort": -1 } で起動する
  • THEN port と apiPort の両方の理由が 1 度の出力にまとめて示される

Requirement: 上限を超えるフレームを受け入れない

システムは maxPayloadBytes を超える長さのフレームを受け入れない SHALL。 上限を持たない状態で運用してはならない（MUST NOT）。

守る対象は悪意ではなく、長い出力の貼り付けのような事故である。

Scenario: 上限を超えるフレームが届く

  • WHEN maxPayloadBytes が 1048576 の状態で、2 MiB のフレームが届く
  • THEN システムはそのフレームを受け入れない

Requirement: 停止は接続を畳んでから終わる

システムは停止の要求を受けた際、次の順で畳む SHALL。

  1. 新しい接続の受け付けを止める
  2. 繋がっている接続に、こちらから畳んでいることを伝える
  3. 接続が閉じ切るのを待つ
  4. 生存確認を止める
  5. 状態公開の口を閉じる

接続に何も伝えずに即座に終了してはならない（MUST NOT）。 乱暴に落とすと、繋がっていたセッションが異常切断を見ることになる。

Scenario: 接続がある状態で停止を要求する

  • WHEN 2 つのセッションが接続している状態で停止が要求される
  • THEN 新しい接続は受け付けられなくなり、2 つの接続には終了が伝えられ、 生存確認と状態公開の口が閉じる

Requirement: 停止の待ち時間に上限を設ける

システムは接続が閉じ切るのを待つ時間に上限を設け、超えたら待たずに終了する SHALL。 上限を持たずに待ち続けてはならない（MUST NOT）。

Scenario: 接続が閉じ切らない

  • WHEN 停止を要求したが、接続が上限時間内に閉じ切らない
  • THEN システムは待つのをやめ、残った接続を切って終了する

Requirement: 停止を二重に要求されても後始末は一度だけ行う

システムは停止の処理中に再び停止を要求された場合、 後始末を二重に実行してはならない（MUST NOT）。

Scenario: 停止の途中でもう一度停止を要求する

  • WHEN 停止の処理中に、もう一度停止が要求される
  • THEN 後始末は二重に行われず、システムは終了する

Requirement: 状態を読み取る口を公開する

システムは apiPort で次の 2 つの読み取り口を公開する SHALL。

口返すもの
/health動作していること、接続中の peer の数
/peers接続中の peer の一覧

状態を変える操作を公開してはならない（MUST NOT）。

Scenario: 稼働状況を読む

  • WHEN peer が 2 つ接続している状態で /health を読む
  • THEN 動作している旨と、peer の数が 2 であることが返る

Scenario: peer が 1 つも居ない状態で一覧を読む

  • WHEN 接続中の peer が無い状態で /peers を読む
  • THEN 空の一覧が返る。エラーにはならない

Scenario: 公開されていない口を叩く

  • WHEN /health でも /peers でもない口を叩く
  • THEN 見つからない旨が返る

Scenario: 状態を変えようとする

  • WHEN /peers に読み取り以外の操作を要求する
  • THEN システムはその操作を受け付けない

Requirement: peer の表現はセッションが受け取るものと同一にする

/peers が返す peer の形は、セッションが list_peers（broker-messaging）で 受け取る形と同一である SHALL。2 つの形を持ってはならない（MUST NOT）。 管理画面が両方に対応せずに済むようにするためである。

Scenario: 同じ peer を 2 つの経路で読む

  • WHEN ある peer について、セッションが list_peers で受け取った内容と /peers が返した内容を比べる
  • THEN 接続 ID、作業ディレクトリ、接続時刻がいずれも同じ形で得られる

Requirement: 常駐サービスとして起動できる

システムは OS のサービスとして常駐し、起動・再起動・ログの管理を OS に委ねる SHALL。

サービスの定義に設定値を書いてはならない（MUST NOT）。 設定は broker.config.json が唯一の出どころであり、二重の置き場所を作らないためである。

Scenario: マシンを再起動する

  • WHEN broker が動作しているマシンを再起動する
  • THEN broker は自動的に起動する

Scenario: 異常終了する

  • WHEN broker が異常終了する
  • THEN OS によって再起動される

Requirement: サービスの定義に公開禁止の警告を含める

サービスの定義には、このサービスを信頼できないネットワークに公開してはならない旨を 記載する SHALL。

認証を持たないという決定が、定義を触る者に伝わらないまま運用されることを防ぐためである。

Scenario: サービスの定義を読む

  • WHEN サービスの定義を開く
  • THEN 認証を持たないこと、信頼できないネットワークに公開してはならないことが読み取れる

Requirement: 外部から到達できるアドレスでの起動時に警告する

システムは、host がループバック以外のアドレスである場合、 認証を持たない旨の警告を起動時に出力する SHALL。

Scenario: 0.0.0.0 で起動する

  • WHEN host が "0.0.0.0" の状態で起動する
  • THEN 認証を持たない旨の警告が出力される

Scenario: 127.0.0.1 で起動する

  • WHEN host が "127.0.0.1" の状態で起動する
  • THEN 警告は出力されない

Non-Functional Requirements

可用性

broker は単一障害点である。これは同一 LAN・1 対 1・履歴を残さないという 前提から導かれる設計の帰結であり、欠陥ではない。

冗長化を実装してはならない（MUST NOT）。要件になった場合は設計のやり直しとなる。

可観測性

ログは OS の仕組みで読める形とする。 構造化ログの形式や、メトリクスの収集基盤を導入してはならない（MUST NOT）。

スコープ外

  • 認証、認可、TLS、トークンの発行と失効
  • レート制限、同時接続数の上限
  • 状態を変える操作の公開
  • 管理画面そのもの（別の capability）
