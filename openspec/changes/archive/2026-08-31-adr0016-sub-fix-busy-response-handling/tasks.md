# adr0016-sub-fix-busy-response-handling — tasks

画面だけの変更。サーバー（409 を返す側）は契約どおりなので触らない。

## 1. 起動要求と待機を1つに寄せる

- [x] 1.1 `app/composables/useWaitingRetry.ts` に「起動を要求して待機に入る」処理を足す。
      **409 は待機へ倒し、busy が解けたら出し直す**（design.md Decision 1・2）。それ以外の
      失敗は呼び出し側へ返し、伝え方はそれぞれに委ねる（Decision 3）

      **当初は「待機へ倒すだけ」で実装していた。それでは足りない**（レビュー指摘・2026-08-30）。
      1回の起動 = 1回の実行で、巡回は `failed` しか拾わず、受理の口は起動を含まない。
      要求を捨てると `idle` の後に誰も次を起こさず、回答が記録されたままセッションが止まる。
      `pendingRun` に覚え、poll が `idle` を観測した時点で出し直す形にした（上限 3 回）
- [x] 1.2 戻り値の形を決める。呼び出し側が「待機に入った / 失敗した」を分けられ、失敗の
      理由（表示用）を取り出せること。例外を投げる形にはしない——3箇所とも try/catch を
      書き直すことになり、書き忘れの余地が戻る

## 4. 実機確認

- [x] 4.1 `yarn check:stroke` を1周させ、**同じ問いへの回答が `strokes.json` に二重に
      記録されないこと**を確認する（proposal の実測: 「実行環境」×3・「完了指定」×2・
      「保存場所」×2 が出ていた）

      実測 2026-08-30: 7往復して proposal に着地。問いは7件すべて別で、重複なし。
      **ただしこの経路では 409 を1度も踏まない**——`settle()` が前の実行の終了を待って
      から答えるためで、道具は人と違って待つ。退行が無いことの確認にはなるが、
      直した経路そのものは踏んでいない（4.2 で別に踏ませた）
- [x] 4.2 回答直後に「AI を起動できませんでした。」が出ないことを確認する

      **409 を狙って踏ませた**（実測 2026-08-30）。`settle()` を通さず、問いが出た瞬間に
      答える——人がやるのと同じ操作である。問いを出した claude はまだ走っているので、
      続けて呼ぶ起動要求が 409 を返す。

      ```
      invoke-agent → 204 / 409 / 409
      「AI を起動できませんでした」が出た: false
      待機の表示（agent-question-waiting）: true
      ```

      修正前はここで失敗の文言が出て止まり、同じ問いに二度答えるしかなくなっていた。
