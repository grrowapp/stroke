# adr0016-sub-fix-busy-response-handling — design

## Context

動機は proposal.md の Why を参照。設計の前提になる事実は次の通り（すべて実装コードで確認）。

- **409 を返す側は正しい。** U7（回答）は実行中でも受理し、多重起動は U13 が 409 で止める
  （`docs/specs/api/contract.md`）。走っている claude が回答を拾って次の問いを出すので、
  画面は待機に入るのが正しい。サーバーは触らない
- 起動要求の直後に待機へ入る処理は3箇所にある。いずれも
  `await $fetch(invoke-agent)` → `waitingRetry.startWaiting()` を try の中に並べ、
  catch で理由を分けている
  - `app/pages/strokes/[sessionId]/index.vue:118-125` — **catch が理由を見ていない。**
    409 でも「AI を起動できませんでした。」を出す。今回の発生源
  - `app/composables/useAgentQuestion.ts:117-128` — 409 の分岐は持つが、
    `startWaiting()` が try の中にあるので**409 では呼ばれない**
  - `app/composables/useProposalReview.ts:307-317` — 同じ形
- `useWaitingRetry.startWaiting()` は `waiting` を立て、3秒間隔で U2 を読み直す。
  `invocation` が `idle` / `failed` / `error` のいずれかになれば待機を降りる。
  **待機の決着は起動要求の成否に依存しない**——W1 の配信か、この巡回のどちらかが付ける
- `useAgentQuestion` は待機が明けたときに、答え終わった問いを手放す（`asked` との照合）。
  409 で待機に入らないと、この決着も走らない。**同じ問いが画面に残り続ける**のはこのためで、
  ユーザーはもう一度答えるしかなくなり、`strokes.json` に回答が重複して記録される
  （実測: 「実行環境」×3・「完了指定」×2・「保存場所」×2）

## 前提の訂正（2026-08-30）

**当初この design は「走っている claude が回答を拾って次の問いを出す」と書いていた。これは誤りである。**

- 1回の `invoke-agent` = 1回の claude 実行で、続きは `continuePrompt` を渡す**次の起動**でしか進まない（`server/utils/stroke/ai.ts`「1回の呼び出しで起こすのは1回だけ」）
- 巡回は `failed` しか拾わない（`server/utils/stroke/sweep.ts`「`idle` にはやり直すものが無い」）
- 受理の口（U7）は起動を含まない（`specs/api/answer`: 起動はフロントが要求する）

したがって 409 で起動要求を**捨てる**と、走っていた claude が終わって `idle` になった後、誰も次を起こさない。回答は記録されたのにセッションが止まる。この症状はこのリポジトリ自身が実測として持っている（`scripts/stroke-check.ts`: 「Q2 の回答は記録されたのに `invocation: idle` のまま4分待って落ちた」）。

**409 は待機へ倒すだけでは足りず、busy が解けたら同じ要求を出し直す必要がある。** Decision 1 はその形に改めてある。

## 画面2 での成立は別 change に依存する

`useAgentQuestion`（proposal の問い返し）は回答の送り先が `/api/<uuid>/answer` で、実在するルート（`/api/strokes/<id>/answer`）に届かない。`send` は受理の段階で必ず失敗するため、**この change が直した 409 の経路にそもそも到達しない**。

画面2 でこの spec が成立するのは、別 change `fix-agent-question-api-path` が入った後である。画面1（`pages/strokes/[sessionId]/index.vue`）では成立しており、実機で確認済み（tasks 4.2）。

## Goals / Non-Goals

**Goals:**

- 409 を失敗として示さず、待機として示す（`specs/agent-question`「前の応答をまだ待っている」）
- **409 でも待機に入る。** 表示を直すだけでは足りない。待機に入らないと問いを手放す決着が
  走らず、同じ問いへ二度答えさせる根本が残る
- 3箇所に散った同じ扱いを1つに揃える（proposal の3つ目の変更）

**Non-Goals:**

- サーバー側の 409 の扱いを変えること。契約どおりであり、触る理由が無い
- 待機の決着の仕組み（W1 の配信・U2 の巡回）を変えること
- 409 以外の起動失敗の扱いを変えること。そちらは失敗のままでよい

## 流れ

```
回答を送る（U7）─── 受理
        │
        ▼
起動を要求（U13）
        │
        ├─ 200 ────────────┐
        │                   ├─→ 待機に入る（startWaiting）
        ├─ 409 busy ───────┘        │
        │   「まだ前の応答を待っている」   │  W1 の配信 or U2 の巡回で決着
        │                              ▼
        └─ その他 ─→ 失敗として示す   次の問い / failed / error
```

**409 と 200 は、画面から見れば同じ状態へ入る。** どちらも「AI は走っており、次の問いが
返るのを待つ」である。違うのは、この呼び出しが起動を起こしたか、既に走っていたかだけで、
待つ側にとっては区別する意味が無い。

## Decisions

### Decision 1: 409 は待機へ倒し、**busy が解けたら出し直す**

**選択肢**: (a) 409 を成功と同じく `startWaiting()` へ倒し、案内だけ別に出す /
(b) 409 専用の第3の状態（`busy` フラグ）を持つ / (c) 409 を無視して何も表示しない。

(a) を採る。待機に入るかどうかで見れば 409 と 200 は同じで、状態を分ける理由が無い。
(b) は `waiting` と併存する状態を増やし、決着の条件（W1・巡回・失敗・終端）を全部その
新しい状態にも書くことになる。得られるのは「busy だったかどうか」という、ユーザーが
行動を変える材料にならない情報である。

(c) は**現に起きていることが伝わらない**。回答は届いていて次を待っている、という事実は
示す価値がある。ただし**失敗としては示さない**（spec の MUST NOT）。

### Decision 2: 待機に入る処理を try の外へ出す

3箇所とも `startWaiting()` が `await $fetch(...)` と同じ try の中に在り、409 で throw した
時点で飛ばされる。**表示の文言だけ直しても、待機に入らない限り問いは手放されない。**

起動要求が「200 か 409 のどちらかで返った」ことを掴んでから待機へ入る形にする。
それ以外の失敗（500・ネットワーク断）は待機に入らず、失敗として示す。

### Decision 3: 判定と扱いを1つの関数に寄せる

**選択肢**: (a) `useWaitingRetry` に「起動を要求して待機に入る」処理を足し、3箇所がそれを
呼ぶ / (b) 判定（409 かどうか）だけを共有し、扱いは各所に残す / (c) 3箇所それぞれで直す。

(a) を採る。`useWaitingRetry` は既に `retryFromError()` で「U13 を叩いて `startWaiting()`」を
持っており、置き場としてそこが自然である。同じ形が4つ目として増えるのではなく、
既に在る形に寄る。

(c) は今回の発生源そのものである——同じ扱いが3箇所にあり、1箇所だけ直され残りが取り残された。
(b) は判定を共有しても「409 で待機に入る」を書き忘れる余地が各所に残る。

呼び出し側に残るのは**どう伝えるか**だけにする。ページは `errorMessage` へ、
`useProposalReview` は `warn()` へ、`useAgentQuestion` は `error` へ出す——出し先は
それぞれの画面の作りで違うので、そこは寄せない。

### Decision 4: 409 のときに出す文言は「待っている」であって、警告ではない

現行は `useAgentQuestion` / `useProposalReview` が「まだ前の応答を待っています」を
**エラーの器**（`error` / `warn`）に入れている。器が失敗を示すものなら、spec の
「失敗を示してはならない」に反する。

409 のときは、待機の表示（`waiting`）に任せて**追加の文言を出さない**。待機の表示は
既に「AI が応答を組み立てています」に相当する面を持っており、そこに重ねて「待っています」を
出しても情報は増えない。エラーの器を空のままにすることで、失敗の表示と混ざらない。

## Risks / Trade-offs

- [409 が「起動できなかった」本物の失敗を隠す] → 409 が返るのは busy ガードだけである
  （`server/api/strokes/[id]/invoke-agent.get.ts`）。前提が欠けている場合は 409 ではなく
  別の状態で返る。409 = 走っている、は契約で決まっている
- [待機に入ったまま決着しない] → 決着は起動要求とは独立に、W1 の配信か U2 の巡回（3秒）が
  付ける。走っている claude が `idle` / `failed` / `error` のいずれかへ必ず落ちるので、
  待機が永久に続くことはない
- [409 で何も表示しないと、ユーザーには送信が無視されたように見える] → 待機の表示が出る。
  回答は `answered` に数えられ、履歴にも積まれる。何も起きないのではなく、待ちに入る
- [3箇所を1つに寄せると、片方の都合が他方へ漏れる] → 寄せるのは「起動を要求して待機に
  入る」だけで、伝え方は各所に残す。漏れる余地を判定と待機に限る

## Migration Plan

画面だけの変更で、保存済みデータにも API にも影響しない。ロールバックは revert で足りる。

検証は実機で行う。`yarn check:stroke` は回答を送ってから次を待つ経路をそのまま通るので、
**同じ問いへの回答が二重に記録されないこと**を `strokes.json` で確認できる。
