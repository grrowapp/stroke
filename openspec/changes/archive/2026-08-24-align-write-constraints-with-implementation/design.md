## Context

See proposal.md - Why。

記述が3か所（main spec 1、steering 2）に散っており、うち1つはセキュリティ上の前提だった。単なる字句修正ではないため、何をどう直すかを先に決める。

## Goals / Non-Goals

**Goals**

- 制約の記述を実装と一致させる
- 認証が無いという事実を、制約の陰に隠さず記述に出す

**Non-Goals**

- 認証・認可の実装（proposal の非目標に同じ）
- 実装コードの変更

## Decisions

### 決定1: 実装ではなく制約の側を直す

書き込みは意図して足したものである。承認・却下は `implement-portal-mvp` の11章で、二重に書き込む主体を作らない形（本家の API を呼ぶ）に落として合意した上で実装した。文書編集も同じ形を踏襲している。実装を制約に戻す理由がない。

**代替案**: 書き込み口を落として読み取り専用に戻す。却下 — MVP の主要機能を失う。

### 決定2: 禁止の対象を「あらゆる書き込み」から「`.spec-workflow/` への直接の書き込み」に絞る

元の Requirement が守ろうとしていたのは「二重に書き込む主体を作らない」ことである。本家の API を呼ぶ形なら、ファイルに触るのは本家のままで、主体は増えない。禁じるべきは stroke-board が自分でファイルを書くことであって、本家に書かせることではない。

この線引きは実装済みの `read-only.test.ts` が既に機械的に固定している（書き込み口は本家 API 経由の3本だけ）。記述をそれに合わせる。

**代替案**: 「本家に書き込まない」を丸ごと削除する。却下 — `.spec-workflow/` への直接書き込みを禁じる部分は今も有効で、失うと歯止めが無くなる。

### 決定3: 認証の欠如を Requirement 本文に書く

`tech.md` の Security Practices から「書き込み操作を一切持たない」を外すと、認証が無いという事実だけが残る。これを Security Practices の1行に留めると、spec を読む側からは見えない。

書き込み口を定義している `upstream-connection` の Requirement 本文に、認証も認可も無いことと、公開手段の制限が運用側の責任であることを明記する。既存の判断（`product.md` の Risks「公開手段は運用側の責任とし、将来の認証導入を閉じない構造にする」）を書き込みにも広げる形になる。

**代替案**: `tech.md` にだけ書く。却下 — spec だけを読む者に伝わらない。

### 決定4: steering は本家の API 経由で書き換える

`.spec-workflow/steering/` は本家が持つ文書であり、決定2で定めた線引きがそのまま当てはまる。`implement-portal-mvp` の 11.8 と同じ手順を踏む — `PUT /api/projects/:projectId/steering/:name` で書き換え、ダッシュボードの承認を通す。

## Risks / Trade-offs

- **認証の欠如が「既知のリスク」として記述されることで、対処が先送りされたまま忘れられる** → `product.md` の Open Questions に Owner と Deadline を付けて積む。Deadline は「外部公開を始める前」とし、既存の同種の項目と揃える
- **記述を緩めたことで、後から書き込み口が無制限に増える** → Requirement に「これ以外に本家の状態を変える口を持ってはならない」を残し、口の一覧を明示する。`read-only.test.ts` が実装側でこれを固定している
- **steering の書き換えに承認が要るため、この change は途中でユーザーの操作待ちになる** → main spec の更新（承認不要）と steering の更新（承認要）をタスクで分け、前者を先に済ませる

## Migration Plan

不要。振る舞いを変えない。
