## Context

動機は proposal.md（Why）を見ること。

- `docs/question-flow.md` は `add-question-flow-diagrams` で作った。図3枚（並び・状態・配信）
- `modularize-agent-question` で `app/composables/useAgentQuestion.ts` が入り、画面側に後始末が1つ増えた——往復の決着で、次の問いが来ないまま待機が明けたら、答え終わった問いを手放す
- サーバは問いの取り下げを配信しない。A7 は `state.json` の `currentQuestion` を `null` にするが、流すのは W2 だけ
- `add-question-flow-diagrams` の design 決定4 は「図に今どうなっているかを書く。あるべき姿は書かない」

## Goals / Non-Goals

**Goals:**

- 画面側の後始末を図に出し、図と実装を揃える
- サーバが取り下げを流さないことと、それを画面側が埋めていることを、事実として示す

**Non-Goals:**

- コードの変更
- サーバの振る舞いの変更（取り下げの配信を足すかどうかは別の判断）
- `docs/schema.md` の変更
- 状態の図と配信の図の作り直し

## Decisions

### 1. 並びの図に後始末を1つ足す。図は増やさない

シーケンス図の中に、画面が今の1問を手放す動きを Note として足す。

**Alternatives considered:**
- 図を4枚目として足す: 後始末は往復の一部で、並びの図から切り離すと前後が読めなくなる
- 状態の図に足す: あの図はサーバのファイルの動きを描いている。画面が持つものは対象外

### 2. 配信の節に、取り下げを誰が埋めているかを書く

「接続時配信は答え済みかを見ていない」で止めず、その先を書く。サーバが取り下げを流さないので、画面側が往復の決着で手放している、という事実まで。

**Alternatives considered:**
- 現状の記述のままにする: 読んだ人が「では答え済みの問いはどう消えるのか」で行き止まる
- おかしい旨の注記を足す: 直すかどうかの判断が入る。`add-question-flow-diagrams` の決定4（事実だけ描く）から外れる

### 3. 事実だけを書く。あるべき姿は書かない

サーバが取り下げを流さないことを、直すべき欠陥としては書かない。

**Alternatives considered:**
- 直すべきと書く: 判断が資料に混ざる。判断はまだ下りていない

## Risks / Trade-offs

- **画面側の作りを図に持ち込むと、実装が変わるたび図が遅れる** → 足すのは「手放す」という1点に留め、composable の名前や関数名は図に入れない
- **サーバの取り下げが将来入ると、この記述が古くなる** → そのときは同じ節を直す。事実として書いてあるので、直す箇所が1つに定まる
