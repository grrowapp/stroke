## Why

承認はプロジェクトを作る唯一の引き金であるのに、承認した本人が「作られた」ことをその場で確かめられない。承認処理はセッションディレクトリをプロジェクト名へ改名するだけなので、**プロジェクトの実体は承認した瞬間に存在している**。にもかかわらず一覧の母集合は `.spec-workflow/` を持つディレクトリに限られており、そこを作るのは承認後に裏で走る steering の claude である。結果として、モーダルを閉じて一覧へ戻ったユーザーが見るのは、さっきまでと変わらない一覧である。

承認が通ったのか、名前が衝突したのか、裏の起動に失敗したのかを、画面から区別する手段が無い。ユーザーにできるのは再読み込みを繰り返すことだけになる。見に行かずに気づけるようにするのがこのプロダクトの目的（`product.md` の Purpose）である以上、自分が起こした変化の結末だけが見に行かないと分からない、という状態を残さない。

## What Changes

- **一覧の母集合に「生成中のプロジェクト」を加える。** 昇格済み（`state.json` の `phase: 'approved'`）でありながら `.spec-workflow/` をまだ持たないディレクトリを、生成中のプロジェクトとして一覧に載せる。承認の直後からこの条件を満たすため、一覧へ戻った時点で必ず行が在る
- **生成中の行は一覧の最下部に置く。** 並びは アクティブ → 未接続 → 生成中 とする
- **生成中であることを、他より薄い行と回転するローダーで示す。** 行の地を他と変え、フォルダのアイコンの位置でローダーを回す。名前と日付は未接続と同じ薄さにする。**明滅は持たない**（一覧の行は情報が詰まっており、周期的に薄くすると「進行中」ではなく「読みにくい行」になる。prototype で確かめた）
- **生成中の行は選択できない。** 未接続と同じく、押しても何も起きず、キーボードのフォーカスも受けない。まだ入れる中身が無いためである
- **判定はファイルシステムの事実だけで行う。** `state.json` の `phase` が `approved` で、走査（`.spec-workflow/` を持つもの）に同じ名前が無ければ生成中。`.spec-workflow/` が出来た時点で完了。`invocation` は見ない
- **一覧に「作成に失敗」の状態を持たない。** 失敗はモーダルで知らせ、その場でユーザーが**やり直すか破棄するか**を選ぶ。どちらを選んでも一覧へ戻り、行は生成中に戻るか、消える。失敗したまま居座る行が生まれないので、一覧の状態は **アクティブ / 未接続 / 生成中** の3つで足りる
- **決着したら、成功でも失敗でも、知らせてから次を選ばせる。** **知らせる面**と**選ばせるモーダル**は**別物**であり、順に出す。【確定 2026-08-29・ユーザー確認済み】
  1. **知らせる面** — 何が起きたか。成功なら祝い（弾ける演出を添える）、失敗なら作りきれなかったこと。**画面の半分くらいを埋める**（小さすぎず、全面でもない）。**フェードアウトで自ら消える**——消えないと操作ができないためである
  2. **選ばせるモーダル** — 知らせる面が引いた後に出す。次に何をするか。ユーザーが選ぶまで閉じない

  成功と失敗で**器は同じ**。中身（文言と、選ばせる操作）だけが違う。

  満たすこと。
  - **一覧の行（バー）の中に押し込まない。** 行に収まる大きさの表示ではない
  - **画面遷移しない。** 今いる一覧の上で完結する
  - **知らせる面は画面全体を覆わない**（半分くらい）
  - **知らせる面はフェードアウトで自ら消え、モーダルはユーザーが選ぶまで閉じない**

  既存のトーストには載せない（あれは本家由来の通知4種のためのもので、1行のテキストに限る仕様である）。

  **選ばせる面の中身**

  | | 問い | 選択肢 | 選んだ後 |
  |---|---|---|---|
  | 成功 | ステアリングの結果をレビューするか | **する** | そのプロジェクトのレビュー画面へ、**対象を開いた状態**で飛ぶ |
  | | | **しない** | 一覧へ戻る |
  | 失敗 | どうするか | **やり直す** | 一覧へ戻る（行は生成中に戻る） |
  | | | **破棄する** | 一覧へ戻る（行が消える） |

  steering が終われば本家に承認リクエストが立つので、成功の「する」はそれを開く。

  **未決** — 「やり直す」と「破棄する」の実装方法。どの口を使うかは決まっていない。

  `projectId` は**一覧の行が既に持っている**（`buildProjectDirectory` が registry を突き合わせて入れている）。追加の問い合わせは要らない。ただし registry に載るのは生きたインスタンスがある間だけなので、**完了の瞬間なら取れる**という前提に立つ。取れなかった場合は「する」を選べない状態にする。

  **生成完了のときだけ、レビュー画面を開いた状態まで遷移する。** 飛び先は `/projects/<projectId>/approvals/<approvalId>` で、`approvalId` は `GET /api/projects/<projectId>/approvals` から引く。

  これは通知の行から開くときの着地点とは**意図的に違える**。`project/ui` は「承認依頼の発生 → そのプロジェクトの承認画面」を開くだけで、開いた先でスクロールもハイライトもしないと定めている。通知は「何かが起きた」を知らせるもので、対象が1つとは限らないためである。一方、生成完了は**対象が1つに決まっている**——今まさに作られた steering への承認依頼であり、ユーザーは「レビューする」と答えて来ている。開くところまで連れて行く。

  同じ承認画面に入る経路が2つになるが、開き方の差はこの理由に基づく。通知側の要件は変えない。
- **削除の口をメソッドで振り分ける。** 破棄のために `DELETE /api/projects/:projectId` を足す。あわせて既存のセッション削除も、spec が既に規定している `DELETE /api/sessions/:id` に実装を揃える。**パスに動詞を置かず、メソッドを絞らない handler も作らない**——削除が `GET` で到達できる形になるためである。phase の判定は各 endpoint が持ち、消す動作だけを1つに切り出す

### 届け方 — 既にある WS に載せる

一覧は今、画面が開いたときに1回だけ取得している（定期実行しない、が `tech.md` の Performance Requirements）。開いたまま出現・完了・失敗を捉えるには契機が要る。**定期取得は足さない。既にある WS に載せる。**

- **上層が既に張っている board WS（`/ws`）にメッセージ型を足す。** 新しい endpoint を立てない。`useBoardSocket` は `createSharedComposable` でアプリ全体に1本なので、接続は増えない
- **接続時の `snapshot` に、生成中のプロジェクトを載せる。** board WS には接続直後に今の分を流す規約が既にある。「一覧を開いた時点で既に生成中のもの」はこれで賄い、この change のために別の仕組みを作らない
- **board WS の位置づけを「本家通知の中継」から「上層へのサーバー発イベントの口」へ改める。** 中身は今すべて `UpstreamMonitor` 由来だが、stroke-board 自身が起こしたイベントも同じ口で運ぶ

### WS の増やし方を規約として置く

WS を使うなら、これは付随作業ではなく前提である。今は**イベントを1つ足すたびに endpoint と registry を1本ずつ生やす**形になっており、その増やし方こそが直す対象である。

現状、2つの体系は「サーバ→画面の一方向」「接続の瞬間に今の分を流す」までは既に同じで、割れているのは増やし方だけである。

| | board `/ws` | ストローク W1 / W2 |
|---|---|---|
| 口の数 | 1本。**メッセージの type で分ける** | **イベントごとに1本**（`question` / `proposal`） |
| 束ね方 | `peers: Set<Peer>` | `createRegistry()` をチャネルの数だけ複製 |
| 接続時配信 | `snapshot` を送る | route が session-store を読んで1件送る |

規約として次を置く。

- **新しいイベントのために新しい WS endpoint を立てない。** 既にある接続にメッセージ型を足す
- **束ね方の実装は1つにする。** `createRegistry()` と board の `peers` は同じものである。キーを持つ／持たないの違いに畳み、2つ書かない
- **接続の瞬間に今の分を流すことを、実装ごとの慣習ではなく規約として書く**

破壊的変更は無い。既存のプロジェクトの見え方と入場、W1 / W2 の振る舞いは変わらない。

## Capabilities

### New Capabilities

- `api/project/delete`: プロジェクトを消す endpoint。**`DELETE /api/projects/:projectId`**（ファイルは `server/api/projects/[projectId]/index.delete.ts`）。破棄の面からのみ呼ばれる。消せるのは `phase` が approval 以降のものに限る
- `ws/delivery`: WS 配信の規約。サーバ→画面の一方向であること、接続の瞬間に今の分を流すこと、**新しいイベントのために新しい endpoint を立てないこと**、束ね方の実装を1つに保つこと。今まで board 側とストローク側がそれぞれの慣習として持っていたものを、1箇所の規定にする

### Modified Capabilities

- `project/directory`: 次の5つの要件が変わる
  - 「プロジェクトの母集合を親パスの走査で作る」— `.spec-workflow` を持たないディレクトリは拾わない、という規定に、昇格済みで生成中のものを載せる例外が加わる
  - 「アクティブと未接続を判定して示す」— 生成中のものは接続の判定の対象にしない
  - 「アクティブを上、未接続を下に並べる」— 最下部に生成中が加わる
  - 「一覧は4つの列を持つ」— 状態の値に**「生成中」だけ**が加わる。失敗の状態は持たない（失敗はモーダルで決着し、行として居座らない）
  - 「未接続のプロジェクトは選択できない」— 生成中の行も選択不可の対象になる
- `project/generation`: **作成の進行と結末を見せることを、この capability に加える。** 別の capability を新設しない。今は昇格（改名）の手順だけを持っているが、承認から steering の完了までは1つの生成の過程であり、その過程がユーザーにどう見えるかを別の場所に置くと、同じ1つのことが2箇所に分かれる。

  **加える要件**
  - **生成中であることを見せる** — 昇格した瞬間から、完了するまで。一覧の最下部・選択不可
  - **決着を知らせ、次を選ばせる** — 成功でも失敗でも、2画面のモーダルで知らせて選ばせる。自分から消えない
  - **失敗を行として残さない** — 失敗はモーダルで決着する。やり直せば生成中に戻り、破棄すれば消える

  **書き換える要件** — 「昇格に失敗したら承認を確定させず、宙吊りの状態を作らない」

  今の要件は順序を名指しで書いている（`phase` を書く → 改名 → 失敗したら `phase` を書き戻す）。この順序は、**プロセスが `phase` を書いた直後に落ちると「uuid のまま `approved`」の残骸を残す**。その残骸は一覧に「生成中」として出てしまい、名前が uuid のプロジェクトが並ぶ。

  順序を **改名 → `phase` を書く → 失敗したら改名を戻す** に変える。巻き戻しが対称になり（移動を1回戻すだけ）、残骸そのものが原理的に生まれない。「`approved` なのに改名されていない状態を作らない」という保証は変わらず、むしろ自然に満たされる。

  なお今の要件が挙げる「改名で `state.json` の場所が変わるので `phase` を後から書けない」という理由は成立していない。**同じファイルの失敗処理が既に改名後の場所へ書いている**（`readState(promoted)` / `writeState(promoted, …)`）。

  変えないもの: 承認の判断そのもの、衝突の確認、409 の3つの意味、`docs/proposal.md` に触れないこと。

- `api/session/delete`: **実装を spec に合わせる。** この capability は既に `DELETE /api/sessions/:id` と規定しているが、実装は `POST /api/strokes/:id/delete` で、メソッドも path も従っていない。プロジェクトの削除を足すこのタイミングで、**spec の path とメソッドに実装を揃える**——`server/api/sessions/[id]/index.delete.ts`（`DELETE /api/sessions/:id`）。

  Nitro はメソッドで handler を振り分ける仕組みを持っており、パスを名詞に保てる。パスに `delete` という動詞を置く必要はない。**`delete.ts` のようにメソッドを絞らない形は採らない**——破壊的な操作が GET でも到達してしまう。

  spec は path を `/api/sessions/:id`、実装と `docs/specs/api/contract.md` は `/api/strokes/:id` としており、元から食い違っていた。**実装が誤り**なので spec 側へ寄せる。ただし移すのは**削除だけ**で、他の U 系（U1・U2・U3・U7・U9・U10・U12・U13・W1・W2）は `strokes` のまま残す。それらを揃えるのは別の話とする。

  なお `openspec/specs/api/**` は U 系を `api/session/**`、A 系（エージェントの口）を `api/stroke/**` と分けており、A 系は `/api/strokes/...` のままで正しい。

`api/session/ws`（W1 / W2 の endpoint 規定）は変えない。既にある2本の振る舞いはそのままで、`ws/delivery` はその上に増やし方の規範を置くだけである。`api/contract`（応答コードの規約）も変えない。

**`replace-polling-with-push` との関係。** あの change は失敗の配信のために W3 という4本目の endpoint を立てる計画で、`ws/delivery` の「新しい endpoint を立てない」に正面から反する。**この change を先に通し、あちらは W1 / W2 の接続にメッセージ型を足す形へ書き換える**必要がある。あちらは 0/30 で未着手なので、書き換えの費用は今なら小さい。

## Impact

**サーバー**

- `server/api/projects.get.ts` — 走査の結果に、生成中のプロジェクトを重ねて返す
- `server/utils/control/directory.ts` — 生成中を含めた並びと状態の組み立て
- **判定はファイルシステムだけから導く。** `phase: 'approved'` を読む薄い列挙を持ち、走査（`.spec-workflow/` を持つもの）に無い名前を生成中とする。`listSessionsCore` には相乗りしない——あれは巡回のための検査（`openspec/` と `config.yaml`）を含んでおり、母集合の判定に使う筋のものではない。新しい保存や登録簿は作らない（`project/directory` の「一覧を永続化しない」を維持する）
- **生成の順序を入れ替える。** 改名 → `phase` を書く → 失敗したら改名を戻す

**削除**

- `server/api/projects/[projectId]/index.delete.ts` — 新規。`DELETE /api/projects/:projectId`
- `server/api/strokes/[id]/delete.post.ts` → `server/api/sessions/[id]/index.delete.ts` — `DELETE /api/sessions/:id` へ移す
- `server/handler/**` — 削除の実行を1つに切り出す。phase の判定は各 endpoint が持つ
- `server/utils/stroke/session-core.ts` — `deleteSessionCore` から phase の判定を外す
- 呼び出し元 — `app/composables/useWaitingRetry.ts`、E2E 4本（`agent-question` / `proposal-persistence` / `stroke-exit` / `ws-disconnect`）、`scripts/ws-disconnect-check.ts`
- `docs/specs/api/contract.md` — U11 の path とメソッド

**画面**

- `app/pages/projects/index.vue` — 生成中の行、決着のモーダル
- `app/composables/useBoardSocket.ts` — 足したメッセージの受け口
- `shared/types` — `ProjectSummary` に生成中を表せる形を足す。`BoardMessage` の union にメッセージを足す
- 決着のモーダル — 2画面。成功は承認画面へ、失敗はやり直す／破棄する

**WebSocket**

- `server/utils/control/board.ts` — 生成の進行を broadcast する口を足す
- `server/utils/stroke/ws-channels.ts` と `board.ts` の束ね方 — 2つある実装を1つに寄せる
- 承認処理と、完了・失敗が決まる箇所 — 書いた後に broadcast する
- `docs/specs/api/contract.md` — WS 配信の記述。W1 / W2 と board を1つの規約の下に並べ直す

**未決**

- **改名失敗の扱い。** 改名失敗も作成の失敗なので同じ面を出す。ただし選択肢の指す先が違う（破棄＝セッション、やり直す＝再承認）。名前の衝突は今は訂正として専用処理になっており、失敗の面に混ぜるかは別
- **「やり直す」と「破棄する」の実装方法。** どの口を使うかは決まっていない
- **文言。** 「生成中」が指しているのは steering の作成であって、プロジェクトの作成ではない。プロジェクトは承認の瞬間に出来ている。`CONTEXT.md` の「生成中」の定義と、一覧の文言をどう言い直すか
- **決着のモーダルの寸法・演出の具体値。** 満たすべき条件（行に押し込まない／画面遷移しない／画面全体を覆わない／自分から消えない）は What Changes に置いた。具体値は実物を出して決める
- **祝いの演出を既存のモジュールで賄えるか。** 「クラッカーを鳴らすようなアニメーションのモジュールでいいものがあれば、それを使うのが一番いい」とのことなので、自前で書く前に既存を当たる（`docs/specs/plan/components-library-replacement.md` と揃える）
- **`projectId` の導出。** 失敗したプロジェクトは本家に登録されておらず `projectId` を持たない。破棄のリクエストを組むには要る。本家の SHA-1 の取り方を確認したうえで、サーバー側で導出して応答に入れるかを決める

## 対象外

- steering が完了した後の流れ（承認待ちの発生と通知）— 既存の仕組みに乗るだけで、新設しない
- 削除以外の U 系 endpoint の path（`strokes` → `sessions`）— 元から spec と食い違っているが、この change では削除だけを揃える
- `/api/projects/[projectId]/**` の作り（本家への素通しをやめる話）と、下層の addressing

| 7 | 完了の判定は今の仕組みを流用でよい。**厳密である必要はなく、ロジックはラフでよい** | 「今の官僚判定を流用で良いんじゃない？」「完了したことを完全に厳密に図る必要がある部分でもない」 |
| 8 | 完了メッセージの**質感**（行に押し込まない／画面遷移しない／弾けて出て引く／占有率と速度感が釣り合う／既存モジュールがあればそれを使う） | 「クラッカーがパーンて弾けて、早すぎずかといって次のアクションに進むのにじゃまにならない位のスピード感で…消えていく感じ」 |
| 9 | 失敗時も見せる。ただし表現方法はちゃんとする | 「2 だけど表現方法はちゃんとして」 |
| 10 | **届け方は既にある WS で行く。**まとまりと再利用性のため。そして**WS を使うなら、増やし方の整理はやって当たり前**であって、含めるかどうかを問うことではない | 「今あちこちに使ってる ws でいくのがまとまりもいいし再利用性が有る」「それぞれが勝手に作りすぎなんだよ」「WS を使うなら、やるの当たり前」 |

7 の「官僚判定」は「今の**完了**判定」の意であることをユーザーに確認済みである。指しているのは `invocation` の `running` → `idle`。あわせて、**この判定に厳密さを求めない**ことも述べられている。取りこぼしや数秒のずれを潰すための作り込みはしない。

8 の「クラッカー」は演出の**イメージとして挙げられたもの**であり、クラッカーという具体的な絵柄の指定ではない。伝えられているのは上に書いた質感の方である。
