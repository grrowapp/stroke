## Context

問いの構造は `shared/types.ts` の `Question` / `QuestionOption` に定義され、`server/utils/question.ts` の zod スキーマ1箇所で組み立てと検証を担っている（AI 応答からも `strokes.json` / `state.json` からも同じ経路を通る）。動機と実測値は proposal.md の Why を参照。

## Goals / Non-Goals

**Goals:**

- キー構成と長さの規定を AskUserQuestion に寄せ、詰め込む先を構造で塞ぐ。
- 検証の置き場所を `question.ts` 1箇所に保ったまま差し替える。

**Non-Goals:**

- 既存セッションの移行。読めなくなることを受け入れる（proposal.md）。
- 回答（`Answer`）の構造の変更。選択／自由入力の2種は据え置き。
- `header` に相当する分類の自動生成や正規化。AI が付けたものをそのまま出す。
- 画面の配置そのものの作り直し。並びは変えるが、縦積みカード（ui.md 画面1 = A）の方針は維持する。

## Decisions

### 1. キー名は AskUserQuestion に合わせ、役割の重なりを解く

| 現行 | 新 | 上限 |
|---|---|---|
| `question` | `header` | 12字 |
| `background` | `detail` | 300字 |
| （新規） | `question` | 20字 |
| `options[].label` | `options[].label` | 規定なし（文言で「1〜5語」） |
| `options[].detail` | `options[].description` | 50字 |
| `options[].rationale` | 削除 | — |
| `options[].recommended` | 据え置き | — |
| `options` 1〜20件 | `options` 1〜5件 | — |

`detail` というキー名が「問いの詳細説明」と「選択肢の説明」の両方で使われていたのが混乱の元だったため、選択肢側を `description` に寄せ、問い側を `detail` に一本化する。画面上の表示ラベルは「詳細説明」。

代替案: 全キーを新しい名前にする（`topic` / `context` / `ask` など）。AskUserQuestion に合わせるという方針から外れるため採らない。

### 2. `label` の「1〜5語」は文言のみで縛り、機械検証しない

AskUserQuestion 自身が `label` に文字数のハード上限を持たず、"Should be concise (1-5 words)" という文言だけで縛っている。日本語では語の区切りが機械判定しにくく、形態素解析を持ち込むのは MVP の範囲を超える。

代替案: 文字数上限（20字程度）で裏を取る。実測の中央22字・最大48字から見て妥当な線だが、AskUserQuestion に合わせるという指示に反するため採らない。

**トレードオフ**: 見出しが長くなっても検証では弾けない。ただし `description` が50字に絞られるため、説明を見出しへ逃がす余地は残る。運用して長さが問題になれば、そのときに上限を入れる。

### 3. 長さの規定は zod スキーマに置き、超過は「構造として読み取れない」に倒す

`question.ts` の `parseQuestion()` は既に「読み取れなければ `null`」という契約を持ち、呼び出し側（`ai.ts`）はそれを失敗としてリトライへ流す。長さ超過を専用のエラーにせず同じ経路へ入れることで、分岐を増やさずに済む。

**トレードオフ**: AI が長すぎる応答を返し続けるとリトライを2回消費して 502 になる。リトライ時の `continuePrompt()` は「応答の形式に従って」としか言わないため、何が長すぎたかは伝わらない。MVP では許容し、頻発するようなら形式の規定文言を強める。

### 4. 保存済みデータにも同じスキーマを適用する

`questionSchema`（`strokes.json` / `state.json` の読み直し）と AI 応答の検証は同じ `parseQuestion()` を通る。片方だけ緩めると検証の強度が2箇所でずれるため、一本のままにする。

**リスク → 緩和**: 既存4セッションが 500（`corrupt`）で開けなくなる → 移行しないことは proposal.md で合意済み。セッションディレクトリは残るため、必要なら手で捨てられる。

### 5. `recommended` は残し、根拠だけを外す

`rationale` を消すと、`question.ts` の不変条件「根拠の無い推奨は推奨として扱わない」が成立しなくなる。推奨の印だけを残し、不変条件は「推奨は多くとも1つ」に縮める。2件目以降の `recommended` を落とす処理はそのまま維持する。

## Risks / Trade-offs

- **話題タグ（12字）に問いの内容が収まらず、意味をなさないタグが並ぶ** → `question` 20字と併せて2段で示すため、タグ単独で意味が通らなくても画面上は補える。実運用で破綻するようなら上限を見直す。
- **詳細説明 300字では文脈が足りず、AI が前提を落とす** → 会話の継続は `--resume` が持っており、詳細説明は画面に出す要約であって AI の記憶ではない。文脈そのものは失われない。
- **既存セッションが開けなくなることに後から気付く** → 開いた時点で 500 が返る。エラー文言は既存の `corrupt` のまま（`state.json が壊れている: <uuid>`）で、原因が規定変更だと分からない。MVP では許容する。
