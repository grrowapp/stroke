## Context

動機は `proposal.md` の Why、振る舞いの契約は `specs/project/ui/spec.md` を参照。

approach を縛る現状は3つ。

**1. 決める操作が2箇所に散っている。** 承認と却下は承認一覧のカード（`ApprovalCard.vue`）にあり、差し戻しは対象文書を読む画面（`ApprovalAnnotator.vue`）の**しまえるコメント欄**の最下部にある。読んで判断した場で終わらせられるのは差し戻しだけで、しかもコメント欄をしまうと差し戻しごと隠れる。

**2. 却下の理由がカードの下に開く欄になっている。** 上の「却下」は入力欄の開閉を反転するだけで、送信は下の「却下する」が行う。送信が成功すると欄が閉じて一覧を取り直すが、**成功したことを示す表示が無い**。押した人からは「閉じただけ」に見える。上のボタンが押すたびに開閉するのも、送信ボタンに見える一因である。

**3. 承認一覧から対象文書へは `NuxtLink` で遷移している。** `approvals/index.vue` が `:to="/projects/:projectId/approvals/:approvalId"` を持ち、一覧を離れる。

**すでに使える前例がある。** ストロークの入口は「一覧から入った先を、オーバーレイ上のモーダルとして画面全体に出す」形で作られている（`app/layouts/stroke.vue`、ADR 0009・0010）。**開閉の状態を持たず、どの場面に居るかは URL が持つ。** リロードすれば同じ場面が開き直る。この形をそのまま承認へ持ち込める。

## Goals / Non-Goals

**Goals:**

- 読んで判断した場で、承認・即時却下・差し戻しのすべてを終わらせられるようにする
- 送った結果が押した人に分かるようにする
- 決める操作を1つの並びに集める

**Non-Goals:**

- 機能そのものを変えない。承認・却下・差し戻しが本家へ何を送るか、サーバーの経路は今のままである
- 承認依頼の URL を捨てない。その場で開くことと URL で指せることは両立させる
- 注釈を付けられる面は変えない。それは `create-module-annotation` が扱う

## Decisions

### 決定1: 承認依頼はルート付きのモーダルで開く

`app/layouts/` にモーダルの器を持つ layout を用意し、`approvals/[approvalId].vue` にそれを指定する。一覧（`approvals/index.vue`）はそのまま `NuxtLink` で遷移させる。

**なぜ:** ストロークが既にこの形である（`layouts/stroke.vue`）。器だけを layout が与え、中身と流れは変えない。**開閉の状態を component に持たせない**ので、URL とは別に「どれを開いているか」を持つ二重化が起きない。

ストロークとの違いは閉じられることである。承認は途中で読むのをやめてよいので、`dismissible` と `close` を立て、閉じたら一覧へ戻す。ストロークは最後まで行く前提なので閉じる道を持たないが、ここは事情が違う。

**代替案1: 一覧のページ内に詳細の状態を持ち、URL を変えない** — 承認依頼を URL で指せなくなる。通知から承認画面へ飛ぶ経路（`project/ui` の「通知の対象を下層の画面で開く」）が壊れる。採らない。

**代替案2: 一覧と詳細を1つのページに畳む** — `approvals/[approvalId].vue` が消え、ルーティングで表せていた「どれを開いているか」を自前の状態で持つことになる。採らない。

**本家との違い（実画面 2026-09-02）:** 本家の「その場で開く」は**カードがその場で展開する**形で、承認依頼を URL で指す口が無い。こちらは通知の飛び先とスペック（「URL で直接指せなければならない」）があるため、ルート付きモーダルで「その場」と「URL」を両立させる。展開したカードの中身（操作行 → 面の切替 → 本文＋コメント欄）は、モーダルの中身として同じ並びを写す。

### 決定2: 決める操作は画面上部の操作行に集める（公式の形）

承認・即時却下・差し戻す（N）を、画面ヘッダ（タイトル・対象ファイル）の直下の**操作行**へ集める。面の切替（segmented control）はその下の行に単独で残す。コメント欄最下部の差し戻しボタンは無くなる。

**なぜ:** 本家の実コードがその形である（v2.2.5 配布物 `dist/dashboard/public/assets/index-Dyq1VhYi.js` の ApprovalsPage を実測 2026-09-02）。決める操作——レビューと注釈の開閉・即時承認（`.btn bg-green-600`）・即時却下（`.btn bg-red-600`）・修正を依頼（`.btn bg-orange-600`・コメント数 `(N)` 付き・0件 disabled）——は**カードの操作行**（`flex flex-wrap items-center gap-3`）に集まり、面の切替（Preview/Annotate/…）は展開部の**別の行**に単独で置かれる。**この design は当初「本家は決める操作を面の切替と同じ帯に置く」と書いていたが、実コードを確認したところ誤り**（ユーザー指摘 2026-09-02「ちゃんと公式みろよ」）。

色は分けない。npm 配布物のコードは緑/赤/橙（`bg-green-600` 等）を指定しているが、**稼働中の本家（port 5000）の実画面では全ボタンが同じ accent 色で描かれる**（pending の承認を開いて実測 2026-09-02）——書いてある方ではなく、実際にそう見えている方に合わせる（ApprovalCard の余白と同じ判断）。

ボタンの実測（computed style・2026-09-02）: 背景 `#6366f1`（accent）・白字・角丸 **6px**・padding **8px 12px**・**12px / weight 500**・アイコンとの間隔 **4px**・ボタン間 gap **12px**。**disabled（差し戻し0件）は同色のまま opacity 50%**。**開閉の口（Close Review ＝ こちらの「レビューを閉じる」）だけは一段明るい `#818cf8`**（focus では無く地の色。開閉と決定を明度で分けている）。高さは 35px（line-height 約 1.4）。本家はデスクトップで長い文言・モバイルで短い文言の2枚看板（`hidden sm:inline` / `sm:hidden`）。`.sb-action`（角丸6px・600）と近いが weight が違うので、実装時は実測値に合わせる。面の切替（`.sb-segmented`）は本家と**完全一致**を実測で確認済み（容器 8px/4px padding/枠、項目 6px 角丸・6×12 padding・12px、選択のみ accent 塗り）。操作行の先頭には「閉じる」を置く（本家は開くと Review & Annotate が Close Review に変わり、同じ並びの先頭に居る）。差し戻すはコメント数を添え、**0件では disabled**（実画面でも灰色 disabled を確認。現実装の「押すと失敗文言」から変わる）。コメントが有る状態の承認は本家どおり止める（警告。サーバーも注釈付き承認を受けない）。

付随して: 決める操作が本文のスクロールに巻き込まれない位置へ出る。現状の差し戻しはしまえるコメント欄の下端にあり、コメントが増えると探すことになるうえ、欄をしまうと差し戻しごと画面から消える。

コメント欄はコメントの一覧と「全体へのコメント」を持つ場所として残す（しまえる作り・幅の固定は変えない）。差し戻しが欄の外へ出ることで、しまっても決める操作は見えたままになる。**コメントを付けることと、決めることを分ける。**

文言の発見（scope 外・報告のみ）: 本家 ja ロケールのデスクトップ表示は「**即時承認**」「即時却下」「修正を依頼」「レビューと注釈」。この change で改名するのは「却下」→「即時却下」だけで、「承認」→「即時承認」への改名は含めない（含めるかはユーザー判断）。

### 決定3: 却下の理由は既存のコメントモーダルと同じ形にする

`CommentModal.vue` は `defineModel('open')` で開閉を受け、`save` を emit し、保存すると自分で閉じる。却下の理由もこの形にする。

共通化するかは実装時に決める。**共通化を先に決めない**のは、コメントモーダルが色の選択と引用の表示を持ち、却下の理由が持たないためである。無理に1つにすると、使わない口を持つ部品になる。

**送った結果を示すことは、モーダルとは別の要件である。** モーダルにしただけでは「閉じただけ」に見える問題は消えない。送信後にその旨を出す（`notification-toast` が既にある）。

### 決定4: 文言は本家の日本語ロケールに合わせ、表示だけに閉じる

画面に出る文言だけを変える。本家へ送る `action`（`approve` / `reject` / `needs-revision`）、`data-testid`、サーバーの経路、specs の概念語（承認・却下・差し戻し。CONTEXT.md のドメイン語）はいずれも変えない。

対応（本家 `approvalsPage.actions` の ja 実測 2026-09-02）:

| 今の画面 | 本家 ja（変更後） |
|---|---|
| レビューする | レビューと注釈 |
| （開いた画面を）閉じる | レビューを閉じる |
| 承認 | 即時承認 |
| 却下 | 即時却下 |
| 差し戻す（N） | 修正を依頼（コメント > 0 のときだけ（N）を付ける） |

**なぜ:** 送る中身が変わっていないのに識別子を変えると、本家側のログや E2E の掴み所が意味なく動く。**利用者に見える名前と、系に流れる名前を分けて考える。**

## Risks / Trade-offs

**モーダルにすると対象文書が読みにくくなる** → 承認の対象は仕様書や設計であり、長い。`fullscreen` で画面全体を使う（ストロークと同じ）。狭い箱に押し込めない。

**閉じたときの戻り先** → 一覧へ戻す。ただし一覧のどこを見ていたかが失われると、依頼が多いときに探し直しになる。スクロール位置の扱いを実装時に確かめる。

**決める操作を1つの並びに集めると、押し間違いが起きやすくなる** → 承認と即時却下が隣り合う。即時却下は理由の入力を挟むので取り消せるが、承認は1押しで確定する。本家は色で見分けさせる（承認=緑・即時却下=赤・差し戻し=橙）。並び順・色とも本家に合わせる。

**`create-module-annotation` は archive 済み（2026-09-02）** → 承認画面は既に「面は2つ（プレビュー / 注釈）でどちらでも指摘が付き、コメント欄はしまえる（幅固定）」の形である。この change はその上に乗る。帯を組むときは、面の切替（`approval-modes`）と、しまえるコメント欄の両方と噛み合わせる。

## Migration Plan

1. モーダルの器となる layout を用意し、`approvals/[approvalId].vue` に指定する。この時点で見た目が変わるので、`e2e/workspace.spec.ts` の承認まわりを合わせる
2. 決める操作をヘッダ直下の操作行へ集める。差し戻しをコメント欄から抜き、承認・即時却下を足す（色・並び順は本家）
3. 却下の理由をモーダルにする。送信後に結果を示す
4. 文言を「即時却下」に変える（表示のみ）
5. `e2e/approval-annotation.spec.ts` に、対象文書を読む画面から却下できることを足す

1 と 2 は独立している。3 は 2 の後（却下ボタンが対象文書の画面に出てから）。
