## ADDED Requirements

### Requirement: 承認の操作は、実行の決着の後にしか存在しない

システムは、phase が `proposed` のときにだけ承認の操作を提供する SHALL。phase `proposed` は、proposal を提出した実行が完了して invokeAi が決着したときにしか立たない（`agent/invocation`「完了は output stream で検知して idle に変える」）。したがって、**対象で claude が走っている間に承認の操作が存在することはない**（SHALL）。

画面は、承認の可否を自分の操作の履歴から導いてはならない（MUST NOT）。phase が唯一の根拠である。

「承認できる状態なのに、対象で AI が走っている」状態を作ってはならない（MUST NOT）。昇格の endpoint（`api/session/promote`）は実行中の要求を想定せず、そこへ到達する経路は画面に無い。

#### Scenario: proposal の提出直後

- **WHEN** 実行中の claude が proposal を提出したが、実行はまだ終わっていない
- **THEN** phase は `proposed` になっておらず、画面2 は開かない。承認の操作は存在しない

#### Scenario: 実行が決着する

- **WHEN** proposal を提出した実行が完了し、invokeAi が phase を `proposed` に切り替えて配信する
- **THEN** 画面2 が開き、承認の操作が現れる。その時点で対象の実行は終わっている

#### Scenario: 承認を押した時点で実行が無い

- **WHEN** ユーザーが承認する
- **THEN** 対象で走っている呼び出しは無く、昇格の改名は誰も置き去りにしない

## MODIFIED Requirements

### Requirement: 承認の成功で画面2を離れてプロジェクト一覧へ戻る

システムは、承認が成功したときにモーダルを閉じ、プロジェクト一覧へ戻す SHALL。承認の応答は、承認後に始まる次の実行の完了を待ってはならない（MUST NOT）。

承認が成功したセッションは、そのセッション id では開けなくなる SHALL。セッションはプロジェクトへ昇格して同じ id のセッションとしては存在しなくなるためである（`project/generation`）。承認後に承認・差し戻しの操作が現れる余地は無い。

承認が成功しなかったときは画面2に留まり、ユーザーが同じセッションで承認し直せる状態を保つ SHALL。

**成功しなかった理由は、ユーザーの次の手が分かる形で示す SHALL。** 理由を捨てて汎用の失敗として示してはならない（MUST NOT）。名前の衝突なら別の名前で承認し直す。昇格の失敗（改名や phase の書き込みの失敗）なら判断は残っているので、昇格だけをやり直すか破棄するかを選ぶ。それ以外の失敗は、サーバが返した理由をそのまま失敗として示す。

#### Scenario: 承認が成功する

- **WHEN** ユーザーがプロジェクト名を確定して承認し、昇格が成功する
- **THEN** モーダルが閉じてプロジェクト一覧が表示される。次の実行の完了は待たない

#### Scenario: 承認したセッションを開こうとする

- **WHEN** 承認が成功した後、そのセッション id の画面2を開こうとする
- **THEN** そのセッションは存在せず画面2は開かない。承認・差し戻しの操作は現れない

#### Scenario: 承認が失敗する

- **WHEN** 名前の衝突や昇格の失敗で承認が成立しない
- **THEN** 画面2に留まり、phase は `proposed` のままで、理由に応じて別の名前で承認し直すか昇格をやり直せる

#### Scenario: 理由の分からない失敗にしない

- **WHEN** 昇格が受理されずに戻る
- **THEN** 画面はサーバが返した理由を捨てず、次の手が分かる形で示す
