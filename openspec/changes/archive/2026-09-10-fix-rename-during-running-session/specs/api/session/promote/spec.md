## ADDED Requirements

### Requirement: 昇格は実行の決着の後にしか要求されない

昇格は**セッションディレクトリの改名**である（`project/generation`）。改名はディレクトリの実体を移さないため、走っている呼び出しがあればそれは改名先で生き続ける一方、自分を名乗る id は改名前のものであり、以後の操作——問いの送信・文書の提出・実行の記録——はすべて対象を見つけられずに落ちる。

システムは、この状況を **昇格の要求が実行中に届かないこと**によって防ぐ SHALL。承認の判断（U10）とその後の昇格（U14）は phase `proposed` でしか行えず、phase `proposed` は proposal を提出した実行の決着でしか立たない（`agent/invocation`・`stroke/frontier`「承認の操作は、実行の決着の後にしか存在しない」）。したがって昇格が要求される時点で、対象に走っている呼び出しは無い。

**「実行中だから受理しない」という応答を持ってはならない（MUST NOT）。** 昇格の endpoint が実行中かどうかを見て受理を分けることは、承認できる局面が実行中に立つことを前提にした設計であり、その前提を無くすのが本旨である。

#### Scenario: 承認の時点で実行が無い

- **WHEN** ユーザーが承認し、昇格が要求される
- **THEN** 対象で走っている呼び出しは無く、改名は誰も置き去りにしない

#### Scenario: 改名が走っている呼び出しを置き去りにしない

- **WHEN** 昇格が成功した
- **THEN** 改名の時点で対象に走っていた呼び出しは無く、改名前の id を名乗ったまま生き残る呼び出しは存在しない
