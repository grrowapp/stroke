# adr0016-sub-add-stroke-check-approval-option Design

## Context

動機と範囲は proposal.md、要求は `specs/tooling/stroke-check/spec.md` を参照。

道具は `scripts/stroke-check.ts`（`yarn check:stroke`）。ブラウザで dev サーバーを操作し、ストロークが着地するかを見る。ランナー（`playwright test`）には載せず、人が意図して叩く。

**2026-08-29 時点で、proposal が挙げた3項目のうち1つは実装済みである。**

| proposal の項目 | 状態 |
|---|---|
| 承認まで進めるかを選べる | 未実装 |
| 承認まで進めた場合、steering 工程の進行も追う | 未実装 |
| 検証で作ったセッションを片付けるかを選べる | **`--cleanup` として実装済み**（uuid のディレクトリを消す。承認で名前が変わる場合は未対応） |

同日、本 change の範囲外だが関係する実装も入っている。

- `--send-back` — proposal を1回差し戻し、出し直されるまで見る。指摘は haiku が書く
- `openStrokes` — 画面1 が開けなければ最大5回開き直す
- `RELOAD_INTERVAL_MS` — 変化が無いまま60秒経ったら画面を取り直す

いずれも dev の不安定さ（ticket `stabilize-dev-module-delivery`。change は未起票）を吸収するためのもので、承認の経路でも同じ手当てが要る。

**承認の画面経路**（`app/pages/strokes/[sessionId]/proposal.vue`、`app/composables/useProposalReview.ts`）:

1. 「承認して作る」ボタン → モーダルが開く
2. プロジェクト名の入力欄。既定値は proposal が提示した名前が入っている
3. 「承認」ボタン。名前が空、または衝突した名前のままだと押せない（`approveBlocked`）
4. `POST /api/strokes/:id/approve` に `{ projectName }` を送る
5. 成功すると `phase` が `approved` になり、**`/projects` へ遷移して流れが終わる**

**承認後の steering は画面に出ない。** `useProposalReview.approve` のコメントがそう書いている。

> 承認で流れは終わる。モーダルごと閉じて一覧へ戻る（ADR 0011: この後の steering はサーバーが裏で起こすので、ユーザーは待たない）。

サーバー側は `approve.post.ts` が昇格の成功後に steering の実行を起こす。人は待たない設計であり、**進行を知らせる画面が承認の導線上に無い**。

## Goals / Non-Goals

**Goals:**

- 承認まで進めるかを実行のたびに選べる。既定は proposal で止める
- 承認まで進めた場合、steering 工程が着地したかを**ブラウザから**見届け、判定に含める
- 片付けの対象を、承認で名前が変わった場合にも取り違えない

**Non-Goals:**

- steering 工程の**中身**の評価。文書の質は人が読んで判断する（道具は着地したかだけを見る。既存の方針と同じ）
- `get-steering` が flontier で 500 になる問題の修正（**切り出し先の change は現在存在しない**。2026-08-29 の午前までは `fix-steering-tool-stage-error` として change・ticket とも在ったが、いずれも見当たらない）
- dev の不安定さの根本解決（ticket `stabilize-dev-module-delivery`。change は未起票）。ここでは既存の吸収を承認経路にも適用するに留める

## Decisions

### Decision: 承認は `--approve` で明示的に選ぶ。既定は proposal で止める

承認は**プロジェクトを生成する不可逆な操作**である。既定で走らせない。オプションを渡したときだけ進む。

`--send-back` と併用できる形にする。差し戻し → 出し直し → 承認、という一周を1回の実行で通せる。

代替案として「常に承認まで進め、止めたいときにオプションで止める」を検討したが不採用。取り違えたときの損害が非対称で、既定は安全側に倒す。

### Decision: steering の着地は書かれた文書で判定する（画面では判定しない）

**改訂した（2026-08-31。実機で1周させて判明）。** 当初は「`/projects/<projectId>/steering` の画面で見る」と決めていた。承認の導線は `/projects` の一覧で終わるが steering 文書を表示する画面は存在するので、そこへ移って product / tech / structure が揃うのを待てば、検証の原則（操作はブラウザのみ）を保ったまま着地を見届けられる——という判断だった。

**その画面は判定に使えない。** 画面は本家 dashboard の `GET /api/projects/:id/info` に依存し、本家は**起動中のプロジェクトしか返さない**（ADR-0006）。プロジェクトが本家の一覧に載るのは、それをワークスペースとする MCP サーバーが動いている間だけで、それは steering の claude が動いている間だけである。**claude が終わった瞬間、画面は「未接続」へ戻る。**

実測では、3文書すべてが書かれて `submit-document` が3回とも 200 を返しているのに、一覧は5回開き直しても出なかった。画面で判定すると、合否が「claude の終了と画面の再読み込みのどちらが先か」という競争になる。

そこで `<projectShareRoot>/<name>/.spec-workflow/steering/{product,tech,structure}.md` の有無で数える。**成果物は書かれた文書であり、それを直接見る。** 一覧は開くだけ開いて、出れば人が見るための表示として使い、出なくても落とさない。

原則（操作はブラウザから行う）は**操作**に掛かるもので、判定の材料まで画面に限る規定ではない。承認までの操作はすべてブラウザのままである。

代替案:

- **本家 dashboard の REST を叩いて文書の有無を見る** — 不採用。原則に反する。画面の状態と食い違う失敗を作り込む（実測 2026-08-28）
- **`debugLogDir` の生出力だけで判定する** — 不採用。呼び出しが起きたことは分かるが、文書が書かれたかは分からない。ただし**待つ間の進捗表示**には使う（既存の `logNames()` と同じ用法）
- **セッションディレクトリのファイルを直接読む** — 不採用。同じく画面を介さない

### Decision: 承認後の遷移先は「名前」から引く

`approve` は `projectName` を送って成功する。**道具はその名前を握っている**ので、`/projects` の一覧からその名前の行を探して開けばよい。projectId を別途解決する必要はない。

一覧に現れるまでに間があるなら、`RELOAD_INTERVAL_MS` と同じ考え方で画面を取り直しながら待つ。

### Decision: 名前の衝突はサフィックスを足して再試行する

`approve` は 409 を3つの意味で返す（名前の衝突 / AI が実行中 / phase 不整合）。画面は衝突と分かったときだけ承認を止め、名前の変更を促す（`conflictName`）。

道具は何度も回すため、**同じ概要を流せば同じ名前が提案されて必ず衝突する**。衝突したら名前に連番なり時刻なりを足して再試行する。人が毎回考えるのは道具の趣旨に合わない。

衝突以外の 409（AI が実行中 / phase 不整合）は再試行しない。前者は `settle` で待ってから承認することで踏まない。

### Decision: 片付けの対象は uuid と承認名の**両方**を候補に持ち、実在を確かめてから消す

**当初この design は「承認の有無で切り替える」と決め、「両方のパスを試して消す」を明示的に不採用としていた。実装で覆った**（2026-08-30）。

承認するとセッションディレクトリが**プロジェクト名へ改名される**（proposal の「注意」）。切り替える案は、道具が承認で使った名前を確実に握っていることを前提にしていた。**その前提が成り立たない。**

`approve()` は承認の応答を 60 秒で取り逃したとき（`response === null`）も名前を返す。そのため名乗られた名前を鵜呑みにすると、承認が名前の衝突で失敗していた場合に2つの壊れ方が起きる。

- 対象を名前へ**差し替える**と、実在する uuid のセッションが対象から外れて残る。`stroking` のまま巡回に拾われ、再キックされ続ける
- その名前を**そのまま消しに行く**と、**他人が作った同名のプロジェクトを消す**。消す先は phase の検査を持たない `removeSessionDir` なので、承認済みでも止まらない。`--cleanup` の約束（消すのはこの実行が作った1本だけ）を破る不可逆な削除になる

そこで**両方を候補に足し、消す前に実在を確かめる**。承認名を候補に入れるのは `uuid が消えている` かつ `その名前が在る` を両方確かめたときだけで、これが「改名が起きた」ことの確認になる。無いほうは `removeSession` が「無かった」と告げて終わる。

不採用の理由だった「実行が作ったものだけを消すという不変条件が緩む」は、その確認によって保たれる。**緩むのは切り替える案のほうだった。**

## Risks / Trade-offs

- **[承認が不可逆で、取り違えると実プロジェクトを壊す]** → 既定を proposal 止めにする。消すのはこの実行が作ったものに限り、名前も道具が握っているものだけを使う
- **[steering の完了をいつまで待つか決まらない]** → 既存の `ROUND_TIMEOUT_MS` と同じ枠で待ち、超えたら未着地として落とす。進捗は claude の呼び出しが増えたかで見せ、止まっているのか進んでいるのかを表す

  **数え方が変わった**（2026-08-30）。当初は「`debugLogDir` の**ファイル数**の増加」で見るつもりだったが、`adr0016-sub-update-debug-log-per-session` 以降、ログは**セッションごとに1ファイルへ追記**されるのでファイルは増えない。ファイル数で見ていると、2往復目からは実行が終わっても気付けず必ず時間切れまで待つ（実測 2026-08-30: `settle` が毎回「実行の終了を確認できないまま答える」に落ちていた）。呼び出しの回数は `# <日時>` の見出し行の本数で数える（`logEntryCount`）。

  `ROUND_TIMEOUT_MS` の値も固定の4分ではなくなり、`claude.timeoutMs + claude.timeoutStepMs × claude.maxRetries` から導く（`adr0016-sub-add-timeout-to-config`）。既定では従来と同じ4分になる。
- **[flontier で `get-steering` が必ず 500 になる]** → 本 change では直さない。**承認後の steering 工程で成功経路が通るのかどうかは、この道具ができて初めて確かめられる**。500 のまま着地しないなら、それはこの道具が明らかにした事実として報告する。**現時点でこの症状を扱う change は存在しない**ので、観測結果は本 change の報告に残し、切り出しは別途判断する

  **未起票であることを確認した**（2026-08-30）。`fix-steering-tool-stage-error` は change にも ticket にも実在しない（`openspec/changes/` と `openspec/tickets/` を走査。`steering` を含むのは `adr0016-sub-create-steering-guidance-mcp-tool` と `move-conventions-to-steering` の2件だけで、どちらも別件）。**500 を観測した場合の引き取り先が無い。** その場合はこの change で起票する
- **[dev が不安定で、承認経路でも画面が固まりうる]** → 既存の吸収（開き直し・画面の取り直し）を承認後の待ちにも適用する

## Migration Plan

道具の変更のみで、アプリのコード・API・仕様には影響しない。ロールバックはオプションを渡さなければよい（既定の挙動は変わらない）。

## Open Questions

- steering 工程の着地を「3文書すべてが揃った」で見るか、「1つでも書かれた」で見るか。**`get-steering` の成功経路が一度も通っていない**ため、実機で1周させるまで実態が分からない。実装時に観測して決める（判定の緩さを変えるだけで、specs・approach・タスクの分割は動かない）
