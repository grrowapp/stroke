# 子 change の担当への共通の指示（親 change `fix-server-api-layout`）

あなたは親 change `fix-server-api-layout` の子 change を 1 本担当する。渡されるのは change-id・Gitea issue 番号と本文・worktree の path。この文書の指示は、渡された issue の本文と同じ重みで守ること。

## 最初に読むもの（必ず。読む前に何も書かない）

1. `<worktree>/CLAUDE.md` — 前提・Dev サーバー・Worktree 運用・repo 直下のフォルダの扱い
2. `<worktree>/docs/agents/issue-tracker.md` — change / ticket / artifact / 参照の方向 / 更新対応 / 進捗と検証
3. `<worktree>/docs/agents/ticket-tracker.md` — ticket の `status`・`origin`・エージェント主体の起票
4. `/opt/projects/stroke-board/openspec/config.yaml` — artifact を書く前に読むもの、tasks のルール（先頭 2 タスク・末尾 2 タスク・santa-method）
5. `<worktree>/CONTEXT.md` — 用語。artifact でドメイン概念を指すときはこの用語を使う
6. `<worktree>/docs/specs/api/overview.md`・`server.md` と、issue が「基準」に挙げるページ — **基準。一切書き換えない**
7. `/opt/projects/stroke-board/openspec/changes/fix-server-api-layout/proposal.md`・`design.md` — 親の決め（Decisions の各節）

## 場所の決まり

- **コードは worktree（`<worktree>`）で触る。** ブランチ名は change-id。`cd` せず絶対パスで扱う
- **openspec の artifact・ticket は親 `/opt/projects/stroke-board/openspec/` に書く。** worktree に `openspec/` は無い（sparse checkout で除外）。`openspec` コマンドは `--store stroke` を付ける
- 起動・テストは `package.json` の scripts 経由（`yarn test` / `yarn typecheck` / `yarn test:e2e`）。3000・5000 は使わない。E2E は空きポートを自動で取る。dev サーバーは要らない。起動したものは必ず止める
- repo 直下に新しいフォルダを作らない

## 触らないもの（全 issue 共通）

- `docs/specs/api/overview.md`・`docs/specs/api/server.md`
- issue の「スコープ外」「触らないもの」に挙がっているもの
- `docs/specs/plan/*`・`docs/adr/*`（当時の記録）
- 他の子 change の担当範囲（issue の番号で分かれている）

## docs の書き換え

issue が「関連 docs」として挙げたページだけ。**design.md に書き換え案（現状 → 追従後）を書き、親がユーザーの承認を取るまで docs を書き換えない。** 承認は親から伝える。

## 進め方

1. `/openspec-ff-change <change-id>` の手順で proposal → specs → design → tasks を揃える（change と ticket は親が起票済み。`.openspec.yaml` は親が置く）。proposal の grill は、issue の本文で決まっている事柄を聞き直さない。決まっていない設計上の決め（handler の粒度や名前など）だけを親に問う
2. tasks.md は `openspec/config.yaml` のルールどおり: 先頭 2 タスク（ticket `Doing`・`tags` に `<change-id>/<セッション ID>`）、末尾 2 タスク（commit・完了承認 → `Wait-for-archive`）、その直前に santa-method レビュー。**末尾の「ユーザーから完了承認」は親が PR のマージで代行する**ので、その 1 つ手前まで進めて親に報告する
3. `/openspec-apply-change <change-id>` の手順で tasks を最後まで。**issue の「完了条件」を自分で確かめてから**報告する
4. commit は worktree のブランチへ。メッセージは既存の流儀（`fix: …（change-id）` の形）。`Co-Authored-By` の行は付けない
5. `git push -u origin <change-id>` してから、`tea pr create --login grrow --repo grrowapp/stroke --base pre3 --head <change-id> --title "<commit 題>" --description "<issue 番号・change-id・完了条件の確認結果>"` で PR を出す。**マージはしない**
6. 親に報告するもの: PR の URL、完了条件の確認結果、santa-method の結果、docs 書き換えの有無、残った懸念

## やってはいけないこと

- 基準の docs を直す。issue の範囲を超えて直す。旧 path の互換を残す
- `develop`・`main`・`pre3` に直接コミットする
- 親の `openspec/` にある他の change の artifact を書き換える
- 完了条件を確かめずに「完了」と報告する
