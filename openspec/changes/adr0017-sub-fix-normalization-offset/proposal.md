# adr0017-sub-fix-normalization-offset

## Why

承認レビューで付けた指摘が、文書によっては**黙って別の場所に付く**。

`app/pages/projects/[projectId]/approvals/[approvalId].vue:60` の `source` は本家から取得した文書の中身そのもの（生文字列）で、それが整形して読む面（`MarkdownView`）にも、指摘の基準にもそのまま渡っている。ところが整形の側が通る `parseMarkdown` は、内部で **CRLF を LF へ潰し、front matter を落としてから**解析する。DOM に載る位置の印は正規化後の文字列を指し、渡した生文字列とは基準が食い違う。

**食い違っても `null` にはならない。切り出しと描かれた字がたまたま揃えば照合を素通りして、別の場所を返す。** 実測の反例が2つある（`test/modules/markdown/runtime/position/edge-cases.test.ts`）。

- CRLF: 3つめの段落の `x`（生ファイルの 15）を選ぶと、2つめの段落の `x`（10）が返る
- front matter: 本文の `**b**` の `b`（生ファイルの 19）を選ぶと、front matter の `a: b` の `b`（7）が返る

本家が返す文書に CRLF も front matter も**含まれうる**。本家は `readFile` / `writeFile` で素通しし、改行を触るコードが `dist` に0件で、文書を書くのは人間か別のエージェントである。アプリ側にも正規化は0件（実測）。「来ない前提」で済ませてよい入力ではない。

先行 `adr0017-sub-create-position-port-preview` は「位置は面に渡された文字列の先頭を基準とする」を定めたが、**改行や front matter を誰が揃えるかは意図的に定めていない**。いま揃える者が居ないので、この基準は型のドキュメントに書かれているだけで実際には成立していない。塞ぐのが本 change である。

**保存された指摘を誰が読むかを調べた**（決めの根拠になるため）。

- 本家のサーバー・MCP・ファイル層は、オフセットを**数値として一切解釈しない**。`grep` で `startOffset` / `endOffset` が0件。保存は受け取った配列を丸ごと代入して JSON へ書き出すだけで、本家自身の型（`ApprovalComment`）にこの2つのフィールドは存在しない。つまり**不透明なペイロード**として素通しされている
- MCP の `approvals` tool は `annotations` 文字列と `comments` 配列をエージェントへそのまま渡す。オフセットも一緒に渡るが、解釈する処理は無い。**エージェントが実際に位置を知る手がかりは引用文字列（`selectedText`）である**
- **オフセットを文書に当てる処理は、系全体で本家ダッシュボードの SPA に1つだけ在る。** コメント配列と本文文字列を受け、範囲が妥当なら `startOffset` / `endOffset` を、妥当でなければ `content.indexOf(selectedText)` を使う。**そこで渡される本文は、生のファイルをそのまま読んだものである**（本家の本文 API は正規化しない）
- ただしその SPA が読むのは送信前のブラウザ内の状態だけで、ディスクへ書かれた後の指摘を読み戻す処理は本家にもストローク側にも無い

**つまり今は誰も読んでいないが、系の中で唯一オフセットを文書へ当てる実装は、生ファイルを基準にしている。**

急ぐ理由が2つある。

- **指摘のオフセットは本家へ送られて保存される。** 座標の基準は外へ出る契約であり、決めずに実装が進むと、後から直しても既に保存された値は直らない
- 後続 `adr0017-sub-create-module-annotation` は、整形された本文の面でも指摘を付けられるようにする。いま**指摘の面（`AnnotateSource`）は生文字列の座標、整形の面は正規化後の座標**で、2つの面の座標系が食い違ったまま合流する

## What Changes

**決めが2件ある。本 change はまずそれを決める。**

- **指摘のオフセットは、本家から取得した文書の中身そのもの（生文字列）を基準に保存する。** 正規化後の座標では保存しない
- **食い違いを吸収するのは面の内側である。** 呼ぶ側は取得した文字列をそのまま渡してよく、揃えるという手続きを持たない

その上で次を行う。

- **整形された本文の面が、渡された文字列と `parseMarkdown` が実際に解析した文字列との対応を内側で持つ。** 位置を答えるときは対応を通して、渡された文字列の座標に直してから返す。逆方向（座標から範囲を引く）も対応を通す
- **対応は推測で作らない。** 実際に正規化した文字列と突き合わせて作り、作れない入力に対しては対応が取れないものとして扱う（`null`）。黙って別の場所を返す経路を残さない
- **`sourceShown`（図に生テキストを添える範囲）も同じ対応を通す。** これは外から渡る `SourceRange[]` で、フェンス側は DOM の印（正規化後の座標）と突き合わせている。片方だけ直すと、ここが新しい食い違いの置き場になる
- **面は渡された文字列を書き換えない。** 正規化するのは位置を突き合わせるためだけで、表示にも保存にも正規化後の文字列を使わない
- `e2e/fixtures/upstream-stub.mjs` が CRLF を含む文書と front matter を持つ文書を返せるようにする。いまは `\n` 直書きのみで、この2件を一切カバーしていない
- CRLF と front matter を含む文書で、指摘が正しい位置に付き、正しい座標で本家へ渡ることを E2E で固定する

**対象外**

- **呼ぶ側で正規化して渡す形。** 「呼ぶ側が忘れずにやる」は、この epic 全体が潰そうとしている黙って壊れる形そのものである。加えて front matter を落とした文字列を指摘の面に渡すと、**レビュアーが front matter に指摘を付けられなくなる**。承認の対象は文書全体であり、見えなくしてよい部分ではない
- **保存の経路。** 承認画面は対象文書をその場で直せる。正規化後の文字列を保存に回すと、本家のディスク上のファイルから CRLF と front matter が消える。本 change は保存に渡る文字列に触らない
- **注釈そのものの作り直し。** 指摘を別のモジュールへ切り出すのも、整形の面から指摘を付けられるようにするのも `adr0017-sub-create-module-annotation` が持つ。本 change は座標の基準を揃えるところまで
- **生テキストの面（`MarkdownSource`）と指摘の面（`AnnotateSource`）の実装変更。** どちらも渡された文字列をそのまま並べており、既に渡された文字列の座標で答えている。直す先は整形の面だけである
- 「口」という語の一括置換（既存のコードコメントと spec に残る。別 change）

## Capabilities

`skip_specs: true` にはしない。**決めた2件がどちらも外から見える振る舞いだからである。** 保存されるオフセットの基準は本家へ出て行く契約であり、面が食い違いを吸収するかどうかは「呼ぶ側が何を渡してよいか」を変える。実装を差し替えても変わらない約束なので、要件として残す。

### New Capabilities

なし。

### Modified Capabilities

- `markdown/module`: 要件を1本足す。**面は、渡された文字列と自分が内部で解析に使う文字列との食い違いを、自分で吸収しなければならない**。先行 change が定めた「位置は面に渡された文字列の先頭を基準とする」は基準だけを決めており、揃える責務を誰も持たないため、いまの実装は要件を満たしていないのに検知されない
- `project/ui`: 要件「承認対象の文書に箇所を指した指摘を付けられる」に、**オフセットの基準が本家から取得した文書の中身そのものであること**を加える。現行は「生テキストに対する文字オフセット」としか定めておらず、レンダリング後の HTML でないことしか縛っていない

**`markdown/module` は `openspec/specs/` にまだ存在しない。** 親 change `create-module-markdown` のデルタで ADDED されるもので、親は未 archive である。先行 `adr0017-sub-create-position-port-preview` と同じ扱いとし、delta は `## ADDED Requirements` で書く。既存要件の書き換えではなく別名の要件を足す形にして、2つの delta が同じ要件名で衝突しないようにする。したがって本 change は親より先に archive できない。

## Impact

**コード**

- `modules/markdown/runtime/position/preview.ts` — 渡された文字列と解析された文字列の対応を作り、両方向とも対応を通して答える。現行の「渡す前に揃えるのは呼ぶ側の責任」という注記はここで反転する
- `modules/markdown/runtime/position/`（新規1本）— 対応そのもの。正規化した文字列と、正規化後 ↔ 渡された文字列 の写像を返す純関数
- `modules/markdown/runtime/render/MarkdownView.vue` — `sourceShown` を対応で写してから `provide` する
- `modules/markdown/runtime/position/types.ts` — 「誰が揃えるかは未定」の但し書きを、決まった内容へ置き換える

**触らないコード**（食い違いの原因ではないことを確かめた上で残す）

- `app/pages/projects/[projectId]/approvals/[approvalId].vue` — 生文字列のまま渡す形が正しくなる。**この change の成果は、ここに手を入れずに済むことである**
- `app/composables/useAnnotations.ts` / `app/components/review/AnnotateSource.vue` — 既に渡された文字列の座標で持っている
- `modules/markdown/runtime/render/MarkdownSource.vue` / `position/plain.ts` — 解析を通らないので食い違いが起きない

**テスト**

- `test/modules/markdown/runtime/position/edge-cases.test.ts` — 「生ファイルを渡すと黙って別の段落を指す」2本は、**通ることが正しくなくなる**。現象を固定したテストなので、直った側を固定する形へ書き換える
- `test/modules/markdown/runtime/position/`（新規）— 対応そのものの単体テスト
- `e2e/fixtures/upstream-stub.mjs` — CRLF と front matter を持つ承認対象文書
- `e2e/approval-annotation.spec.ts` — CRLF と front matter の文書で指摘が正しい座標で本家へ渡ること

**資料**

- `docs/specs/core/file-composables.md` の「注釈は生テキストへの文字オフセット……で持つ」— 上位資料への整合反映。design.md で提案し、ユーザー承認を経てから触る

**依存**

## 私が取った決め（未承認の仮定）

このセッションではユーザーへの grilling を行っていない。**次の決めは私が取ったもので、ユーザーの承認を得ていない。** 差し戻す場合はこの表の行を指すこと。

| 件 | 決め | 理由 |
| --- | --- | --- |
| 6.11.1 保存する座標 | **生ファイルの座標**（本家から取得した文書の中身そのもの） | 調べた結果、いまオフセットを数値として読む処理は本家にもストローク側にも無い。**唯一オフセットを文書へ当てる実装（本家ダッシュボードの SPA）は生ファイルを基準にしている。** 正規化後の座標を保存すると、その基準と食い違う値がディスクに残る。しかも front matter が落ちた分だけ値は小さくなるので、あちらの妥当性の判定（長さの範囲内か・開始が終了より前か）を通ってしまい、**弾かれずに別の場所が塗られる**。読み手が居ないことは、こちらの都合で基準を選んでよい理由にならない |
| 6.11.2 正規化を行う場所 | **面の内側**。かつ返す座標は渡された文字列の基準へ戻す | 「呼ぶ側が忘れずにやる」形を消すのがこの epic の目的である。内側で正規化するだけで座標を戻さないと、先行 change が定めた「渡された文字列を基準とする」に反し、呼ぶ側が別の対応表を持つ羽目になる |
| 対象外の線引き | 保存（編集した文書の PUT）には正規化を持ち込まない | 正規化後の文字列を保存すると、本家のディスク上のファイルから CRLF と front matter が消える。位置合わせの都合で他人のファイルを書き換えない |
| 指摘の面に渡す文字列 | 生文字列のまま（front matter を隠さない） | 承認の対象は文書全体である。front matter を落とした文字列を見せると、そこに指摘を付ける手段が消える |
| specs を作るか | **作る**（`skip_specs` にしない） | 保存座標の基準は本家へ出て行く契約、吸収の責務は「呼ぶ側が何を渡してよいか」を変える。どちらも実装を差し替えても変わらない約束である |
| `markdown/module` の delta の書き方 | `## ADDED Requirements` で別名の要件を足す | ベースの spec が `openspec/specs/` にまだ無い（親が未 archive）。既存要件を `MODIFIED` で書き換えると、先行 change の delta と同じ要件名で衝突する |
| ADR を起こすか | **起こさない。design.md で提案するに留める** | 外へ出る契約なので ADR 相当だが、ADR は会話を経て決めるものであり、私が独断で立てるものではない |
