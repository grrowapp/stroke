## Context

動機は `proposal.md` の Why、振る舞いの契約は `specs/project/ui/spec.md` を参照。

approach を縛る現状は3つ。

**1. 決める操作が2箇所に散っている。** 承認と却下は承認一覧のカード（`ApprovalCard.vue`）にあり、差し戻しは対象文書を読む画面（`ApprovalAnnotator.vue`）の右サイドバー最下部にある。読んで判断した場で終わらせられるのは差し戻しだけである。

**2. 却下の理由がカードの下に開く欄になっている。** 上の「却下」は入力欄の開閉を反転するだけで、送信は下の「却下する」が行う。送信が成功すると欄が閉じて一覧を取り直すが、**成功したことを示す表示が無い**。押した人からは「閉じただけ」に見える。上のボタンが押すたびに開閉するのも、送信ボタンに見える一因である。

**3. 承認一覧から対象文書へは `NuxtLink` で遷移している。** `approvals/index.vue` が `:to="/projects/:projectId/approvals/:approvalId"` を持ち、一覧を離れる。

**すでに使える前例がある。** ストロークの入口は「一覧から入った先を、オーバーレイ上のモーダルとして画面全体に出す」形で作られている（`app/layouts/stroke.vue`、ADR 0009・0010）。**開閉の状態を持たず、どの場面に居るかは URL が持つ。** リロードすれば同じ場面が開き直る。この形をそのまま承認へ持ち込める。

## Goals / Non-Goals

**Goals:**

- 読んで判断した場で、承認・即時却下・差し戻しのすべてを終わらせられるようにする
- 送った結果が押した人に分かるようにする
- 決める操作を1つの並びに集める

**Non-Goals:**

- 機能そのものを変えない。承認・却下・差し戻しが本家へ何を送るか、サーバーの経路は今のままである
- 承認依頼の URL を捨てない。その場で開くことと URL で指せることは両立させる
- 注釈を付けられる面は変えない。それは `adr0017-sub-create-module-annotation` が扱う

## Decisions

### 決定1: 承認依頼はルート付きのモーダルで開く

`app/layouts/` にモーダルの器を持つ layout を用意し、`approvals/[approvalId].vue` にそれを指定する。一覧（`approvals/index.vue`）はそのまま `NuxtLink` で遷移させる。

**なぜ:** ストロークが既にこの形である（`layouts/stroke.vue`）。器だけを layout が与え、中身と流れは変えない。**開閉の状態を component に持たせない**ので、URL とは別に「どれを開いているか」を持つ二重化が起きない。

ストロークとの違いは閉じられることである。承認は途中で読むのをやめてよいので、`dismissible` と `close` を立て、閉じたら一覧へ戻す。ストロークは最後まで行く前提なので閉じる道を持たないが、ここは事情が違う。

**代替案1: 一覧のページ内に詳細の状態を持ち、URL を変えない** — 承認依頼を URL で指せなくなる。通知から承認画面へ飛ぶ経路（`project/ui` の「通知の対象を下層の画面で開く」）が壊れる。採らない。

**代替案2: 一覧と詳細を1つのページに畳む** — `approvals/[approvalId].vue` が消え、ルーティングで表せていた「どれを開いているか」を自前の状態で持つことになる。採らない。

### 決定2: 決める操作は面の切替と同じ帯に置く

承認・即時却下・差し戻しを、対象文書の見え方を切り替える segmented control と同じ行へ移す。右サイドバー最下部の差し戻しボタンは無くなる。

**なぜ:** 本家がその形である。加えて、決める操作が本文のスクロールに巻き込まれない位置に固定される。現状の差し戻しは右サイドバーの下端にあり、コメントが増えると押しに行くのに探すことになる。

右サイドバーはコメントの一覧と「全体へのコメント」を持つ場所として残す。**コメントを付けることと、決めることを分ける。**

### 決定3: 却下の理由は既存のコメントモーダルと同じ形にする

`CommentModal.vue` は `defineModel('open')` で開閉を受け、`save` を emit し、保存すると自分で閉じる。却下の理由もこの形にする。

共通化するかは実装時に決める。**共通化を先に決めない**のは、コメントモーダルが色の選択と引用の表示を持ち、却下の理由が持たないためである。無理に1つにすると、使わない口を持つ部品になる。

**送った結果を示すことは、モーダルとは別の要件である。** モーダルにしただけでは「閉じただけ」に見える問題は消えない。送信後にその旨を出す（`notification-toast` が既にある）。

### 決定4: 「即時却下」への改称は表示だけに閉じる

画面に出る文言だけを変える。本家へ送る `action`（`reject`）、`data-testid`、サーバーの経路はいずれも変えない。

**なぜ:** 送る中身が変わっていないのに識別子を変えると、本家側のログや E2E の掴み所が意味なく動く。**利用者に見える名前と、系に流れる名前を分けて考える。**

## Risks / Trade-offs

**モーダルにすると対象文書が読みにくくなる** → 承認の対象は仕様書や設計であり、長い。`fullscreen` で画面全体を使う（ストロークと同じ）。狭い箱に押し込めない。

**閉じたときの戻り先** → 一覧へ戻す。ただし一覧のどこを見ていたかが失われると、依頼が多いときに探し直しになる。スクロール位置の扱いを実装時に確かめる。

**決める操作を上の帯に集めると、押し間違いが起きやすくなる** → 承認と即時却下が隣り合う。即時却下は理由の入力を挟むので取り消せるが、承認は1押しで確定する。並びと間隔を本家に合わせ、承認だけが突出しないようにする。

**`adr0017-sub-create-module-annotation` と同じ画面を触る** → あちらは注釈を付けられる面を増やし、並列表示を落とす。**この change を先に通す。** 逆順だと面の並びを2度直すことになる。

## Migration Plan

1. モーダルの器となる layout を用意し、`approvals/[approvalId].vue` に指定する。この時点で見た目が変わるので、`e2e/workspace.spec.ts` の承認まわりを合わせる
2. 決める操作を面の切替と同じ帯へ移す。差し戻しを右サイドバーから抜き、承認・即時却下を足す
3. 却下の理由をモーダルにする。送信後に結果を示す
4. 文言を「即時却下」に変える（表示のみ）
5. `e2e/approval-annotation.spec.ts` に、対象文書を読む画面から却下できることを足す

1 と 2 は独立している。3 は 2 の後（却下ボタンが対象文書の画面に出てから）。
