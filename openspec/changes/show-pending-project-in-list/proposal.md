## Why

承認はプロジェクトを作る唯一の引き金であるのに、承認した本人が「作られた」ことをその場で確かめられない。承認処理はセッションディレクトリをプロジェクト名へ改名するだけなので、**プロジェクトの実体は承認した瞬間に存在している**。にもかかわらず一覧の母集合は `.spec-workflow/` を持つディレクトリに限られており、そこを作るのは承認後に裏で走る steering の claude である。結果として、モーダルを閉じて一覧へ戻ったユーザーが見るのは、さっきまでと変わらない一覧である。

承認が通ったのか、名前が衝突したのか、裏の起動に失敗したのかを、画面から区別する手段が無い。ユーザーにできるのは再読み込みを繰り返すことだけになる。見に行かずに気づけるようにするのがこのプロダクトの目的（`product.md` の Purpose）である以上、自分が起こした変化の結末だけが見に行かないと分からない、という状態を残さない。

## What Changes

- **一覧の母集合に「生成中のプロジェクト」を加える。** 昇格済み（`state.json` の `phase: 'approved'`）でありながら `.spec-workflow/` をまだ持たないディレクトリを、生成中のプロジェクトとして一覧に載せる。承認の直後からこの条件を満たすため、一覧へ戻った時点で必ず行が在る
- **生成中の行は一覧の最下部に置く。** 並びは アクティブ → 未接続 → 生成中 とする
- **生成中であることを、ボケ・回転するローダー・行全体の明滅の3つで示す。** 他の行より不透明度を落とし、状態の位置に回転するローダーを置き、あわせて行全体をゆっくり明滅させる
- **生成中の行は選択できない。** 未接続と同じく、押しても何も起きず、キーボードのフォーカスも受けない。まだ入れる中身が無いためである
- **作成が完了したら、生成中の表現を外して通常の行に変える。** 完了の判定は既存の完了判定をそのまま使う——`invokeAi` が子プロセスの出力で検知して `invocation` を `running` から `idle` へ変えるもの（`docs/specs/plan/portal-stroke-exit.md`「完了とリトライ」）。新しい判定を作らない
- **完了したとき、そのプロジェクトについて一度だけ、一覧の上で祝う。** 「プロジェクト `<name>` の作成が完了しました！」を出す。求められているのは文言よりも**質感**である。次の4つを満たすこと。
  - **一覧の行（バー）の中に押し込まない。** 行に収まる大きさの表示ではない
  - **画面遷移もしない。** 今いる一覧の上で完結する
  - **弾けて、出て、消える。** 速すぎず、かといって次の操作を待たせない速さで、メッセージとアニメーションが出て、そのまま引く
  - **画面の占有率も上の速度感と釣り合う大きさにする。** 行より大きく、画面を覆うほどではない

  既存のトーストには載せない（あれは本家由来の通知4種のためのもので、1行のテキストに限る仕様である）
- **作成が最終的に失敗したときは、失敗として見せる。** `invocation: 'error'`（リトライ上限に達した終端）に至った行は、生成中の表現を止め、作成に失敗したことが分かる行に変える。回り続ける行を放置しない

### 届け方 — 既にある WS に載せる

一覧は今、画面が開いたときに1回だけ取得している（定期実行しない、が `tech.md` の Performance Requirements）。開いたまま出現・完了・失敗を捉えるには契機が要る。**定期取得は足さない。既にある WS に載せる。**

- **上層が既に張っている board WS（`/ws`）にメッセージ型を足す。** 新しい endpoint を立てない。`useBoardSocket` は `createSharedComposable` でアプリ全体に1本なので、接続は増えない
- **接続時の `snapshot` に、生成中のプロジェクトを載せる。** board WS には接続直後に今の分を流す規約が既にある。「一覧を開いた時点で既に生成中のもの」はこれで賄い、この change のために別の仕組みを作らない
- **board WS の位置づけを「本家通知の中継」から「上層へのサーバー発イベントの口」へ改める。** 中身は今すべて `UpstreamMonitor` 由来だが、stroke-board 自身が起こしたイベントも同じ口で運ぶ

### WS の増やし方を規約として置く

WS を使うなら、これは付随作業ではなく前提である。今は**イベントを1つ足すたびに endpoint と registry を1本ずつ生やす**形になっており、その増やし方こそが直す対象である。

現状、2つの体系は「サーバ→画面の一方向」「接続の瞬間に今の分を流す」までは既に同じで、割れているのは増やし方だけである。

| | board `/ws` | ストローク W1 / W2 |
|---|---|---|
| 口の数 | 1本。**メッセージの type で分ける** | **イベントごとに1本**（`question` / `proposal`） |
| 束ね方 | `peers: Set<Peer>` | `createRegistry()` をチャネルの数だけ複製 |
| 接続時配信 | `snapshot` を送る | route が session-store を読んで1件送る |

規約として次を置く。

- **新しいイベントのために新しい WS endpoint を立てない。** 既にある接続にメッセージ型を足す
- **束ね方の実装は1つにする。** `createRegistry()` と board の `peers` は同じものである。キーを持つ／持たないの違いに畳み、2つ書かない
- **接続の瞬間に今の分を流すことを、実装ごとの慣習ではなく規約として書く**

破壊的変更は無い。既存のプロジェクトの見え方と入場、W1 / W2 の振る舞いは変わらない。

## Capabilities

### New Capabilities

- `ws/delivery`: WS 配信の規約。サーバ→画面の一方向であること、接続の瞬間に今の分を流すこと、**新しいイベントのために新しい endpoint を立てないこと**、束ね方の実装を1つに保つこと。今まで board 側とストローク側がそれぞれの慣習として持っていたものを、1箇所の規定にする

### Modified Capabilities

- `project/directory`: 次の4つの要件が変わる
  - 「プロジェクトの母集合を親パスの走査で作る」— `.spec-workflow` を持たないディレクトリは拾わない、という規定に、昇格済みで生成中のものを載せる例外が加わる
  - 「アクティブを上、未接続を下に並べる」— 最下部に生成中が加わる
  - 「一覧は4つの列を持つ」— 状態の値に「生成中」と「作成に失敗」が加わる
  - 「未接続のプロジェクトは選択できない」— 生成中と失敗の行も選択不可の対象になる
- `project/generation`: **作成の進行と結末を見せることを、この capability に加える。** 別の capability を新設しない。今は昇格（改名）の手順だけを持っているが、承認から steering の完了までは1つの生成の過程であり、その過程がユーザーにどう見えるかを別の場所に置くと、同じ1つのことが2箇所に分かれる。加える要件は次の3つ。
  - **生成中であることを見せる** — 昇格した瞬間から、完了するまで。一覧の最下部・ボケ・ローダー・明滅・選択不可
  - **完了を見せる** — 生成中の表現を外し、そのプロジェクトについて一度だけ祝う
  - **失敗を見せる** — 終端の失敗に至った行を、失敗として見せる

`api/session/ws`（W1 / W2 の endpoint 規定）は変えない。既にある2本の振る舞いはそのままで、`ws/delivery` はその上に増やし方の規範を置くだけである。`api/contract`（応答コードの規約）も変えない。

**`replace-polling-with-push` との関係。** あの change は失敗の配信のために W3 という4本目の endpoint を立てる計画で、`ws/delivery` の「新しい endpoint を立てない」に正面から反する。**この change を先に通し、あちらは W1 / W2 の接続にメッセージ型を足す形へ書き換える**必要がある。あちらは 0/30 で未着手なので、書き換えの費用は今なら小さい。

## Impact

**サーバー**

- `server/api/projects.get.ts` — 走査の結果に、生成中のプロジェクトを重ねて返す
- `server/utils/control/directory.ts` — 生成中を含めた並びと状態の組み立て
- 判定の材料は既に在る。`listSessionsCore`（`server/utils/stroke/session-core.ts`）が保存先の直下を列挙し、`phase` と `invocation` と `path` を返している。新しい保存や登録簿は作らない（`project/directory` の「一覧を永続化しない」を維持する）

**画面**

- `app/pages/projects/index.vue` — 生成中の行、完了時の祝い、失敗の行
- `app/composables/useBoardSocket.ts` — 足したメッセージの受け口
- `shared/types` — `ProjectSummary` に生成中・失敗を表せる形を足す。`BoardMessage` の union にメッセージを足す

**WebSocket**

- `server/utils/control/board.ts` — 生成の進行を broadcast する口を足す。`snapshot` に生成中のプロジェクトを載せる
- `server/utils/stroke/ws-channels.ts` と `board.ts` の束ね方 — 2つある実装を1つに寄せる
- `server/api/strokes/[id]/approve.post.ts` と、完了・失敗を書いている箇所 — 書いた後に broadcast する
- `openspec/specs/notification-feed` — board WS が本家由来の通知だけを運ぶ、という前提が変わる
- `docs/specs/api/contract.md` — WS 配信の記述。W1 / W2 と board を1つの規約の下に並べ直す

**未決（design で決める）**

- **同じ名前が両方に出る間の扱い。** 完了を `invocation: 'idle'` で判定するため、`.spec-workflow/` が先に現れて走査に載り、まだ `idle` になっていない時間帯が生じる。名前で重ね、その間は生成中を優先する想定だが、規定として置く
- **祝いの表示を、既存のモジュールで賄えるか。** ユーザーは「クラッカーを鳴らすようなアニメーションのモジュールでいいものがあれば、それを使うのが一番いい」と述べている。自前で書く前に、まず既存のものを当たる。`docs/specs/plan/components-library-replacement.md`（ライブラリ置換の方針）と揃える
- **祝いの表示の寸法・速度・消え方の具体値。** 満たすべき質感（行に押し込まない／画面遷移しない／弾けて出て引く／占有率が速度感と釣り合う）は What Changes に置いた。何 ms でどこまで出すか、閉じられるか、アニメーションを抑える設定（`prefers-reduced-motion`）にどう従うかは、実物を出して見せながら決める

**仮定（specs で確定させる）**

- 「一度だけ」は、**完了の瞬間を見ていたブラウザに対して一度**とする。サーバーに既読を持たず、再読み込みや後から開いた場合には出さない。既存のトーストが「初回ロードで過去分をトーストにしない」と定めているのと同じ考え方に揃える

## 対象外（これも AI の判断であり、未承認）

- steering が完了した後の流れ（承認待ちの発生と通知）— 既存の仕組みに乗るだけで、新設しない
- 失敗した作成の再実行の口 — リトライは既存のサーバーの巡回が持つ。画面から起こし直す操作は足さない
- 承認処理そのもの（改名・steering の起動・巡回）の変更

**この proposal はまだ何も承認されていない。** 以下は「誰の言葉から来たか」の区別であって、確定した決定の一覧ではない。
