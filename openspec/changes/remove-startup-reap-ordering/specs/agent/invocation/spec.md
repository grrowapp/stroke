## ADDED Requirements

### Requirement: 起動時の後始末と巡回は、互いの完了を待たない

システムは、起動時の後始末と定期巡回（`portal/batch`）の間に、呼び出し順序についての取り決めを持たない SHALL。一方が他方の完了を待ってはならない（MUST NOT）。待ち合わせのための仕組み（門・フラグ・シグナルなど、処理どうしを同期させる機構）を設けてはならない（MUST NOT）。

二重起動を防いでいるのは、**対象1件ごとの順序**である——後始末は、走っている claude の終了を確かめてから `invocation` を `failed` へ変える SHALL。確かめられなければ `failed` へ変えず `error` へ変える（本 capability の別の Requirement が規定する）。巡回は `invocation` が `failed` の対象だけを拾い、`running` の対象には触れない（`portal/batch`「巡回は failed だけを拾って起動し直す」「running・idle・error は拾わない」）。したがって、ある対象が `failed` になるのは、その対象の孤児の終了を確かめた後だけであり、巡回がいつ走っても、後始末がまだ `failed` へ変えていない対象（`running` のまま）が起こし直されることはない。処理どうしの順序を取り決める必要はない。

#### Scenario: 後始末の完了を待たずに巡回が動く

- **GIVEN** 起動時の後始末がまだ完了していない
- **WHEN** 巡回の最初の周回が走る
- **THEN** 巡回は後始末の完了を待たず、その時点で `invocation` が `failed` の対象だけを拾って起動し直す。後始末がまだ `failed` へ変えていない対象（`running` のまま）は拾われない

#### Scenario: 順序の取り決めを追加しない

- **WHEN** 起動時の後始末または巡回を実装・変更する
- **THEN** 互いの完了を待ち合わせる仕組みは設けない。二重起動の防止は、後始末が対象ごとに終了を確かめてから `failed` を書くという順序だけで足りる
