## Purpose

WebSocket を乱暴に切られたときに開発用サーバーが止まらないことを、その場で確かめる口を規定する。この停止は開発用サーバーでしか起きず、ビルド済みの出力を立てる E2E では再現しないため、通常のテストとは別の確認手段が要る。

## ADDED Requirements

### Requirement: 動いている開発用サーバーへ異常切断を当てて生死を判定する

確認の口は、動いている開発用サーバーに対して WebSocket の異常切断を当て、その後もサーバーが応答するかを判定する SHALL。判定は応答の有無だけで行い、内部の作りを見てはならない。

当てる対象は、接続時に配信を持つチャネルと持たないチャネルの両方とする。停止はチャネルの種類によらず起きるため、片方だけでは確認にならない。

行儀のよい切断では症状が出ないため、確認は接続を**閉じる挨拶なしに落とす**形で行う SHALL。

#### Scenario: 止まらない

- **WHEN** 動いている開発用サーバーへ、各チャネルに対する異常切断を繰り返し当てる
- **THEN** 全て当て終えた後もサーバーは応答し、確認は成功として終わる

#### Scenario: 止まる

- **WHEN** 異常切断の途中でサーバーが応答しなくなる
- **THEN** 確認は失敗として終わり、どのチャネルで止まったかが分かる

#### Scenario: サーバーが動いていない

- **WHEN** 開発用サーバーが動いていない状態で確認が実行される
- **THEN** 確認は成功も失敗も名乗らず、先にサーバーを起こす必要があることが伝わる

### Requirement: 確認が症状を捉えていることを検められる

システムは、症状を防いでいる詰め物を外した状態で開発用サーバーを起こせる口を持つ SHALL。詰め物を外せば確認は失敗しなければならない。

これが無いと、確認が緑であることが「症状が起きない」ためなのか「確認が症状を捉えていない」ためなのか区別できない。

#### Scenario: 詰め物を外して確かめる

- **WHEN** 詰め物を外した状態の開発用サーバーに対して確認を実行する
- **THEN** 確認は失敗する

#### Scenario: 外しても失敗しなくなった

- **WHEN** 詰め物を外しても確認が失敗しない
- **THEN** 上流で直ったか、確認が症状を捉えなくなったかのどちらかであり、確認の作り直しか詰め物の撤去を検討する合図とする
