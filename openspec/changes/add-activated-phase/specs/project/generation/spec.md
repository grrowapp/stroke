## ADDED Requirements

### Requirement: 完成した状態を記録する

システムは、承認で昇格したプロジェクトについて、**steering が成果物を出し終えた状態を記録しなければならない（SHALL）**。承認しただけの状態と、完成した状態を、同じ値で表してはならない（MUST NOT）。

システムは、この状態を**成果物の有無を確かめてから**立てなければならない（SHALL）。エージェントのプロセスが終了したことを、完成の根拠にしてはならない（MUST NOT）——プロセスは何も作らずに正常終了しうる。

#### Scenario: steering が成果物を出して終わる

- **WHEN** 承認したプロジェクトで steering が走り、成果物ができている
- **THEN** そのプロジェクトは完成した状態として記録される

#### Scenario: エージェントが何も作らずに正常終了する

- **WHEN** 承認したプロジェクトで steering のエージェントが起動し、成果物を1つも作らずに正常終了した
- **THEN** そのプロジェクトは完成した状態にならない

#### Scenario: 承認しただけのプロジェクトを見る

- **WHEN** 承認は済んだが steering がまだ終わっていないプロジェクトを見る
- **THEN** 完成した状態とは区別できる

### Requirement: 行と決着は同じ状態を根拠にする

システムは、一覧の行が示す生成の状態と、決着として配信する結果を、**同じ状態から導かなければならない（SHALL）**。一方をファイルシステムの走査から、他方をエージェントの実行状態から導いてはならない（MUST NOT）。

根拠が2つあると、同じプロジェクトについて行と決着が食い違う。実測 2026-08-30、行は走査で「完了」、配信はプロセスの終了で「完了」を出し、成果物が無いまま完成として扱われた。

#### Scenario: 行と決着を突き合わせる

- **WHEN** あるプロジェクトについて、一覧の行の状態と、そのとき配信された決着を見比べる
- **THEN** 2つは矛盾しない

#### Scenario: 成果物が無いまま実行が終わる

- **WHEN** 承認したプロジェクトでエージェントの実行が終わったが、成果物が無い
- **THEN** 一覧の行も決着も、完成としては扱わない

### Requirement: 実行の失敗は失敗として届く

システムは、steering のエージェントがエラーで終わったとき、**それを失敗として上層へ届けなければならない（SHALL）**。失敗を、決着が起きなかったものとして黙らせてはならない（MUST NOT）。

ユーザーには、失敗に対して次を選ぶ手段が要る。作りかけのまま画面から見えなくなる状態を作らない。

#### Scenario: エージェントがエラーで終わる

- **WHEN** 承認したプロジェクトで steering のエージェントがエラーで終わる
- **THEN** 失敗が上層へ届き、ユーザーは次の行動を選べる

#### Scenario: 失敗のあとで選ぶ

- **WHEN** 失敗が届いた
- **THEN** ユーザーは「やり直す」か「破棄する」かを選べる

## MODIFIED Requirements

### Requirement: 生成の進行は、開いている一覧へ届く

システムは、生成の開始・完了・失敗を、既にプロジェクト一覧を開いている画面へ届けなければならない（SHALL）。利用者に再読み込みを求めてはならない（MUST NOT）。

システムは、そのために一覧を繰り返し取得してはならない（MUST NOT）。配信は `ws/delivery` の規約に従う。

配信が運ぶのは**決着したという合図**であって、行の状態そのものではない（SHALL）。受け取った画面は一覧を取り直し、行の内容はサーバーの判定に従う。

届ける合図は、**記録された状態の変化を根拠とする（SHALL）**。エージェントの実行状態そのものを合図の材料にしてはならない（MUST NOT）——実行が終わったことと、生成が決着したことは別である。

#### Scenario: 一覧を開いたまま承認が行われる

- **WHEN** プロジェクト一覧を開いている状態で、別の画面から proposal が承認される
- **THEN** 一覧を再読み込みしなくても、生成中の行が最下部に現れる

#### Scenario: 一覧を開いたまま完了する

- **WHEN** プロジェクト一覧を開いたまま生成が完了する
- **THEN** 一覧を再読み込みしなくても、その行が通常の行に変わる

#### Scenario: 何も起きていない間

- **WHEN** 生成中のプロジェクトがある状態で、何の出来事も起きない時間が続く
- **THEN** 画面からサーバへの繰り返しの取得は発生しない

#### Scenario: 実行が始まっただけのとき

- **WHEN** エージェントの実行が始まった
- **THEN** それだけでは決着として届かない

### Requirement: 生成中か完了かは記録された状態だけで判定する

システムは、昇格したプロジェクトが生成中か完了かを、**記録された状態だけ**で判定しなければならない（SHALL）。生成中は承認から完成までの区間の内側であり、その両端はいずれも1点の書き込みである。

システムは、**本家がプロジェクトルートとして読むディレクトリの有無を、この判定の材料にしてはならない（MUST NOT）**。そのディレクトリは本家の MCP サーバーが接続した瞬間に作るものであって、ステアリングを作り終えた印ではない。実測 2026-09-01、そのディレクトリができてから最初のステアリング文書が書かれるまでに37分の開きがあり、その間プロジェクトは完了として一覧に並び、接続の判定の対象にもなり、下層へ入場できた。

システムは、AI の呼び出しの実行状態を、**完了**の判定の材料にしてはならない（MUST NOT）。実行状態は永続値として記録される一方、その見張りは実行中のプロセスの中にしか無く、プロセスが失われると実行中のまま誰も戻さない。加えて、エージェントは成果物を1つも作らずに正常終了しうる（実測 2026-08-30）。

システムは、走査の結果を**プロジェクトの母集合を作るためだけ**に使う SHALL。行の状態の判定に使ってはならない（MUST NOT）。

システムは、完了を測るための判定・告知の口・突き合わせの仕組みを、この目的のために新設してはならない（MUST NOT）。

この判定に厳密さを求めない（SHALL NOT）。数秒の遅れ、および取りこぼしを埋めるための作り込みを行ってはならない（MUST NOT）。表示は、次に一覧を取得し直した時点で必ず正しくなればよい。

#### Scenario: 生成が完了する

- **WHEN** 承認後に走った生成が成果物を出し終え、完成した状態が記録される
- **THEN** そのプロジェクトは生成中ではなくなり、通常のプロジェクトとして一覧に並ぶ

#### Scenario: 本家のディレクトリだけができる

- **WHEN** 承認後に本家の MCP サーバーが接続し、プロジェクトルートのディレクトリができたが、ステアリングはまだ1本も無い
- **THEN** そのプロジェクトは引き続き生成中として出ており、完了として扱われることも、接続の判定の対象になることも無い

#### Scenario: 生成中に画面を移って戻る

- **WHEN** 生成中のプロジェクトがある状態で別の画面へ移り、プロジェクト一覧へ戻る
- **THEN** その行は引き続き生成中として出ている

#### Scenario: 完了の瞬間を取りこぼす

- **WHEN** 完了の瞬間の配信が届かないまま、後で一覧を取得し直す
- **THEN** そのプロジェクトは生成中ではない状態で出ている

#### Scenario: 実行状態の記録が実行中のまま残る

- **WHEN** 生成の実行を記録したプロセスが失われ、実行状態が実行中のまま残った
- **THEN** そのプロジェクトの生成中か完了かは、実行状態ではなく記録された状態から導かれる
