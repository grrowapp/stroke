# add-activated-phase — tasks

区間はこの形で確定している。

```
approved ──────────── 生成中 ────────────> activated
 [承認後]                                    [提出後]
```

書く主体と契機は決まっている。

```
誰が   invokeAi（claude のプロセスを終了まで握っている）
いつ   プロセスが終わり、結果を判定した時点
どう   承認 API を phase 付きで叩く。新規 endpoint を生やさない
```

## 1. 契約を決める

- [ ] 1.1 承認 API が phase を受け取る形を決める。**任意の phase を書かせない。** 受け取れる遷移を限るか、遷移そのものを引数にするか
- [ ] 1.2 ADR-0014 に照らす。判定の材料が契約から読めることを確かめる
- [ ] 1.3 「初回の承認依頼の提出」をどう見分けるか決める。2回目以降に書き直しても実害が無いなら、初回に限らない形でもよい
- [ ] 1.4 `CONTEXT.md` に用語として足す。「生成中」は既にあるが、その終わりを指す言葉が無い
- [ ] 1.5 `docs/specs/api/contract.md` の承認（U10）の記述を、phase を受ける形に合わせて直す

## 2. phase の値を1箇所に閉じる（先にこれ）

いま値の集合が4箇所にある。値を足す前に閉じておかないと、足すたびに全部を触ることになる。

- [ ] 2.1 `shared/stroke.ts` の `Phase` を、値の一覧を1つ持つ形にする。型はそこから導く
- [ ] 2.2 `server/handler/phase.ts` の `readPhase` から `=== 'stroking' || === 'proposed' || === 'approved'` の連鎖を外し、2.1 の一覧に照らす形にする
- [ ] 2.3 `session-store.ts` の zod を、リテラル3本の列挙から 2.1 の一覧を使う形にする
- [ ] 2.4 **判定は述語で表す。** `isBeforeApproval` / `isAfterApproval` に倣い、イコール比較を呼び出し側へばら撒かない
- [ ] 2.5 ここまでで振る舞いが変わっていないことを確かめる（値はまだ3つのまま）

## 3. `activated` を足す

- [ ] 3.1 2.1 の一覧に `activated` を足す
- [ ] 3.2 既存の `state.json` に `activated` は無い。読めない値として弾かれないこと、既存のプロジェクトが `approved` のまま読めることを確かめる
- [ ] 3.3 述語を見直す。`isAfterApproval` が `activated` を含むか、別の述語が要るかを決める。**削除の口2つがこの述語で分かれている**ので、含め方を誤ると消せる/消せないが変わる

## 4. `invokeAi` から書く

- [ ] 4.1 承認 API が phase を受け取れるようにする（1.1 で決めた形）。**新規 endpoint は生やさない**
- [ ] 4.2 `invokeAi` の成功の分岐（`ai.ts:112-123`）から、承認 API を叩いて `activated` を書く
- [ ] 4.3 **何を以て「出し終えた」とするかを決める。** steering の承認依頼が提出されたことをどう確かめるか（`.spec-workflow/approvals/` に現れたか、提出の呼び出しが通ったか）
- [ ] 4.4 steering の起動にも `didWork` を渡す。**いまストローク側にしか渡っておらず**（`invoke.ts:148`）、未指定は `ai.ts:120` で素通りする。素通りしている限り、空振りの正常終了が成功の分岐へ落ちる
- [ ] 4.5 判定に失敗したとき `activated` を書かないことを確かめる。**書けないときに黙って成功へ倒さない**

## 5. 決着の判定を phase に移す

- [ ] 5.1 `creationOutcomeOf` から `invocation` を外し、phase を見る形にする
- [ ] 5.2 `server/utils/control/directory.ts` の行の `creation` を phase から引く。走査は母集合を作るためだけに使う
- [ ] 5.3 **行と配信が同じ根拠を見ていることを確かめる。** 同じプロジェクトで2つが食い違わないこと
- [ ] 5.4 `session-store.ts` の「`invocation` を合図の材料に使っても…」のコメントを、実態に合わせて書き直す

## 6. 失敗の応答

- [ ] 6.1 claude がエラーで終わったとき `invocation` を `error` に倒す経路が実際に通ることを確かめる。**いまは `error` を立てる者がいない**
- [ ] 6.2 `error` が W3 の失敗として配信され、モーダルが「やり直す / 破棄する」を出すところまで通す
- [ ] 6.3 `invocation` は失敗の応答に専念させる。成功の判定材料に使っている箇所が残っていないことを確かめる
