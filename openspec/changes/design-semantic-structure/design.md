## Context

現状のディレクトリは、意味ではなく**種類**で切れている。`server/utils/` は平置き15本で名前は機能名の羅列、`app/components/` は `stroke/` `review/` と直下が混在し、区分の基準が書かれたものが無い。

統合すると、この木の上にマージ先の資産が同居する。詳細は proposal を参照。

判断の材料は揃っている。

- **入口は既に決まっていた。** マージ先の `/projects` には **作成** ボタンが実装済みで、非活性の理由が `target-undecided`（実処理を担う接続先の別プロジェクトに繋がっていない）として画面に出る。入口だけ先に置いて実処理を別プロジェクトに任せる形になっていて、その別プロジェクトがこちらである
- **`.scratch/stroke-board-frontier/decisions.md` が2件を既に決めている。** 実行環境のパスに `frontier` を持ち込まないこと、承認後のセッションディレクトリのクリーニングを MVP に入れないこと
- **`CONTEXT.md` が語彙を持っている。** ストローク / 概要 / 設計ツリー / フロンティア / 把握完了 / proposal / 差し戻し / 承認 / プロジェクト

## Goals / Non-Goals

**Goals:**

- 統合したときに相手と席を奪い合わない状態にする
- 統合時の確認を「名前空間が被っていないか」の判断に落とす

**Non-Goals:**

- **マージ先の区分に合わせない**（ADR 0002）。あちらが何回組み替えても、こちらの設計は動かない
- **振る舞いを変えない。** 公開する口の数も、受理・拒否の条件も動かさない
- **名前空間の内側を切らない。** 統合に要らない（決定2）。判断材料として棚卸しだけ残す
- **統合を妨げないものは扱わない。** 置き場の要求の強さ、起動時チェックの振る舞いは `docs/known-issues.md` へ

## Decisions

### 決定1: 領域名を `stroke` の1語に定め、全ディレクトリで一貫して使う

こちらの資産は、Nuxt が規約で決めている各ディレクトリの下で、**`stroke` という1語の名前空間に閉じる**。

```
app/pages/strokes/            画面
app/components/stroke/        画面の部品
app/composables/stroke/       画面のロジック
app/layouts/stroke.vue        画面の殻
server/api/strokes/           endpoint
server/routes/api/strokes/    WebSocket
server/utils/stroke/          サーバー側の実装
shared/stroke.ts              画面とサーバーが共有する型
```

**マージ先が何を使っていようが、`stroke` を使わない限り被らない。** これが「意味で切れば名前は自然に分かれる」の実装である。相手の区分を知る必要が無く、相手が組み替えても影響を受けない。

語の選定は `CONTEXT.md` の第一項目「ストローク」による。この製品の中核概念であり、マージ先の語彙（プロジェクト / 承認依頼 / タスク / ステアリング文書 / 本家）と重ならない。

_代替案1_: `session`。実装用語であってドメイン用語ではない。`CONTEXT.md` に載っていない。
_代替案2_: `frontier`。`.scratch/decisions.md` が「実行時のディレクトリ名には持ち込まない」と決めている。
_代替案3_: 領域名を持たず、機能ごとに個別の名前を付ける。相手と被らないことを1つずつ確認する必要が生まれ、確認が終わらない。

### 決定2: 名前空間の内側は切らない

`server/utils/stroke/` の中も、`app/components/stroke/` の中も、**今の並びのまま移す**。区分を作らない。

切り方の案は検討した。`server/utils/` を「何に触るか」（外部プロセス / ファイルシステム / 形だけ / プロセスのメモリ / 設定）で5つに分ける案、`app/components/` をページで分ける案。どちらも成り立つが、**統合には要らない**。

名前空間が分かれていれば席は奪い合わない。内側がどう並んでいても、相手からは見えない。統合のために動かす範囲を、統合に要るところだけに絞る。

内側の切り直しは、必要になったときに別の change で扱う。判断材料として現状の棚卸しを `docs/file-composables.md` と `docs/file-components.md` に残す。**棚卸しであって規則ではない**と明記してある。

_代替案_: この change で内側まで切る。統合の準備と内部の整理を一度に済ませられるが、切り方の判断は統合とは無関係に難しく、統合を止めてまで決める理由が無い。動かす量が増えれば壊す危険も増える。

### 決定3: 画面のパスは `/strokes/` の下に置き、`/` は持たない

```
/strokes                  概要入力（セッション開始前）
/strokes/<uuid>           画面1（ストローク）
/strokes/<uuid>/proposal  画面2（proposal 確認）
```

`/` は持たない。マージ先が通知画面として使っている。

**入口は `/projects` の作成ボタンである。** ユーザーが `/strokes` を直接開くことは想定するが、導線としては作成ボタンから入る。ポータルのタブ（通知 / プロジェクト一覧）は増やさない——増やすと、まだ何も無い状態の「作りかけ」がタブとして常設されることになる。

endpoint も同じ形にする。

```
POST /api/strokes            概要の投稿（旧 /api/overview）
GET  /api/strokes            一覧（旧 /api/sessions）
GET  /api/strokes/<id>/…     取得・提出・起動（旧 /api/<id>/…）
     /api/strokes/<id>/ws/…  WebSocket
```

これで `/api/` 直下の動的セグメントの占有が解ける。マージ先の `/api/projects/…` と同じ空間に重ならない。

**BREAKING**: 旧パスは残さず、互換のための転送も置かない。エージェント向けスキル6本は接続先を `STROKE_BASEURL` から組み立てているので、サーバーとスキルが同時に変われば繋がったままになる。

### 決定4: 置き場の非対称を、要求の強さとして明示する

`/opt/projects` は、こちらが**書き込む**先であり、マージ先が**読む**先でもある。同じディレクトリに対して要求の強さが違う。

| 置き場 | 誰が | 要求 |
|---|---|---|
| `/var/lib/stroke-board/sessions` | ストローク側だけ | 書き込み |
| `/opt/projects` | ストローク側（承認時に生成） | 書き込み |
| `/opt/projects` | ポータル側（一覧の母集合として走査） | 読み取り |

**この change では扱わない。** 席の奪い合いではないので、統合を妨げない。要求が満たされないときにプロセスごと落ちる件と併せて、`docs/known-issues.md` が持つ。

ここに記すのは、統合後に `/opt/projects` へ両側から異なる強さで手が伸びる、という事実の確認までとする。

### 決定5: セッションの寿命は変えない

承認後もセッションディレクトリは残す。誰も自動では片付けない。

`.scratch/stroke-board-frontier/decisions.md` が「承認後のセッションディレクトリのクリーニングは MVP に入れない」と決めており、`project-generation` にも「セッションディレクトリは承認後も削除しない SHALL」として入っている。統合はこの前提を変えない。

片付ける手段は既にある（`GET /api/strokes` で一覧し、削除の口と script がある）。統合によって新しく必要になるものは無い。

### 決定6: 実行時の同居を、割り切りの明示で扱う

統合後は1プロセスが `claude` を spawn しながら、ポータルの配信も回す。`claude` の呼び出しは最大 180 秒 × 3 試行かかる。

**spawn は非同期で、イベントループを塞がない。** 起動要求は応答の完了を待たずに受理を返して完結する仕様（`api/invoke-agent`）になっており、待つのは呼び出し側ではなくタイムアウト監視である。したがってポータル側の配信が止まることはない。

ただし実行中フラグ・提出到着の通知・WS 接続の束ねは、いずれも**単一プロセスであること**を前提にした割り切りの上に立っている（コードのコメントに「単一プロセスの MVP なので」と書かれている）。統合してもプロセスは1つなので前提は保たれる。

### 決定7: `frontier` は実行時にも文書にも残さない

`.scratch/stroke-board-frontier/decisions.md` は「`frontier` はドキュメント上で本 MVP を識別するための呼称であり、実行時のディレクトリ名には持ち込まない」と決めている。実行時には元々存在しない。

統合すると、別走していたものを識別する必要が無くなるので、**文書上の呼称としても不要**になる。製品は `stroke-board` 1つで、その中の領域が `stroke` である。

`package.json` の `name`（`stroke-board-frontier`）は統合時に畳まれる。

### 決定8: アプリ全体に1つだけ在るものは、領域に属さない

`app/app.vue`（アプリの殻）、`app/assets/css/main.css`（全体に効くスタイル）、`nuxt.config.ts`、`package.json`、`tsconfig.json`、`server/plugins/` は、どの領域にも属さない。統合後も1つずつしか無い。

`app/app.vue` はマージ先のものを土台とし、こちらが持っていた殻は `app/layouts/stroke.vue` へ移す。**画面の殻は領域ごとに持てるが、アプリの殻は1つしか持てない**という区別による。

これらのファイルの衝突は設計では消せない。統合時に手で畳む対象として、`docs/mainline-merge.md` の「未決の論点」が持つ。

### 決定9: 資料は `docs/structure.md` に置く

決定1〜8を、**新しいものが来たときに参照される形**で書き出す。「なぜその配置なのか」を記し、配置そのものは実体が持つ。

`CLAUDE.md` の Docs 一覧に足す。

## Risks / Trade-offs

**[`stroke` が領域名として広すぎる]** → `CONTEXT.md` の「ストローク」は1往復を指す語で、領域全体を指すには意味が広がる。ただし領域名は「その製品の何についてのものか」を示すもので、`stroke` はこの製品の中核概念そのものである。代わりに、コード内で1往復を指すときは `Stroke` 型を使い続けて区別する。

**[内側を切らないまま統合すると、後で切りにくくなる]** → 切りにくさは増えない。名前空間の中は相手から見えないので、統合の前に切っても後に切っても同じ作業になる。むしろ統合を止めて切り方を決めるほうが、判断の材料（統合後に何がどう使われるか）が揃わないまま決めることになる。

**[パスの変更でエージェントが繋がらなくなる]** → スキル6本は `STROKE_BASEURL` から組み立てているので、サーバーとスキルを同じ change で変えれば繋がったままになる。ただし**変更中に走っている呼び出しは生き延びない**。統合作業中に実行中のセッションを持たないこと。

**[マージ先が `stroke` を使い始める]** → 今は使っていないことを確認済み（あちらの語彙はプロジェクト / 承認依頼 / タスク / ステアリング文書 / 本家）。使い始めれば衝突するが、それは意味区分が被ったということなので、統合時の確認（`docs/mainline-merge.md` の「衝突の測り方」）で検出できる。
