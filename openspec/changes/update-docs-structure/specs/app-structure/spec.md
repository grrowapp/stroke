## MODIFIED Requirements

### Requirement: 階層を表すディレクトリでモジュールを分ける

`app/components/` の配下は、**構造の規範（`docs/specs/core/system-structure.md`）が定める区切り**で分けられていなければならない（SHALL）。

コンポーネントを `app/components/` の直下に、区切りのディレクトリを介さず直接置いてはならない（MUST NOT）。

**`app/composables/` は本要件の対象外である。** composable は関心単位の `useXxx` を `app/composables/` の直下に平置きし、区切りのディレクトリを作ってはならない（MUST NOT）。正は規範の「composables は関心単位の `useXxx` を平置きにする。境界のディレクトリを作らない」。

**区切りの名前をこの spec が持たない。** 構造の正は `docs/specs/core/system-structure.md` であり、そこが到達点を定める。ここに現状の区切りの名前を書くと、到達点へ動かす作業がそのたびにこの spec に反することになる。この spec が持つのは、**どう判定するか**だけである。

#### Scenario: 下層からだけ使うコンポーネントを追加する

- **WHEN** 単一の範囲からのみ参照されるコンポーネントを追加する
- **THEN** そのファイルは規範が定める、その範囲に当たる区切りのディレクトリに置かれる

#### Scenario: 階層をまたいで使うコンポーネントを追加する

- **WHEN** 複数の範囲から参照されるモジュールを追加する
- **THEN** そのファイルは規範が定める、共有に当たる区切りのディレクトリに置かれる

#### Scenario: 階層ディレクトリを介さない配置

- **WHEN** `app/components/Something.vue` のように区切りのディレクトリを介さずファイルが置かれている
- **THEN** その配置は本要件に反しており、いずれかの区切りへ移す対象になる

#### Scenario: composable を追加する

- **WHEN** どの範囲から参照されるかによらず composable を追加する
- **THEN** そのファイルは `app/composables/useXxx.ts` として直下に置かれ、区切りのディレクトリは作られない

#### Scenario: 規範の区切りが変わる

- **WHEN** `docs/specs/core/system-structure.md` が定める区切りが変わる
- **THEN** この spec を書き換えずに、新しい区切りへ移す作業が行える

### Requirement: 配置は実際の参照範囲に従う

本要件は `app/components/` の配下に置かれるコンポーネントに適用する。`modules/` に置かれるものは本要件の対象外であり、その配置は「画面の階層に属さない機能は `modules/` に置く」の判定に従う（SHALL）。`app/composables/` は区切りで分けないので、本要件の対象外である。

`app/components/` の配下では、コンポーネントの置き場所は、そのモジュールを実際に参照しているファイルの範囲によって決めなければならない（SHALL）。役割・名前・将来の想定によって決めてはならない（MUST NOT）。

単一の範囲からのみ参照されているモジュールを、複数の範囲から参照されるものの置き場に置いてはならない（MUST NOT）。複数の範囲から参照されているモジュールを、単一の範囲の置き場に置いてはならない（MUST NOT）。どの置き場がどの範囲に当たるかは規範が定める。

#### Scenario: 参照範囲が単一階層に閉じている

- **WHEN** あるモジュールの参照元が単一の範囲に閉じている
- **THEN** そのモジュールはその範囲の置き場に置かれ、共有の置き場には置かれない

#### Scenario: 参照範囲が広がった

- **WHEN** 単一の範囲に置かれているモジュールが、別の範囲からも参照されるようになる
- **THEN** そのモジュールは共有の置き場へ移され、参照元の import パスが更新される

#### Scenario: 参照範囲が狭まった

- **WHEN** 共有の置き場にあるモジュールの参照元が、単一の範囲だけになる
- **THEN** そのモジュールはその範囲の置き場へ移される

#### Scenario: 複数の階層から参照される自己完結の機能

- **GIVEN** ある機能が複数の範囲から参照されており、画面の階層に依存せず、公開する口が定まっている
- **WHEN** その置き場所を決める
- **THEN** 共有の置き場ではなく `modules/<機能名>/` に置かれる

## ADDED Requirements

### Requirement: 構造の正はひとつに定める

構造の正は `docs/specs/core/system-structure.md` でなければならない（SHALL）。この spec と規範が食い違った場合、規範が優先される（SHALL）。

同じ対象について、区切りの名前や配置の到達点を2箇所で別々に定めてはならない（MUST NOT）。

規範と現状の差は `docs/specs/plan/structure-migration.md` が持つ。**差があること自体は、この spec に反しない。**

#### Scenario: 構造の判断に迷う

- **WHEN** ファイルの置き場所に迷う
- **THEN** `docs/specs/core/system-structure.md` を読めば決まる

#### Scenario: 規範と現状に差がある

- **GIVEN** 現状の配置が規範の到達点と違う
- **WHEN** その差を確かめる
- **THEN** `docs/specs/plan/structure-migration.md` に移行課題として載っており、差があること自体は違反ではない

### Requirement: テストは写し元の構造に従う

単体テストは、写し元のソースの構造をそのまま写した位置に置かなければならない（SHALL）。写し元がモジュールへ移った場合、テストも追随しなければならない（SHALL）。

**写し元を持たないテストは、その旨が分かる場所に置く（SHALL）。** 採用しなかった選択肢を記録するテストのように、対応するソースが存在しないものがある。それを写し元があるものと同じ場所に混ぜてはならない（MUST NOT）。

#### Scenario: ソースをモジュールへ移す

- **WHEN** `app/` にあったソースを `modules/` へ移す
- **THEN** そのテストも `test/modules/` 配下の対応する位置へ移る

#### Scenario: 写し元の無いテスト

- **WHEN** 採用しなかったライブラリの挙動を記録するテストを置く
- **THEN** 写し元があるテストとは別の場所に置かれ、対応するソースが無いことが分かる
