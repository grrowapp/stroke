# Design — restructure-app-directories

## Context

動機は proposal.md — Why を参照。ここでは設計判断に必要な現状だけを挙げる。

- 画面の階層は `layouts/` と `pages/` に既に現れている。上層は `layout: 'portal'` の2ページ（`/`、`/projects`）、下層は `layout: 'workspace'` の10ページ（`/projects/:projectId/**`）。シェルの形も横タブと左サイドバーで変えてある。
- `nuxt.config.ts` が `imports: { autoImport: false }` と `components: { dirs: [] }` を設定しており、auto-import は完全に無効。全モジュールが `~/...` の明示 import で参照されている。
- したがってディレクトリ移動は Nuxt の名前解決に影響しない。影響範囲は import 文を書いているファイルだけで、grep で網羅できる。
- 移動時点で作業ツリーには `implement-portal-mvp` の未コミット変更が29ファイル分あった。

## Goals / Non-Goals

**Goals:**

- モジュールの所属階層をディレクトリ名だけで判別できるようにする
- 配置の判断基準を、参照元の実測という検証可能な形で固定する
- 移動を完全に巻き戻せる形（`git mv` によるリネーム追跡）で行う

**Non-Goals:**

- モジュールの中身を改善すること。移動と import パスの書き換え以外は行わない
- `pages/` と `layouts/` の再編。ここは既に階層を表現できており、触る理由が無い
- `server/` の再編。`server/utils/control/` と `server/utils/upstream/` は既に層で分かれている
- 上層のコンポーネントを新設して構造を対称にすること

## Decisions

### 切り分けの軸に階層を選んだ

**選択肢**

1. **階層軸**（`shared/` / `workspace/`）— `layouts/` と `pages/` が既に持っている区切りを `components/` と `composables/` にも通す
2. **ドメイン軸**（`specs/` / `steering/` / `tasks/` / `approvals/`）— 画面の機能単位でまとめる
3. **移動せず、ドキュメントだけで見える化する**

**選んだのは 1。** 理由は3つ。

- 参照元の実測がそのまま階層に一致していた。`useProjectApi` は下層9ページのみ、`useSteeringDocuments` は steering 2ページのみ、`useBoardSocket` と `useRelativeTime` は上層・下層の両方。振り分けに判断の余地が無く、境界を引き直す必要がない。
- 2 はドメイン専用のモジュールがほぼ存在しない。ドメインに紐づくのは `ApprovalCard` だけで、`WorkspacePanel`（下層9ページ）・`RecordList`（4ページ）・`DocumentView`（3ページ）はいずれもドメインをまたぐ共有部品である。ドメインで切ると大半が「共有」に落ち、集合として意味を成さない。
- 2 は `pages/` を `features/` 配下へ動かすことになり、Nuxt のファイルベースルーティングから外れる。ルーティングの再設定という、構造の見通しとは無関係のコストが乗る。

3 は差分ゼロで安全だが、要求は「配置したい」であり、資料だけでは配置は変わらない。なお構造資料そのものは別 change（`document-app-structure`）で作る。

### `ui/` と `notification/` を廃止して `shared/` に統合した

`ui/` は役割（見た目の部品）を、`notification/` は機能（通知）を表しており、軸が揃っていなかった。実測でも `SbIcon`（両レイアウト + 上層2ページ）、`UpstreamIcon`（下層3コンポーネント + Toaster + 下層1ページ）、`NotificationToaster`（`app.vue`）はいずれも階層をまたいでおり、両者を隔てる実態が無い。

3つとも「階層をまたぐ」という一点で共通するため `shared/` に集約した。将来 `shared/` が肥大したら、そのときは中で再分割すればよい。実体の無いうちから分けても、今回のように軸のずれた分類が残るだけになる。

### `components/portal/` を作らなかった

上層専用のコンポーネントが1つも実在しない。空ディレクトリは git で表現できず、`.gitkeep` を置いて対称性を作ると「上層にも専用部品がある」という誤った印象を与える。

上層が薄いのは現状の事実であり、構造はそれをそのまま示すべきである。この判断は spec の「実体を伴わないディレクトリを作らない」として要件化した。

### `components/workspace/` は移動しなかった

実測で6ファイルすべてが下層専用と確認できたため、既に正しい位置にある。動かす理由が無い。

### `git mv` を使い、中身を1行も変えなかった

未コミットの変更が29ファイル分ある状態での移動だったため、差分が「移動」と「編集」の混在にならないことを優先した。`git mv` ならリネームとして追跡され、巻き戻しも移動の逆操作だけで済む。

untracked だった `UpstreamIcon.vue` のみ通常の `mv`（git の管理下に無いためリネーム追跡の対象外）。

### import 書き換えを `sed` の一括置換で行った

7つの旧パスから新パスへの単純な文字列置換で、パスは十分に固有（`~/composables/useProjectApi` 等）であり誤爆の余地が無い。置換後に旧パスの残骸がゼロであること、および参照先ごとの件数内訳が移動前と完全一致することの2点で網羅性を確認した。

## Risks / Trade-offs

- **未コミットの変更と移動が同じ作業ツリーで混ざる** → `git mv` でリネームとして追跡させ、中身の編集を一切混ぜないことで、`git status` 上で移動と編集を区別できる状態にした。
- **`shared/` が「その他置き場」に堕ちる** → 「単一階層からのみ参照されるものを `shared/` に置いてはならない」を spec の要件にした。参照範囲が狭まったモジュールは階層側へ戻す。
- **参照範囲が変わったときに移動が必要になる** → モジュールを移す手間が定期的に発生する。これは配置が実態を反映し続けるための対価であり、意図した設計。auto-import を使っていないため移動コスト自体は grep で機械的に処理できる。
- **上層専用の部品が生まれたときに `portal/` を作り忘れる** → spec に「上層専用のコンポーネントが初めて追加されたとき `portal/` を作る」というシナリオを書いて、判断のタイミングを残した。

## Migration Plan

一度きりの移動で、段階的な移行は不要。ロールバックは `git mv` の逆操作と import 書き換えの逆置換で完結する。

検証は移動の前後で同じコマンドを走らせ、結果が同値であることを見た。

| | 移動前 | 移動後 |
| --- | --- | --- |
| `yarn typecheck` | exit 0 | exit 0 |
| `yarn test` | 106 passed | 106 passed |
| `yarn test:e2e` | 129 passed | 129 passed |

振る舞いを変えない change なので、テストが同値であることが正しさの根拠になる。新しいテストは追加していない。
