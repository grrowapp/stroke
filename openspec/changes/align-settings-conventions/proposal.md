# align-settings-conventions

## Why

サーバ側を全数洗い出したところ、**運用で変えたくなるのに再ビルドしないと変えられない値が 62 箇所**あった。うち明示的な定数は 31、残りはインラインのマジックナンバーと文字列である。

外出しされているのは `runtimeConfig.claude` の8つだけで、そこから漏れたものが実害を出している。

- **合わないとアプリが起動しない。** `SESSIONS_ROOT = '/var/lib/stroke-board/sessions'` と `PROJECTS_ROOT = '/opt/projects'` は起動時チェックが書き込み権限を必須にし、満たさなければ `process.exit(1)` で即死する。開発機・コンテナ・別ボリュームのいずれでも真っ先に変えたくなる値が、再ビルドでしか変えられない
- **AI の成功率に直結する。** 問いの閾値（`QUESTION_MAX = 20` など）を超えた提出は 400 で弾かれ、提出が届かないままリトライ経路へ落ちる。超過が続けば試行を使い切って `invocation: failed` に至る。最も頻繁に微調整したい値が固定されている
- **総待ち時間を制御できない。** `MAX_RETRIES = 2` はコード自身が「MVP の割り切りで設定値にしない」と書いている意図的な負債。`timeoutMs` だけ外出しされているため、最悪 3 試行 × 180 秒でセッションが約9分ふさがるのに、運用者はその長さを決められない
- **同じ値が2箇所に直書きされている。** ポート 3001 が `package.json` の `dev` と `apiBaseUrl` の二重管理になっていて、片方だけ変えるとエージェントだけが古い接続先を掴む

**統合すると、運用者が設定を1箇所で把握できなくなる。** 単一の Nuxt アプリになれば、運用者が向き合う設定も1組になる。そこに「外に出ている値」と「コードに埋まったまま外から見えない値」が混在すると、一覧を読んでも何が変えられるのかが分からない。書かれていないことが「変えられない」なのか「書き漏れ」なのかを、コードを読まないと判別できない。

## What Changes

**まず境界を引く。** `nuxt.config.ts` には性質の違う設定が混在していて、読んでもどちらか分からない。実測（`nuxt build` の出力で確認）で3層あることが分かっている。

| 層 | 例 | 実行時に変えられるか |
|---|---|---|
| `runtimeConfig` に宣言済み | `claude.timeoutMs` / `claude.model` | **変えられる**。`.output` に対して `NUXT_CLAUDE_TIMEOUT_MS` を与えると届き、不正なら起動が拒否される |
| ただの `const` | `SESSIONS_ROOT` / `PROJECTS_ROOT` | 変えられない。ただし `runtimeConfig` へ移せば変えられるようになる |
| ビルドが消費する設定 | `nitro.experimental.websocket` / `devtools` / `ignore` | **変えられない。移すこともできない** |

3層目が問題である。実行時に差し替えられるものと、ビルド時に決まって二度と変えられないものが同じファイルに並んでいて、どちらなのかを示すものが無い。このため「変えられない値を設定値だから外に出せる」と判断して無駄に検討する（この分類を決める過程で実際に起きた）、運用者が環境変数で変えようとしても何も起きず理由が分からない、といったことが起きる。

- **設定を、ビルド時に決まるものと実行時に差し替えられるものに区別して並べる。** どちらなのかがファイルを読んで分かる形にする
- **ビルド時に決まる設定には、なぜそれがビルド時なのかを添える。** `nitro.experimental.websocket` はビルドが消費するので `runtimeConfig` に置けない、といった理由を残す。後から「これも外に出せるのでは」と再検討させない
- **環境ごとに切り替えたい値がビルド時にあるなら、切り替えるにはビルドを分ける必要があることを明記する。** 今は `devtools` がこれに当たる

**そのうえで、実行時側を外に出す。**

- **設定値をコードに直書きしない。** 洗い出した全件を `runtimeConfig` へ出し、環境変数で実行時に差し替えられるようにする。再ビルドを要さない。対象は絶対パス、閾値、リトライ回数、ファイル名、prompt の文言、実行するバイナリ名とフラグ、CLI 出力の判定に使う値、正規表現、ログのプレフィックスまで含む
- **同じ値の二重定義をなくす。** 出どころを1つにし、参照側はそこを読む
- **外に出した値は起動時に検証する。** 直書きをやめる以上、誤った値が入る経路が増える。形をなしていない値で走り出さず、起動の時点で落とす。検証は値の形だけでなく、外部インターフェースとの整合が壊れると分かるものについては、それが分かる形で行う
- **検証はスキーマで表し、設定の型はそこから導く。** 手書きの条件分岐を各所に散らさない。既に `claude-config.ts` が `runtimeConfig.claude` を zod のスキーマで検証していて、`describeClaudeConfigError()` を起動時チェックが呼ぶ形になっている。同じ形を、外に出す値の全体へ広げる。型を別に書き起こすと検証と型が二重定義になるため、型はスキーマから導く
- **運用者に見える一覧を持つ。** マージ先が `.env.example` でやっているのと同じ形で、外に出した値を並べる

外に出す単位（1つの平たい設定にするか、`claude` のように意味ごとに束ねるか）と、各値の具体的な検証規則は design で確定する。読み口をマージ先の `server/utils/config.ts` と同じ「1箇所に閉じる」形にするかも design の判断とする。

## Capabilities

### New Capabilities

- `configuration`: 設定がどこで決まり、いつ変えられるかを規定する。両側を1つの capability に入れる。**ビルド時に決まる設定は作り直すまで動作に現れない**こと、**実行時に差し替えられる設定は再ビルドなしに差し替わり、差し替えられた値は起動の時点で検証され、不正なまま走り出さない**こと。設定値が動作を決めている以上、いつ変わるかは観測できる振る舞いである（WS を無効にして作り直せば、問いと proposal は画面へ配信されなくなる）

境界の両側を別々の capability に分けると、境界がどこにあるのかが2箇所に散って読めなくなる。

### Modified Capabilities

- `ai-invocation`: 既存の「起動設定は再ビルドなしで変更できる」は AI の起動フラグだけを対象にしている。同じ性質の規定が `configuration` に一般形で入るため、重複しないよう対象を整理する

## Impact

- `nuxt.config.ts` — `runtimeConfig` の追加
- `server/utils/paths.ts` — `SESSIONS_ROOT` / `PROJECTS_ROOT`
- `server/utils/ai.ts` — `MAX_RETRIES`
- `server/utils/question.ts` — 問いの構造の閾値6件
- `server/utils/claude-config.ts` — 既にあるスキーマ検証を、外に出す値の全体へ広げる土台
- `server/utils/request-schemas.ts` — リクエストの閾値17件
- `server/utils/session-store.ts` — セッション内のファイル名
- `server/utils/project.ts` — 生成先のディレクトリ名・ファイル名、名前規則
- `server/utils/claude.ts` — 実行バイナリ名、フラグ、子プロセスへ渡す環境変数名、タイムアウト時のシグナル、CLI の出力とメッセージの判定に使う値
- `server/utils/openspec.ts` — `openspec` のバイナリ名とサブコマンド
- `server/utils/prompt.ts` — prompt の固定文言2本
- `server/routes/` の WS — セッション id を抜く正規表現
- `server/utils/running.ts` — セッションあたりの同時実行数
- `server/plugins/00.startup-checks.ts` — 追加した設定の検証
- 各所のログのプレフィックス
- `package.json` — ポートの二重管理の解消
- `.env.example` — 新規。外に出した値の一覧
- `README.md` / `docs/session-workflow.md` — 設定できる値の記載

- `docs/adr/` — ビルド時と実行時の境界をどこに引くかは、後から変えにくい判断にあたる。ADR に残すかを design で判断する

**tasks の順序**: 境界を引くことを先に、外出しを後に置く。外に出す対象は境界の内側にあるものだけなので、境界が確定していないと対象が決まらない。

**前提**:
- `align-coding-conventions` — テストの安全網（62 箇所の値を読み口経由に付け替える書き換えは、型を通ったまま挙動だけ変わる）と、ポートの二重管理の解消。後者はそちらが先に片付け、ここでは一般形として引き取るだけにする

起動時チェックが `process.exit(1)` でプロセスごと落とす件は、統合とは別の不具合として `docs/known-issues.md` にある。設定の検証をどう扱うかはそれと関わるので、design で扱いを決める。

`remove-store-dependency` を前提としていたが、それは `add-session-management-command` に統合されて archive 済み（`e15494d`）。`storeId` は既に無く、セッションディレクトリの位置も確定している。

**この change に含めないもの**: 洗い出しで見つかった、設定値ではない不具合。プロジェクト名の連番採番が上限のない無限ループであること、コメントが実在しないファイル名を指していること、起動時チェックがプロセスごと落とすこと。いずれも `docs/known-issues.md` に記録済みで、統合とは別軸の修正として扱う。

なお、WS の URL からセッション id を抜く正規表現は設定値として外へ出すため、リバースプロキシでサブパス配信したときに接続が無言で閉じる問題は、この change の範囲で解ける。

**吸収した change**: `separate-build-time-settings`（ビルド時設定の区別）を畳んで取り込んだ。同じ capability `configuration` の境界の両側で、同じ `nuxt.config.ts` を触り、順番に実施するしかない。2本に割る理由が無く、割ると境界がどこにあるかが2箇所に散る。

**経緯**: この change は一度起こされた後（`d48df6a` ほか）、`e15494d` で archive されずに削除されている。統合の準備として立て直した。
