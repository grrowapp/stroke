## MODIFIED Requirements

### Requirement: 決着したら、知らせてから次を選ばせる

システムは、生成が決着したとき——成功でも失敗でも——**知らせる面**と**選ばせるモーダル**を順に出さなければならない（SHALL）。この2つは別のものとする（SHALL）。器は成功と失敗で同じとし（SHALL）、違うのは文言と選択肢だけとする。

**知らせる面**は次を満たす（SHALL）。

- 何が起きたかを伝える。成功は祝い、失敗は作りきれなかったこと
- そのプロジェクトの名前を含む
- **画面の半分くらいを埋める大きさとする**。小さすぎてはならず（MUST NOT）、画面全体を覆ってもならない（MUST NOT）
- **フェードアウトで自ら消える（SHALL）**。ユーザーの操作を要求してはならない（MUST NOT）——画面の半分を占める面が残り続けると、その間は何も操作できないためである
- **一覧の行の中に収めてはならない（MUST NOT）**
- **画面を遷移させてはならない（MUST NOT）**

**選ばせるモーダル**は、知らせる面が引いた後に出す（SHALL）。次を持つ（SHALL）。

| | 問い | 選択肢 | 選んだ後 |
|---|---|---|---|
| 成功 | ステアリングの結果をレビューするか | する | そのプロジェクトの承認画面へ移る。開ける対象が在れば、それを開いた状態で移る |
| | | しない | 一覧へ戻る |
| 失敗 | どうするか | やり直す | 一覧へ戻る。行は生成中に戻る |
| | | 破棄する | 一覧へ戻る。行は消える |

**成功の決着は、3本の steering 文書それぞれの承認依頼が本家に在ると確かめたときにだけ記録される**（`agent/invocation`「作業が行われたかの判定を工程ごとに持ち、完成の記録より先に問う」）。したがって成功の「する」で開ける対象は、決着の時点で在る（SHALL）。それでもユーザーが決着からモーダルを選ぶまでの間に承認を済ませて依頼が消えていることはありうるので、開ける対象が無いときは承認の一覧まで連れて行く SHALL——行き止まりにしてはならない（MUST NOT）。

モーダルは次のすべてを満たす（SHALL）。

- **画面を遷移させてはならない（MUST NOT）**。プロジェクト一覧の上で完結する
- **自ら消えてはならない（MUST NOT）**。ユーザーが選ぶまで閉じない。時間で引く形にしてはならない（MUST NOT）——決着は「見た」だけでは終わらず、次を選ぶところまでが1つの出来事である

システムは、知らせる面もモーダルも、既存の通知トーストとして出してはならない（MUST NOT）。トーストは本家由来の通知のためのもので、1行のテキストに限る形が定まっている。

決着を知らせるのは、**その瞬間を受け取った画面に対してだけ**とする（SHALL）。既に決着したプロジェクトについて、一覧を開き直した画面や、後から開いた画面に出してはならない（MUST NOT）。

#### Scenario: 一覧を見ている最中に完了する

- **WHEN** プロジェクト一覧を開いている最中に、生成中のプロジェクトの作成が完了する
- **THEN** その行から生成中の表現が外れて通常の行になり、あわせて完了を知らせる面が一覧の上に浮かび上がる

#### Scenario: 知らせる面を放っておく

- **WHEN** 知らせる面が出た後、何も操作しない
- **THEN** その面はフェードアウトして自ら消え、続いて選ばせるモーダルが出る

#### Scenario: モーダルを放っておく

- **WHEN** 選ばせるモーダルが出た後、何も操作しない
- **THEN** モーダルは消えず、選ぶまで残っている

#### Scenario: 成功でレビューを選ぶ

- **WHEN** 成功のモーダルで「する」を選び、開ける承認依頼が在る
- **THEN** そのプロジェクトの承認画面へ、その対象を開いた状態で移る

#### Scenario: 成功の決着の時点で承認依頼が在る

- **WHEN** 生成中のプロジェクトの成功の決着が届く
- **THEN** その時点で本家にはその3本の steering 文書の承認依頼が在る

#### Scenario: 成功でレビューを選ぶが承認依頼が無い

- **WHEN** 成功のモーダルで「する」を選ぶが、決着からその間に承認が済み、開ける承認依頼が1件も無い
- **THEN** そのプロジェクトの承認の一覧まで移る。行き止まりにはならない

#### Scenario: 成功でレビューしないを選ぶ

- **WHEN** 成功のモーダルで「しない」を選ぶ
- **THEN** モーダルが閉じてプロジェクト一覧に戻り、そのプロジェクトは通常の行として並んでいる

#### Scenario: 決着した後に一覧を開き直す

- **WHEN** 決着のモーダルを閉じた後、または決着した後に、プロジェクト一覧を開き直す
- **THEN** モーダルは出ない

#### Scenario: 決着より後に別のブラウザで開く

- **WHEN** 既に決着しているプロジェクトがある状態で、別のブラウザからプロジェクト一覧を開く
- **THEN** モーダルは出ない

### Requirement: 昇格したプロジェクトを本家に存在させるのは生成の依頼だけであり、AI のプロセスではない

システムは、昇格したプロジェクトを本家 spec-workflow に存在させる（本家の一覧に載せ、`.spec-workflow/` を持たせる）手段として、**生成の endpoint（`api/project/generate`）による本家への登録の依頼だけ**を持たなければならない（SHALL）。生成はサーバー自身のアクションである。

**AI のプロセスにプロジェクトを生成させてはならない（MUST NOT）。** 承認の後の実行（steering）の起動定義に本家 spec-workflow の MCP を含めるのは、**生成の依頼が受理された後**に限る SHALL（`agent/invocation`「承認の後の実行は、起動の材料を組み立てるたびに生成を依頼する」）。生成が受理されていない対象で、本家 MCP を含めた起動定義の AI を起動してはならない（MUST NOT）——本家 MCP の起動時の自己登録が、生成の代わりになる形を残さない。本家 MCP を含める目的は承認依頼を出すことである。

生成を依頼するのはサーバーである SHALL。**ユーザーが叩く endpoint（画面が呼ぶ受理系と起動の endpoint）に生成を持たせてはならない（MUST NOT）。** 承認の判断（U10）・昇格（U14）・起動（U13）・完成の記録（U15）はいずれも生成に触れない。依頼する時点は `agent/invocation` が定める（承認の後の実行の、起動の材料を組み立てるとき）。

生成は phase を動かさない SHALL。生成中か完了かの判定（この capability「生成中か完了かはファイルシステムの事実だけで判定する」）は変わらず、本家に登録されたことを完了の根拠にしてはならない（MUST NOT）。

#### Scenario: 承認するとプロジェクトが本家に現れる

- **GIVEN** 本家 dashboard が動いている
- **WHEN** ユーザーが proposal を承認し、昇格が成功し、承認の後の実行が起動される
- **THEN** AI が起動する前に生成が依頼され、そのプロジェクトが本家の一覧に載る。AI の中で何が起きるかに依らない

#### Scenario: AI の起動はプロジェクトを生成しない

- **GIVEN** 生成の依頼が通らない状態で（本家 dashboard を止めて）昇格したプロジェクトが在る
- **WHEN** その対象の AI を起動しようとする
- **THEN** 生成が受理されないので AI は起動されず、本家の登録簿にそのプロジェクトは現れず、`.spec-workflow/` もできない。本家 MCP が自己登録する機会は無い

#### Scenario: 本家に載る生きたインスタンスは本家自身のものだけ

- **GIVEN** 本家 dashboard が動いている
- **WHEN** 昇格したプロジェクトの承認の後の実行が起動され、終わる
- **THEN** 実行中は本家の登録簿でそのプロジェクトが持つ生きたインスタンスに、AI が起動した本家 MCP のプロセスが1つ加わる。実行が終わればそれは消え、残るのは本家 dashboard 自身のプロセスだけである。`projectId` は生成の依頼で得たものと同じで、増えない

#### Scenario: 昇格の受け口は生成に触れない

- **WHEN** 昇格（U14）が成功する
- **THEN** その時点では本家へ何も依頼されていない。昇格の応答は本家の状態に依らず返る

#### Scenario: 生成は完了の根拠にならない

- **GIVEN** phase が `approved` のプロジェクトの生成が受理され、本家の一覧に載った
- **WHEN** 一覧を見る
- **THEN** そのプロジェクトは生成中のまま出ている。完了になるのは完成の記録が書かれたときである

#### Scenario: 本家が停止していても承認は成立する

- **GIVEN** 本家 dashboard が起動していない
- **WHEN** ユーザーが proposal を承認する
- **THEN** 昇格は成功し、画面は一覧へ戻り、生成中の行が出ている。生成は承認の後の実行が依頼して失敗し、その実行は起動し直しの対象として残る
