## MODIFIED Requirements

### Requirement: 下層で状態を変えられるのは承認への応答だけ

システムは、下層の画面に **承認と却下** を置かなければならない（SHALL）。あわせて、仕様書とステアリングの文書に **編集と保存** を置かなければならない（SHALL）。それ以外に本家の状態を変える操作を置いてはならない（MUST NOT）。タスクの状態変更・プロジェクトの登録と解除はいずれも持たない。

承認と却下は本家の `POST /api/projects/:projectId/approvals/:id/:action` を呼ぶ。文書の保存は本家の `PUT /api/projects/:projectId/specs/:name/:document` と `PUT /api/projects/:projectId/steering/:name` を呼ぶ。いずれも stroke-board のサーバーを経由し、ブラウザから本家へ直接送ることはない。

編集できる文書の範囲、直しかけのまま離れようとしたときの扱い、保存に失敗したときの見せ方は `document-editing` が定める。

差し戻し（`needs-revision`）は持たない。本家のそれは注釈コメントを前提にした流れで、stroke-board はコメントを持たないため。

#### Scenario: 承認画面を開く

- **WHEN** 承認画面を開く
- **THEN** 保留中の承認依頼とその対象文書の中身が読め、承認と却下が行える

#### Scenario: 承認する

- **WHEN** 保留中の承認依頼を承認する
- **THEN** 本家へ承認が伝わり、その承認依頼が保留中の一覧から消える

#### Scenario: 却下する

- **GIVEN** 却下の理由を入力していない
- **WHEN** 却下しようとする
- **THEN** 送れない。理由は本家に応答として残るため、空のままでは送らない

#### Scenario: 理由を添えて却下する

- **WHEN** 却下の理由を入力して却下する
- **THEN** 本家へ却下と理由が伝わり、その承認依頼が保留中の一覧から消える

#### Scenario: 仕様書の文書を直す

- **WHEN** 仕様書の文書を開いて直し、保存する
- **THEN** 本家へ保存が伝わり、開き直すと直した内容が出る

#### Scenario: ステアリングの文書を直す

- **WHEN** ステアリングの文書を開いて直し、保存する
- **THEN** 本家へ保存が伝わり、開き直すと直した内容が出る

#### Scenario: タスク画面を開く

- **WHEN** タスク画面を開く
- **THEN** タスクとその状態が読めるが、状態を変える操作は無い

#### Scenario: 承認依頼から対象文書を直す

- **WHEN** 承認依頼のカードから対象文書を開く
- **THEN** その場で直して保存でき、別の画面へ移り直す必要が無い
