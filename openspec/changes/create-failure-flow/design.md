## Context

現状は proposal.md「Why」にある。設計として押さえる事実は3つ。

- **判定はもう在る。** リトライの上限に達したら `invocation` を `error` にする判定は invokeAi が持ち（`agent/invocation`「リトライ上限に達したら error に変える」）、巡回は `error` を拾わない（`portal/batch`）。**この change は判定を作らない。** 判定の後——ユーザーへ引き渡した先——だけを定める
- **画面へ届く経路も在る。** `useWaitingRetry` が U2 を数秒おきに読み、`invocation` が `error` なら `errored` を立てる。出せる操作は `retryFromError`（`U13?reset=1`）と `discard`（U11）の2つ
- **`error` を持つのはセッションとプロジェクトだけである。** 上層の他の失敗（本家 REST が落ちている・文書の保存が通らない）は `invocation` を持たず、トースト（`notification-toast`）で流れて消える

## Goals / Non-Goals

**Goals**

- 完全な失敗に達した後、ユーザーが**必ず何かを選べる**状態を規範として持つ
- 破壊を伴う選択肢に承諾を課し、承諾の前に何も消えないことを保証する
- セッションの画面（`stroke/frontier`）を、その規範の適用として書き直す

**Non-Goals**

- リトライの回数・タイムアウト・巡回の対象を変えること
- `invocation` を持たない失敗（トーストで流れる本家由来の失敗）をこの規範の対象に入れること。**将来ここへ寄せる余地は残すが、この change では扱わない**
- 選択肢の見た目の詳細（配置・文言・色の値）。規範が持つのは「警告色で示す」「通常の操作と並べない」までで、実際の意匠は ui.md の対象

## Decisions

### 書き出し先は `docs/specs/architecture/failure.md`（新設）

ユーザーへ3案を諮って確定済み（2026-09-09）。`architecture/` は「4者が何を送り、どう動くか」を持つ層で、失敗の後の流れもここに属する。`api/contract.md` は endpoint の境界の資料であり、承諾や警告色の規定を持てない。`session-workflow.md` はセッション限定の資料で、上層まで届かない。

**代案として退けたもの** — `openspec/specs/` にだけ置いて docs を持たない形。specs は docs に付随する物差しであり（`docs/agents/issue-tracker.md`「各層の性質」）、規範の正を specs に置くことはできない。

### docs への整合反映（**承認を求める**）

`docs/agents/issue-tracker.md`「更新対応」に従い、上位資料への反映をここで諮る。承認を得るまで docs は書き換えない。

| 資料 | 反映の内容 |
|---|---|
| `docs/specs/architecture/failure.md`（新設） | 失敗の段階・通知・選択肢の4性質・承諾・行き止まりの禁止。proposal.md「What Changes」の箇条がそのまま節になる |
| `docs/specs/api/contract.md` | U2 の `error` の説明から「画面は再実行か削除を出す」を外し、`failure.md` への参照にする。**`error` が終端であること自体は残す**（endpoint の応答が何を意味するかは contract の持ち物） |
| `docs/specs/architecture/session-workflow.md` | 「実行の記録（`invocation`）」の状態遷移図と各行は残す。`error --> [*]: ユーザーの削除` の行に、削除が承諾を経ること（`failure.md`）への参照を添える |

### セッションの画面が出す選択肢は3つ

規範は「性質の異なる選択肢を2つ以上、うち1つは対象を壊さない」までを定める。セッションの画面では次を出す。

| 性質 | 操作 | 壊すか |
|---|---|---|
| そのまま再実行する | 再実行（`U13?reset=1`） | 壊さない |
| 時間を置いて再開する | 一覧へ戻る | 壊さない |
| 最初からやり直す | 最初に戻る（U11 → 概要の入力へ） | **壊す。承諾を課す** |

**「人へ引き渡す」はセッションの画面に出さない。** 出すには問い合わせ先の値が要り、それは設定である（「問い合わせ先は設定として持つ」）。規範には性質として残し、画面への適用は設定が入ってからにする。

### 問い合わせ先は設定として持つ（**承認を求める**。この change では入れない）

`docs/specs/core/settings-reference.md`「ここに無いものは設定ではない」に従うと、問い合わせ先は設定に足す必要がある（`app/app.config.ts` 側。画面が出す文言と行き先であり、サーバーは使わない）。設定を足すには change を起票してユーザーの承認を得る、と同資料が定めている。

**この change では足さない。** 理由は2つ——値（誰へ、どこへ）が決まっていないこと、`failure.md` の規範は「人へ引き渡す」を4性質の1つとして持てば足り、画面への適用を待てること。足すときは別の change を起票する。

### 削除した後の行き先を概要の入力へ変える（**挙動の変更**）

いまの `stroke/frontier` は「セッションは削除され、モーダルが閉じてプロジェクト一覧へ戻る」。ユーザー指示の例は「最初へ戻る」であり、やり直しの起点は概要の入力（`/`）である。削除した対象を見に行く先が一覧である理由は無い。

**一覧へ戻る道は消さない。** 「時間を置いて再開する」（「セッションの画面が出す選択肢は3つ」）として残り、そちらは削除を伴わない。**2つの行き先は別の性質に割り当て直される**のであって、片方が消えるのではない。

### 承諾は既存のモーダルの形に載せる

承諾の一手は `app/components/review/` のモーダル群と同じ作りで出す。新しい仕組みを作らない。**押し間違いで到達できる位置に置かない**という規範（`failure`「破壊を伴う選択肢は消えるものを示して承諾を得る」）は、警告色と承諾の2つで満たす。

## Risks / Trade-offs

- **[規範が画面の先を走る]** `failure.md` は4性質を定めるが、画面が出すのは3つで、「人へ引き渡す」は当面どこにも無い → 規範側に「どの性質を出すかは画面が選ぶ。4つすべては求めない」と明記した（`failure` の Requirement「対処の選択肢を提示する」）。規範が未実装を強いる形にしない
- **[承諾を挟むと操作が1つ増える]** `error` に達したユーザーは既に待たされており、そこへ確認を足す → 承諾を課すのは破壊を伴うものだけで、再実行と一覧へ戻るは1手のまま
- **[`invocation` を持たない失敗が規範の外に残る]** 上層のトーストで流れる失敗には段階も終端も無い → この change の Non-Goals に置いた。寄せるなら別の change で、`notification-toast` と併せて見る

## Migration Plan

`state.json` にも API の応答にも変更が無く、巻き戻しは docs と画面のコードを戻すだけで済む。**データの移行は無い。**

## Open Questions

- **一覧に `error` の件がどう見えるか。** 「時間を置いて再開する」は一覧から同じセッションへ戻れることが前提になる。`portal` の一覧は `invocation` を持つ（U12）が、`error` の件を見分けられる表示になっているかは実装を見て確かめる。表示が足りなければ tasks に足す——規範と specs は変わらない
