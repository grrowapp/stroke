## 判定

**保留。** 合格条件3つは満たすが、未解決の欠陥が1件ある。

1. proposal 提出まで到達（`phase: proposed`）
2. 取得・提出が MCP ツール経由のみ（Skill / Bash による取得・提出が0件）
3. 提出物が仕事になっている（問いが概要に沿った設計判断を扱い、proposal が概要と往復の内容を反映）

### 欠陥: flontier 工程で `get-steering` が必ず 500 になる

`get-steering` の3回はいずれも失敗した。

```
[500] この接続は steering 工程向けではない。
```

flontier 工程の接続は `sessionId` を持ち `projectPath` を持たないため、`requireConnectionProjectPath` が投げる。

`server/utils/mcp/require-connection.ts` のコメントは「steering 工程の接続で flontier 向けツールが呼ばれることは normal フローでは起きない（**呼び出し元ごとに渡すツール定義が分かれる**）」としているが、**この前提が成立していない**。ツール定義はモジュールが `server/mcp/tools/` を自動発見して単一の `/mcp` で配るため、`--mcp-config` が flontier 向けでも6本すべてが見える。エージェントには使えるツールとして提示され、呼べば必ず 500 になる。

往復自体は成立したが、エージェントは毎回この無駄な失敗を踏んでいる。工程ごとにツールを出し分けるか、工程外のツールを呼んだときの結果を契約の形（`status` / `errorCode`）で返すかの判断が要る。

## この検証に至るまでに直した不具合

### 1. 全ツールが `structuredContent` を返さず、MCP SDK に弾かれていた

```
MCP error -32602: Output validation error:
Tool get-overview has an output schema but no structured content was provided
```

モジュールの `normalizeToolResult` が素のオブジェクトを `content` だけに包むため、`outputSchema` を宣言した6ツールの結果が全て拒否されていた。`server/utils/mcp/define-tool.ts` で定義の入口から包むよう修正（tasks 3.10 / 3.11）。

### 2. 入力の上限が契約に書かれておらず、`send-question` が通らなかった

修正前は `send-question` が13回中8回 `400 validation_error`。エージェントは上限を知る手立てが無く「テスト」のような短い問いしか通せなかった。`.describe()` で上限を契約の説明として書いた（tasks 3.12）。**修正後は4回すべて1発で 204。**

### 3. MCP ツールが `--allowedTools` に無く、呼べなかった

`server/utils/mcp/allowed-tools.ts` で呼び出しごとに `mcp__stroke-board` を足す（tasks 4.5）。

## 残る既知の問題（本 change の成果物の欠陥ではない）

初回起動が1度失敗し `retries: 1` になっている。`firstPrompt` 先頭にあった `/openspec-ff-change` が `Unknown command` になり、assistant のターンを持たずに終わる問題（tasks「案内スキルの実体が無い」）。本検証では起動を外して回避した。
