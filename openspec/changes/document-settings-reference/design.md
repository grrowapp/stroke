## Context

proposal.md の Why を参照。ここでは、資料の形を決めるのに要る実測と制約だけを置く。

**書く対象の実測**（`align-settings-conventions` の 10 章まで適用した姿）:

| 区分 | 件数 | 置き場 |
|---|---|---|
| `runtimeConfig`（`.env` で差し替えられる） | 2 | `nuxt.config.ts` ＋ `NUXT_SESSIONS_ROOT` / `NUXT_PROJECTS_ROOT` |
| `runtimeConfig`（差し替えない） | 7 | `nuxt.config.ts` |
| `runtimeConfig.public` | 1 かたまり | `nuxt.config.ts`（`claude` の `command` / `args`） |

資料に**載せない**もの:

| 区分 | 件数 | 理由 |
|---|---|---|
| `settings.ts` の固定値 | 15 | システム内部の決め事であって設定ではない |
| schema の定義に畳んだ閾値 | 5 | AI 応答を読み取れるかの契約であって設定ではない |
| 廃した上限 | 14 | 設定でないどころか、キャップ自体が要らなかった |
| ビルド時に決まる設定 | 5 | `nuxt.config.ts` が見出しで分けており、資料が書き直すと二重定義になる |

**制約**:

- **資料が正である**（ADR 0004）。コードが資料に追随する。資料を「コードの写し」として扱わない
- `.env.example` は**コピーして使うテンプレート**である（`cp .env.example .env`）。置き場2件だけを持つ
- 資料はコードから生成しない。生成物にすると正がコード側へ戻る

## Goals / Non-Goals

**Goals:**

- 運用者が「今この瞬間、何が設定か」を1箇所で引ける
- **資料に無い＝設定ではない**が成立する
- 設定を増やす行為に、change とユーザー承認が挟まる

**Non-Goals:**

- **コードを変えない。** `server/` / `nuxt.config.ts` / `package.json` に手を入れない。環境変数の全廃と `settings.ts` への集約は `align-settings-conventions` が持つ
- **資料を自動生成しない。** 生成スクリプトも CI 検査も作らない
- **`.env.example` を置き換えない。** 役割が違う
- **設定でないものを資料に載せない。** システム既定値・schema の定義・ビルド時の設定は対象外
- **対応表を持たない。** `align-settings-conventions` の対応内容を写さない

## Decisions

### 決定1: 置き場は `docs/settings-reference.md` 1本

**代替案**:

- `README.md` に節を足す — README は入口である。設定の一覧を抱えると入口として読めなくなる
- `.env.example` のコメントを厚くする — 差し替えられる2件しか置けない。残り8件が書けない
- 読み口ごとに複数ファイルへ分ける — 「どこに書けば効くか」を引くには、`runtimeConfig` と `runtimeConfig.public` が並んで見えている必要がある

`docs/` の既存（`structure.md` / `session-workflow.md` / `mainline-merge.md` / `api-contract.md`）と同じ粒度・同じ命名に収まる。

### 決定2: 資料が正である。コードが資料に追随する

**この change の中核であり、ADR 0004 として独立させた。**

以前は逆だった（ADR 0003）。既定値も検証規則もコードが持ち、資料はそれを読める形に写しただけとしていた。**その形では設定が増えるのを止められない。** コードを1行足せば設定が1つ増え、資料の更新は後追いの善意に依存する。実際、コードと `.env.example` と資料の3者が食い違った。

資料を正に置くと、設定を増やすには資料を編集することになり、資料の編集には change とユーザー承認が要る（ADR 0004）。**承認の対象が「設定を増やすこと」そのものになる。**

**代替案**: コードを正のまま、資料の更新を change のタスクに含める規約にする — 規約は破れる。破れたことに気付く仕組みが無い。

### 決定3: 各行は「キー / 既定値」。出どころのモジュール名は書かない

設定は `nuxt.config.ts` にしか無い。出どころが1箇所しか無いので、行ごとに書く意味が無い。

`.env` で差し替えられる2件だけ、環境変数名の列を持つ。**列の有無が「差し替えられるか」を表す。**

**代替案**: 全行に環境変数の列を置き、差し替えられない行を空欄にする — 空欄が「まだ付けていない」に見える。差し替えられないことを表に語らせるなら、列ごと分ける方が誤読が無い。

### 決定4: 設定でないものは資料に載せない。「載せない」という記載も置かない

`settings.ts` の固定値・schema に畳んだ閾値・ビルド時に決まる設定は、資料に一切現れない。**「これは設定ではない」という節も置かない。**

置けば、資料が設定以外のものを語り始める。何が設定かを引く資料が、何が設定でないかも引ける資料になると、両者の境界が資料の中でぼやける。**資料に無いものは設定ではない**という一文だけを冒頭に置き、個別の列挙はしない。

**代替案**: 「外に出さないと決めたもの」の節を持つ — 判断の記録としては要るが、それは ADR と change の役割である。設定の一覧が抱えるものではない。

### 決定5: 対応表を持たない

`align-settings-conventions` の対応内容を資料へ書き写すと、archive された履歴の複製が本体に残る。**複製は履歴であって、もう一つの本体ではない。**

資料は「今この瞬間、何が設定か」だけを持つ。なぜその設定になったのかは、change（archive を含む）と ADR が持つ。

**代替案**: タスク番号単位の対応表を最終セクションに置く — 一度これで書いた。結果、`align-settings-conventions` に 10 章が足された時点で対応表の大半が「覆った対応」になり、資料が履歴の管理を始めた。

### 決定6: `.env.example` との重複は残す

置き場2件の「名前と既定値」は、`.env.example` と資料の両方に載る。これは避けられない（`.env.example` はテンプレート、資料は読み物）。2件なので、ずれても目視で足りる。

**代替案**: `.env.example` を廃してドキュメントに一本化する — `cp .env.example .env` で始められる利点を失う。

## Risks / Trade-offs

**[資料が古くなる]** → ADR 0004 が「資料の編集を伴わない設定変更は差し戻す」と定める。**古くなるのは規約違反であって、避けられない摩耗ではない**という扱いにする。自動検査は作らない（Non-Goals）。

**[承認が手間になる]** → 設定を増やすたびに change とユーザー承認が要る。これは費用ではなく目的である。設定が増えにくくなることこそ、この change が狙ったことである。

**[`align-settings-conventions` が未実装のまま資料を書く]** → 10 章（環境変数を置き場2件に絞る・`settings.ts` への集約・起動定義の JSON 化）は未着手である。**ADR 0004 の下では、資料が先で実装が後になる。** 資料に書いた姿へコードを合わせるのが `align-settings-conventions` 10.19 の役割である。両者を1つの流れとして続けて片付ける。
