## ADDED Requirements

### Requirement: 起動に至らずに終わった実行も失敗として記録する

システムは、AI を1度も起こさないまま——起動の材料を組み立てる段で——終わった実行も、実行の失敗として記録する SHALL。記録を残さずに終わってはならない（MUST NOT）。記録が残らなければ、その対象は平常（`idle`）のまま止まり、失敗を拾う巡回にも掛からず、サーバーのログ1行しか残らない。

記録は、起動して失敗した実行と同じ4値・同じ書き込み口で行う SHALL。この失敗のためだけの値を増やしてはならない（MUST NOT）。

この失敗も、起こし直しの回数に数える SHALL。数えないと、直るまで通らない原因に対して起こし直しが際限なく繰り返され、終端へ到達しない。

記録する値は次のとおりとする SHALL。

- 起こし直しの上限に達していないとき: `failed`。失敗を拾う巡回の対象になる
- 上限に達しているとき、または上限そのものを読み出せないとき: `error`（終端）。システムは自動では何もせず、回復はユーザーの再実行または削除だけとする

材料を組み立てられたときの振る舞いを変えてはならない（MUST NOT）。すでに失敗として記録している経路——実行環境を整えられない・提出が届かない・時間切れ・上限到達——の振る舞いも変えてはならない（MUST NOT）。

#### Scenario: 材料を組み立てられずに終わる

- **WHEN** 起動の材料を組み立てられず、AI が1度も起こされないまま実行が終わる
- **THEN** その対象の実行の記録は `failed` になり、失敗を拾う巡回の対象になる

#### Scenario: 記録が残らないまま終わらない

- **WHEN** 起動の前段で実行が失敗する
- **THEN** その対象の実行の記録は `idle` のまま据え置かれない

#### Scenario: 組み立ての失敗も回数に数える

- **WHEN** 起動の前段で失敗した実行が記録される
- **THEN** その対象の起こし直した回数は1つ進み、次の起動のタイムアウトと上限の判定はその値を見る

#### Scenario: 上限に達していれば終端になる

- **WHEN** 起こし直しの上限に達した対象で、起動の前段の失敗が起こる
- **THEN** その対象の実行の記録は `error` になり、システムは自動では起こし直さない

#### Scenario: 上限そのものを読み出せない

- **WHEN** 起動の材料も、起こし直しの上限も読み出せない状態で起動が要求される
- **THEN** その対象の実行の記録は `error` になり、起こし直しが際限なく繰り返されることはない

#### Scenario: 材料を組み立てられた実行は変わらない

- **WHEN** 起動の材料を組み立てられ、AI が起こされる
- **THEN** 実行の記録は `running` になり、完了・時間切れ・上限到達の扱いはいずれも変わらない
