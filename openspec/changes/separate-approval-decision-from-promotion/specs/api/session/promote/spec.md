## Purpose
承認の判断が記録されたセッションを、プロジェクトへ昇格させる受け口（U14）を規定する。昇格の実行だけを担い、判断を下すことも、昇格の後に続く実行を起こすことも受け持たない。承認・昇格・起動を別々の段として扱うための、真ん中の段である。

## ADDED Requirements

### Requirement: U14 POST /api/sessions/:id/promote — 判断のあるセッションを昇格させる

システムは `POST /api/sessions/:id/promote` を公開する SHALL。記録された判断が持つ確定された名前で、昇格（`project/generation` が規定する改名と phase の書き換え）を実行する SHALL。

**記録された判断が無いセッションの昇格を受理してはならない（MUST NOT）。** 承認はプロジェクト生成の唯一の引き金であり、その関係はこの受け口で守られる。判断と昇格が同じ呼び出しの中で起こることは求めない。

**昇格の要求は、確定された名前を引数に取らない SHALL。** 名前はユーザーが判断とともに確定したものであり、昇格の段はそれを引き直すだけである。**判断に含まれるものとは別の名前で昇格できる形にしてはならない（MUST NOT）**——名前の決定はユーザーのものであり、昇格はシステムの動作である。

昇格が成功したときは受理を返す SHALL。**次の実行を起こしてはならない（MUST NOT）**——steering の起動は起動の受け口（`api/session/invoke-agent`）が受け持ち、昇格の成功を見た側がそれを要求する。

昇格が失敗したときは失敗を返す SHALL。**記録された判断は残す SHALL**——同じ判断のまま、昇格だけをやり直せる。

既に昇格した対象への重ねての昇格は受理しない SHALL。存在しないセッション id への昇格は受理しない SHALL。

#### Scenario: 判断のあるセッションを昇格させる

- **WHEN** 判断が記録されたセッションへ `POST /api/sessions/:id/promote` が届く
- **THEN** 判断が持つ名前へ改名され、そのセッションはプロジェクトになる。受理が返り、次の実行は起こされない

#### Scenario: 判断の無いセッションを昇格させようとする

- **WHEN** 判断が記録されていないセッションへ昇格が要求される
- **THEN** システムは受理せず、改名は起こらない。セッションは元の名前のまま残る

#### Scenario: 昇格が失敗する

- **WHEN** 昇格が要求されたが、改名または phase の書き込みが失敗する
- **THEN** 失敗が返り、セッションは元の名前・phase `proposed` のまま残る。**記録された判断はそのまま残っており**、同じ判断のまま昇格をもう一度要求できる

#### Scenario: 既に昇格した対象を昇格させようとする

- **WHEN** 既に昇格した対象へ昇格が要求される
- **THEN** システムは受理せず、何も変えない

#### Scenario: 存在しない id で昇格が要求される

- **WHEN** 存在しないセッション id に昇格が要求される
- **THEN** システムは受理せず、存在しないことを伝え、何も変えない

### Requirement: 昇格した時点で、steering の実行はまだ済んでいないものとして残る

システムは、昇格が成功した対象を、**steering の実行がまだ済んでいないもの**として残さなければならない（SHALL）。昇格の受け口が起動を要求しないため、起動の要求が一度も届かなかった場合でも、系はそれを自力で起こし直せなければならない（SHALL）。

そのために新しい巡回や新しい判定を設けてはならない（MUST NOT）——既にある「失敗した実行を起こし直す巡回」（`portal/batch`）がそのまま拾える形で残す。巡回が拾う条件そのものを変えてはならない（MUST NOT）。

昇格の直後に起動が要求された場合、同じ対象の実行が二重に始まってはならない（MUST NOT）——多重起動を止めるのは起動の受け口である（`api/session/invoke-agent`）。

#### Scenario: 昇格の後に起動が一度も届かない

- **WHEN** 昇格は成功したが、steering の起動が一度も要求されないまま巡回が走る
- **THEN** 巡回がその対象を拾い、steering の実行が起こされる

#### Scenario: 昇格の直後に起動が要求される

- **WHEN** 昇格の成功を見た側が、続けてその対象の起動を要求する
- **THEN** steering の実行が始まる。同じ対象が巡回によって二重に起こされることはない

#### Scenario: 起動の要求が届かずに終わる

- **WHEN** 昇格の成功を見た側が起動を要求したが、その要求が届かずに失敗する
- **THEN** 昇格はそのまま残り、起動の段だけがやり直しの対象として残る。昇格は巻き戻らない

### Requirement: 後始末は段ごとに閉じる

システムは、承認の判断・昇格・steering の起動のそれぞれの失敗を、**その段の中だけで後始末**しなければならない（SHALL）。ある段の失敗が、その前の段の結果を巻き戻してはならない（MUST NOT）。

- 判断の記録に失敗したとき、セッションは何も変わらない
- 昇格に失敗したとき、改名は元へ戻り、**記録された判断は残る**
- 起動に失敗したとき、**昇格は残る**。やり直すのは起動の段だけである

やり直しの入口は段ごとに分かれていなければならない（SHALL）。**承認をもう一度実行することが、失敗した段をやり直す唯一の手段であってはならない（MUST NOT）。**

#### Scenario: 昇格だけをやり直す

- **WHEN** 昇格に失敗した後、ユーザーが同じ判断のままやり直す
- **THEN** 承認の判断を下し直すことなく、昇格だけが再実行される

#### Scenario: 起動だけをやり直す

- **WHEN** 昇格は済んだが steering の起動に失敗した後、やり直しが起こる
- **THEN** 改名も判断もやり直されず、起動だけが再実行される

#### Scenario: 起動の失敗で昇格が巻き戻らない

- **WHEN** 昇格の後に steering の起動が失敗する
- **THEN** プロジェクトはそのまま在り、セッションの名前へ戻ることはない
