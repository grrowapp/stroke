## ADDED Requirements

### Requirement: 承認はセッションディレクトリをプロジェクト名へ改名して昇格させる

システムは承認時に、そのセッションのディレクトリを確定された名前 `<name>` へ改名することでプロジェクトを作る SHALL。セッションとプロジェクトは同じ親（共有の置き場）の下に置き、昇格は同じ親の下での改名で行う SHALL。

システムは、昇格にあたって新しいディレクトリを作ってはならない（MUST NOT）し、ファイルを別の場所へ複製・移動してはならない（MUST NOT）。セッションディレクトリの中身はすべてそのままプロジェクトの中身になる。

システムは `.spec-workflow/` の内部構造を作ってはならない（MUST NOT）。

#### Scenario: 承認によって昇格する

- **WHEN** ユーザーが名前 `<name>` で承認する
- **THEN** そのセッションのディレクトリが同じ親の下で `<name>` へ改名され、プロジェクトになる

#### Scenario: 中身はそのまま引き継がれる

- **WHEN** 昇格が成功した直後にプロジェクトの中身を見る
- **THEN** セッションの時点にあったファイルがすべて同じ相対位置のまま入っている

#### Scenario: 内部構造には踏み込まない

- **WHEN** 昇格した直後の中身を見る
- **THEN** `.spec-workflow/` 配下のファイルやディレクトリは1つも作られていない

### Requirement: proposal はセッションの時点から docs 配下にある

proposal を書くのは AI である。システムのコードは proposal のファイルを作ってはならない（MUST NOT）し、上書きしてはならない（MUST NOT）。

AI はセッションの時点から proposal をセッションディレクトリの `docs/proposal.md` に置く SHALL。昇格はこのファイルを動かさないため、昇格後は `<name>/docs/proposal.md` としてそのまま読める。

#### Scenario: セッション中の proposal の在り処

- **WHEN** AI が proposal を起こした後にセッションディレクトリを見る
- **THEN** `docs/proposal.md` に proposal の全文が入っている

#### Scenario: 昇格後の proposal の在り処

- **WHEN** 昇格が成功した後にプロジェクトの中身を見る
- **THEN** `<name>/docs/proposal.md` に、承認された proposal と同じ内容が入っている

#### Scenario: システムは proposal を書かない

- **WHEN** 承認の処理が走る
- **THEN** システムは proposal のファイルを新たに書き出さず、既にある `docs/proposal.md` に触れない

## MODIFIED Requirements

### Requirement: 生成の直前に既存名との衝突を確認する

システムは昇格の直前に、置き場に `<name>` が既に存在するかを確認する SHALL。既に存在する場合は改名を行わない。

#### Scenario: 承認の時点で同名が存在する

- **WHEN** 昇格しようとした時点で置き場に `<name>` が既に存在する
- **THEN** システムは改名を行わず、衝突を伝え、phase を `proposed` のままにする

### Requirement: 生成に失敗したら承認を確定させない

改名に失敗した場合、システムは phase を `approved` にしない SHALL。確定された名前を実行環境がディレクトリ名として受け付けない場合も、この失敗として扱う SHALL。失敗は、それが起きた場所のエラーとして伝える。

失敗したとき、セッションディレクトリは元の名前のまま残っていなければならない（SHALL）。同じセッションで再度承認できる状態を保つ。

#### Scenario: 書き込みに失敗する

- **WHEN** 置き場への書き込み（改名）が失敗する
- **THEN** システムはエラーを表示し、phase を `proposed` のままにして、セッションを元の名前のまま残し、再度承認できる状態にする

#### Scenario: 環境が名前を受け付けない

- **WHEN** 確定された名前を実行環境がディレクトリ名として受け付けず、改名が失敗する
- **THEN** システムはその失敗をエラーとして表示し、phase を `proposed` のままにして、別の名前で再度承認できる状態にする

## REMOVED Requirements

### Requirement: 承認時にプロジェクトのトップディレクトリを作る

**Reason**: プロジェクトの作り方が「新規生成」から「セッションディレクトリの改名による昇格」に変わった（ADR-0011 / `docs/specs/plan/portal-stroke-exit.md`）。ディレクトリを新しく作る処理そのものが無くなる。

**Migration**: 「承認はセッションディレクトリをプロジェクト名へ改名して昇格させる」が引き継ぐ。`.spec-workflow/` の内部構造を作らないという線引きはそのまま維持される。

### Requirement: 承認された proposal を配置する

**Reason**: proposal はセッションの時点から AI 自身が `docs/proposal.md` に書くようになり、承認時にシステムが書き出す対象ではなくなった。昇格は改名だけなので、ファイルは動かない。

**Migration**: 「proposal はセッションの時点から docs 配下にある」が引き継ぐ。承認後の在り処 `<name>/docs/proposal.md` は変わらない。

### Requirement: セッションディレクトリは承認後も残す

**Reason**: 昇格はセッションディレクトリそのものの改名であり、セッションディレクトリとプロジェクトは同一の実体になった。「承認後もセッションディレクトリが別に残る」という状態が存在しない。

**Migration**: 中身が失われないことは「承認はセッションディレクトリをプロジェクト名へ改名して昇格させる」の「中身はそのまま引き継がれる」が保証する。承認に失敗したときにセッションが元の名前のまま残ることは「生成に失敗したら承認を確定させない」が規定する。
