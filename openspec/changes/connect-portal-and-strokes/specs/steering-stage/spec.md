## Purpose

承認の次の工程として steering 文書の作成を自動で始め、その実行が終わったか失敗したかをシステム側だけで見届ける。ユーザーの操作も待ち時間も挟まずに、承認されたプロジェクトが本家 spec-workflow の土俵に乗るまでを担う。

## ADDED Requirements

### Requirement: 承認の成功が steering 工程を始める

システムは、承認が成功したときに steering 文書の作成工程を自ら始める SHALL。ユーザーの操作を挟んではならない（MUST NOT）。承認が成功しなかったときは始めてはならない（MUST NOT）。

#### Scenario: 承認が成功する

- **WHEN** ユーザーが proposal を承認し、プロジェクトへの昇格が成功する
- **THEN** ユーザーの追加操作なしに steering 作成の工程が始まる

#### Scenario: 承認が失敗する

- **WHEN** 承認の処理が失敗し、プロジェクトへの昇格が成立しない
- **THEN** steering 作成の工程は始まらない

### Requirement: steering はストロークとは別の実行として生成先で走る

システムは、steering 作成をストロークのセッションとは別の AI 実行として起動する SHALL。作業場所は生成されたプロジェクトのディレクトリとし、本家 spec-workflow の MCP を与えて実行する。

システムは `.spec-workflow/` の内部構造を自ら作ってはならない（MUST NOT）。内部構造は steering を作る AI が呼ぶ本家 MCP が作る。

#### Scenario: steering の実行が起動する

- **WHEN** steering 作成の工程が始まる
- **THEN** ストロークのセッションとは別の実行が、生成されたプロジェクトを作業場所として、本家 spec-workflow の MCP を与えられた状態で起動する

#### Scenario: 内部構造は本家が作る

- **WHEN** steering の実行が完了してプロジェクトの中身を見る
- **THEN** `.spec-workflow/` の内部構造は本家 MCP の手で作られており、システムが直接書いたものは含まれない

#### Scenario: steering が終わるとプロジェクトが一覧に現れる

- **WHEN** steering 作成が完了して `.spec-workflow/` ができた後にプロジェクト一覧を開く
- **THEN** そのプロジェクトが一覧に現れる

### Requirement: steering の進捗と失敗をユーザーに見せない

システムは、steering 工程の進捗・失敗をユーザーの画面に出してはならない（MUST NOT）。承認の応答は steering の実行完了を待たずに返す SHALL。

#### Scenario: 承認直後の画面

- **WHEN** ユーザーが承認する
- **THEN** steering の完了を待たずに応答が返り、画面はプロジェクト一覧へ戻る

#### Scenario: steering が失敗する

- **WHEN** steering の実行が失敗する
- **THEN** ユーザーの画面には何も現れず、失敗の後始末はシステム側だけで行われる

### Requirement: 起動した実行を記録し、完了で消す

システムは steering の実行を起動したとき、その実行のセッション id を **実行中** として記録する SHALL。記録は次の2つの経路でのみ変わる。

- **タイムアウト**: 設定されたタイムアウト時間を過ぎても提出の告知が無い場合、その記録を **失敗** に変える SHALL
- **提出の告知**: steering 文書を提出し終えた AI からの告知を受理したとき、その記録を消す SHALL（＝完了）

システムは、記録の変化に上記以外の判定を持ち込んではならない（MUST NOT）。

#### Scenario: 起動して記録する

- **WHEN** steering の実行が起動する
- **THEN** そのセッション id が実行中として記録される

#### Scenario: 提出の告知を受ける

- **WHEN** steering 文書を提出し終えた AI が提出を告知する
- **THEN** そのセッション id の記録が消える

#### Scenario: タイムアウトする

- **WHEN** タイムアウト時間を過ぎても提出の告知が無い
- **THEN** そのセッション id の記録が失敗に変わる

#### Scenario: 完了した実行は失敗にならない

- **WHEN** 提出の告知で記録が消えた後にタイムアウト時間が過ぎる
- **THEN** 失敗の記録は作られない

### Requirement: 失敗した実行は巡回が拾ってリトライする

システムは、失敗として記録されたセッション id を定期的な巡回で拾い、steering の実行を起動し直す SHALL。巡回は条件判定を持ってはならない（MUST NOT）— 失敗の記録があることだけがリトライの根拠である。

リトライで起動し直した実行は、起動時に再び実行中として記録される SHALL。

#### Scenario: 失敗した実行を拾う

- **WHEN** 失敗として記録されたセッション id がある状態で巡回が走る
- **THEN** その実行が起動し直され、記録は実行中に戻る

#### Scenario: 失敗が無いときの巡回

- **WHEN** 失敗の記録が1件も無い状態で巡回が走る
- **THEN** 何も起動されない

#### Scenario: リトライが完了する

- **WHEN** リトライした実行が提出を告知する
- **THEN** その記録が消え、以降の巡回では拾われない

### Requirement: steering の定型は設定値、MCP の設定は生成先から導出する

システムは、steering の実行へ渡す定型を設定値として外に出し、その変更をコード変更・再ビルドなしに次回の起動から反映する SHALL。

システムは、本家 spec-workflow の MCP へ渡す設定を設定値として持ってはならない（MUST NOT）。生成先プロジェクトのパスから導出して起動時に組み立てる。設定ファイルをディスク上に作ってはならない（MUST NOT）。

#### Scenario: 定型を変更する

- **WHEN** 運用者が steering の定型の設定値を変更し、その後に steering の実行が起こる
- **THEN** 再ビルドなしに、変更後の定型が渡る

#### Scenario: MCP の設定は生成先から決まる

- **WHEN** steering の実行が起動する
- **THEN** 本家 MCP の設定は生成先プロジェクトのパスから導出され、設定ファイルはディスク上に作られない
