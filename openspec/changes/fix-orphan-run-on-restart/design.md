## Context

動機は proposal.md「Why」。要件は `specs/` 配下の delta（`bootstrap/system/cleanup-agent-process`・`agent/invocation`・`startup-readiness`）。

approach を縛る現状の制約は3つある。

- **前のプロセスが起こした claude を、新しいプロセスは何も知らない。** pid も接続表もメモリと共に消えている。手がかりは、走っているプロセスの argv に起動時点で載っているものだけである
- **記録の参照は API の応答から得る。** ファイルを直接読んで実行状態を判定してはならない（`agent/invocation`）。一覧（U12）が返す `SessionSummary` に載っていない値は、照合の手がかりにできない
- **`claude -p` は自力で終わる。** 放置しても終わるので、後始末が必要なのは「起こし直すまでに終わっていない」場合に限られる（proposal.md の実測）

## Goals / Non-Goals

**Goals:**

- 起こし直す時点で、同じ会話を担う claude が2本にならないこと
- 後始末が判定できなかったとき、黙って通り過ぎないこと
- 巡回と後始末の責務が重ならないこと
- 起動時に走る処理が、振る舞いの規定を持つものだけになること

**Non-Goals:**

- 孤児が残した作業の救出。接続表が消えているのでツール呼び出しは通らず、救うものが無い
- 孤児の寿命を縮めること。終わらせるのは後始末であって、起動の仕方を変える話ではない
- 接続表の永続化
- 前提の検査そのものを直すこと。定数を実行時に検査している点も、`claude` の起動引数を静的にしか見ていない点も、この change では**外すだけ**で作り直さない

## Decisions

### 決定1: 後始末を巡回から切り出し、起動時の専用ステップに置く

巡回が初回周回だけ `running` も倒す形をやめ、起動のたびに1回だけ走る別の処理にする。

**代案: 巡回に「終了させてから倒す」を持たせる。** 採らない。巡回は 60 秒ごとに回り続けるので、毎周回でプロセス一覧を取る負担が乗る。後始末が要るのは起動の直後だけで、周期処理に混ぜる理由が無い。加えて `portal/batch`「巡回は `failed` だけを拾う」に反したままになる。

### 決定2: 対象の照合は argv の中身で行い、pid は記録しない

走っている claude が「どの対象の実行か」は、argv に載っている会話 id（`--session-id` / `--resume`）と cwd（`--mcp-config` の中身）で判定する。

**代案: 起動時に pid を `state.json` へ書き、後始末はそれを探す。** 採らない。pid は OS が再利用するので、記録した pid が生きていても同じプロセスとは限らない。**殺す前に argv の照合が結局要る**のなら、記録を増やす分だけ損である。記録が古くなる経路（書く前に落ちる・書いた後に別プロセスが同じ pid を取る）も増える。

### 決定3: 終了は SIGKILL で送り、終了したことを確かめてから記録を書く

シグナルは既存のタイムアウトが使うものと揃える。送っただけでは終わりとせず、対象が消えたことを確かめてから `failed` を書く。

**代案: SIGTERM で丁寧に落とす。** 採らない。終了処理の途中の claude は MCP を叩いて記録を書き換えうる。倒したはずの対象が後から動くのが最も困る。

**代案: シグナルを送った時点で `failed` を書く。** 採らない。同じ理由である。確かめる前に書くと、書いた記録がその後に上書きされる余地が残る。

### 決定4: 判定できないときは `error` に倒す

走っているプロセスを調べられない環境（`ps` が無い・権限が無い）や、対象の種別から照合の手がかりを組み立てられない対象は、`error` にする。

**代案: 何もしない（触らない）。** 採らない。記録が `running` のまま固まり、巡回は `failed` しか拾わないので誰も動かせなくなる。

**代案: `failed` にする。** 採らない。`failed` は巡回が拾って起こし直す値である。終了を確かめられていない対象を起こし直すと、まさに防ぎたい2本目が立つ。**確かめられないものは自動で起こさない**側へ倒す。

### 決定5: どのサーバーインスタンスが起こしたかを判定条件にしない

対象を指していると判定できた claude は、このアプリが起こしたものとして扱う。

**代案: 起動時に渡した MCP の接続先が argv に載っているかで、自インスタンス発と判定する。** 採らない。proposal.md「この change で扱わないもの」のとおり、複数インスタンスを同時に走らせる前提を置かない。判定を足すと、その前提が規定に固定される。

### 決定6: 巡回との間に順序の取り決めを持たない

後始末と巡回は互いの完了を待たない。対象1件ごとの順序——終了を確かめてから `failed` を書く——だけで、2本目は防げている。巡回が先に回っても、その時点の対象は `running` なので拾わない。

**代案: 巡回の開始を後始末の完了まで待たせる。** 採らない。待ち合わせの仕組みは、それ自体が壊れる場所になる。順序で守れているものを、仕組みで二重に守る必要が無い。

### 決定7: 起動時の前提検査は外し、要求ごとの判定だけ残す

`startup-readiness` を落とすにあたり、起動時に走るプラグインを消す。前提を確かめる関数そのものは残し、AI の起動要求を受けたときだけ呼ぶ形にする。

要求ごとの判定は `api/session/invoke-agent`「前提が欠けている間は起動を受け付けない」が規定しており、外から観測できる。起動時の検査はログを出すだけで、規定を持たない。

**代案: 関数ごと消す。** 採らない。要求ごとの判定は規定があり、消すと `api/session/invoke-agent` を満たせなくなる。

**代案: 起動時のログだけ残す。** 採らない。規定の無い処理を起動時に走らせ続けることになり、`startup-readiness` を落とす理由がそのまま残る。

## Risks / Trade-offs

- **[プロセス一覧を取れない環境では、正常な残骸も `error` になる]** → 決定4 の帰結。`running` で固まるよりは良い、という判断。ユーザーの再実行で回復できる
- **[argv の照合が、起動側の組み立てとずれる]** → 起動側が `--mcp-config` や `--session-id` の形を変えると、照合が黙って外れる。**組み立て側と同じ事実を見ていることをテストで固定する**。照合を直すときは組み立て側も一緒に確かめる
- **[同じ cwd で steering の実行が複数走ると区別できない]** → 会話 id が一覧の応答に載らない対象は cwd でしか照合できない。同じプロジェクトの steering が同時に2本走る形は現状無いが、増えたら手がかりが足りなくなる
- **[起動のたびにプロセス一覧を取る]** → 起動時の1回だけなので、常時のコストにはならない

## Migration Plan

**後始末の追加と、巡回からの初回掃除の除去は同時に入れる。** 片方だけ入れると穴が開く。

- 後始末だけ入れる → 巡回も `running` を倒すので、後始末が終了を確かめている最中に巡回が `failed` を書きうる
- 除去だけ入れる → `running` を倒す者が居なくなり、記録が固まる

戻すときも同時に戻す。`state.json` のスキーマも API の契約も変えないので、記録の移行は要らない。

**起動時の前提検査の除去（決定7）は、上の2つとは独立に入れて戻せる。** 触る場所が重ならず、消えるのは起動時のログだけである。運用への影響は、前提が欠けた状態で起動したときに理由がログに出なくなること——AI の起動要求を出した時点で同じ内容が返るので、気付く手段は残る。
