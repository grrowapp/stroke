## Context

動機は proposal.md「Why」。ここは実装の形を決めるのに要る現状だけを置く。

実装を読んで確かめた事実（`/home/vagrant/work/stroke-board/pre5`、2026-09-01〜09-02）。

- `server/utils/stroke/claude.ts` の `spawn` に `detached` は無く、終了させる口は `runClaude` の中のタイムアウト（`SIGKILL`）だけである。**サーバー側に「起こした子プロセス」の台帳は無い**（`server/` に `spawn` は1箇所、`kill` はそのタイムアウトのみ）
- 接続表（`server/utils/mcp/connection-table.ts` の `Map`）と busy ガード（`server/utils/stroke/running.ts` の `Set`）はどちらもモジュール変数で、再起動で空になる
- 起動時の後始末は独立した処理ではなく、**巡回プラグイン（`server/plugins/01.retry-failed.ts`）の初回周回**が兼ねている。`first` のときだけ `running` を `failed` へ倒し、その周回では起こし直さず、`SWEEP_INTERVAL_MS = 60_000` 後の次の周回が U13 を叩く
- 起こし直しの経路に busy ガードはあるが（`invoke-agent.get.ts` → `beginRun`）、再起動後は空なので必ず通る
- 画面が回復の操作（`reset=1` の再実行）を出すのは `invocation` が `error` のときだけである（`app/composables/useWaitingRetry.ts`）
- `claude` に渡している `--allowedTools` に HTTP を叩く手段は無く、孤児の MCP 呼び出しは接続表が空なので 401 になる

**孤児は自力で終わる。** `claude -p` は非対話なのでターンを終えれば exit する（proposal の実測）。したがって守るべきは「孤児を永久に殺し続けること」ではなく、**起こし直しの時点で孤児が残っていないこと**である。

## Goals / Non-Goals

**Goals:**

- 再起動をまたいで残った AI を、起動時に**終了させてから**記録を畳む
- 終了させられなかったものを自動で起こし直さない
- 巡回を `portal/batch` の規定どおり「`failed` だけを拾う」形へ戻す

**Non-Goals:**

- 接続表の永続化。archive 済み change `provide-operations-via-mcp` の design.md「接続表はメモリ上の層とする」を覆さない。孤児側のツール呼び出しが 401 になること自体は変えない
- 孤児が途中まで進めた作業の救済。会話は `--resume` で続くので、起こし直しが続きから拾う
- 正常なシャットダウン時に子を道連れにする仕組み（`nitro.hooks.hook('close')` での kill）。dev の再起動は必ずしも hook を通らず、これに頼っても起動側の後始末は要る
- タイムアウト・リトライ上限・巡回間隔の設計変更
- **複数のサーバーが同じ保存先を同時に使う前提**（proposal「この change で扱わないもの」）

## Decisions

### Decision 1: 後始末の対象は「記録した pid」ではなく「走っているプロセスの照合」で見つける

起動時に走っているプロセスの一覧（`ps -ww -e -o pid=,args=` 相当）を取り、**argv の中身**で対象を特定する。手がかりは argv に載っている——ストロークは `--session-id` / `--resume` の会話 id、steering は `--mcp-config` に載る cwd（プロジェクトパス）。

**pid を `state.json` に持つ案は採らない。** A8 の契約（受けるのは `invocation` と `retries` だけ）と `state.json` のスキーマ（`docs/specs/core/schema.md`）を広げることになり、書き込み口の追加まで要る。しかも pid は再利用されるので、終了させる前に argv の照合が結局要る——照合が要るなら、照合だけで足りる。本 change より前に起こされた孤児も拾えるという利点もある。

### Decision 2: 「どのサーバープロセスが起こしたか」は判定条件に入れない

複数のサーバーが同じ保存先を同時に使う前提を置かないので（Non-Goals）、`running` として残っているものは前のプロセスの残骸として扱う。会話 id や cwd が一致すれば、それはこのアプリが起こした実行である。

**代替案「argv に載る MCP の URL（ポート）で起こし主のインスタンスを見分ける」は採らない。** その判定は複数インスタンスを同時に走らせる前提の下でしか意味を持たず、単一で動かす通常の運用には不要な重さになる。見分けが要る構成が出てきたら、その時に別 change で扱う。

代替案「ppid が 1 になっているものを孤児とみなす」も採らない。dev の再起動はワーカー（`worker_threads`）の入れ替えで起こることがあり、その場合 OS プロセスは生き残るため ppid が 1 にならない。**ppid では孤児かどうかを決められない。**

### Decision 3: 後始末を巡回から切り出し、起動時の専用ステップにする

いまは巡回プラグインの初回周回が兼ねているが、これは `portal/batch` の規定（「巡回は `failed` だけを拾う」「`running`・`idle`・`error` は拾ってはならない」「それ以外の条件判定を持ってはならない」）と**食い違っている**。後始末を専用のプラグインへ出すと、巡回は `failed` だけへ戻り、規定と再び合う。

- 後始末: 起動時に1回だけ走る。プロセスの照合 → 終了 → 記録の書き換え
- 巡回: `failed` を拾って U13 を叩くだけ

**両者の間に呼び出し順序の取り決めは置かない。** 巡回が拾うのは `failed` だけで、後始末は「終了を確かめてから `failed` を書く」ので、対象1件ごとの順序だけで二重起動は防げている。順序の門を設けても守る相手が居ない。

### Decision 4: 終了させられなかった／調べられなかったものは `error` へ倒す

`failed` へ倒すと巡回が拾って起こし直し、**終了を確かめられていない AI と2つ目が並ぶ**。かといって `running` のまま放置すると、画面に回復の操作が出ない（`useWaitingRetry` が再実行を出すのは `error` のときだけ）。`error` は「自動では何もせず、ユーザーの再実行または削除を待つ」終端として既にあるので、これを使う。

その結果 `error` の意味は「リトライ上限到達の終端」から「**自動では回復しない終端**」へ広がる（specs の MODIFIED）。4値は増やさない——新しい値を足すと、画面・CLI・スキーマ・巡回の判定がすべて影響を受ける。

### Decision 5: 終了のシグナルは既存のタイムアウトと同じ `SIGKILL`

`runClaude` のタイムアウトが既に `SIGKILL` を使っており、そこで終了させられた実行が `--resume` で続けられることは実測で確かめられている（`.scratch/stroke-board-frontier/decisions.md`: 強制終了させても入力は履歴に入っている）。後始末だけ別のシグナルにする理由が無い。

**signal を送っただけで `failed` を書かない。** 終了処理の途中の AI が、まだ MCP を呼んで記録を上書きし得るため、終了を確かめてから書く。

## Risks / Trade-offs

- [プロセス一覧を取れない環境（`ps` が無い・権限が無い）] → 「調べられない」に倒れ、対象は `error` になる。自動では動かなくなるがユーザーに引き渡される。黙って `failed` にして二重起動するより安全側
- [AI が持つ孫プロセス（steering の `npx @pimzino/spec-workflow-mcp`）が残る] → 親を終了させると stdio が閉じ、通常はそれで終わる。残った場合、次の後始末では拾えない（照合に当たらない）
- [argv に頼る照合] → `--mcp-config` の渡し方（JSON 直渡し）を変えると照合が壊れる。`invoke.ts` の組み立てと後始末の照合が同じ事実を見ていることを、テストで固定する
- [pid の再利用] → argv の照合を通してから終了させるので、無関係のプロセスを終了させない
- [同じ保存先を複数のサーバーが同時に使う構成] → Decision 2 のとおり前提に置かない。その構成では、片方の再起動がもう片方の走行中の記録を畳みうる。**扱うなら別 change**

## Migration Plan

- 状態の移行は無い。`state.json` の形は変えず、新しい設定値も増やさない
- 本 change より前に起こされた孤児も、pid の記録に頼らないので初回の起動時後始末で拾える
- ロールバックは、後始末プラグインを外して巡回の初回周回に戻すだけでよい
