## Why

**症状**: 実行の途中でサーバーが再起動すると、走っていた claude が孤児として残る。巡回が記録を `failed` へ倒し、その次の周回（`SWEEP_INTERVAL_MS = 60_000`）が U13 を叩いて起こし直すが、**そのとき孤児がまだ走っていれば、同じ会話 id に claude が2本並ぶ**。

`spawn` に `detached` は付いていないが、親が死んでも子は死なない。

**実測（2026-09-02、本物の `claude -p`）**: `server/utils/stroke/claude.ts` と同じ `stdio: ['ignore','pipe','pipe']` で起こし、2秒後に親だけ `exit` させた。子は `ppid=1` へ里子に出されたまま走り続け、**自分のターンを終えた時点（約38秒後）に自力で exit した**。stdout のパイプが閉じても早く落ちることはない。

つまり**孤児は永久には残らないが、その寿命は親の死ではなくターンの長さで決まる**。「10 から 1 まで数える」程度で38秒。ストロークの実行は guide を読み、`openspec` を叩き、文書を書いてから提出するので分単位になる。**60秒の隙間は容易に越える。**

孤児の側に救うものは無い。再起動で接続表（メモリ）が消えているため、孤児のツール呼び出しは軒並み 401 になり、提出も記録もできない。**新しいサーバープロセスとの関係は既に切れていて、維持する対象ではない。**

**記録が `running` のまま固まること自体は、既に手当てされている。** 巡回（`server/plugins/01.retry-failed.ts`）が「立ち上がって最初の周回だけは `running` も倒す」を持つ。足りていないのは、**起こし直す前に前のプロセスの claude を終わらせること**である。

ただしその初回掃除は、`portal/batch` の規定（「巡回は `failed` だけを拾う」「`running` を拾ってはならない」「それ以外の条件判定を持ってはならない」）と**食い違っている**。後始末を起動時の専用ステップへ出せば、殺すことと記録を倒すことが同じ場所に収まり、巡回は規定どおり `failed` だけを拾う形へ戻る。

出どころ: `provide-operations-via-mcp` の santa-method レビュー 9周目（2026-08-31）。同 change の範囲外として記録していたが、**範囲外の扱いは不正だった**（ユーザー指摘 2026-09-01）ので change を立てる。

## What Changes

- 変更: サーバーの起動時に、**前のプロセスが起こした claude を終了させる**。終了を確かめてから記録を倒す
- 変更: 記録を倒す役目を巡回の初回周回から起動時のステップへ移し、**巡回は `failed` だけを拾う形へ戻す**（`portal/batch` の規定に合わせる）
- 変更しない: 巡回が拾う条件そのもの（`invocation === 'failed'`）・接続表をメモリに置く決定

### この change で扱わないもの

**サーバーインスタンスを同時に複数走らせる前提は持ち込まない。** その前提を置くと「その `running` を起こしたのはどのインスタンスか」を判定する仕掛けが要るが、それは**単一インスタンスで動かす通常の運用には不要なオーバーヘッド**である。`pre5` と本体が同じ `/opt/projects` を見るのは worktree を並走させる開発の都合であって、仕様上の要請ではない。

したがって、終了させる対象は「**前のプロセスがこのアプリとして起こした claude**」であり、インスタンスの区別は判定条件に入れない。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

- `agent/invocation`: 起動時に前のプロセスが残した claude を終了させることを規定に加える

## Impact

- `server/plugins/` — 起動時に前のプロセスの claude を終了させるステップ
- `server/utils/stroke/` — 走っているプロセスを見つけて終了させる手立て
- 記録の書き換え・巡回の条件・接続表の永続化は変えない
