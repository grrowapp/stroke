## Purpose

サーバ API の契約を1つの資料として持ち、画面・エージェントとサーバの境界をコードを読まずに掴める状態と、その資料が実装と食い違わない状態を保つ。

## ADDED Requirements

### Requirement: API の契約は単一の場所に置く

サーバ API の契約を説明する資料は `docs/specs/api/contract.md` の1ファイルでなければならない（SHALL）。同じ内容を複数の場所に置いてはならない（MUST NOT）。

#### Scenario: 境界を知りたい

- **WHEN** 人間またはエージェントが、画面・エージェントとサーバのあいだで何がやり取りされるかを知ろうとする
- **THEN** `docs/specs/api/contract.md` を読めば口の一覧・入出力・エラーが分かり、他のファイルを横断して回る必要が無い

#### Scenario: 契約の説明を書き足したくなった

- **WHEN** API の契約についての説明を新たに書く必要が生じる
- **THEN** 別の資料を作らず `docs/specs/api/contract.md` に加える

### Requirement: 資料は口・入出力・エラー・約束を示す

`docs/specs/api/contract.md` は次のすべてを含まなければならない（SHALL）。

- 公開している口の一覧と、それぞれが誰（画面・エージェント）向けか
- 各口の入力と出力
- 各口が返すエラーと、その意味
- 状態コードの使い分けなど、口をまたいで共通する約束

#### Scenario: 口を1つ調べる

- **WHEN** ある口が何を受け取って何を返すかを調べる
- **THEN** その口の入力・出力・エラーが資料の中で揃って読める

### Requirement: 資料の記述は実装で裏が取れる

資料に書く口・入出力・エラー・振る舞いは、実装から確認できる事実でなければならない（SHALL）。将来の構想、望ましい姿、未実装のものを、現状として書いてはならない（MUST NOT）。

現状にまだ存在しないものに触れる場合は、存在しないことが分かる形で書かなければならない（SHALL）。

#### Scenario: 実装と突き合わせる

- **WHEN** 資料に書かれた口の振る舞いを実装で確かめる
- **THEN** 資料の記述と実装が一致している

#### Scenario: まだ無い口

- **WHEN** 資料が予定している口に触れる
- **THEN** それが未実装であることが明記され、実装済みの記述と混同されない

### Requirement: API の契約を変えたら同じ change のなかで資料も更新する

口の追加・削除、入出力の変更、エラーの変更、または口が担う責務の変更を行ったときは、同じ変更のなかで `docs/specs/api/contract.md` を更新しなければならない（SHALL）。資料と実装が食い違ったまま残してはならない（MUST NOT）。

口の外から見える振る舞いを変えない内部の変更（実装の書き換え・整理）では、更新は要求されない。

#### Scenario: 口の責務が変わる

- **WHEN** ある口が新たに担う仕事が増える、あるいは担わなくなる
- **THEN** `docs/specs/api/contract.md` のその口の記述も同じ変更のなかで更新される

#### Scenario: エラーが変わる

- **WHEN** ある口が返すエラーの条件や種類が変わる
- **THEN** 資料のエラーの記述も同じ変更のなかで更新される

#### Scenario: 内部だけの変更

- **WHEN** 口の入出力もエラーも責務も変えずに実装だけを書き換える
- **THEN** 外から見える契約が変わらないため、資料の更新は要求されない
