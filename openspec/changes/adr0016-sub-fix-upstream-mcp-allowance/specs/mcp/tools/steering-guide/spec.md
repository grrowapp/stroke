# mcp/tools/steering-guide Delta

## ADDED Requirements

### Requirement: 手順は配線された本家 MCP の扱いを、許可の状態と一致する形で述べる

手順の本文は、同じ起動に本家 spec-workflow の MCP が配線されていることと、**この工程ではそのツールを1つも呼ばないこと**を述べる SHALL。

述べる内容は、その起動の許可（`--allowedTools`）と一致していなければならない SHALL。許可されていないツールを「呼んでよい」と読める書き方をしてはならない（MUST NOT）。また、禁じる根拠を手順の文言だけに置いてはならない（MUST NOT）——禁じるなら許可の側でも通らない状態にする（`agent/invocation`）。手順は二重の守りの片方である。

手順の本文は、呼ばない理由を述べる SHALL。少なくとも次を含む。

- 本家の手順（`steering-guide` / `spec-workflow-guide`）は本家のワークフロー向けで、提出の入口が違うこと
- 承認依頼（`approvals`）は、口頭の承認を受け付けず問い合わせ続けることを促すため、無人の実行は待ち続けて打ち切られること。この工程の終わりは3文書が受理されたときで、承認は終わりの条件ではないこと
- 呼んでも許可されていないため通らないこと

手順は、呼ばれた結果として起きることを事実として述べる SHALL。呼べるかのように書いた上で「呼ぶな」とだけ添える形にしてはならない（MUST NOT）。

#### Scenario: 呼ばないと判断できる

- **GIVEN** エージェントが steering 工程の手順を読んでいる
- **WHEN** ツールの一覧に本家 MCP のツールが並んでいる
- **THEN** 手順から、それらを呼ばないことと、呼んでも通らないことが分かる

#### Scenario: 手順と許可が食い違わない

- **WHEN** 手順が本家 MCP について述べていることと、その起動の `--allowedTools` の内容を突き合わせる
- **THEN** 両者は同じことを述べており、許可だけが通している状態にならない

#### Scenario: 承認依頼を出さない

- **GIVEN** エージェントが3文書のうち何本かを提出し終えている
- **WHEN** 手順に従って次の手を決める
- **THEN** 承認依頼を出さずに、残りの文書の提出へ進むか、3本が揃った時点で工程を終える
