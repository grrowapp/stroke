## Why

**起動時チェックが、その前提を必要としない機能まで巻き添えにして落とす。**

`server/plugins/00.startup-checks.ts` は3つを検査し、1つでも欠けると `process.exit(1)` で Nitro のサーバープロセスごと終了する。

1. `/var/lib/stroke-board/sessions` への書き込み
2. `/opt/projects` への書き込み
3. `claude` の起動定義に `--setting-sources project` が含まれるか（ADR 0001）

`throw` が握り潰されるという問題への回避策としてプロセスを殺しているが、意図（実行中に初めて気付かせない）に対して手段が広すぎる。

**AI を起動しないセッションの一覧や削除も、`claude` の起動定義が不正だと実行できない。** それらは `claude` を1度も呼ばない。

**置き場への要求の強さも、機能ごとに違う。** `/opt/projects` は、承認時にプロジェクトを生成する側には書き込みが要るが、そこに何があるかを読むだけの用途には読み取りで足りる。`stroke-board` へ統合すると、プロジェクト一覧の母集合として走査する側が同じディレクトリを**読むだけ**で使う。厳しいほうの要求を全体に及ぼすと、読み取りで足りる使い方が書き込み権限の不足で止まる。

**今やる理由**: 統合するとプロジェクト置き場を読むだけの機能が入る。その時点で書き込み必須の要求が残っていると、統合した側が動かない。

## What Changes

**チェック結果の適用範囲を、プロセス全体から機能単位に絞る。**

- 起動時に検査すること自体は変えない。実行中に初めて気付かせない、という意図は保つ
- 検査の結果を、その前提を必要とする機能だけに効かせる。前提を使わない機能は動かす
- `/opt/projects` への要求を、書き込みが要る用途と読み取りで足りる用途に分ける

`process.exit(1)` をやめる場合、`throw` が握り潰される問題をどう解くかは design で決める。

## Capabilities

### New Capabilities

なし。

### Modified Capabilities

`configuration` — 起動時チェックの適用範囲。実装時に delta を書く。

## Impact

- `server/plugins/00.startup-checks.ts` — 検査の適用範囲
- `server/utils/stroke/settings.ts` — 置き場の検査（`describePathsError()`）が用途を区別する必要があるか
- 各 endpoint / CLI — 前提を必要とする側で結果を受け取る形になる

**出どころ**: `docs/known-issues.md` の「置き場への要求の強さが、機能ごとに違うのに書かれていない」と「起動時チェックがプロセスごと落とす」。同資料が「合わせて直すのが自然」としていたため1つの change にまとめた。同資料はこの change を起こしたことで廃止する。
