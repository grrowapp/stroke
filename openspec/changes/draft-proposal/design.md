## Context

setai はスキーマに依存しないサブコマンド構成の CLI で、Claude Code の `settings.json` を対象にする（動機は proposal.md の Why を参照）。基盤に Go 製の JSON 編集ライブラリを置き、その上に汎用 JSON 編集 CLI と setai 本体の CLI を重ね、さらに setai の操作をメニュー形式で呼び出す TUI を重ねる、4層構成になる。

## Goals / Non-Goals

**Goals:**
- レイヤーの依存方向を一方向に保つ（`json-edit-lib` → `json-edit-cli` / `setai-cli` → `setai-tui`）
- 新しい `settings.json` のキーに対応するサブコマンドを追加する際、メインコマンドの変更を不要にする

**Non-Goals:**
- `settings.json` の全キーを初期リリースでカバーすること（対象キーの範囲は本 design の対象外）
- Claude Code 本体との統合（設定の自動リロードなど）

## Decisions

### レイヤー構成: json-edit-lib → json-edit-cli / setai-cli → setai-tui
副産物である `json-edit-lib` と `json-edit-cli` を `setai` から独立させ、`setai` 固有の知識（どのキーがどう構造化されているか）をそちらに漏らさない。setai の内部にのみ JSON 編集処理を実装し、後から切り出す案も考えられるが、先に切り出しておく方が、setai 側の実装がキー固有ロジック以外に依存しないことを設計の時点で強制できる。

### サブコマンドの登録方式: 各サブコマンドが自己完結したハンドラを持つ
「メインコマンドはキーの知識を持たない」という proposal.md の要求を満たすには、サブコマンド側が読み込み・検証・書き込みの全責務を持つ必要がある。共通のスキーマ定義から動作を導出する方式も考えられるが、「スキーマに依存しない構成を取る」という要求と矛盾するため採らない。

### サブコマンド名とキー名の対応: 明示的なマッピングを各サブコマンドが持つ
サブコマンド名からキー名を機械的に導出しないという要求があるため、各サブコマンドが自身の担当キーを明示的に指定する。メインコマンドはこの対応表を持たず、サブコマンドの登録時に各サブコマンドが自己申告する形にする。

## Risks / Trade-offs

- [対応キーを増やすたびにサブコマンドの実装が要り、キー数の増加に伴って実装コストが線形に増える] → メインコマンドが個々のキーに依存しない構造のため、追加は既存コードに影響せず、コストは新規サブコマンドの実装に局所化される
- [TUI が CLI サブコマンドの実装に依存するため、CLI 側のインターフェース変更が TUI に伝播する] → TUI はサブコマンドが公開する呼び出し口だけに依存させ、サブコマンドの内部実装には依存させない

## Open Questions

- TUI に使う Go 製 TUI ライブラリの選定は未確定。サブコマンドの呼び出し口さえ固まれば後から決められるため、setai-tui の実装着手前に確定させる
- 初期リリースで対応する `settings.json` のキーの範囲は未確定。サブコマンド単位で独立して追加できる構造のため、後から範囲を広げても設計への影響はない
