## ADDED Requirements

### Requirement: 承認の操作は、対象の実行が平常のときにだけ存在する

システムは、セッションの実行の記録（`invocation`。`agent/invocation` が規定する）が `idle` のときにだけ、承認の操作と削除の操作を提供する SHALL。`running`・`failed`・`error` の間はこれらを受け付けてはならず（MUST NOT）、AI が作業中であることを画面に示す SHALL。

**可否は、サーバが持つ実行の記録から導く SHALL。** 画面が自分で起動した実行（差し戻し・問い返しの回答）を覚えているかどうかで導いてはならない（MUST NOT）。画面が起動していない実行——proposal を提出した後にまだ走っている実行、巡回が再起動した実行、別の画面が起動した実行——も、同じ記録から同じように扱われる。

実行の記録の変化は、サーバからその画面へ届く（`api/session/ws`）。画面は届いた記録で可否を更新する SHALL。記録が `idle` に変わった時点で操作が現れる。

「承認できる状態なのに、対象で AI が走っている」状態を作ってはならない（MUST NOT）。サーバ側は実行中の昇格・削除を断らず予約する（`api/session/promote`・`api/session/delete`）が、それは別々の画面が同時に操作したときのためであり、1つの画面からそこへ到達する経路があってはならない（MUST NOT）。

#### Scenario: proposal が届いた直後

- **WHEN** proposal が画面に届いたが、それを提出した実行がまだ終わっていない
- **THEN** proposal は読めるが承認の操作は無く、AI が作業中であることが示されている。実行が終わって記録が `idle` になると承認の操作が現れる

#### Scenario: 差し戻し中にリロードする

- **WHEN** 差し戻しへの応答を待っている最中に画面をリロードする
- **THEN** 実行の記録が `running` として届き、承認の操作は現れない。応答が返って記録が `idle` になると現れる

#### Scenario: 巡回が再起動している

- **WHEN** 前の実行が `failed` に倒れ、巡回がその対象を再起動して走らせている
- **THEN** 画面はその実行を起動していないが、記録が `running` として届くので承認の操作は無い

#### Scenario: 別の画面が実行を起動している

- **WHEN** 同じセッションを開いた別のブラウザが差し戻し、AI が走っている
- **THEN** この画面にも記録が `running` として届き、承認の操作は無い

#### Scenario: 実行が終わる

- **WHEN** 対象の実行が終わり、記録が `idle` に変わる
- **THEN** 承認の操作が現れ、押せる

#### Scenario: 実行が error に達している

- **WHEN** 記録が `error`（自動では回復しない終端）である
- **THEN** 承認の操作は無く、再実行と削除の操作が示される（「実行が error に達したら画面が示し、回復はユーザーが選ぶ」）

## MODIFIED Requirements

### Requirement: 承認の成功で画面2を離れてプロジェクト一覧へ戻る

システムは、承認が成功したときにモーダルを閉じ、プロジェクト一覧へ戻す SHALL。承認の応答は、承認後に始まる次の実行の完了を待ってはならない（MUST NOT）。

**承認の後の steering の起動を、画面が要求してはならない（MUST NOT）。** 昇格の endpoint が起動の段へ引き渡し（`api/session/promote`）、起動は巡回（`portal/batch`）が行う。画面と巡回の両方が起動を要求すると、同じ意図の起動が2つになる。

承認が成功したセッションは、そのセッション id では開けなくなる SHALL。セッションはプロジェクトへ昇格して同じ id のセッションとしては存在しなくなるためである（`project/generation`）。承認後に承認・差し戻しの操作が現れる余地は無い。

承認が成功しなかったときは画面2に留まり、ユーザーが同じセッションで承認し直せる状態を保つ SHALL。

**成功しなかった理由は、ユーザーの次の手が分かる形で示す SHALL。** 理由を捨てて汎用の失敗として示してはならない（MUST NOT）。名前の衝突なら別の名前で承認し直す。昇格の失敗（改名や phase の書き込みの失敗）なら判断は残っているので、昇格だけをやり直すか破棄するかを選ぶ。

昇格が予約として受理されたとき（別の画面が起動した実行が走っていた場合）は、画面はそれを成功と同じに扱い、プロジェクト一覧へ戻る SHALL。一覧には、昇格が行われた時点で生成中の行が現れる（`project/generation`「昇格した瞬間から、生成中であることを一覧で示す」）。

#### Scenario: 承認が成功する

- **WHEN** ユーザーがプロジェクト名を確定して承認し、昇格が成功する
- **THEN** モーダルが閉じてプロジェクト一覧が表示される。次の実行の完了は待たず、画面は起動を要求しない

#### Scenario: 承認したセッションを開こうとする

- **WHEN** 承認が成功した後、そのセッション id の画面2を開こうとする
- **THEN** そのセッションは存在せず画面2は開かない。承認・差し戻しの操作は現れない

#### Scenario: 承認が失敗する

- **WHEN** 名前の衝突や昇格の失敗で承認が成立しない
- **THEN** 画面2に留まり、phase は `proposed` のままで、理由に応じて別の名前で承認し直すか昇格をやり直せる

#### Scenario: 理由の分からない失敗にしない

- **WHEN** 昇格が受理されずに戻る
- **THEN** 画面はサーバが返した理由を捨てず、次の手が分かる形で示す

#### Scenario: 昇格が予約として受理される

- **WHEN** 承認した瞬間に別の画面が起動した実行が走っており、昇格が予約として受理される
- **THEN** モーダルが閉じてプロジェクト一覧へ戻る。実行が終わった時点で昇格が行われ、一覧に生成中の行が現れる
