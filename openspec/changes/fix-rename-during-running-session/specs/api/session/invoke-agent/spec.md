## MODIFIED Requirements

### Requirement: 同一対象の多重起動を受け付けない

システムは、同じ対象で2つの呼び出しを同時に走らせてはならない（MUST NOT）。**実行中の対象への起動要求は、断らずに予約として受理する SHALL。** 予約された起動は、今の実行が終わった時点でシステムが行う。呼び手は起動の要求を出し直さない——要求は1回で足りる。

**「同一対象」は、要求に使われた id ではなく、その実行の作業場所（cwd が指す物理ディレクトリ）を単位とする SHALL。** 同じ物理ディレクトリを作業場所とする呼び出しどうしは、異なる id で要求されても同一対象とみなす SHALL。昇格（`api/session/promote`）は対象の id を uuid からプロジェクト名へ変えるが、ディレクトリの実体は改名の前後で同じものである。したがって昇格前の id で始まった呼び出しと、昇格後の id で起動する呼び出しは同一対象であり、同時に走ってはならない（MUST NOT）。作業場所が異なる呼び出しどうしは別の対象とし、同時に走ることを妨げてはならない（MUST NOT）。

予約は対象ごとに1件とし、実行中に届いた2つ目以降の起動要求は1件に畳む SHALL——次の実行は1回で、要求の数だけ走らせてはならない（MUST NOT）。対象の昇格または削除が予約されているときは、起動の予約は捨てる SHALL（対象が変わる、または消える）。

実行中かどうかを見る他の endpoint——セッションの削除（`api/session/delete`）・プロジェクトの削除・昇格（`api/session/promote`）——は、この同じ単位で判定し、同じく断らずに予約する SHALL。endpoint ごとに別の単位で数え直してはならない（MUST NOT）。

**「実行中だから受け付けない」という応答を、この endpoint も他の endpoint も持ってはならない（MUST NOT）。** 実行中は断る理由ではなく、順番を待つ理由である。

#### Scenario: 実行中に起動を要求する

- **WHEN** 実行中の呼び出しを持つ対象に起動が要求される
- **THEN** システムは要求を予約として受理し、AI は二重に起動されない。今の実行が終わると予約された起動が行われる

#### Scenario: 呼び出しが終わった後に再び起動を要求する

- **WHEN** 実行中だった呼び出しが終わった対象に、再び起動が要求される
- **THEN** システムは受理し、AI の呼び出しをすぐに開始する

#### Scenario: 実行中に2回起動を要求する

- **WHEN** 実行中の対象に起動が2回要求される
- **THEN** 予約は1件に畳まれ、今の実行が終わった後に走る次の実行は1回である

#### Scenario: 昇格の前後で同じディレクトリに起動が要求される

- **WHEN** 昇格前の id で始まった呼び出しが実行中のまま、同じ物理ディレクトリを作業場所として昇格後の id で起動が要求される
- **THEN** そのディレクトリで2つ目の呼び出しは始まらず、起動は予約される

#### Scenario: 別のディレクトリなら同時に走る

- **WHEN** 実行中の呼び出しを持つ対象とは別のディレクトリを作業場所として起動が要求される
- **THEN** システムは受理し、AI の呼び出しをすぐに開始する

#### Scenario: 削除が予約されている対象への起動

- **WHEN** 実行中の対象に削除が予約されており、そこへ起動が要求される
- **THEN** 起動の予約は残らない。実行が終わると削除が行われ、次の実行は始まらない
