## ADDED Requirements

### Requirement: 対象で実行中の呼び出しがある間は昇格させない

システムは、対象に実行中の呼び出しがある間、昇格を実行してはならない（MUST NOT）。昇格の前に対象が実行中かを確認し、実行中であれば **何も変えずに busy であることを伝える** SHALL。改名は起こらず、phase は `proposed` のまま、記録された判断もそのまま残る。呼び出しが終わった後は、同じ判断のまま昇格をやり直せる SHALL。

**これは防波堤である。** 画面は実行中の対象に承認の操作を出さない（`stroke/frontier`「承認の操作は、対象の実行が平常のときにだけ存在する」）ので、正しく動いている系でこの拒否に到達する経路は無い。それでもサーバは画面を信用せず、自分で確認する SHALL。

実行中かの判定の単位は、起動の受け口（`api/session/invoke-agent`）が定める「同一対象」と同じものとする SHALL——別の単位で数え直してはならない（MUST NOT）。

**確認から昇格の完了までの間に、対象への新しい呼び出しの起動が始まってはならない（MUST NOT）。** 昇格の完了とは、改名・phase の書き込み・起動の段への引き渡し（「昇格した時点で、steering の実行はまだ済んでいないものとして残る」）がすべて終わった時点である。実行中でないことを確認した後に起動が入り込めると、確認をすり抜けた呼び出しが改名の最中に走り出す。システムはこの区間を、起動が割り込めない1つの区間として扱う SHALL。区間の途中に、起動を受け付けるが起こし直す印がまだ無い瞬間を作ってはならない（MUST NOT）。

昇格が完了した後、昇格の成功を見た側が続けて要求する起動は、**昇格自身の占有を理由に断られてはならない（MUST NOT）**。昇格の応答を受け取った時点で、その対象は起動を受け付けられる状態にある SHALL。

理由は、昇格が**セッションディレクトリの改名**だからである（`project/generation`）。改名はディレクトリの実体を移さないため、走っている呼び出しは改名先で生き続ける一方、その呼び出しが自分を名乗る id は改名前のものである。改名の後はその id で参照できるものが無く、以後その呼び出しが行う操作——問いの送信・文書の提出・実行の記録——はすべて対象を見つけられずに落ちる。走らせたまま改名すると、その呼び出しの成果はどこにも残らない。

#### Scenario: 実行中に昇格が要求される

- **WHEN** 対象に実行中の呼び出しがある状態で昇格が要求される
- **THEN** システムは受理せず busy であることを伝える。ディレクトリは改名されず、phase は `proposed` のまま、記録された判断は残っている

#### Scenario: 呼び出しが終わった後に昇格をやり直す

- **WHEN** 実行中だった呼び出しが終わった後に、同じ対象へ再び昇格が要求される
- **THEN** システムは受理し、記録された判断の名前で昇格を実行する

#### Scenario: 確認の後に起動が割り込もうとする

- **WHEN** 昇格が実行中でないことを確認した後、改名と phase の書き込みが終わる前に、同じ対象への起動が要求される
- **THEN** その起動は昇格の完了までは始まらず、改名の最中に走る呼び出しは生まれない

#### Scenario: 改名が走っている呼び出しを置き去りにしない

- **WHEN** 昇格が受理されて成功した
- **THEN** 改名の時点で対象に走っていた呼び出しは無く、改名前の id を名乗ったまま生き残る呼び出しは存在しない

#### Scenario: 昇格の成功を見た側が起動を要求する

- **WHEN** 昇格の成功応答を受け取った側が、続けてその対象の起動を要求する
- **THEN** その起動は昇格自身の占有を理由に断られず、受理される
