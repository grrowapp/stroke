## ADDED Requirements

### Requirement: 対象で実行中の呼び出しがある間は改名せず、実行の終わりに昇格する

システムは、対象に実行中の呼び出しがある間、改名を行ってはならない（MUST NOT）。実行中に昇格が要求されたときは、**断らずに予約として受理し、今の実行が終わった時点で昇格を行う SHALL。** 予約の時点では何も変えない——改名は起こらず、phase は `proposed` のまま、記録された判断もそのまま残る。

実行中かの判定の単位は、起動の endpoint（`api/session/invoke-agent`）が定める「同一対象」と同じものとする SHALL。

**予約された昇格は、実行の終わりに、記録された判断の名前で行う SHALL。** 昇格の内容は即時の昇格と同じであり、衝突確認・改名・phase の書き込み・起動の段への引き渡し（「昇格した時点で、steering の実行はまだ済んでいないものとして残る」）をすべて行う。予約された昇格が失敗したときは、即時の昇格が失敗したときと同じ状態——元の名前・`proposed`・判断つき——で残す SHALL。

**確認から昇格の完了までの間に、対象への新しい呼び出しの起動が始まってはならない（MUST NOT）。** 昇格の完了とは、改名・phase の書き込み・起動の段への引き渡しがすべて終わった時点である。区間の途中に、起動を受け付けるが retry 対象の印がまだ無い瞬間を作ってはならない（MUST NOT）。この区間に届いた起動要求は予約される（`api/session/invoke-agent`）。

昇格が予約されている対象に起動の予約があれば、それは捨てる SHALL——昇格後の対象の起動は、起動の段への引き渡しから始まる。

「実行中だから受理しない」という応答を持ってはならない（MUST NOT）。画面は実行中の対象に承認の操作を出さない（`stroke/frontier`「承認の操作は、対象の実行が平常のときにだけ存在する」）ので、予約に落ちるのは同じセッションを別々の画面が同時に操作したときだけである。

理由は、昇格が**セッションディレクトリの改名**だからである（`project/generation`）。改名はディレクトリの実体を移さないため、走っている呼び出しは改名先で生き続ける一方、その呼び出しが自分を名乗る id は改名前のものである。改名の後はその id で参照できるものが無く、以後その呼び出しが行う操作——問いの送信・文書の提出・実行の記録——はすべて対象を見つけられずに落ちる。走らせたまま改名すると、その呼び出しの成果はどこにも残らない。

#### Scenario: 実行中に昇格が要求される

- **WHEN** 対象に実行中の呼び出しがある状態で昇格が要求される
- **THEN** システムは予約として受理する。ディレクトリは改名されず、phase は `proposed` のまま、記録された判断は残っている

#### Scenario: 予約された昇格が実行の終わりに行われる

- **WHEN** 昇格が予約された対象の実行が終わる
- **THEN** システムは記録された判断の名前で昇格を行い、対象はプロジェクトになる。改名の時点で対象に走っていた呼び出しは無い

#### Scenario: 予約された昇格が失敗する

- **WHEN** 予約された昇格が実行の終わりに行われ、衝突または改名・書き込みの失敗で成立しない
- **THEN** セッションは元の名前・`proposed`・判断つきのまま残り、同じ判断のまま昇格をやり直せる

#### Scenario: 確認の後に起動が届く

- **WHEN** 昇格が実行中でないことを確認した後、昇格の完了前に、同じ対象への起動が要求される
- **THEN** その起動は予約され、改名の最中に走る呼び出しは生まれない

#### Scenario: 改名が走っている呼び出しを置き去りにしない

- **WHEN** 昇格が成功した（即時でも予約でも）
- **THEN** 改名の時点で対象に走っていた呼び出しは無く、改名前の id を名乗ったまま生き残る呼び出しは存在しない
