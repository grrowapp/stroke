## Context

動機は proposal.md「Why」。ここでは形を決めるのに要る現状だけを置く。

- 実行の記録 `invocation` は `state.json` にあり、書き込みは A8（`writeInvocation`）の1箇所。画面へは push されておらず、`useWaitingRetry` が**自分が起こした待機の間だけ** U2 を3秒おきに読む
- 画面2 の待機は `pendingAction`（差し戻し）と `agentQuestion.waiting`（問い返し）で、どちらもメモリ上。承認ボタンの無効化はこの2つから導いている
- セッション向けの WS は W1（問い）と W2（proposal）の2本。`ws/delivery` は「同じ相手へ届く出来事が増えても口を増やさず、メッセージの種別で分ける」「接続の瞬間に現在分を配信する」を定める
- 昇格（U14）は `beginRun` で改名前の実体を占有し、`finally` で解放してから配信・A8 への引き渡し・204 の順。占有の解放位置の根拠（「後に回すと U13 が 409 になる」）は、U13 が 204 の後に叩かれる実際の順序と合っていない
- 防波堤（`running.ts` の inode キー・U14 の 409 busy）は入っている。`running.test.ts` は「design.md D2」を参照している

## Goals / Non-Goals

**Goals:**

- 「承認できる状態なのに、対象で AI が走っている」が**存在しない**こと。画面が知らない実行（proposal 直後・リロード・巡回・別タブ）を含めて
- 承認の可否の源を1つ（サーバの `invocation`）にすること
- 防波堤（409 busy）は残すが、そこへ到達する経路を持たないこと

**Non-Goals:**

- `useWaitingRetry` のポーリング撤去（`replace-polling-with-push` の本題）。本 change は push を足すところまで
- 画面1（ストローク中）の回答操作に同じ原則を通すこと。同じ形で解けるが、範囲を広げない
- 差し戻し・問い返しの待機表示（`sendingBack` / `followupWaiting`）の統廃合。文言を場面ごとに与える都合で残す

## Decisions

### D1. 承認の可否はサーバの `invocation` から導く。画面の行動からは導かない

画面2 は `phase === 'proposed' && invocation === 'idle'` のときだけ承認の操作を出す。`running`・`failed`・`error` では出さず、AI が作業中であることを示す。

- `failed` も出さない。`failed` は「起こし直す対象」の印で、巡回が 60 秒以内に再び走らせる。承認できる瞬間として扱うと、巡回との競合を作る
- `error` は既存の規定（再実行／削除）に委ねる。承認は出さない。proposal は残っているので、再実行すれば締めの実行が走って `idle` に戻る

代替: 「承認を押した瞬間に U2 を読んで確認する」——押した時点と昇格の時点の間に窓が残る。源を1つにする方が単純で、窓も無い。

代替: 「A7 の受理を実行の終わりまで遅らせる（proposal の配信を後ろへ）」——ユーザーが proposal を読み始めるのが遅れる。proposal は読めて承認だけ待つ方がよい。

### D2. busy ガードのキーは作業場所ディレクトリの実体（`stat` の `dev`/`ino`）

`running.test.ts` が参照する D2 はこれ。判断は実装済みで、ここに理由を残す。

- id をキーにすると、昇格の改名で uuid → プロジェクト名に変わった瞬間、同じディレクトリが別の枠になる。inode は改名で変わらないので、実体をキーにすれば改名の前後で同じ枠になる
- キーの導出（`keyOf`）は1箇所に置く。口ごとに別の導出を持つと、同じディレクトリが口によって別物に見える
- `stat` に失敗したら投げる。既定値で補って別のキーに落ちる経路を作らない——枠を取り違えるくらいなら、枠を取れない方がまし
- `endRun` は `beginRun` が返したキーで解放する。実行中に改名・削除されても `stat` し直さずに外せる

### D3. `invocation` の変化はセッション向けの WS（W1・W2）にメッセージ種別として載せる

`ws/delivery` に従い口は増やさない。W1・W2 のメッセージを判別できる形（種別を持つ union）にし、`invocation` の種別を足す。

- 源は `writeInvocation`（A8 の実体）。書き込みが成功した後に publish する。既に `broadcastProjectCreation` を同じ場所から呼んでいるので、置き場は決まっている
- 接続時の現在分は W1・W2 の route が `readState` して配信する。既存の「現在の1問／proposal を接続時に1件流す」と同じ形
- W1 と W2 の両方に載せる。運ぶ相手は「そのセッションを見ている画面」で同じ。画面1 は W1、画面2 は W2 を張っているので、どちらでも届く
- 種別を付けると既存の `ProposalMessage` / `Question` の形が変わる（`docs/specs/api/contract.md` の W1/W2）。**docs の改訂はユーザー承認を経て行う**（提案は下の「docs への反映」）

代替: 新しい口 W3——`ws/delivery` に反する。`replace-polling-with-push` も同じ理由で要改訂になっている。

代替: 画面2 が常時 U2 をポーリング——push の原則（`upstream-connection`「定期ポーリングで取りに行かない」）に反する。

### D4. 占有は起動の段への引き渡しまで持つ

U14 の `endRun` を A8 への引き渡し（`invocation: failed` の書き込み）の後ろへ動かす。順序は「占有 → 衝突確認 → 改名 → phase → 配信 → 提出記録の破棄 → A8 → 解放 → 204」。

- 今の位置の根拠「解放を後に回すと自分の占有で U13 が 409 になる」は成り立たない。U13 を叩くのは 204 を見た画面で、204 は A8 の後
- 今の位置だと「枠が空きで `invocation` が `idle`」の窓がある。今そこで叩く者は居ないが、規定（「区間の途中に、起動を受け付けるが起こし直す印がまだ無い瞬間を作らない」）を素直に満たすには閉じるのが筋
- 巡回が窓の直後に `failed` を拾って先に起こすことはある。それは画面の U13 が 409 busy を受ける形で決着し、画面はそれを失敗と扱わない（既存）

`docs/specs/api/sessions/promote.md`「占有は改名と `phase` の書き込みが終わった直後に解く」の根拠の文を直す。**docs の改訂はユーザー承認を経て行う。**

### D5. 409 の文言は断る側が持つ

`beginRun` の「完了するまで新しい**起動**は受け付けない」は起動を断る文言で、改名を断る U14 がそのまま出すと合わない。`beginRun` は理由 `busy` を投げ、文言は呼び出し側（U13・U14）が与える。

### D6. 承認画面は失敗の理由を握りつぶさない（ADR 0021）

`promote()` の失敗は理由ごとに分ける。`name-conflict` は名前の入れ直し、500 は昇格のやり直し／破棄、`busy` は D1 により到達しないので、届いたら**欠陥**としてサーバの文言をそのまま失敗に出す。「待てば通る」の器は作らない——作ると、到達しないはずの状態を正常系として抱えることになる。

### D7. `ui` artifact は作らない

画面の変更は「承認の操作が出ない間、AI が作業中であることを示す」だけで、既存の待機の器（`WaitingIndicator`・薄くした固定バー）で足りる。見比べて選ぶ設計問題が無い。

### docs への反映（承認後に行う）

| docs | 直す内容 |
|---|---|
| `docs/specs/api/contract.md` W1/W2 | メッセージが種別を持つ union になり、`invocation` の種別が加わること。U2「回答や差し戻しを送って待っている間だけ、数秒おきに読み直す」は `replace-polling-with-push` の範囲なので触らない |
| `docs/specs/api/sessions/promote.md` | 「占有は改名と `phase` の書き込みが終わった直後に解く」→ 起動の段への引き渡しの後。根拠の文を「解放を後にすると U13 が 409 になる」から「引き渡し前に枠を空けると、起動を受け付けるが起こし直す印が無い窓ができる」へ |

## Risks / Trade-offs

- [W1/W2 のメッセージ形が変わる] → 既存の受け手（`useAgentQuestion`・`useProposalReview`・E2E の WS スタブ）を同じ change で揃える。種別の無いメッセージを受けたら無視する猶予は置かない——2種類の形を同時に抱えない
- [`replace-polling-with-push` との重複] → あちらの W3 は本 change の種別で吸収される。あちらの proposal は要改訂。ポーリング撤去はあちらに残す。本 change が先に入れば、あちらは「購読へ入れ替える」だけになる
- [`idle` が届く前に画面が承認を出す実装漏れ] → 承認の可否を `computed` 1つに閉じ、その源を `invocation` の ref だけにする。E2E で「proposal 到着 → `running` のまま → 承認なし → `idle` → 承認あり」を固定する
- [占有を長く持つことで U14 の応答が遅れる] → 延びるのは A8 への内部 fetch 1回分。もともと応答前に待っていた
- [接続の瞬間の `readState` と、直後の書き込みの順序] → 現在分の配信と出来事の配信は区別できる（`ws/delivery`）。画面は後に届いた方で上書きする

## Migration Plan

1. サーバ: `writeInvocation` の publish と W1/W2 の接続時配信、メッセージ型の種別化
2. 画面: 受け手を種別で分岐させ、承認の可否を `invocation` から導く
3. U14: 占有の解放位置、`beginRun` の文言
4. 承認画面の失敗理由の分岐
5. docs の反映（承認後）

ロールバックは change 単位。W1/W2 の形が変わるので、サーバと画面を別々に戻さない。
