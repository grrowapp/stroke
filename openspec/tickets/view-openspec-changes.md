# view-openspec-changes

プロジェクト下層に changes 画面を新設する。openspec/tickets/ を主役に一覧し、change のアーティファクトを閲覧する（読むだけ）

## Triage Notes

> *This was generated by AI during triage.*

**範囲が「読むだけ」で足りるかが決まっていない（2026-08-25 の確認）。**

この change は閲覧に範囲を絞っている。しかし change を単位にした継続管理（線）を持ち込む構想が別にあり、`openspec/tickets/` の存在自体がその所以である。線を入れるなら、この画面は「読むだけ」では足りず、状態を動かす盤になる。

**被せる方式の候補が具体化している。** Cork（`~/work/repo/Cork`。ローカルの Markdown をカンバンで管理するツール）の方式を `openspec/tickets/` に被せることが検討されている。Cork は1タスク = 1つの Markdown で、frontmatter に `status` / `order` / `tags` / `date` を持ち、`status` は任意文字列、列はワークスペース側がラベルの一覧として持つ。`openspec/tickets/` は既に「1 change = 1 md」なので構造がそのまま重なる。

2026-08-25 の triage で、この方式に沿った frontmatter（`status` に triage の状態、`tags` に分類）を全チケットへ入れた。**盤としての実体は既にファイル側にある。**

**決めてもらう必要があること:**

- **この画面の役割。** 閲覧専用のままか、状態を動かせる盤にするか。後者なら Cork 相当のカンバン UI をこの画面に持つことになり、規模が大きく変わる。
- **Cork との関係。** Cork をそのまま使うなら、この画面は不要かもしれない（`openspec/tickets/` を Cork のワークスペースとして開けば済む）。画面を作るのは、ポータルの中で完結させたい場合。
- **見せる場所。** proposal はプロジェクト下層に限り、ポータル（上層）での横断は別の検討としている。線の管理を入れるなら、複数プロジェクトを束ねて見たくなる可能性がある。

**関連:** この change の対象である `openspec/tickets/` は OpenSpec 標準には無い独自の追加で、線の器として置かれたもの。change 本体の artifact（`openspec/changes/`）とは別物であり、両者の関係（カードを動かしても change は動かない）をどう扱うかも設計の論点になる。
