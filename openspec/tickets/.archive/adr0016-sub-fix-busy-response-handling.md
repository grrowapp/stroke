# adr0016-sub-fix-busy-response-handling

回答したあと画面が「AI を起動できませんでした。」で止まり、同じ問いにもう一度答えるまで先へ進めない。

## 何が起きているか

実測（ブラウザで一から通した結果、毎回発生）:

1. ユーザーが問いに答える → U7 は受理される（`strokes.json` に記録される）
2. 画面が続けて U13 を呼ぶ → 前の claude がまだ走っているので **409 busy**
3. 画面が「AI を起動できませんでした。」を出す
4. 走っていた claude がそのまま終了すると `invocation` は `idle` に戻るが、`currentQuestion` は残ったまま。誰も AI を起こし直さない
5. ユーザーにできるのは同じ問いにもう一度答えることだけ。2回目は `idle` なので U13 が通る

結果、`strokes.json` に同じ問いへの回答が重複して記録される（実測: 「実行環境」×3・「完了指定」×2・「保存場所」×2）。

## 409 自体は仕様どおり

`docs/specs/api/contract.md`:

- `:29-30` AI の起動は U13 が唯一の入口。受理系（U1・U7・U9）は AI を起動しない。画面は受理の成功応答の直後に U13 を呼ぶ
- `:111` U7 — 実行中でも受理する（busy は見ない。**多重起動は U13 が止める**）
- `:180` U13 — 409 busy（実行中の多重起動）

前の claude が走っている間に 409 が返るのは設計どおりの正常な結果である。**壊れているのは画面側の受け取り方。**

## 触るファイル

- `app/pages/strokes/[sessionId]/index.vue:118-125` — **ここが今回の発生源。** `catch` が理由を見ずに一律「AI を起動できませんでした。」を出す。409 とそれ以外を区別していない。`waitingRetry.startWaiting()` も `try` の中にしかなく、409 のとき待機状態に入らない
- `app/composables/useAgentQuestion.ts:117-128` — 409 を区別する分岐は持っている（「まだ前の応答を待っています」）が、`waitingRetry.startWaiting()` は成功時しか呼ばれない
- `app/composables/useProposalReview.ts:306-317` — 上と同じ形。同じ扱いが3箇所に散っている

## 論点

- **409 は「失敗」ではない。** 前の実行がまだ走っており、その claude が答えを拾って次の問いを出す。画面は待機に入るのが正しい
- 3箇所に同じ扱いが散っており、ページ側だけ区別を持っていない。どこか1本にまとめるべきか
- 走っていた claude が次の問いを出さずに終了した場合、誰も起こし直さない経路が残る。409 の扱いを直すだけでは塞がらない可能性がある（`invocation: idle` + `currentQuestion` あり、という状態を誰が拾うか）
