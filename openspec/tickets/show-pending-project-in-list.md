# show-pending-project-in-list

承認の直後から、作られつつあるプロジェクトを一覧に出す。作り終わったこと・作りきれなかったことを、その場で知らせて次を選ばせる。

承認はプロジェクトを作る唯一の引き金であり、処理はセッションディレクトリをプロジェクト名へ改名するだけなので、**実体は承認した瞬間に存在している**。にもかかわらず一覧の母集合は `.spec-workflow/` を持つディレクトリに限られていて、それを作るのは承認後に裏で走る steering である。モーダルを閉じて一覧へ戻ったユーザーが見るのは、さっきまでと変わらない一覧になる。

## 決定（2026-08-29・ユーザー確認済み）

**1. 決着の知らせ方は2つに分かれる**

| | 知らせる面 | 選ばせるモーダル |
| --- | --- | --- |
| 大きさ | **画面の半分くらい**。小さすぎず、全面でもない | 確認を出す寸法 |
| 終わり方 | **フェードアウトで自ら消える** | **選ぶまで閉じない** |

順序は 知らせる面 → フェードアウト → モーダル。**知らせる面が自ら消えるのは、消えないと操作ができないためである。** 「1つの器が2画面を持ち、どちらも自ら消えない」という当初の記述は誤りで、訂正済み。

**2. 成功で「レビューする」を選んだときの飛び先**

`/projects/<projectId>/approvals/<approvalId>`。今まさに作られた steering への承認依頼を**開いた状態**で表示する。`approvalId` は `GET /api/projects/<projectId>/approvals` から引く。

通知の行から開くとき（承認画面を開くだけで、スクロールもハイライトもしない）とは**意図的に違える**。通知は対象が1つとは限らないが、生成の完了は対象が1つに決まっている。

**3. 承認は「決定」と「昇格の実行」を分ける**

今の `approve.post.ts` は、確定した名前をリクエストの body で受け取り、**どこにも書かないまま**改名に入る。成功して初めて `writeState` で残る。だから改名に失敗すると名前が消え、回復にはユーザーへ承認をやり直させることになる。**システム動作の失敗を、ユーザーの決定のやり直しへ escalate している。**

順序を変える。

1. 確定した名前を `state.json` に書き、`phase` を `approved` にする
2. その上で改名し、`phase` を `activated` にする
3. 失敗したら、やり直しは `state.json` の名前を読んで**実行だけを再試行する**。再承認を挟まない

`phase` は4値になる。

| 値 | 意味 |
| --- | --- |
| `stroking` / `proposed` | 従来どおり |
| `approved` | **決定済み。まだ uuid のディレクトリ** |
| `activated` | **昇格済み。ディレクトリはプロジェクト名** |

**4. phase の型判定は zod で行う**

`state.json` から読む値なので、規定の値かどうかは検証しないと分からない。今は3箇所が**手書きの文字列比較**で読んでいる（`session-core.ts` の `readPhase`、`handler/phase.ts` の `readPhase`、`session-store.ts` の `stateSchema`）。**`session-core` と `handler/phase` の修正は必須。**

置き場は `shared/` 配下。画面もサーバーも使うためである。**直置きはしない。**

```
shared/
├── schema/    zod の定義（phaseSchema など）
└── type/      schema から z.infer で生成した型
```

**5. 一覧の行は3状態**

アクティブ / 未接続 / 生成中。**「作成に失敗」の状態を持たない**——失敗はモーダルで決着し、やり直せば生成中に戻り、破棄すれば行が消える。

**6. 生成中の見せ方**

行の地を変え、フォルダアイコンの位置でローダーを回す。名前と日付は未接続と同じ薄さ。**行の明滅は持たない**——一覧の行は情報が詰まっており、周期的に薄くすると「進行中」ではなく読みにくい行になる（prototype で確認）。

**7. 生成中か完了かの判定はファイルシステムの事実だけ**

`phase` が昇格済みで `.spec-workflow/` が無ければ生成中、有れば完了。**`invocation` は見ない**——永続値なのに時間切れの見張りがプロセス内にしかなく、サーバーが落ちると `running` のまま誰も戻さないためである。

**8. 配信は既にある WS に載せる**

新しい endpoint を立てない。board WS（`/ws`）にメッセージ型を足す。WS が運ぶのは「決着したから取り直せ」という合図であって、行の状態そのものではない。

## 未決

- **`shared/` の再編**（`schema/` と `type/` に割る）を、この change に含めるか別 change に切るか。宣言36件・import 45箇所に触れる
- **`project/generation` の既存要件の書き換え。** 「`phase` が `approved` なのに昇格していない状態を作ってはならない」は、`approved` が「決定済み・未昇格」を指す値になることで成り立たなくなる
- **決着の見せ方の実物。** 知らせる面の寸法・出方・フェードアウトの速さ・confetti の量・モーダルへ移る間合い。**次の着手は prototype**（tasks 9.1）。前の prototype の3案はすべて「自ら消える帯」を比べたもので、根拠にならない
- **`projectId` の導出。** 本家が id の材料にしているのは `workspacePath` で、こちらが渡しているのは `workflowRootPath` という名前のフィールドである。承認で作ったものは一致するが、`SPEC_WORKFLOW_SHARED_ROOT` の下では分かれる。実機で突き合わせる
