# proposal-review Specification

## Purpose
把握完了時に AI が起こした proposal をユーザーが確認し、差し戻すか承認するかを決める場を提供する。承認はプロジェクト生成の唯一の引き金であり、その確定もここで行う。

## Requirements

### Requirement: proposal を Markdown プレビューで示す

システムは最新の proposal を画面2で Markdown としてレンダリングして示す SHALL。proposal は OpenSpec の proposal 形式（`## Why` / `## What Changes` / `## Capabilities` / `## Impact`）に従う。

#### Scenario: 画面2を開く

- **WHEN** phase が `proposed` のときユーザーが画面2を開く
- **THEN** 最新の proposal が Markdown プレビューとして表示され、承認と差し戻しの操作が並ぶ

### Requirement: proposal の見せ方を切り替えられる

システムは proposal の見せ方として、整形されたプレビュー、指摘を付けられる素の本文、その両方を並べた表示を用意する SHALL。指摘を付けられるのは素の本文の側とする。

#### Scenario: 見せ方を切り替える

- **WHEN** ユーザーが見せ方を切り替える
- **THEN** 同じ proposal が、選んだ見せ方で表示される

#### Scenario: プレビューでは指摘を付けない

- **WHEN** 整形されたプレビューだけを見ている
- **THEN** そこから箇所を選んで指摘を付けることはできない

### Requirement: 指摘は proposal の本文に紐づけて積める

システムはユーザーが proposal の一部を選び、その箇所に対する指摘を付けられるようにする SHALL。箇所は素の本文における位置として保持し、引用した文字列も併せて保持する。同じ語が本文に複数回現れても、選んだ箇所が一意に定まらなければならない。箇所に紐づかない全体への指摘も同じ一覧に積める。

指摘を書くときは、選んだ箇所が引用として示され、本文上でその箇所を目立たせる色を選べる。

#### Scenario: 本文の一部に指摘を付ける

- **WHEN** ユーザーが proposal 本文の一部を選んで指摘を書く
- **THEN** その指摘は選んだ箇所と結び付いて一覧に積まれ、本文上でもその箇所が選んだ色で目立つ

#### Scenario: 同じ語が複数回現れる

- **WHEN** 選んだ語と同じ語が本文の別の場所にもある
- **THEN** 目立つのは選んだ箇所だけで、他の同じ語は変わらない

#### Scenario: 全体への指摘を付ける

- **WHEN** ユーザーが箇所を選ばずに指摘を書く
- **THEN** その指摘は全体への指摘として同じ一覧に積まれる

### Requirement: 積んだ指摘を見直し、直し、取り消せる

システムは積まれた指摘を一覧で示す SHALL。一覧の各件は、全体への指摘か本文への指摘かの別、引用の全文、指摘本文を持つ。本文への指摘は書き直せる。取り消しは確認を挟む。

#### Scenario: 一覧を見る

- **WHEN** ユーザーが指摘の一覧を見る
- **THEN** 各件について、種別・引用の全文・指摘本文が分かる

#### Scenario: 本文上から指摘に戻る

- **WHEN** ユーザーが本文上の目立たせた箇所を選ぶ
- **THEN** その箇所に付けた指摘を書き直せる

#### Scenario: 指摘を取り消す

- **WHEN** ユーザーが一覧から指摘を取り消そうとする
- **THEN** システムは確認を求め、確認が取れたときだけ一覧と本文上の両方から消す

#### Scenario: 指摘がまだ無い

- **WHEN** 指摘が1件も積まれていない
- **THEN** 一覧は空であることと、指摘の付け方が分かる形で示される

### Requirement: 差し戻すと proposal が出し直される

システムは積まれた指摘を1回の差し戻しとして送り、出し直された proposal で表示を更新する SHALL。差し戻しの受理と AI へ渡る内容の用意は `api/send-back` が、AI の起動は `api/invoke-agent` が規定する。

#### Scenario: 指摘を積んで差し戻す

- **WHEN** ユーザーが1件以上の指摘を積んで差し戻す
- **THEN** システムは全ての指摘を1回の差し戻しとして送り、出し直された proposal で表示を更新する。phase は `proposed` のまま変わらない

#### Scenario: 指摘が1件も無いまま差し戻す

- **WHEN** 指摘が1件も積まれていない状態で差し戻し操作が行われる
- **THEN** システムは差し戻さず、指摘が必要であることとその付け方を示す

#### Scenario: 差し戻した後

- **WHEN** 差し戻しが送られる
- **THEN** 積まれていた指摘は消え、更新された proposal に対して新しく積み直せる

#### Scenario: 何度でも差し戻す

- **WHEN** ユーザーが更新された proposal に対してさらに差し戻す
- **THEN** 回数の上限なく同じ手順で差し戻せる

### Requirement: 差し戻しの応答待ちは修正中と分かる待ち受け画面で示す

システムは差し戻しの応答を待っている間、「AI が修正中です」をブリンク表示する待ち受け画面を示す SHALL。この待ち受け画面は、ストロークの待機表示と基本の仕様（点滅による表示）を同じくし、文言のみ差し戻し固有とする。待機中であることを proposal 画面のヘッダーで示してはならない。待機表示の文言は場面ごとに規定し、示す側が与える。

待ち受け中、上部固定バー（パンくず・ビュー切替・差し戻す・承認）は薄く表示したまま残し、操作を受け付けない。

#### Scenario: 差し戻すと待ち受け画面に移る

- **WHEN** ユーザーが差し戻す
- **THEN** 「AI が修正中です」がブリンク表示される待ち受け画面に遷移する。proposal 画面のヘッダーには待機表示を出さない。上部固定バーは薄く表示され、さわれない

#### Scenario: 修正が返ると proposal 画面に戻る

- **WHEN** 差し戻しへの応答として出し直された proposal が返る
- **THEN** 待ち受け画面を抜けて proposal 画面に戻り、更新された proposal が表示される

#### Scenario: 応答が問い返しだった

- **WHEN** 差し戻しへの応答として問い返しが返る
- **THEN** 待ち受け画面を抜け、問い返しが届いたことが示される

### Requirement: 差し戻しに対して AI が問い返せる

差し戻しを受けた AI が、proposal を出し直す前に確認を返すことがある。システムはこれを画面2 の中で受ける SHALL。画面1 へ戻してはならない。指摘の対象である proposal を見たまま答えられることを優先する。

問い返しが届いたことは、他の表示と区別できる形で目立たせて知らせる。知らせを選ぶと、答えるための面が開く。

#### Scenario: 問い返しが届く

- **WHEN** 差し戻しに対して AI が確認を返す
- **THEN** 画面2 のまま、問い返しが届いたことが目立つ形で示される

#### Scenario: 答える面を開く

- **WHEN** ユーザーがその知らせを選ぶ
- **THEN** 答えるための面が開き、proposal を離れずに回答できる

### Requirement: 問い返しは1問1答を繰り返す

システムは問い返しをストロークと同じ1問1答で扱う SHALL。1問には話題タグ・詳細説明・問い本文・選択肢とその説明・自由入力欄が揃い、推奨があればその印が付く。並びと長さの規定はストロークの問いと同じとする。回答すると次の問いが同じ面に現れ、面は閉じない。

問いの総数を先に示してはならない。何問続くかは AI が決めるため、決め打ちの数を出すと実態と食い違う。

問い返しに答えて次を待つ間の待機は、答える面の中で示す。待機表示の文言は場面ごとに規定し、示す側が与える。この場面の文言は「AI が次を考えています…」とする。

#### Scenario: 続けて問われる

- **WHEN** ユーザーが問い返しの1問目に答える
- **THEN** 面は閉じず、次の問いが同じ面に現れる

#### Scenario: 問い返しもストロークと同じ形で出る

- **WHEN** 問い返しが画面に出る
- **THEN** 話題タグ・詳細説明・問い本文・選択肢・自由入力欄が、ストロークの問いと同じ並びで表示される

#### Scenario: 総数を示さない

- **WHEN** 問い返しに答えている
- **THEN** 残り何問あるかは示されない

#### Scenario: 次を待っている

- **WHEN** 回答を返してから次の問いが返るまでの間
- **THEN** 答える面は開いたまま、その中で「AI が次を考えています…」が点滅し、待機中であることが示される

#### Scenario: 問いが尽きる

- **WHEN** AI が問い返しを打ち止める
- **THEN** 答えるための面は閉じ、出し直された proposal が表示される

### Requirement: プロジェクト名を提案し、ユーザーが確定する

AI は kebab-case のプロジェクト名を提案する SHALL。システムは画面2で名前の候補を当てる際、既存のプロジェクトの名前を除いた候補を当てる SHALL。ユーザーは画面2でその名前を編集し、承認時に確定する。

システムは確定する名前を、受理と保存のどちらでも、長さを理由に拒否しない SHALL。名前の長さに対する製品側の上限を持たない。実行環境がディレクトリ名として受け付けない名前は、プロジェクト生成の失敗として扱う（project-generation が規定する）。

#### Scenario: 提案された名前をそのまま確定する

- **WHEN** ユーザーが提案された名前を変更せずに承認する
- **THEN** その名前が確定名としてプロジェクト生成に渡る

#### Scenario: 名前を書き換える

- **WHEN** ユーザーが画面2でプロジェクト名を書き換える
- **THEN** 書き換えた名前が確定名の候補になる

#### Scenario: 長い名前を確定する

- **WHEN** ユーザーが kebab-case を満たす長い名前を確定して承認する
- **THEN** 長さを理由とする拒否は起きず、その名前が確定名としてプロジェクト生成に渡る

#### Scenario: 候補が既存のプロジェクトと衝突している

- **WHEN** 画面2を開いた時点で、候補と同名のプロジェクトが既に存在する
- **THEN** システムは既存と衝突しない名前に候補を変えて表示する

#### Scenario: 既存のプロジェクトと名前が衝突する

- **WHEN** 確定しようとした名前のプロジェクトが既に存在する
- **THEN** システムは衝突を伝え、別の名前が確定されるまで承認を通さない

### Requirement: 承認はプロジェクト生成の唯一の引き金

システムはユーザーの承認以外でプロジェクトを生成してはならない SHALL。承認時に phase を `approved` に変える。確認や結果の表示にパスを出さず、プロジェクト名で示す。

#### Scenario: 承認する

- **WHEN** ユーザーがプロジェクト名を確定して承認する
- **THEN** システムは後戻りできないことを示して確認を求め、確認が取れたらプロジェクト生成を実行し、成功したら phase を `approved` にする

#### Scenario: 指摘を積んだまま承認する

- **WHEN** 指摘が積まれている状態で承認しようとする
- **THEN** システムは、その指摘が渡らないまま確定することを承認の前に示す

#### Scenario: 承認していない

- **WHEN** phase が `stroking` または `proposed` である
- **THEN** `/opt/projects/` 配下には何も作られていない

### Requirement: 承認後は承認と差し戻しを提供しない

phase が `approved` になった後、システムは同じセッションに対する承認・差し戻しの操作を提供しない SHALL。

#### Scenario: approved で画面2を開く

- **WHEN** phase が `approved` のときユーザーが画面2を開く
- **THEN** 承認済みであることと確定したプロジェクト名が表示され、承認と差し戻しの操作は出ない
