# project/generation Specification

## Purpose
承認されたセッションを、後に spec-workflow がプロジェクトルートとして受け取れるプロジェクトへ昇格させる。昇格はセッションディレクトリの改名だけで行い、`.spec-workflow/` の内部構造には踏み込まない。project-generation を畳んだもの。

## Requirements

### Requirement: 承認はセッションディレクトリをプロジェクト名へ改名して昇格させる

システムは昇格の要求を受けたとき、そのセッションのディレクトリを、**記録された承認の判断が持つ確定された名前** `<name>` へ改名することでプロジェクトを作る SHALL。セッションとプロジェクトは同じ親（共有の保存先）の下に置き、昇格は同じ親の下での改名で行う SHALL。

**昇格は、承認の判断が記録されているときにだけ起こる SHALL**——承認はプロジェクト生成の唯一の引き金である。ただし、判断と昇格が**同じ呼び出しの中で**起こることは求めない（SHALL NOT）。引き金であることと、同じ操作の中で走ることは別である。

システムは、昇格にあたって新しいディレクトリを作ってはならない（MUST NOT）し、ファイルを別の場所へ複製・移動してはならない（MUST NOT）。セッションディレクトリの中身はすべてそのままプロジェクトの中身になる。

システムは `.spec-workflow/` の内部構造を作ってはならない（MUST NOT）。

#### Scenario: 承認によって昇格する

- **WHEN** ユーザーが名前 `<name>` で承認し、続けて昇格が起こる
- **THEN** そのセッションのディレクトリが同じ親の下で `<name>` へ改名され、プロジェクトになる

#### Scenario: 承認の判断が無いまま昇格しようとする

- **WHEN** 承認の判断が記録されていないセッションを昇格させようとする
- **THEN** 改名は起こらず、プロジェクトは作られない

#### Scenario: 中身はそのまま引き継がれる

- **WHEN** 昇格が成功した直後にプロジェクトの中身を見る
- **THEN** セッションの時点にあったファイルがすべて同じ相対位置のまま入っている

#### Scenario: 内部構造には踏み込まない

- **WHEN** 昇格した直後の中身を見る
- **THEN** `.spec-workflow/` 配下のファイルやディレクトリは1つも作られていない

### Requirement: proposal はセッションの時点から docs 配下にある

proposal はセッションの時点から、セッションディレクトリの `docs/proposal.md` に在る SHALL。昇格はこのファイルを動かさないため、昇格後は `<name>/docs/proposal.md` としてそのまま読める。

誰がそこへ置くかは、外から観測できないためここでは規定しない。置かれることと、置かれた後に動かされないことだけを規定する。

昇格（承認の処理）は proposal のファイルを書き出さず、既にあるものに触れない SHALL。

#### Scenario: セッション中の proposal の在り処

- **WHEN** proposal が起こされた後にセッションディレクトリを見る
- **THEN** `docs/proposal.md` に proposal の全文が入っている

#### Scenario: 昇格後の proposal の在り処

- **WHEN** 昇格が成功した後にプロジェクトの中身を見る
- **THEN** `<name>/docs/proposal.md` に、承認された proposal と同じ内容が入っている

#### Scenario: システムは proposal を書かない

- **WHEN** 承認の処理が走る
- **THEN** システムは proposal のファイルを新たに書き出さず、既にある `docs/proposal.md` に触れない

### Requirement: 昇格の直前に既存名との衝突を確認する

システムは昇格の直前に、保存先に `<name>` が既に存在するかを確認する SHALL。既に存在する場合は改名を行わない。

#### Scenario: 承認の時点で同名が存在する

- **WHEN** 昇格しようとした時点で保存先に `<name>` が既に存在する
- **THEN** システムは改名を行わず、衝突を伝え、phase を `proposed` のままにする

### Requirement: 昇格に失敗したら承認を確定させず、宙吊りの状態を作らない

システムは、**改名を先に行い、成功してから phase を `approved` にしなければならない（SHALL）**。逆順にしてはならない（MUST NOT）——phase を書いた直後に処理が失われると、**元の名前のまま承認済み**という残骸が残り、それが生成中のプロジェクトとして一覧に並ぶためである。

**承認の判断を記録することは、phase を動かさない SHALL。** 判断が記録されただけのセッションは phase `proposed` のままであり、承認済みとしても生成中としても扱われない。この禁止は昇格の段の中で成立する。

改名に失敗した場合、システムは phase を `approved` にしない SHALL。確定された名前を実行環境がディレクトリ名として受け付けない場合も、この失敗として扱う SHALL。失敗は、それが起きた場所のエラーとして伝える。

phase の書き込みに失敗した場合、システムは**改名を戻さなければならない（SHALL）**。戻す先は元の名前である。

失敗したとき、セッションは phase `proposed`・元の名前のディレクトリとして残り、**記録された承認の判断もそのまま残る SHALL**。ユーザーは判断を下し直すことなく、**同じ判断のまま昇格だけをやり直せる SHALL**。**phase が `approved` なのに昇格していない**——承認済みとして画面から開けず、改名もされていない——状態を作ってはならない（MUST NOT）。

#### Scenario: 改名に失敗する

- **WHEN** 保存先での改名が失敗する
- **THEN** システムはエラーを表示し、phase は `proposed`・ディレクトリは元の名前のままで、記録された判断は残り、同じ判断のまま昇格をやり直せる

#### Scenario: 環境が名前を受け付けない

- **WHEN** 確定された名前を実行環境がディレクトリ名として受け付けず、改名が失敗する
- **THEN** システムはその失敗をエラーとして表示し、phase は `proposed` のままで、判断を取り下げて別の名前で改めて承認できる

#### Scenario: 改名の後に phase の書き込みが失敗する

- **WHEN** 改名は成功したが、続く phase の書き込みが失敗する
- **THEN** 改名は元の名前へ戻り、phase は `proposed` のままで、セッションは元の名前で画面から開けて、記録された判断のまま昇格をやり直せる

#### Scenario: phase を書いた後に改名が失敗する

- **WHEN** phase を `approved` に書いた後に改名を試みる
- **THEN** この順序は起こらない——改名が先であり、成功したときだけ phase を書く。したがって `approved` かつ未改名の状態は、どの時点で処理が失われても生まれない

#### Scenario: phase を書く前に処理が失われる

- **WHEN** 改名の直後、phase を書く前に処理が失われる
- **THEN** ディレクトリはプロジェクト名になっているが phase は `proposed` であり、承認済みとして扱われることも、生成中のプロジェクトとして一覧に並ぶことも無い

#### Scenario: 判断だけが記録された状態で一覧を見る

- **WHEN** 承認の判断が記録され、まだ昇格していない状態でプロジェクト一覧を見る
- **THEN** そのセッションは一覧に現れない。生成中の行も出ていない

### Requirement: 昇格した瞬間から、生成中であることを一覧で示す

システムは、承認によって昇格したプロジェクトを、昇格した瞬間から生成中として一覧に示さなければならない（SHALL）。承認してから一覧に現れるまでの空白を作ってはならない（MUST NOT）。

生成中であることは、次の2つで示す（SHALL）。

- **行の地を他の行と変える** — まだ確定していないものであることが、読む前に分かる。名前と日付の薄さは未接続の行と同じにする
- **回転するローダーを置く** — 止まっているのではなく進行中であることが分かる。置く位置は他の行がアイコンを持つ位置とする

**行を明滅させてはならない（MUST NOT）。** 一覧の行は情報が詰まっており、周期的に薄くすると「進行中」ではなく「読みにくい行」になる。動きはローダーだけが持つ。

#### Scenario: 承認してモーダルを閉じる

- **WHEN** proposal を承認し、モーダルが閉じてプロジェクト一覧へ戻る
- **THEN** 承認で確定した名前のプロジェクトが、一覧の最下部に生成中として出ている

#### Scenario: 生成中の行の見え方

- **WHEN** 生成中のプロジェクトの行を見る
- **THEN** 行の地が他の行と異なり、回転するローダーが出ており、行全体は明滅していない

#### Scenario: 生成中に一覧を開き直す

- **WHEN** まだ生成中のうちにプロジェクト一覧を開き直す
- **THEN** その行は引き続き生成中として、同じ見え方で出ている

### Requirement: 生成中か完了かはファイルシステムの事実だけで判定する

システムは、昇格したプロジェクトが生成中か完了かを、**`state.json` の `phase` だけで判定しなければならない（SHALL）**。`approved` は生成中、`activated` は完了である。完了の記録（`activated`）は、呼び手が完成と判定したときに `api/session/activate` が書く。判定は呼び手（`agent/invocation` の実行ごとの判定と、下の起動時の書き上げ）が持ち、`api/session/activate` は持たない。

システムは、本家がプロジェクトルートとして読む `.spec-workflow/` の有無を、生成中か完了かの判定に使ってはならない（MUST NOT）。そのディレクトリは本家 MCP が接続した瞬間にでき、成果物が1つも無いうちから完了に見えるためである。`.spec-workflow/` の有無は、一覧に載せるプロジェクトの母集合を作るためにだけ使う SHALL。

システムは、AI の呼び出しの実行状態を、この判定の材料にしてはならない（MUST NOT）。実行状態は永続値として記録される一方、その見張りは実行中のプロセスの中にしか無く、プロセスが失われると実行中のまま誰も戻さない。それを判定に使うと、**完了することのない行**が生まれる。

この禁止が掛かるのは、**行が生成中か完了かを読み出すとき**である（SHALL）。下の「既に完成しているプロジェクトは起動時に完成を記録し直す」が実行状態で対象を選ぶことは、これに含まれない（SHALL）——あちらは phase を**書く**一度きりの移行で、書いた後の読み出しはこの Requirement のとおり phase だけを見る。禁止の理由（実行状態に依存すると完了することのない行が生まれる）も、一度きりで終わる移行には当たらない。

生成中の行を本家との接続の判定から外すこと、および生成中の行に入場できないことは、`project/directory` が定める。生成中であるかどうかの根拠は、そこでもこの phase とする（`.spec-workflow/` の有無を根拠にしない）。

この判定に厳密さを求めない（SHALL NOT）。数秒の遅れ、および取りこぼしを埋めるための作り込みを行ってはならない（MUST NOT）。表示は、次に一覧を取得し直した時点で必ず正しくなればよい。

#### Scenario: 生成が完了する

- **WHEN** 承認後に走った生成が steering 文書を出し終え、完成が記録される
- **THEN** そのプロジェクトは生成中ではなくなり、通常のプロジェクトとして一覧に並ぶ

#### Scenario: 完了の瞬間を取りこぼす

- **WHEN** 完了の瞬間の配信が届かないまま、後で一覧を取得し直す
- **THEN** そのプロジェクトは生成中ではない状態で出ている

#### Scenario: 実行状態の記録が実行中のまま残る

- **WHEN** 生成の実行を記録したプロセスが失われ、実行状態が実行中のまま残った状態で、完成は記録されている
- **THEN** そのプロジェクトは完了として出ている

#### Scenario: .spec-workflow/ ができただけでは完了にならない

- **WHEN** 本家 MCP が接続して `.spec-workflow/` ができたが、完成がまだ記録されていない
- **THEN** そのプロジェクトは生成中のまま出ている。本家の登録に載っていてもアクティブにはならず、入場できない

#### Scenario: 成果物ゼロで実行が正常終了する

- **WHEN** steering の実行が文書を1本も出さずに正常終了する
- **THEN** そのプロジェクトは生成中のまま出ており、完了として扱われない

### Requirement: 決着したら、知らせてから次を選ばせる

システムは、生成が決着したとき——成功でも失敗でも——**知らせる面**と**選ばせるモーダル**を順に出さなければならない（SHALL）。この2つは別のものとする（SHALL）。器は成功と失敗で同じとし（SHALL）、違うのは文言と選択肢だけとする。

**知らせる面**は次を満たす（SHALL）。

- 何が起きたかを伝える。成功は祝い、失敗は作りきれなかったこと
- そのプロジェクトの名前を含む
- **画面の半分くらいを埋める大きさとする**。小さすぎてはならず（MUST NOT）、画面全体を覆ってもならない（MUST NOT）
- **フェードアウトで自ら消える（SHALL）**。ユーザーの操作を要求してはならない（MUST NOT）——画面の半分を占める面が残り続けると、その間は何も操作できないためである
- **一覧の行の中に収めてはならない（MUST NOT）**
- **画面を遷移させてはならない（MUST NOT）**

**選ばせるモーダル**は、知らせる面が引いた後に出す（SHALL）。次を持つ（SHALL）。

| | 問い | 選択肢 | 選んだ後 |
|---|---|---|---|
| 成功 | ステアリングの結果をレビューするか | する | そのプロジェクトの承認画面へ移る。開ける対象が在れば、それを開いた状態で移る |
| | | しない | 一覧へ戻る |
| 失敗 | どうするか | やり直す | 一覧へ戻る。行は生成中に戻る |
| | | 破棄する | 一覧へ戻る。行は消える |

**成功の「する」で開ける対象が無いことがありうる**（SHALL）。完成の記録は steering が文書を出し終えたことを根拠にしており、承認依頼が在ることを根拠にしていない（`api/session/activate`）。steering の工程には承認依頼を出す手段が無いため、承認依頼が1件も無いまま成功が決着する。そのときは承認の一覧まで連れて行く SHALL——行き止まりにしてはならない（MUST NOT）。**承認依頼が確実に在る状態で完成を記録する形は、この capability の外で別途定める。**

モーダルは次のすべてを満たす（SHALL）。

- **画面を遷移させてはならない（MUST NOT）**。プロジェクト一覧の上で完結する
- **自ら消えてはならない（MUST NOT）**。ユーザーが選ぶまで閉じない。時間で引く形にしてはならない（MUST NOT）——決着は「見た」だけでは終わらず、次を選ぶところまでが1つの出来事である

システムは、知らせる面もモーダルも、既存の通知トーストとして出してはならない（MUST NOT）。トーストは本家由来の通知のためのもので、1行のテキストに限る形が定まっている。

決着を知らせるのは、**その瞬間を受け取った画面に対してだけ**とする（SHALL）。既に決着したプロジェクトについて、一覧を開き直した画面や、後から開いた画面に出してはならない（MUST NOT）。

#### Scenario: 一覧を見ている最中に完了する

- **WHEN** プロジェクト一覧を開いている最中に、生成中のプロジェクトの作成が完了する
- **THEN** その行から生成中の表現が外れて通常の行になり、あわせて完了を知らせる面が一覧の上に浮かび上がる

#### Scenario: 知らせる面を放っておく

- **WHEN** 知らせる面が出た後、何も操作しない
- **THEN** その面はフェードアウトして自ら消え、続いて選ばせるモーダルが出る

#### Scenario: モーダルを放っておく

- **WHEN** 選ばせるモーダルが出た後、何も操作しない
- **THEN** モーダルは消えず、選ぶまで残っている

#### Scenario: 成功でレビューを選ぶ

- **WHEN** 成功のモーダルで「する」を選び、開ける承認依頼が在る
- **THEN** そのプロジェクトの承認画面へ、その対象を開いた状態で移る

#### Scenario: 成功でレビューを選ぶが承認依頼が無い

- **WHEN** 成功のモーダルで「する」を選ぶが、承認依頼が1件も無い
- **THEN** そのプロジェクトの承認の一覧まで移る。行き止まりにはならない

#### Scenario: 成功でレビューしないを選ぶ

- **WHEN** 成功のモーダルで「しない」を選ぶ
- **THEN** モーダルが閉じてプロジェクト一覧に戻り、そのプロジェクトは通常の行として並んでいる

#### Scenario: 決着した後に一覧を開き直す

- **WHEN** 決着のモーダルを閉じた後、または決着した後に、プロジェクト一覧を開き直す
- **THEN** モーダルは出ない

#### Scenario: 決着より後に別のブラウザで開く

- **WHEN** 既に決着しているプロジェクトがある状態で、別のブラウザからプロジェクト一覧を開く
- **THEN** モーダルは出ない

### Requirement: 作成の失敗を一覧の行として残さない

システムは、作成に失敗したことを表す状態を、一覧の行に持ってはならない（MUST NOT）。失敗は決着のモーダルで片付き、**やり直せば生成中に戻り、破棄すれば行が消える**。失敗したまま居座る行を作ってはならない（MUST NOT）。

これにより一覧の行が持つ状態は **アクティブ / 未接続 / 生成中** の3つで足りる（SHALL）。

システムは、失敗した後に「やり直す」が選ばれたとき、生成を起こし直さなければならない（SHALL）。起こす口は、AI を起動する唯一の入口を使う（SHALL）——この目的のために別の起動の口を作ってはならない（MUST NOT）。

システムは、失敗した後に「破棄する」が選ばれたとき、そのプロジェクトを消さなければならない（SHALL）。消す口はプロジェクトの削除とする（SHALL）。

#### Scenario: 失敗してやり直す

- **WHEN** 失敗のモーダルで「やり直す」を選ぶ
- **THEN** 生成が起こし直され、一覧のその行は生成中として出ている

#### Scenario: 失敗して破棄する

- **WHEN** 失敗のモーダルで「破棄する」を選ぶ
- **THEN** そのプロジェクトは消え、一覧に現れない

#### Scenario: 失敗した状態の行を探す

- **WHEN** 決着のモーダルを閉じた後に一覧を見る
- **THEN** 「作成に失敗」を表す行はどこにも無い

### Requirement: 生成の進行は、開いている一覧へ届く

システムは、生成の開始・完了・失敗を、既にプロジェクト一覧を開いている画面へ届けなければならない（SHALL）。利用者に再読み込みを求めてはならない（MUST NOT）。

システムは、そのために一覧を繰り返し取得してはならない（MUST NOT）。配信は `ws/delivery` の規約に従う。

配信が運ぶのは**決着したという合図**であって、行の状態そのものではない（SHALL）。受け取った画面は一覧を取り直し、行の内容はサーバーの判定に従う。

#### Scenario: 一覧を開いたまま承認が行われる

- **WHEN** プロジェクト一覧を開いている状態で、別の画面から proposal が承認される
- **THEN** 一覧を再読み込みしなくても、生成中の行が最下部に現れる

#### Scenario: 一覧を開いたまま完了する

- **WHEN** プロジェクト一覧を開いたまま生成が完了する
- **THEN** 一覧を再読み込みしなくても、その行が通常の行に変わる

#### Scenario: 何も起きていない間

- **WHEN** 生成中のプロジェクトがある状態で、何の出来事も起きない時間が続く
- **THEN** 画面からサーバへの繰り返しの取得は発生しない

### Requirement: 既に完成しているプロジェクトは起動時に完成を記録し直す

システムは、完成の記録（`activated`）が導入される前に昇格し、**既に生成を終えていた**プロジェクトを、起動時に一度だけ完成として記録し直さなければならない（SHALL）。

対象は、phase が `approved` で、かつ**実行の記録（`invocation`）が `idle`** のものとする SHALL——最後の実行が正常終了して平常に戻っている、つまり生成が終わっているものである。判定の材料は一覧が返す state だけとし、ファイルシステムを読んで成果物を数えてはならない（MUST NOT）——`.spec-workflow/` は本家 MCP が接続した瞬間にでき、成果物が無いうちから在る。

実行の記録が `failed`・`error`・`running` のものは生成中のまま残す SHALL——`failed` と `error` は生成が終わっていないもの（巡回とユーザーの再実行が拾う）、`running` は起動時の後始末が `failed` へ倒す途中である。起動時の記録し直しに失敗しても起動を止めてはならない（MUST NOT）。

#### Scenario: 導入前に生成を終えていたプロジェクト

- **WHEN** phase が `approved` で実行の記録が `idle` のプロジェクトが在る状態でサーバーが起動する
- **THEN** 起動後の一覧で、そのプロジェクトは完了として出ている

#### Scenario: 導入前に生成が終わらなかったプロジェクト

- **WHEN** phase が `approved` で実行の記録が `failed` または `error` のプロジェクトが在る状態でサーバーが起動する
- **THEN** 起動後の一覧で、そのプロジェクトは生成中として出ている

#### Scenario: 宙に浮いた実行の記録を持つプロジェクト

- **WHEN** phase が `approved` で実行の記録が `running` のまま残ったプロジェクトが在る状態でサーバーが起動する
- **THEN** 書き上げの対象にならず、生成中のまま残る。起動時の後始末がその実行を畳んだ後は、巡回が起こし直す
