## Requirements

### Requirement: 下層は4つの画面を持つ

システムは、プロジェクト単位の下層として **仕様書 / ステアリング / タスク / 承認** の4画面を持たなければならない（SHALL）。統計・実装ログ・ジョブの画面を持ってはならない（MUST NOT）。

#### Scenario: 下層に入る

- **WHEN** アクティブなプロジェクトの下層に入る
- **THEN** 仕様書 / ステアリング / タスク / 承認 の4つに移動できる

### Requirement: 下層のナビゲーションは上層と形を変える

システムは、下層のナビゲーションを画面左の縦並びとしなければならない（SHALL）。上層のナビゲーション（ヘッダー直下の横並び）と同じ形にしてはならない（MUST NOT）。ナビゲーションの形を見た時点でどちらの階層にいるかが分かるようにする。

#### Scenario: 上層と下層を見比べる

- **WHEN** 上層と下層をそれぞれ開く
- **THEN** ナビゲーションの形と位置が異なっており、どちらの階層かが見て分かる

### Requirement: 下層から上層へ戻る導線を持つ

システムは、下層から上層のポータルへ戻る導線をヘッダーの左に置かなければならない（SHALL）。

システムは、下層にプロジェクトを切り替える口を置いてはならない（MUST NOT）。別のプロジェクトへ移るときは上層を経由する。

#### Scenario: 上層へ戻る

- **WHEN** 下層でヘッダー左の戻る導線を選ぶ
- **THEN** 上層のポータルに戻っている

#### Scenario: 別のプロジェクトへ移る

- **WHEN** 下層にいる状態で別のプロジェクトを見たい
- **THEN** 下層に切り替えの口は無く、上層のプロジェクト一覧を経由して入り直す

### Requirement: 下層は今いるプロジェクトを示す

システムは、下層の各画面で、今どのプロジェクトを見ているかとそのプロジェクトの接続状態を示さなければならない（SHALL）。

#### Scenario: 下層の画面を見る

- **WHEN** 下層のいずれかの画面を開いている
- **THEN** プロジェクト名と接続状態が画面上に出ている

### Requirement: 通知の対象を下層の画面で開く

システムは、通知の行を選んだとき、その通知の種別に応じた下層の画面を、対象のプロジェクトの文脈で開かなければならない（SHALL）。対応は次のとおりとする。

- **承認依頼の発生** → そのプロジェクトの **承認** 画面。承認依頼が仕様ドキュメントに対するものかステアリング文書に対するものかを問わず、承認画面を開く
- **タスク完了 / タスク着手 / 全件完了** → そのプロジェクトの **タスク** 画面

システムは、開いた先で対象の箇所へスクロールしたりハイライトしたりしてはならない（MUST NOT）。開くだけとする。

#### Scenario: 仕様ドキュメントに対する承認依頼の通知を選ぶ

- **WHEN** 仕様ドキュメントに対する承認依頼の通知の行を選ぶ
- **THEN** そのプロジェクトの承認画面が開いている

#### Scenario: ステアリング文書に対する承認依頼の通知を選ぶ

- **WHEN** ステアリング文書に対する承認依頼の通知の行を選ぶ
- **THEN** そのプロジェクトの承認画面が開いている

#### Scenario: タスクの通知を選ぶ

- **WHEN** 「タスク完了」の通知の行を選ぶ
- **THEN** そのプロジェクトのタスク画面が開いている

### Requirement: 対象が既に存在しない場合を示す

システムは、通知の対象が開く時点で存在しない場合に、その旨を示さなければならない（SHALL）。空白の画面や取得中のまま止まった画面にしてはならない（MUST NOT）。

#### Scenario: 対象のドキュメントが削除されている

- **WHEN** 通知の行を選んだ時点で、その対象のドキュメントが削除されている
- **THEN** 対象が見つからないことが画面に出る

#### Scenario: 対象の承認依頼が既に保留中でなくなっている

- **WHEN** 承認依頼の通知の行を選んだ時点で、その承認依頼が既に保留中でなくなっている
- **THEN** 承認画面が開き、その承認依頼が保留中の一覧に無いことが分かる

### Requirement: 下層で状態を変えられるのは承認への応答と文書の保存だけ

システムは、下層の画面に **承認・却下・差し戻し** を置かなければならない（SHALL）。あわせて、仕様書とステアリングの文書に **編集と保存** を置かなければならない（SHALL）。それ以外に本家の状態を変える操作を置いてはならない（MUST NOT）。タスクの状態変更・プロジェクトの登録と解除はいずれも持たない。

承認・却下・差し戻しは本家の `POST /api/projects/:projectId/approvals/:id/:action` を呼ぶ。文書の保存は本家の `PUT /api/projects/:projectId/specs/:name/:document` と `PUT /api/projects/:projectId/steering/:name` を呼ぶ。いずれも stroke-board のサーバーを経由し、ブラウザから本家へ直接送ることはない。

編集できる文書の範囲、直しかけのまま離れようとしたときの扱い、保存に失敗したときの見せ方は `document-editing` が定める。

**差し戻し（`needs-revision`）は注釈コメントを運ぶ。** 承認・却下は `response` しか持たない。注釈を承認・却下に付けて送ることはできない（MUST NOT）。

**画面に出す名前は本家の日本語ロケールに合わせる（SHALL）**——承認は「即時承認」、却下は「即時却下」、差し戻しは「修正を依頼」、レビューを開く口は「レビューと注釈」、閉じる口は「レビューを閉じる」。差し戻しがやり直しを求めて返すのに対し、却下はその場で終わらせる——名前で区別が付かなければならない（SHALL）。本家へ送る action と記録の語は変えてはならない（MUST NOT）。

**承認・却下・差し戻しは、対象文書を読んでいる画面から行えなければならない（SHALL）。** 読んで判断した場で終わらせられず、別の画面へ戻らせてはならない（MUST NOT）。

#### Scenario: 承認画面を開く

- **WHEN** 承認画面を開く
- **THEN** 保留中の承認依頼とその対象文書の中身が読め、承認・即時却下・差し戻しが行える

#### Scenario: 承認する

- **WHEN** 保留中の承認依頼を承認する
- **THEN** 本家へ承認が伝わり、その承認依頼が保留中の一覧から消える

#### Scenario: 却下する

- **GIVEN** 却下の理由を入力していない
- **WHEN** 却下しようとする
- **THEN** 送れない。理由は本家に応答として残るため、空のままでは送らない

#### Scenario: 理由を添えて却下する

- **WHEN** 却下の理由を入力して却下する
- **THEN** 本家へ却下と理由が伝わり、その承認依頼が保留中の一覧から消える

#### Scenario: 対象文書を読んだ場で却下する

- **GIVEN** 承認依頼の対象文書を読んでいる
- **WHEN** 即時却下を選ぶ
- **THEN** その場で理由を入力して送れる。別の画面へ戻る必要が無い

#### Scenario: 仕様書の文書を直す

- **WHEN** 仕様書の文書を開いて直し、保存する
- **THEN** 本家へ保存が伝わり、開き直すと直した内容が出る

#### Scenario: ステアリングの文書を直す

- **WHEN** ステアリングの文書を開いて直し、保存する
- **THEN** 本家へ保存が伝わり、開き直すと直した内容が出る

#### Scenario: タスク画面を開く

- **WHEN** タスク画面を開く
- **THEN** タスクとその状態が読めるが、状態を変える操作は無い

#### Scenario: 承認依頼から対象文書を読む

- **WHEN** 承認依頼のカードから対象文書を開く
- **THEN** その場で読めて指摘を付けられる。直すのはその文書自身の画面で行う（`document-editing`）

#### Scenario: 差し戻す

- **WHEN** 保留中の承認依頼に注釈コメントを1件以上付けて差し戻す
- **THEN** 本家へ差し戻しが伝わり、その承認依頼が保留中の一覧から消える

#### Scenario: コメントを付けずに差し戻そうとする

- **WHEN** 注釈コメントが1件も無い状態で差し戻そうとする
- **THEN** 本家へは送られず、コメントが要ることが分かる

#### Scenario: 承認・却下に注釈を付けて送ろうとする

- **WHEN** `approve` または `reject` に注釈コメントを添えて送る
- **THEN** サーバーが受け付けず、コメントを運べるのは差し戻しだけであることが分かる

### Requirement: 本家が停止している間の下層を示す

システムは、下層にいる間に本家との接続が切れた場合、その状態を示さなければならない（SHALL）。取得できない内容を、取得済みであるかのように見せてはならない（MUST NOT）。

#### Scenario: 下層を開いている間に本家が停止する

- **WHEN** 下層の画面を開いている間に、そのプロジェクトの本家プロセスが停止する
- **THEN** 接続状態の表示が「未接続」に変わり、内容が取得できないことが分かる

### Requirement: 承認対象の文書に箇所を指した指摘を付けられる

システムは、承認画面で対象文書に指摘を付けられるようにする SHALL。見せ方は **整形された本文 / 素の本文** の2つとし、そのどちらの面でも指摘を付けられる SHALL。いずれかの面を読むだけに限り、指摘を付けられない状態にしてはならない（MUST NOT）。指摘を付けるためだけに面を切り替えさせてはならない（MUST NOT）。

両方を並べて見せる面を持ってはならない（MUST NOT）。並べる面は、読む面と指摘する面が別だったことに由来する。どちらの面でも指摘を付けられる以上、並べる理由が無い。

どちらの面で付けた指摘も、両方の面に出る SHALL。どちらの面で付けたかによって、出る／出ないが変わってはならない（MUST NOT）。一方の面で消した指摘は、もう一方の面からも消える SHALL。

指摘は、レンダリング後の HTML ではなく**生テキストに対する文字オフセット**（開始位置・終了位置）と引用文字列で持つ SHALL。同じ語が本文に何度現れても、選んだ箇所だけが指摘の対象になる。面ごとに別の位置の持ち方をしてはならない（MUST NOT）。

**オフセットの基準は、本家から取得した文書の中身そのものとする SHALL。** 整形して読むために内部で行う作り変え（改行の表現を揃える・先頭の前置きを落とす）の後の文字列を基準にしてはならない（MUST NOT）。本家へ渡す値は、本家が保持している文書へそのまま当てて同じ箇所を指すものでなければならない。

箇所に紐づかない指摘（文書全体への指摘）も付けられる SHALL。

見せ方を切り替えても、対象文書の編集の直しかけを捨ててはならない（MUST NOT）。

指摘を付けるために、対象文書の一部を隠してはならない（MUST NOT）。先頭の前置きを含め、取得した文書はそのまま指摘の対象になる。

#### Scenario: 承認画面を開いた直後

- **WHEN** 承認画面を開く
- **THEN** 整形された本文が出る。この面からも箇所を選んで指摘を付けられる

#### Scenario: 本文の箇所を選んで指摘を付ける

- **WHEN** 整形された本文の面と素の本文の面のいずれかで本文の一部を選び、指摘を書く
- **THEN** どちらの面であっても選んだ箇所に指摘が結び付き、本文上でその範囲が目立つ

#### Scenario: 読んだ面のまま指摘する

- **GIVEN** 整形された本文を読んでいる
- **WHEN** 気になった箇所へ指摘を付ける
- **THEN** 面を切り替えずにその場で付けられる

#### Scenario: 付けた指摘がもう一方の面にも出る

- **GIVEN** 一方の面で本文の箇所に指摘を付けた
- **WHEN** もう一方の面へ切り替える
- **THEN** 対応する箇所に同じ指摘が出る

#### Scenario: 見せ方を選ぶ

- **WHEN** 承認画面で見せ方を切り替える
- **THEN** 選べるのは整形された本文と素の本文の2つで、両方を並べる面は無い

#### Scenario: 箇所に紐づかない指摘を付ける

- **WHEN** 文書全体への指摘を書く
- **THEN** 箇所を持たない指摘として一覧に加わる

#### Scenario: 付けた指摘を消す

- **WHEN** 付けた指摘を消す
- **THEN** 一覧から消え、両方の面から本文上の目立たせも消える

#### Scenario: 面を切り替える

- **WHEN** 対象文書を直しかけたまま見せ方を切り替える
- **THEN** 直しかけは残る

#### Scenario: 改行の表現や前置きを持つ文書に指摘を付ける

- **GIVEN** 取得した文書に、整形の過程で潰される改行の表現や、落とされる先頭の前置きが含まれる
- **WHEN** 本文のある箇所を選んで指摘を付け、差し戻す
- **THEN** 本家へ渡るオフセットは、本家が保持している文書へ当てて選んだ箇所を指す

#### Scenario: 前置きに指摘を付ける

- **WHEN** 素の本文の面で、文書の先頭の前置きの中を選んで指摘を書く
- **THEN** そこにも指摘を付けられる。前置きは面から取り除かれていない

### Requirement: 差し戻しの指摘は3つのフィールドに分けて本家へ渡す

システムは、差し戻しで送る指摘を **人間可読の要約（`response`）・JSON 化した記録（`annotations`）・構造化配列（`comments`）** の3つに分けて本家へ渡す SHALL。1本のテキストに畳んではならない（MUST NOT）。畳むと箇所と指摘の対応が失われるためである。

`annotations` に載せる記録は `decision` / `comments` / `summary` / `timestamp` を持つ SHALL。

#### Scenario: 指摘を付けて差し戻す

- **WHEN** 箇所に紐づく指摘と全体への指摘を付けて差し戻す
- **THEN** 本家の承認依頼に、要約・記録・構造化配列の3つが別々のフィールドとして保存される

### Requirement: 承認画面の指摘の一覧はしまえる

システムは、承認画面の指摘の一覧（コメント欄）をユーザーがしまえるようにしなければならない（SHALL）。しまった一覧は、戻すためのつまみ（44px 幅）だけを画面に残さなければならない（SHALL）。つまみを操作すると一覧だけが戻らなければならない（SHALL）。

しまう／戻すの口は、コメント欄そのものを掴んで左右へ引く操作、見出し帯のボタン、しまった帯のクリック、コメント欄の右辺に沿ったレールの4つを持つ（SHALL）。レールは見た目を持たず、押しても光ってはならない（MUST NOT）。

**左のナビゲーションと一覧は連動してはならない（MUST NOT）。** 左を畳んでも一覧は出たままで、一覧をしまっても左は動かない。

**一覧の幅は固定でなければならない（SHALL）。** 左のナビゲーションを畳んで空いた幅は本文だけが取り、一覧は広がらない。本文に固定の幅を与えてはならず（MUST NOT）、本文の幅はビューポートに追従する（SHALL）。左右に余白が残ることは差し支えない。

しまった状態は保存しない（MUST NOT）。開き直したとき一覧は出ている。URL にも含めない。

一覧をしまっている間も、上層へ戻る導線と今いるプロジェクトの表示は見えたままでなければならない（SHALL）。

#### Scenario: 一覧をしまう

- **WHEN** 承認画面で一覧をしまう
- **THEN** 一覧は 44px のつまみだけを残し、本文がその分だけ広がる

#### Scenario: つまみから戻す

- **GIVEN** 一覧をしまっている
- **WHEN** つまみを押す
- **THEN** 一覧が元の幅で戻る。左のナビゲーションは動かない

#### Scenario: 掴んで引く

- **WHEN** コメント欄を掴んで右へ引き、開いた幅の半分より狭い位置で放す
- **THEN** 一覧がしまわれる。半分より広い位置で放せば開いたまま

#### Scenario: 左を畳む

- **WHEN** 左のナビゲーションを畳む
- **THEN** 一覧は出たままで幅も変わらず、空いた幅は本文だけが取る

#### Scenario: 開き直す

- **GIVEN** 一覧をしまっている
- **WHEN** 同じ URL を開き直す
- **THEN** 一覧は出ている

### Requirement: 決める操作は1つの並びに集める

システムは、承認依頼に対して決める操作（承認・即時却下・差し戻し）を、対象文書を読む画面の上部に**1つの並び**として置かなければならない（SHALL）。並びは、対象文書の見え方を切り替える操作より上に置く（SHALL）。本家がその形である——決める操作は操作の行に集まり、見え方の切替はその下に別の行として置かれる。

決める操作を、画面の離れた場所に散らしてはならない（MUST NOT）。見え方を切り替える操作の並びに、決める操作を混ぜてはならない（MUST NOT）。

#### Scenario: 対象文書を読む画面を開く

- **WHEN** 承認依頼の対象文書を読む画面を開く
- **THEN** 決める操作が1つの並びに出ており、見え方の切替はその下に別の並びである

#### Scenario: 見え方を切り替える

- **WHEN** 対象文書の見え方を切り替える
- **THEN** 決める操作は同じ位置にあり続ける

### Requirement: 理由を求める入力は本文の上に重ねて出す

システムは、送る前に理由や指摘の文言を求めるとき、その入力を本文の上に重ねて出さなければならない（SHALL）。本文の流れの中に入力欄を差し込んではならない（MUST NOT）。

入力を求める面は、**そこで送るか、やめるかのどちらかを選んで閉じる**ものでなければならない（SHALL）。入力欄を閉じることと、送ることを、別の操作にしてはならない（MUST NOT）。

送った結果は、送った人に分かるように示さなければならない（SHALL）。入力を求める面が閉じただけの状態にしてはならない（MUST NOT）。

この要件は、却下の理由と、注釈のコメントの双方に適用する。

#### Scenario: 却下の理由を入力する

- **WHEN** 即時却下を選ぶ
- **THEN** 理由を入力する面が本文の上に重なって出る

#### Scenario: 理由を入力して送る

- **GIVEN** 却下の理由を入力する面が出ている
- **WHEN** 理由を書いて送る
- **THEN** 面が閉じ、送られたことが分かる

#### Scenario: 理由を入力せずにやめる

- **GIVEN** 却下の理由を入力する面が出ている
- **WHEN** やめる
- **THEN** 面が閉じ、何も送られない

#### Scenario: 送ったのに結果が分からない

- **WHEN** 理由を入力して送る
- **THEN** 入力の面が閉じるだけで終わってはならない。送れたことが読み取れる

### Requirement: 承認依頼はその場で開く

システムは、承認の一覧から承認依頼を開くとき、一覧を離れずにその場で開かなければならない（SHALL）。

開いた承認依頼は URL で直接指せなければならない（SHALL）。その場で開くことと、URL で指せることは両立する。

#### Scenario: 一覧から承認依頼を開く

- **WHEN** 承認の一覧で承認依頼を開く
- **THEN** その場で対象文書が開き、一覧から別の画面へ移らない

#### Scenario: 開いた承認依頼を閉じる

- **GIVEN** 承認依頼をその場で開いている
- **WHEN** 閉じる
- **THEN** 一覧に戻り、どこを見ていたかが保たれる
