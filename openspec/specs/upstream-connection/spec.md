# upstream-connection Specification

## Purpose
アクティブなプロジェクトごとに本家 spec-workflow-mcp へ接続して状態を受け取り、その接続が今どうなっているかを画面に出す。本家に触るのはこの範囲だけで、ブラウザは本家に直接つながらない。

## Requirements

### Requirement: 本家への接続はサーバーだけが張る

システムは、本家への接続を stroke-board のサーバーからのみ張らなければならない（MUST）。ブラウザから本家の WebSocket や REST へ直接つないではならない（MUST NOT）。

#### Scenario: ブラウザが状態を受け取る

- **WHEN** ブラウザが通知やプロジェクトの状態を受け取る
- **THEN** その通信相手は stroke-board のサーバーだけであり、本家への接続はブラウザから発生しない

### Requirement: アクティブなプロジェクトごとに接続を1本だけ張る

システムは、アクティブなプロジェクト1つにつき本家への WebSocket 接続を1本だけ張らなければならない（SHALL）。同じプロジェクトに対して2本以上張ってはならない（MUST NOT）。

システムは、未接続のプロジェクトに対して接続を張ってはならない（MUST NOT）。

#### Scenario: アクティブなプロジェクトが複数ある

- **WHEN** アクティブなプロジェクトが3つある
- **THEN** 本家への WebSocket 接続はちょうど3本になる

#### Scenario: 同じプロジェクトを重ねて購読する

- **WHEN** 既に購読しているプロジェクトに対して再度購読が要求される
- **THEN** 新しい接続は張られず、既存の1本が使われる

### Requirement: 本家の状態を定期ポーリングで取りに行かない

システムは、本家の状態変化を WebSocket の受信を起点として扱わなければならない（SHALL）。本家 REST を定期的に呼んで変化を探ってはならない（MUST NOT）。本家 REST は、画面または MCP ツールからの要求を受けたときにのみ呼ぶ SHALL——要求を伴わない呼び出しを行ってはならない（MUST NOT）。

#### Scenario: 何も起きていない間

- **WHEN** 本家で承認依頼もタスクの変化も起きていない
- **THEN** stroke-board から本家への REST 呼び出しは発生しない

### Requirement: 本家が停止していても stroke-board は動き続ける

システムは、本家が停止している、または接続が切れている状態でも起動し、動作を続けなければならない（SHALL）。本家プロセスの起動・停止・監視に責任を持ってはならない（MUST NOT）。

#### Scenario: 本家が起動していない状態で stroke-board を開く

- **WHEN** 本家ダッシュボードが1つも起動していない状態で stroke-board を開く
- **THEN** 画面は表示され、接続状態が「未接続」として出る

#### Scenario: 稼働中に本家が停止する

- **WHEN** 接続していた本家のプロセスが停止する
- **THEN** 接続状態の表示が「未接続」に変わり、stroke-board 自身は動作を続ける

### Requirement: 接続が切れたら再接続を試みる

システムは、本家への接続が切れたとき、再接続を試みなければならない（SHALL）。再接続が成功したら接続状態の表示を戻さなければならない（SHALL）。

#### Scenario: 本家が再起動する

- **WHEN** 本家が停止し、その後で再び起動する
- **THEN** 再接続が成立し、接続状態の表示が「接続済み」に戻る

### Requirement: 接続状態を画面に出す

システムは、本家との接続状態を画面上で判別できる形で示さなければならない（SHALL）。

#### Scenario: 接続状態を確認する

- **WHEN** 利用者が画面を見る
- **THEN** 本家とつながっているかどうかが画面上で分かる

### Requirement: 本家から受け取ったペイロードを検証する

システムは、本家から受け取ったペイロードを、扱う前に形の検証にかけなければならない（SHALL）。想定と異なる形のペイロードを黙って通してはならない（MUST NOT）。

#### Scenario: 想定と異なる形のペイロードが届く

- **WHEN** 本家から、想定するスキーマに合わないペイロードが届く
- **THEN** そのペイロードは通知として扱われず、形が合わなかったことが記録に残る

### Requirement: 本家の接続先と監視する親パスは環境から受け取る

システムは、本家ダッシュボードの URL と監視する親パスを環境変数から読まなければならない（SHALL）。これらをソースコードに埋め込んではならない（MUST NOT）。

#### Scenario: 接続先を変えて起動する

- **WHEN** 環境変数で別の本家 URL を与えて起動する
- **THEN** その URL に対して接続が張られる

### Requirement: パスから本家の projectId を引き当てる

システムは、あるパスに対応する本家の `projectId` を、本家 `GET /api/projects/list` の応答だけを手掛かりに引き当てなければならない（SHALL）。本家の登録簿ファイル（`activeProjects.json`）を projectId の引き当てのために読んではならない（MUST NOT）——引き当ては MCP ツールの代行経路にあり、`mcp/server`「ハンドラは対応する endpoint へ要求を発行してその応答だけから結果を作る」に従う。

**禁じているのは引き当てのための読み取りだけである。** 登録簿の読み取りそのものは、アクティブ判定の用途で認められている（ADR-0006「アクティブ判定だけを `activeProjects.json` / 本家 API で重ねる」）。

引き当ては、一覧のエントリの `projectPath` が、与えたパスと**一致する**ときにだけ成立しなければならない（SHALL）。比較の前に両側のパスを正規化する SHALL（`.` / `..` の畳み込みと末尾スラッシュの除去）。一致しないエントリを引き当ててはならない（MUST NOT）。

**本家は与えられたパスをそのまま登録するとは限らない。** 本家は登録の前にパスを自分の規則（`git rev-parse --show-toplevel`）で解決し、解決後のパスを一覧に載せる。解決でパスが変わると引き当ては外れるが、**その差をシステムが吸収して引き当ててはならない（MUST NOT）。** 差が出る場面では本家自身が複数のセッションを1つの `projectId` にまとめており、吸収して引き当てると別のセッションと共有の id を返して、steering 文書を取り違えて書くことになる。引き当てを外し、失敗として返すこと。

システムは、本家がパスをどう解決するかの手続き（git のトップレベルを取るなど）を自分で再実行してはならない（MUST NOT）。再実行は本家の実装への依存を複製するだけで、本家の版が変われば同じ形で壊れる。

引き当てられなかったときは、その旨を失敗として返さなければならない（SHALL）。失敗の形と本文の要件は `mcp/server` にある。

#### Scenario: 与えたパスがそのまま登録されている

- **GIVEN** 本家の一覧に `projectPath` が `/opt/projects/example` のエントリがある
- **WHEN** `/opt/projects/example` に対応する `projectId` を引き当てる
- **THEN** そのエントリの `projectId` が返る

#### Scenario: 書き方が違うだけのパスは引き当てる

- **GIVEN** 本家の一覧に `projectPath` が `/opt/projects/example/` のエントリがある
- **WHEN** `/opt/projects/foo/../example` に対応する `projectId` を引き当てる
- **THEN** 正規化した結果が一致するので、そのエントリの `projectId` が返る

#### Scenario: 一致するエントリが1件も無い

- **GIVEN** 本家の一覧に、与えたパスと一致するエントリが無い
- **WHEN** そのパスに対応する `projectId` を引き当てる
- **THEN** 引き当ては成立せず、失敗として返る。本家の登録簿ファイルは読まれない
