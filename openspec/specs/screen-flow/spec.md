# screen-flow Specification

## Purpose
URL と画面の対応、各画面が何を担うか、画面と画面をつなぐ遷移の正を1つに定める。どの URL を開いたとき何が出るか、どの操作でどこへ移るか、自動で移してよいのはどこかを、画面の実装とは独立して読み取れる状態にする。

## Requirements

### Requirement: 上層の URL は3つの責務に切り分ける

システムは、上層の URL を次の3つの責務に切り分けなければならない（SHALL）。1つの URL に2つ以上の責務を持たせてはならない（MUST NOT）。

| URL | 画面 | 責務 |
| --- | --- | --- |
| `/` | stroke 初期画面 | ストロークを始める。AI との応対の入口 |
| ストローク開始の URL（`/` とは別の path） | stroke 開始画面 | ストロークを始める。プロジェクト一覧の「作成」から入ったときの入口 |
| `/projects` | プロジェクト画面 | プロジェクトの一覧と、そのプロジェクトへの入場 |

`/` とストローク開始の URL は、**同じ画面を出す**（SHALL）。違いは Nuxt の page routing 上の path だけであり、画面の中身・できる操作・そこから進む先を違えてはならない（MUST NOT）。

#### Scenario: ルートを開く

- **WHEN** `/` を開く
- **THEN** stroke 初期画面が出ており、ストロークを始められる

#### Scenario: ストローク開始の URL を開く

- **WHEN** ストローク開始の URL を開く
- **THEN** `/` と同じ画面が出ており、中身もできる操作も `/` と変わらない

#### Scenario: プロジェクト画面を開く

- **WHEN** `/projects` を開く
- **THEN** プロジェクトの一覧が出ており、ストロークの入力欄は出ていない

### Requirement: ルートは他の URL へ自動で移さない

システムは、`/` を開いたとき、他の URL へ自動で移してはならない（MUST NOT）。リダイレクト・middleware・route rule・画面のマウント時の遷移のいずれの手段によるかを問わない（MUST NOT）。

`/` が出すものは、ユーザーが操作するまで変わらない（SHALL）。

#### Scenario: ルートを開いたまま待つ

- **WHEN** `/` を開き、何も操作せずに待つ
- **THEN** URL は `/` のままで、`/projects` を含む他の URL へ移らない

#### Scenario: ルートを開き直す

- **WHEN** `/` を開いて再読み込みする
- **THEN** URL は `/` のままで、stroke 初期画面が出ている

### Requirement: 上層の通知は固有の URL を持つ

システムは、プロジェクト横断の通知の一覧を、`/` とは別の固有の URL に置かなければならない（SHALL）。通知の一覧を `/` に置いてはならない（MUST NOT）——`/` は stroke 初期画面が占めるためである。

通知の一覧が何を出すかは `notification-feed` が規定する。ここが定めるのは置き場だけである。

#### Scenario: 通知の URL を開く

- **WHEN** 通知の URL を開く
- **THEN** プロジェクト横断の通知の一覧が出ている

#### Scenario: ルートに通知を探す

- **WHEN** `/` を開く
- **THEN** 通知の一覧は出ていない

### Requirement: 上層の画面は URL で辿り直せる

システムは、上層のどの画面についても、その画面を出す URL を持たせなければならない（SHALL）。URL を持たない上層の画面を作ってはならない（MUST NOT）。

ユーザーが URL を直接開いたとき、ブックマークから開いたとき、再読み込みしたときのいずれでも、その URL に対応する画面が出る（SHALL）。

#### Scenario: URL を直接入力して画面へ入る

- **WHEN** 上層のいずれかの画面の URL を、ブラウザのアドレス欄へ直接入力して開く
- **THEN** その URL に対応する画面が出ている

#### Scenario: 画面を再読み込みする

- **WHEN** 上層のいずれかの画面を開いた状態で再読み込みする
- **THEN** 同じ画面が出ており、別の画面に置き換わらない

### Requirement: 画面遷移の正を資料として持つ

システムは、URL と画面の対応・各画面の責務・画面と画面をつなぐ遷移を、`docs/specs/architecture/screen-flow.md` の1ファイルに書き出さなければならない（SHALL）。

資料は次のすべてを含む（SHALL）。

- 上層の URL の一覧と、各 URL が出す画面、その画面が担う責務
- どの操作でどの画面からどの画面へ移るか
- 自動で移す箇所があるなら、その箇所と、そうしてよい理由

遷移を変えたときは、同じ change のなかでこの資料を更新しなければならない（SHALL）。資料と実装を食い違わせたまま残してはならない（MUST NOT）。

#### Scenario: 遷移の正を知りたい

- **WHEN** どの URL が何を出し、どの操作でどこへ移るかを知ろうとする
- **THEN** 資料を読めば分かり、画面の実装を読み回る必要が無い

#### Scenario: 遷移を変える

- **WHEN** 画面と画面をつなぐ遷移を変更する
- **THEN** 同じ change のなかで資料が更新されており、資料と実装が食い違っていない
