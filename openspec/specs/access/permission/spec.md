# access/permission Specification

## Purpose
利用者ごとに、どのプロジェクトとストロークに入れるかを許可で決め、画面・API・WebSocket・通知のすべてをその範囲に絞る。

## Requirements

### Requirement: 許可は利用者とプロジェクトの組で持ち、段階を持たない

システムは、利用者（メールアドレス）とプロジェクトの組ごとに、許可があるか無いかを持たなければならない（SHALL）。許可に段階を持ってはならない（MUST NOT）。

許可のある利用者は、そのプロジェクトで今できる操作（文書の保存・承認への応答・削除を含む）をすべてできなければならない（SHALL）。

管理者は、許可の有無に関わらず、すべてのプロジェクトとストロークに入れ、すべての操作ができなければならない（SHALL）。

許可はサーバーを再起動しても失われてはならない（MUST NOT）。

#### Scenario: 許可のある利用者が操作する

- **WHEN** プロジェクト `alpha` に許可のある利用者が、`alpha` の文書を保存し、承認依頼に応答する
- **THEN** どちらも許可の無い場合と区別なく行える

#### Scenario: 管理者が許可の無いプロジェクトを開く

- **WHEN** 管理者が、誰にも許可の付いていないプロジェクトの下層を開く
- **THEN** 下層が開く

#### Scenario: 再起動の後

- **WHEN** 利用者に許可を付けた後でサーバーを再起動する
- **THEN** その利用者は再起動前と同じプロジェクトに入れる

### Requirement: 許可の無いプロジェクトは存在しないものとして扱う

システムは、利用者に許可の無いプロジェクトについて、その下層の画面と、そのプロジェクトを対象とする API に 404 を返さなければならない（SHALL）。存在するが入れないことが分かる応答（403 など）を返してはならない（MUST NOT）。

システムは、許可の無いプロジェクトの出来事を WebSocket で配信してはならない（MUST NOT）。許可の無いプロジェクトを対象とする接続は、何も送らずに閉じる SHALL。

#### Scenario: 許可の無いプロジェクトの URL を開く

- **WHEN** プロジェクト `alpha` に許可の無い利用者が、`alpha` の下層の URL を開く
- **THEN** 404 の画面が出る

#### Scenario: 許可の無いプロジェクトの API を呼ぶ

- **WHEN** プロジェクト `alpha` に許可の無い利用者のリクエストで、`alpha` の文書を取る API が呼ばれる
- **THEN** 404 が返る

### Requirement: 作成途中のストロークは始めた本人と管理者にだけ見せる

システムは、ストロークを始めたときに、始めた利用者のメールアドレスをそのストロークに記録しなければならない（SHALL）。token が無い接続で始めたときは、始めた利用者を持たないストロークとして記録する SHALL。

システムは、プロジェクトへ昇格する前のストロークを、始めた利用者と管理者にだけ見せなければならない（SHALL）。それ以外の利用者には、一覧に出さず、そのストロークの画面・API に 404 を返さなければならない（SHALL）。そのストロークの WebSocket の接続は、何も送らずに閉じる SHALL。

始めた利用者を持たないストロークは、管理者にだけ見せる SHALL。

#### Scenario: 始めた本人が続きを開く

- **WHEN** `guest@example.com` が始めた作成途中のストロークを、`guest@example.com` が開く
- **THEN** そのストロークが開き、問いに回答できる

#### Scenario: 他の利用者が開く

- **WHEN** `guest@example.com` が始めた作成途中のストロークの URL を、管理者でない `other@example.com` が開く
- **THEN** 404 の画面が出る

#### Scenario: 中断したストロークの一覧

- **WHEN** 管理者でない `guest@example.com` がプロジェクト一覧を開き、中断したストロークが自分のものと他の利用者のもので1件ずつある
- **THEN** 自分のものだけが出ている

#### Scenario: 管理者が中断したストロークを見る

- **WHEN** 管理者がプロジェクト一覧を開く
- **THEN** 誰が始めたかに関わらず、中断したストロークがすべて出ている

### Requirement: 昇格したら始めた本人に許可を付ける

システムは、ストロークがプロジェクトへ昇格したとき、そのストロークを始めた利用者に、そのプロジェクトの許可を付けなければならない（SHALL）。始めた利用者を持たないストロークでは、許可を付けない SHALL。

#### Scenario: 承認して一覧へ戻る

- **WHEN** `guest@example.com` が始めたストロークの proposal を承認し、プロジェクト一覧を開く
- **THEN** 昇格したプロジェクトが生成中として一覧に出ている

### Requirement: 既にあるプロジェクトは管理者にだけ見える状態で始める

システムは、この機能が入った時点で既にあるプロジェクトについて、どの利用者にも許可が無い状態で始めなければならない（SHALL）。既存のストロークの記録から、始めた利用者を推し量って許可を付けてはならない（MUST NOT）。

#### Scenario: 導入直後に一般の利用者が一覧を開く

- **WHEN** この機能を入れた直後に、まだ何の許可も付いていない一般の利用者がプロジェクト一覧を開く
- **THEN** プロジェクトは1件も出ていない

### Requirement: 作成は誰でも始められる

システムは、管理者でない利用者にも、ストロークを始めることを許さなければならない（SHALL）。作成の入口を、利用者の種類によって押せなくしたり隠したりしてはならない（MUST NOT）。

#### Scenario: 一般の利用者が作成を押す

- **WHEN** 管理者でない利用者がプロジェクト一覧で「作成」を押す
- **THEN** ストロークが開き、概要を入力して始められる
