# architecture-docs Specification

## Purpose
システムがどの層で組まれ、どのディレクトリに何が置かれ、依存がどちら向きに流れているかを1つの資料として持ち、コードを読まずに全体像を掴める状態と、その資料が実装と食い違わない状態を保つ。

## Requirements

### Requirement: 構造資料は単一の場所に置く

システムの構造を説明する資料（以下「構造資料」）は `docs/specs/structure/system-structure.md` の1ファイルでなければならない（SHALL）。同じ内容を複数の場所に置いてはならない（MUST NOT）。

#### Scenario: 全体像を知りたい

- **WHEN** リポジトリを初めて触る人間またはエージェントが構造を知ろうとする
- **THEN** 構造資料を読めば層・配置・依存の向きが分かり、他のファイルを横断して回る必要が無い

#### Scenario: 構造の説明を書き足したくなった

- **WHEN** 構造についての説明を新たに書く必要が生じる
- **THEN** 別の資料を作らず構造資料に加える

### Requirement: 資料は層・配置・依存・流れを示す

構造資料は次のすべてを含まなければならない（SHALL）。

- 層の一覧と、各層が何に責任を持つか
- ディレクトリツリーと、各ディレクトリが何を持つか
- 依存がどちら向きに流れるか、および越えてはならない境界
- 本家で起きた変化が画面に出るまでの経路

#### Scenario: モジュールの置き場所を判断する

- **WHEN** 新しいモジュールをどの層に置くか判断する必要がある
- **THEN** 資料の層の責務を読めば、そのモジュールがどの層に属するかが決まる

#### Scenario: 依存を追加してよいか判断する

- **WHEN** あるモジュールから別のモジュールへ依存を足そうとする
- **THEN** 資料の依存の向きを見れば、その依存が境界を越えるものかどうかが分かる

### Requirement: 資料の記述は実装で裏が取れる

資料に書く構成・依存・件数は、実装から確認できる事実でなければならない（SHALL）。将来の構想、望ましい姿、未実装のものを、現状として書いてはならない（MUST NOT）。

現状にまだ存在しないものに触れる場合は、存在しないことが分かる形で書かなければならない（SHALL）。

#### Scenario: 実在しないディレクトリ

- **WHEN** 資料が上層の構造を説明する
- **THEN** 上層専用のコンポーネントディレクトリが存在しないことが、欠落ではなく現状として読み取れる

#### Scenario: 未実装の機能

- **WHEN** 資料が MVP から外した機能に触れる
- **THEN** それが未実装であることが明記され、実装済みの記述と混同されない

### Requirement: 実装を変えたら資料も更新する

モジュールの配置、層の構成、または層をまたぐ依存の向きを変更したときは、同じ変更のなかで構造資料を更新しなければならない（SHALL）。資料と実装が食い違ったまま残してはならない（MUST NOT）。

単一の層の内部だけで完結する変更（層をまたぐ依存も配置も変えないもの）では、更新は要求されない。

#### Scenario: モジュールを別の階層へ移す

- **WHEN** モジュールの参照範囲が変わり、別の階層ディレクトリへ移す
- **THEN** 構造資料のディレクトリツリーも同じ変更のなかで更新される

#### Scenario: 新しい層をまたぐ依存が生まれた

- **WHEN** これまで繋がっていなかった層のあいだに依存が生まれる
- **THEN** 資料の依存の向きの記述が更新される

#### Scenario: 層の内部だけの変更

- **WHEN** ある層の内部で関数を追加する、あるいは実装を書き換える
- **THEN** 配置も層をまたぐ依存も変わらないため、資料の更新は要求されない

### Requirement: 既存ドキュメントと役割を分ける

構造資料は「今どう組まれているか」だけを扱わなければならない（SHALL）。次のものを持ってはならない（MUST NOT）。

- ドメイン用語の定義 — `CONTEXT.md` が持つ
- なぜその選択をしたかという決定の記録 — `docs/adr/` が持つ
- これから何を作るかという計画 — `openspec/changes/` が持つ
- コーディング規約 — steering（`.spec-workflow/steering/`）が持つ

ここでいうコーディング規約は、Requirement「コーディング規約は steering が持つ」が列挙するものを指す。層の構成、部品の切り方、依存の向き、各ディレクトリが何を持つかは**構造**であり、引き続き構造資料が持つ。ディレクトリツリーに `test/` が在ることは構造、単体テストをそのどこへ置くかは規約である。

決定の理由に触れる必要があるときは、該当する ADR または change を参照しなければならない（SHALL）。理由そのものを資料に書き写してはならない（MUST NOT）。規約に触れる必要があるときも同じく、steering への参照だけを置かなければならない（SHALL）。

#### Scenario: 配置の理由を知りたい

- **WHEN** 資料を読んでいて、なぜその配置なのかを知りたくなる
- **THEN** 資料から該当の ADR または change への参照が辿れ、理由はその参照先にある

#### Scenario: 決定が変わった

- **WHEN** ある技術的決定が新しい ADR で覆される
- **THEN** 理由が1箇所にしか無いため、資料側に古い理由が取り残されることがない

#### Scenario: 規約が変わった

- **WHEN** コーディング規約が steering で更新される
- **THEN** 構造資料は参照しか持たないため、古い規約が資料側に取り残されることがない

### Requirement: コーディング規約は steering が持つ

コーディング規約の実体は steering 文書（`.spec-workflow/steering/` の `structure.md` / `tech.md`）に置かなければならない（SHALL）。ここでいうコーディング規約とは、コードをどう書き、テストをどこに置き、何を通すかの取り決めを指す — 命名、import の書き方、テストの置き場、通す門番（どのテストを実行の条件とし、どれを外すか）、書き方の原則。この5つが規約であり、これ以外の置き場（components / composables をどう切ってどこへ置くか）は構造として構造資料が持つ。

`docs/` 配下の資料は同じ規約を書き写してはならない（MUST NOT）。規約に触れる必要があるときは steering への参照だけを置かなければならない（SHALL）。

#### Scenario: 規約を引く

- **WHEN** 人間またはエージェントが、テストをどこに置くか・どのテストを通すか・import をどう書くかを知ろうとする
- **THEN** steering を読めば決まり、`docs/` 側には steering への参照しか無い

#### Scenario: 規約を新たに書く

- **WHEN** コードの書き方についての取り決めを新たに書く必要が生じる
- **THEN** `docs/` ではなく steering へ書く

#### Scenario: 規約に実装がまだ従っていない

- **WHEN** steering が定める規約に対して、実装がまだ従っていない
- **THEN** 規約そのものは steering にあり、従っていないという事実は現状の記録として `docs/specs/plan/structure-migration.md` にある。規約の文面が `docs/` 側へ複製されることはない
