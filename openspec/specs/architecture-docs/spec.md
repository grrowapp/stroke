# architecture-docs Specification

## Purpose
システムがどの層で組まれ、どのディレクトリに何が置かれ、依存がどちら向きに流れているかを1つの資料として持ち、コードを読まずに全体像を掴める状態と、その資料が実装と食い違わない状態を保つ。

## Requirements

### Requirement: 構造資料は単一の場所に置く

システムの構造を説明する資料は `docs/structure-design.md` の1ファイルでなければならない（SHALL）。同じ内容を複数の場所に置いてはならない（MUST NOT）。

#### Scenario: 全体像を知りたい

- **WHEN** リポジトリを初めて触る人間またはエージェントが構造を知ろうとする
- **THEN** `docs/structure-design.md` を読めば層・配置・依存の向きが分かり、他のファイルを横断して回る必要が無い

#### Scenario: 構造の説明を書き足したくなった

- **WHEN** 構造についての説明を新たに書く必要が生じる
- **THEN** 別の資料を作らず `docs/structure-design.md` に加える

### Requirement: 資料は層・配置・依存・流れを示す

`docs/structure-design.md` は次のすべてを含まなければならない（SHALL）。

- 層の一覧と、各層が何に責任を持つか
- ディレクトリツリーと、各ディレクトリが何を持つか
- 依存がどちら向きに流れるか、および越えてはならない境界
- 本家で起きた変化が画面に出るまでの経路

#### Scenario: モジュールの置き場所を判断する

- **WHEN** 新しいモジュールをどの層に置くか判断する必要がある
- **THEN** 資料の層の責務を読めば、そのモジュールがどの層に属するかが決まる

#### Scenario: 依存を追加してよいか判断する

- **WHEN** あるモジュールから別のモジュールへ依存を足そうとする
- **THEN** 資料の依存の向きを見れば、その依存が境界を越えるものかどうかが分かる

### Requirement: 資料の記述は実装で裏が取れる

資料に書く構成・依存・件数は、実装から確認できる事実でなければならない（SHALL）。将来の構想、望ましい姿、未実装のものを、現状として書いてはならない（MUST NOT）。

現状にまだ存在しないものに触れる場合は、存在しないことが分かる形で書かなければならない（SHALL）。

#### Scenario: 実在しないディレクトリ

- **WHEN** 資料が上層の構造を説明する
- **THEN** 上層専用のコンポーネントディレクトリが存在しないことが、欠落ではなく現状として読み取れる

#### Scenario: 未実装の機能

- **WHEN** 資料が MVP から外した機能に触れる
- **THEN** それが未実装であることが明記され、実装済みの記述と混同されない

### Requirement: 実装を変えたら資料も更新する

モジュールの配置、層の構成、または層をまたぐ依存の向きを変更したときは、同じ変更のなかで `docs/structure-design.md` を更新しなければならない（SHALL）。資料と実装が食い違ったまま残してはならない（MUST NOT）。

単一の層の内部だけで完結する変更（層をまたぐ依存も配置も変えないもの）では、更新は要求されない。

#### Scenario: モジュールを別の階層へ移す

- **WHEN** モジュールの参照範囲が変わり、別の階層ディレクトリへ移す
- **THEN** `docs/structure-design.md` のディレクトリツリーも同じ変更のなかで更新される

#### Scenario: 新しい層をまたぐ依存が生まれた

- **WHEN** これまで繋がっていなかった層のあいだに依存が生まれる
- **THEN** 資料の依存の向きの記述が更新される

#### Scenario: 層の内部だけの変更

- **WHEN** ある層の内部で関数を追加する、あるいは実装を書き換える
- **THEN** 配置も層をまたぐ依存も変わらないため、資料の更新は要求されない

### Requirement: 既存ドキュメントと役割を分ける

`docs/structure-design.md` は「今どう組まれているか」だけを扱わなければならない（SHALL）。次のものを持ってはならない（MUST NOT）。

- ドメイン用語の定義 — `CONTEXT.md` が持つ
- なぜその選択をしたかという決定の記録 — `docs/adr/` が持つ
- これから何を作るかという計画 — `openspec/changes/` が持つ

決定の理由に触れる必要があるときは、該当する ADR または change を参照しなければならない（SHALL）。理由そのものを資料に書き写してはならない（MUST NOT）。

#### Scenario: 配置の理由を知りたい

- **WHEN** 資料を読んでいて、なぜその配置なのかを知りたくなる
- **THEN** 資料から該当の ADR または change への参照が辿れ、理由はその参照先にある

#### Scenario: 決定が変わった

- **WHEN** ある技術的決定が新しい ADR で覆される
- **THEN** 理由が1箇所にしか無いため、資料側に古い理由が取り残されることがない
