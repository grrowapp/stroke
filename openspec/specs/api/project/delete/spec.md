# api/project/delete Specification

## Purpose
作りきれなかったプロジェクトを消す endpoint を規定する。承認で昇格したが steering を書けずに終わったものを、ユーザーの選択で片付けられるようにする。中身のある本物のプロジェクトは消せない。

## Requirements

### Requirement: DELETE /api/projects/:projectId — プロジェクトを消す

システムは `DELETE /api/projects/:projectId` でプロジェクトの削除を受け付けなければならない（SHALL）。削除が成立したとき、そのプロジェクトのディレクトリ配下は残ってはならない（MUST NOT）。片方だけ消えて片方が残る状態を作ってはならない（MUST NOT）。

**メソッドで振り分けなければならない（SHALL）。** パスに `delete` のような動詞を置いてはならない（MUST NOT）。メソッドを絞らない handler にしてはならない（MUST NOT）——削除は最も破壊的な操作であり、`GET` で到達できる形にしてはならない。

存在しない `projectId` への削除は受理せず、何も消してはならない（MUST NOT）。

#### Scenario: 消す

- **WHEN** 作りきれなかったプロジェクトに `DELETE /api/projects/:projectId` が要求される
- **THEN** そのプロジェクトのディレクトリ配下は残らず消え、以後そのプロジェクトは一覧に現れない

#### Scenario: 存在しないプロジェクトを消そうとする

- **WHEN** 存在しない `projectId` の削除が要求される
- **THEN** システムは存在しないことを伝え、何も消さない

#### Scenario: 削除以外のメソッドで叩く

- **WHEN** 同じ path に `GET` が要求される
- **THEN** 削除は起こらない

### Requirement: 消せるのは承認以降の局面にあるものだけとする

システムは、`phase` が承認以降の局面にあるものだけを削除の対象としなければならない（SHALL）。承認より前の局面にあるもの——まだプロジェクトになっていないセッション——をこの口で消してはならない（MUST NOT）。それらはセッションの削除が扱う。

承認以降のうち、実際に消せるのは **phase が `approved` のものだけ**とする SHALL。`activated` は「中身のある本物のプロジェクトは消さない」が別に断る。**この2つを併せて、受理する局面は `approved` の1つに定まる**（SHALL）。

**局面の判定はこの endpoint が持たなければならない（SHALL）。** 消す動作そのものはセッションの削除と共通の1つとし（SHALL）、同じ動作を2箇所に書いてはならない（MUST NOT）。共通の動作に呼び出し元を知らせて分岐させてはならない（MUST NOT）——どの局面を許すかは、呼ぶ側が決める。

#### Scenario: 承認前のセッションをこの口で消そうとする

- **WHEN** まだ承認されていないセッションの id で `DELETE /api/projects/:projectId` が要求される
- **THEN** システムは受理せず、何も消さない

#### Scenario: 承認以降のプロジェクトを消す

- **WHEN** phase が `approved`（承認で昇格し、まだ生成中）のプロジェクトの削除が要求される
- **THEN** システムは受理し、そのディレクトリ配下は残らず消える

### Requirement: 中身のある本物のプロジェクトは消さない

システムは、完成を記録したプロジェクト——phase が `activated` のもの——を消してはならない（MUST NOT）。それは steering が文書を出し終え、レビューできる状態に達した実体であり、この口が扱う対象ではない。

この判定に `.spec-workflow/` の有無を使ってはならない（MUST NOT）。そのディレクトリは生成の依頼を本家が受理したときに本家が作り、AI が起動する前からできているため、作りきれなかったプロジェクトも持っている。`.spec-workflow/` を持つことを理由に削除を断ると、失敗の決着で「破棄する」を選んだプロジェクトが消せず、一覧に居座る。

#### Scenario: 完成したプロジェクトを消そうとする

- **WHEN** phase が `activated` のプロジェクトの削除が要求される
- **THEN** システムは受理せず、何も消さない

#### Scenario: .spec-workflow/ を持つが作りきれなかったプロジェクトを消す

- **WHEN** phase が `approved` のまま生成が失敗し、`.spec-workflow/` はできているプロジェクトに削除が要求される
- **THEN** システムは受理し、そのディレクトリ配下は `.spec-workflow/` ごと残らず消える

### Requirement: 削除は実行の決着の後にしか要求されない

画面がプロジェクトの削除の操作を出す局面——生成の失敗の決着（`project/generation`「決着したら、知らせてから次を選ばせる」）——は、実行が終わった後である。したがって削除が要求される時点で、対象に走っている呼び出しは無い SHALL。

「実行中だから受理しない」という応答を持ってはならない（MUST NOT）。実行中に削除の要求が届いたなら、それは欠陥である。システムはそれを握りつぶさず失敗として返す SHALL（ADR 0022）。リロード・複数タブ・再起動に由来する状態は後始末の問題として別に扱う。

#### Scenario: 削除の時点で実行が無い

- **WHEN** ユーザーが一覧から削除を要求する
- **THEN** 対象で走っている呼び出しは無く、そのディレクトリ配下は残らず消える
