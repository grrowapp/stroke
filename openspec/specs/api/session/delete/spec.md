# api/session/delete Specification

## Purpose
セッションの削除を受理する endpoint（U11 `DELETE /api/sessions/:id`）を規定する。セッションに属するものを残さず消すことと、実行中の削除を受けないことを担う。api/session の削除の要件をメソッドと path の変更込みで引き継いだもの。

## Requirements

### Requirement: U11 DELETE /api/sessions/:id — セッションを消す

システムは `DELETE /api/sessions/:id` でセッションの削除を受け付ける SHALL。削除が成立したとき、そのセッションに属するもの——セッションディレクトリ配下の状態・生成物・openspec の change——は残らない SHALL。片方だけ消えて片方が残る状態を作ってはならない（MUST NOT）。

**メソッドで振り分ける SHALL。** パスに `delete` のような動詞を置いてはならない（MUST NOT）。メソッドを絞らない handler にしてはならない（MUST NOT）——削除が `GET` で到達できる形になるためである。

存在しないセッション id への削除は受理せず、何も消さない SHALL。

#### Scenario: 消す

- **WHEN** 実行中の呼び出しを持たないセッションに `DELETE /api/sessions/:id` が要求される
- **THEN** そのセッションに属するものは残らず消え、以後そのセッションは存在しないものとして扱われる

#### Scenario: 存在しないセッションを消そうとする

- **WHEN** 存在しないセッション id の削除が要求される
- **THEN** システムは存在しないことを伝え、何も消さない

#### Scenario: 削除以外のメソッドで叩く

- **WHEN** 同じ path に `GET` が要求される
- **THEN** 削除は起こらない

### Requirement: 消せるのは承認より前の局面にあるものだけとする

システムは、`phase` が承認より前の局面にあるものだけを削除の対象としなければならない（SHALL）。承認以降の局面にあるもの——既にプロジェクトへ昇格したもの——をこの口で消してはならない（MUST NOT）。それらはプロジェクトの削除が扱う。

**局面の判定はこの endpoint が持たなければならない（SHALL）。** 消す動作そのものはプロジェクトの削除と共通の1つとし（SHALL）、同じ動作を2箇所に書いてはならない（MUST NOT）。共通の動作に呼び出し元を知らせて分岐させてはならない（MUST NOT）——どの局面を許すかは、呼ぶ側が決める。

#### Scenario: 昇格したプロジェクトをこの口で消そうとする

- **WHEN** 承認によって昇格したものの id で削除が要求される
- **THEN** システムは受理せず、何も消さない

#### Scenario: 承認前のセッションを消す

- **WHEN** まだ承認されていないセッションの削除が要求される
- **THEN** システムは受理し、そのセッションに属するものは残らず消える

### Requirement: 削除は実行の決着の後にしか要求されない

画面がセッションの削除の操作を出す局面——`error` に達した実行からの回復、初回起動の失敗からの回復——は、いずれも実行が終わった後である（`stroke/frontier`）。したがって削除が要求される時点で、対象に走っている呼び出しは無い SHALL。

「実行中だから受理しない」という応答を持ってはならない（MUST NOT）。実行中に削除の要求が届いたなら、それは欠陥である。システムはそれを握りつぶさず失敗として返す SHALL（ADR 0022）。リロード・複数タブ・再起動に由来する状態は後始末の問題として別に扱う。

#### Scenario: 削除の時点で実行が無い

- **WHEN** ユーザーが画面から削除を要求する
- **THEN** 対象で走っている呼び出しは無く、セッションに属するものは残らず消える
