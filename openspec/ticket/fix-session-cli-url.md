## Agent Brief

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** セッション作成の CLI が出力する URL のパスセグメントが古いままで、開いても 404 になる。

**Current behavior:**
CLI がセッションを作った後に表示する URL が、画面のルートが移る前の古いセグメントを使っている。該当するページは存在せず、catch-all も無いため 404。値の解決（基底 URL・セッション識別子）は正しく、**パスの組み立てだけが古い**。

出所は追えている。画面のルートを移した過去の change で CLI の出力だけが取り残され、設定の外出しを進める別 change の実測中に発見されて、範囲外として切り出されたもの。

**Desired behavior:**
CLI が出力する URL が、実在するセッション画面のルートを指す。

**Key interfaces:**
- セッション作成 CLI の出力行 — 基底 URL とセッション識別子の間に入るパスセグメントだけを、実在するルートに合わせる

**Acceptance criteria:**
- [ ] 型検査が通る
- [ ] CLI で実セッションを作り、出力された URL を開いて 200 が返る
- [ ] 確認に使ったセッションを CLI の削除コマンドで消す

**Out of scope:**
- サーバ API 側のパス（画面のルートとは別物で、変更しない）

**着手前に tasks と design を現況に合わせること:**
この change の tasks / design は、修正箇所を行番号と識別子で名指ししているが、どちらも既に古い。`connect-portal-and-strokes` が設定の読み口を1本化したため、出力行が参照する識別子が変わり、行の位置もずれている。記載どおりに探すと存在しない識別子を追うことになる。

さらに同 change の未完タスクに API のパス移設があり、画面のルート自体が動く可能性がある（`relocate-stroke-routes` も画面ルートの移設を扱う）。修正先のセグメントを決める前に、両者の状態を確認すること。
