# specs/api/session — delta

## ADDED Requirements

### Requirement: 概要の投稿を受理してセッションを作る

システムは概要の投稿を受け付ける endpoint を1つ公開し、投稿を受理したときは AI を起動せず、セッションを1つ作成して phase を `stroking` とし、セッション id を返して完結する SHALL。

#### Scenario: 概要を投稿する

- **WHEN** 概要の投稿が届く
- **THEN** セッションが1つ作成され、phase は `stroking` となり、セッション id が返る。AI の起動はこの endpoint では行われない

#### Scenario: 空の概要が届く

- **WHEN** 概要が空の投稿が届く
- **THEN** システムはセッションを作成せず、入力が必要である旨を返す

### Requirement: 回答を受理して記録する

システムは回答——ユーザーが選んだ選択肢、または自由入力の本文——を受け付ける endpoint を1つ公開し、回答を受理したときは AI を起動せず、回答を履歴の記録に加えて完結する SHALL。

#### Scenario: 選択肢で回答する

- **WHEN** 選択肢を1つ選んだ回答が届く
- **THEN** どの選択肢を選んだかが記録され、受理が返る。AI の起動はこの endpoint では行われない

#### Scenario: 自由入力で回答する

- **WHEN** 自由入力の本文による回答が届く
- **THEN** その本文が回答として記録され、受理が返る

#### Scenario: 空の回答が届く

- **WHEN** 選択も本文も持たない回答が届く
- **THEN** システムは受理せず、回答が必要である旨を返す

#### Scenario: 存在しないセッション id で回答が届く

- **WHEN** 存在しないセッション id に対する回答が届く
- **THEN** システムは受理せず、存在しないことを伝え、何も記録しない

#### Scenario: 実行中のセッションに回答が届く

- **WHEN** 実行中の呼び出しを持つセッションに回答が届く
- **THEN** 回答は受理され記録される。AI の起動はこの endpoint では行われない

#### Scenario: 承認後のセッションに回答が届く

- **WHEN** phase が `approved` のセッションに回答が届く
- **THEN** システムは受理せず、何も記録しない

### Requirement: 差し戻しを受理して記録する

システムは積まれた指摘を1回の差し戻しとして受け付ける endpoint を1つ公開し、差し戻しを受理したときは AI を起動せず、指摘を記録し、AI へ渡る内容を整えて完結する SHALL。

#### Scenario: 差し戻しが届く

- **WHEN** 1件以上の指摘を伴う差し戻しが届く
- **THEN** 指摘が記録され、受理が返る。AI の起動はこの endpoint では行われない

#### Scenario: 指摘が1件も無い差し戻しが届く

- **WHEN** 指摘が1件も無い差し戻しが届く
- **THEN** システムは受理せず、指摘が必要である旨を返す

#### Scenario: 存在しないセッション id で差し戻しが届く

- **WHEN** 存在しないセッション id に対する差し戻しが届く
- **THEN** システムは受理せず、存在しないことを伝え、何も記録しない

#### Scenario: 実行中のセッションに差し戻しが届く

- **WHEN** 実行中の呼び出しを持つセッションに差し戻しが届く
- **THEN** 差し戻しは受理され記録される。AI の起動はこの endpoint では行われない

#### Scenario: proposal がまだ無いセッションに差し戻しが届く

- **WHEN** phase が `stroking` で proposal がまだ無いセッションに差し戻しが届く
- **THEN** システムは受理せず、差し戻す対象の proposal が無いことを伝え、何も記録しない

#### Scenario: 承認後のセッションに差し戻しが届く

- **WHEN** phase が `approved` のセッションに差し戻しが届く
- **THEN** システムは受理せず、何も記録しない

### Requirement: 差し戻しは同じ内容を複数の形で AI へ渡るよう整える

システムは差し戻しを1つの形に畳まず、受理したとき次の4つを AI へ渡る形で用意する SHALL。

- **要約** — 全体への指摘と本文への指摘を並べた、人間可読のテキスト
- **構造化された指摘の一覧** — 指摘ごとに、種別（全体 / 本文）・引用・指摘本文を持つ
- **決定の記録** — 差し戻したという決定・指摘一覧・要約・時刻を1つにまとめたもの
- **手続き** — 差し戻されたこと、プロジェクトが作られていないこと、proposal を出し直すこと、および各指摘の列挙

手続きに書いてよいのは、差し戻し後に何が起きたか・何を出し直すかまでとする。

#### Scenario: 差し戻しを渡す

- **WHEN** 差し戻しが受理され、AI へ渡る内容が用意される
- **THEN** 要約・構造化された指摘の一覧・決定の記録・手続きの4つが揃って用意される

#### Scenario: 本文への指摘を渡す

- **WHEN** 本文の一部に紐づく指摘が含まれる
- **THEN** どの箇所を指しているかが分かる引用が、指摘本文と組で用意される

### Requirement: 差し戻しに対応方法を指示しない

システムは、AI へ渡るよう用意する内容に「全文を書き直す」「一部だけ直す」といった対応方法の指示を含めてはならない SHALL。対応方法は AI が指摘内容を読んで判断する。

#### Scenario: 対応方法を渡さない

- **WHEN** 差し戻しの内容が用意される
- **THEN** 用意される内容に、proposal をどう直すかの指示は含まれない

### Requirement: AI の起動を受け付ける endpoint を1つ公開する

システムは AI の起動要求を受け付ける endpoint を1つ公開し、起動要求を受理したときは AI の呼び出しを開始して、応答の完了を待たずに受理を返して完結する SHALL。

起動要求は対象の id と **cwd（実行する場所）を引数で受け取る** SHALL。endpoint が cwd を自分で導出してはならない（MUST NOT）——キックする側（画面・巡回・承認処理）が、一覧の応答の path または生成先の path を渡す。承認によって昇格した対象への起動要求も、この endpoint で受け付ける SHALL。

#### Scenario: 起動を要求する

- **WHEN** 存在する対象に cwd を添えて起動が要求される
- **THEN** システムは AI の呼び出しを開始し、応答の完了を待たずに受理を返す。実行は渡された cwd で行われる

#### Scenario: 存在しない対象に起動を要求する

- **WHEN** 存在しない id で起動が要求される
- **THEN** システムは起動せず、存在しないことを伝える

#### Scenario: 昇格したプロジェクトに起動を要求する

- **WHEN** 承認で昇格したプロジェクトの id と生成先の path で起動が要求される
- **THEN** システムは受理し、AI の呼び出しをその場所で開始する

### Requirement: 同一対象の多重起動を受け付けない

システムは、実行中の呼び出しを持つ対象への起動要求を受理しない SHALL。呼び出しが終わった後は、同じ対象に再び起動を要求できる。

#### Scenario: 実行中に起動を要求する

- **WHEN** 実行中の呼び出しを持つ対象に起動が要求される
- **THEN** システムは受理せず busy であることを伝え、AI は二重に起動されない

#### Scenario: 呼び出しが終わった後に再び起動を要求する

- **WHEN** 実行中だった呼び出しが終わった対象に、再び起動が要求される
- **THEN** システムは受理し、AI の呼び出しを開始する

### Requirement: 前提が欠けている間は起動を受け付けない

システムは、AI の起動に必要な前提（startup-readiness）が揃っていない対象への起動要求を受理しない SHALL。要求元には受理しなかったことと、欠けている前提の内容が返る。前提が満たされた後は、同じ対象に再び起動を要求できる。

#### Scenario: 前提が欠けた状態で起動を要求する

- **WHEN** AI の起動設定が成立しない状態で起動が要求される
- **THEN** システムは受理せず欠けている前提を伝え、AI は起動されない

#### Scenario: 前提が満たされた後に起動を要求する

- **WHEN** 欠けていた前提が満たされた後で、同じ対象に起動が要求される
- **THEN** システムは受理し、AI の呼び出しを開始する

### Requirement: 承認を受け付ける endpoint を1つ公開する

システムは承認を受け付ける endpoint を1つ公開する SHALL。受理したときは確定された名前で昇格（`project/generation`）を実行し、成功したら次の実行を起こして、その完了を待たずに応答を返す SHALL。昇格が失敗したときは失敗を返し、次の実行を起こしてはならない（MUST NOT）。

#### Scenario: 承認が届く

- **WHEN** 確定された名前を伴う承認が届き、昇格が成功する
- **THEN** 受理が返る。応答は次の実行の完了を待たない

#### Scenario: 昇格が失敗する

- **WHEN** 承認が届いたが昇格が失敗する
- **THEN** 失敗が返り、次の実行は起こされない

## MODIFIED Requirements

### Requirement: 残っているセッションを一覧する endpoint を1つ公開する

システムは残っているセッションの一覧を返す endpoint を1つ公開する SHALL。一覧には実体の揃ったセッション——ディレクトリがあり、openspec ルートがあり、ワークフロースキーマが設定済みのもの——だけが載る SHALL。一覧の各件には、セッション id・phase・いつのものかが分かる時点情報に加え、**そのセッションのディレクトリの path と `invocation`** が載る SHALL。ai-invocation を畳んだ `agent/invocation` はこの一覧との符合で初回か継続かを判定し、巡回（`portal/batch`）は各件の `invocation` と path をリトライに使う。

#### Scenario: 一覧する

- **WHEN** 一覧が要求される
- **THEN** 実体の揃った全セッションについて、id・phase・時点情報・path・`invocation` が返る

#### Scenario: 作成直後のセッションは載らない

- **WHEN** 概要の受理直後で、まだ初回の起動が行われていないセッションがある状態で一覧が要求される
- **THEN** そのセッションは一覧に載らない

#### Scenario: 何も残っていない

- **WHEN** セッションが1件も残っていない状態で一覧が要求される
- **THEN** 空の一覧が返る
