# Overview

Version: 1.0.3
Last Updated: 2026-08-19

## Purpose

**プロジェクト横断の通知ポータル stroke-board を、複数プロジェクトを並行して回している開発者のために作る。解決するのは「どのプロジェクトで承認待ちが起きたかを、各プロジェクトのダッシュボードを順に開くまで知れない」という問題であり、その結果、起きたことに気づいてから対象ドキュメントを開くまでが1画面で完結する。**

問題の根拠: 本家 spec-workflow-mcp のダッシュボードはプロジェクト単位で、`projectId` を `localStorage` に持ち URL に出さないため、プロジェクトを横断して対象を指すリンクが作れない。通知も開いているプロジェクトの分しか出ない。

測定指標は置かない。

## Target Users

単一のペルソナに絞らない。開発者本人を含む複数の関係者が同じ画面を見る。役割ごとの機能差もユーザー概念も持たない。

### Primary Persona

- **Role**: 複数プロジェクトを並行して回している開発者
- **Context**: spec-workflow-mcp を複数プロジェクトで使い、本家ダッシュボードは自分で起動する。現在は開発中で、到達範囲は localhost に限る。外部公開はその先の段階とする
- **Pain points**: 承認待ちやタスク進行が「見に行かないと分からない」。プロジェクトごとにダッシュボードを開き直す必要がある
- **Current behaviour**: 各プロジェクトのダッシュボードを順に開いて確認する

### Jobs-to-Be-Done

- **Functional job**: 複数プロジェクトで起きたことに気づき、そこから対象ドキュメントを開く
- **Emotional job**: 🔶 Assumption（未取得）
- **Social job**: 🔶 Assumption（未取得）

## Solution Description

stroke-board は本家 spec-workflow-mcp とは別のアプリケーションとして動き、本家には変更を加えない。構成は2層とする。

**上層はプロジェクト横断のポータル**で、通知画面とプロジェクト一覧画面を持つ。通知画面には、監視しているすべてのプロジェクトで起きた承認依頼とタスクの変化が、プロジェクト / 種別 / 内容 / 最終更新 の4列で並ぶ。プロジェクト一覧画面には監視対象のプロジェクトが並び、アクティブなものが上、未接続のものが下に来る。プロジェクトの登録と作成はこの画面の操作として持つ。

**下層はプロジェクト単位の画面群**で、仕様書 / ステアリング / タスク / 承認 / 設定を見られる。上層と下層は階層が違うため同じナビゲーションには並べず、ナビゲーションの形そのものを変える（上層はタブ、下層は左サイドバー）。

**How it works:**

1. 利用者が監視する親パスを設定する。stroke-board はその配下で `.spec-workflow` を持つディレクトリをプロジェクトとして拾う
2. stroke-board のサーバーが、アクティブなプロジェクトごとに本家ダッシュボードへ接続する
3. 本家で承認依頼が出る、またはタスクの状態が変わると、stroke-board のサーバーがそれを検知してブラウザへ送る
4. ブラウザの右上にトーストが出る（例: `Task completed in auth-spec (3/5)`）。5秒で消え、× でも閉じられる
5. 利用者が通知画面を開くと、起きたことがプロジェクト横断で1つの表に並んでいる
6. 行を選ぶと対象ドキュメントが開く。開くだけで、承認や却下はしない
7. プロジェクト一覧から特定のプロジェクトを選ぶと下層に入り、そのプロジェクトの仕様書・ステアリング・タスク・承認・設定を見られる

### Key Features

- **横断で気づく**: 複数プロジェクトで起きた承認依頼とタスクの変化を、1つの画面で見られる
- **その場で知る**: 起きた瞬間に画面内へトーストが出る。本家と同じ4種（タスク完了 / タスク着手 / 全件完了 / 承認依頼の発生）
- **対象へ直行する**: 通知の行から対象ドキュメントを開ける。開くだけで、該当セクションへのスクロールやハイライトはしない
- **プロジェクトを見渡す**: どのプロジェクトが今つながっていて、どれが止まっているかが分かる
- **プロジェクトを増やす**: 一覧画面から登録・作成の入口に入れる。実処理は接続先の別プロジェクトが担う
- **プロジェクトの中に入る**: 一覧から下層に入り、仕様書・ステアリング・タスク・承認・設定を見られる
- **日本語と英語**: 2言語に対応する

## Project Principles

-【MUST】stroke-board は `.spec-workflow/` に直接書き込まない。本家が持つ範囲の状態を変えるときは本家の API を呼び、ファイルに触るのは本家に委ねる
-【MUST】通知・既読状態を独自に永続化しない。表示は本家のデータ状態から導出する
-【MUST】ブラウザは stroke-board のサーバーとだけ話す。本家 WebSocket にブラウザから直接つながない
-【MUST】本家から受け取った情報を加工・再構成する仕様を勝手に足さない。足すかどうかはユーザーが決める（ADR-0001）
-【SHOULD】取得手段は ①本家 REST API → ②MCP ツール → ③`.spec-workflow/` の直接読み取り の順で選ぶ
-【SHOULD】本家に見た目を合わせる。design token は本家 v2.2.5 に準拠する
-【MAY】本家に無い範囲（プロジェクトの作成など）は stroke-board 側の機能として持ってよい

## Out of Scope

### Not Included in This Release

- **Jobs / Logs / Statistics** — 使わないため
- **他ソースの集約** — spec-workflow-mcp 以外のイベントは受けない。汎用化するとイベントモデルの抽象化コストが本体を上回るため
- **タスクの状態変更** — 本家に委ねる。二重に書き込む主体を作らないため
- **通知の永続化** — 履歴も既読未読も持たない。自前のデータストアを持たないため
- **ユーザー概念と購読モデル** — 認証・認可が未実装のため、紐づける相手がまだ決められない
- **本家プロセスの起動・監視** — 本家は利用者が別途起動するため
- **OS 通知** — 必要なのは画面内の通知だけであり、Notification API / Service Worker / Push API / VAPID をいずれも使わないため

### Future Considerations

- **認証・認可** — 未実装。到達範囲を localhost の外へ広げる段階で設計に入れる
- **登録・作成の中身** — 入口を先に作り、中身は接続先が決まってから

## Dependencies & Risks

### Dependencies

- **Technical**: spec-workflow-mcp v2.2.5（別途起動されている前提）。REST API、WebSocket、`SPEC_WORKFLOW_HOME` 配下の `activeProjects.json`、各プロジェクトの `.spec-workflow/` 構造
- **External**: なし
- **Team**: プロジェクト作成の実処理を担う接続先プロジェクト

### Risks & Mitigations

**Value**

- **Risk**: 開発者本人以外の関係者が何を必要とするか分からないまま外部公開する
  - **Mitigation**: 役割ごとの機能差を作らず単一の画面で出す。必要が判明してから足す
- **Risk**: 測定指標を置かないため、価値があったかを事後に判定できない
  - **Mitigation**: 判定が必要になった時点で指標を決める

**Usability**

- **Risk**: 通知に出ない変化（ステアリング更新、承認と却下の区別）を見落とす
  - **Mitigation**: 取れないものを取れると見せない。本家と同じ4種だけを通知とし、限界を tech.md に明記する
- **Risk**: 選べるのに実は繋がっていないプロジェクトが一覧に出る
  - **Mitigation**: 生存判定の限界を既知の制約として記録し、未接続の表示と区別できる状態で出す

**Feasibility**

- **Risk**: 本家の内部実装に依存しており、本家の更新で壊れる
  - **Mitigation**: 基準を v2.2.5 と明示し、本家に触る範囲を接点層に閉じ込める
- **Risk**: プロジェクト一覧が親パスの走査頼みで、設定を誤ると一覧が空になる
  - **Mitigation**: 「親パス未設定」と「プロジェクト0件」を区別できる状態として画面に出す
- **Risk**: プロジェクト作成の実処理が外部にあり、単独で完成させられない
  - **Mitigation**: 入口と「接続先が無い」状態の表示まで作る

**Viability**

- **Risk**: 認証・認可が未実装のまま到達範囲を広げると、誰でも本家の文書を書き換えられる
  - **Mitigation**: 到達範囲を広げる段階を認証・認可の実装と同じ段階に置く。開発中は localhost に閉じる
- **Risk**: 本家に追随し続けるコストが、横断ポータルから得られるものを上回る
  - **Mitigation**: 本家に触る範囲を接点層に閉じ込め、本家の全画面を再現しようとしない
